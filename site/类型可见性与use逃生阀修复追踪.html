类型可见性与 use 逃生阀修复追踪

最后更新：2026-10-12（建档 + US1 完成 + US2 复核收口 ⇒ 全表关闭：US1✅ US2✅ US3❌不做 US4✅ US5✅）。 关联：docs/import使用指南.md（§0.2 漏列 / §8.2 规则表）、 docs/语言摩擦与隐式契约清单.md 的 M9、docs/语言陷阱速查.md 的 ㉝。 本文定位：不是"use 怎么用"（那是 import使用指南），而是这套类型可见性设计缺的那一环—— 「不用 use 也能写对」的能力（逃生阀）。

0. 为什么开这张表（一次设计评估的落点）

评估结论：机制选对了，规则的完备性差一环。

对的部分（有证据，不是客套）：

  • 「import 管值/模块命名空间（带别名）+ use 管类型命名空间（可扁平化）」与 Java import / C# using / Rust use 同谱系，比 Go（不给扁平化）友好；
  • use m.(A, B) 批量 + 支持尾逗号（Java/C# 都没有）；
  • use 只收类型、明确不收 func/var ⇒ 规则边界干净（import使用指南 §8.2 规则表）；
  • 报错自带处方（未定义的类型: Pt（它其实是模块 'm' 导出的 struct ⇒ 请补一句 use m.Pt））。

真缺陷（本表要修的那一环）：限定名只在表达式位置合法。

var p = new m.Pt()      // ✓ 表达式位置（parser_expr.c:732 专门支持）
m.Pt p = m.mk()         // ✗ 类型位置（parser_func.c:662 / parser.c:225 明确拒绝）

这一个不对称，把 use 从「便利」变成了「义务」，并派生三笔次生负担：

# 次生负担 证据
① §0.2 那类 bug：use 必须列全本文件真正用到的类型，漏一个报错点在 use 那一行，与缺的类型毫无关系；且类型名只出现在 use 里 ⇒ 静态检查 / lint 抓不到，必须真编译 import使用指南 §0.2
② 传导型类型：中间层为了把类型传下去，得 use 一个自己根本不用的类型 ⇒ 同一行 use 承载两种意图（自用 / 转出口），语法上无法区分（Rust 为此专门有 pub use） import使用指南 §8.3 链式传导
③ 没有通配兜底：上面两条没有退路（parse_use_stmt 无 * 分支 ✓ 实测） 本文 §1-⑨

主流对照（凡是给扁平化的语言，都留了至少一个逃生阀）：

语言 逃生阀
Java / C# import java.util.* / using System.Collections.Generic（通配）
Rust std::collections::HashMap 在类型位置合法 + use x::{a,b}
Go 压根不扁平化 ⇒ 全限定（没有"必须 import 类型"这回事）
Leno（现状） 两个都没有 ⇒ 唯一的路是"显式列全"

⇒ 本表的目标：把"不用 use 也能写对"补上（US1），其余条目围绕它收口。

1. 现状事实（全部核对过，不靠记忆）

# 事实 证据位置 结论
① 类型位置拒绝是有意设计，不是漏做 src/parser/parser_func.c:662 parser_reject_module_qualified_type()，由 parse_type_internal 收尾调用（:641）；文案：不支持带模块前缀的类型名（如 'a.Point'）：请先 use a.Point，然后直接写 'Point' 改它是改设计决定，不是补 bug ⇒ 必须把"为什么原来拒"写下来（见 US1 §方案）
② 声明位置另有一处拒绝（Module.Type varName = …） src/parser/parser.c:225-231（注释自称 Leno 不支持此写法，报友好错误避免级联误导） US1 要动两处，只改一处会"参数位置能过、声明位置报错"
③ 表达式位置早就支持（这是不对称的来源） src/parser/parser_expr.c:732（new module.StructName(...)；:41 的 TOK_DOT → parse_dot） 表达式的解析/查名链路可复用（M8/M9 已证实能做到"指到真因"）
④ 类型解析有单一入口 parse_type_internal()（parser_func.c）；对外 parse_type() 23 个调用点，parser 内部 parse_type_internal 16 处 解析侧改动面收敛在一个函数（加"点号 + 模块名"分支即可）
⑤ 类型名归一化有单一入口（本表最关键的一条） src/semantic/semantic_visit_func.c 的 resolve_alias_in_type(s, TypeInfo**, line) —— 递归覆盖 generic_args / element_type / key_type / value_type / return_type / param_types；调用点覆盖 var 声明 / 函数形参与返回 / struct 字段 / destruct 槽 ⇒ 在这里做限定名解析，下游那些"未定义类型"校验点一行都不用改 ✓（含泛型实参，天然一起解决）
⑥ TypeInfo 没有模块限定字段 src/include/leno_types.h:285-308（只有 struct_name / type_param_name / constraint_name / generic_args …） 解析侧要把"模块前缀"带下来 ⇒ 需要新字段（或把 a.Point 塞进 struct_name，见 US1 的两个备选）
⑦ use 只收 6 类类型 import使用指南 §8.2 规则表：struct / cstruct / clib / face / enum / alias；use module.func / use module.var ❌ 边界正确，不要动（见 §4 明确不做）
⑧ native 类型规格全局可见（共 5 个） native_register_struct_spec() 调用点：DirEntry（dirs.walk）/ DirInfo（dirs.stat）/ RegexMatch（regexs.find_all）/ ExecResult（_exec）/ DictEntry（dicts.items）；兜底在 src/semantic/semantic_type.c:553 实践无害，但它是第三套可见性规则，用户看不见分界线（见 US5）
⑨ 没有通配 use m.* parse_use_stmt()（parser_module.c）无 TOK_STAR 分支；全仓 TOK_STAR 只出现在乘法/*= 上面①②的负担因此没有退路
⑩ 没有"use 了没用"的诊断 全仓搜 未使用 无相关检查 ⇒ 传导型 use（②）无法与自用 use 区分，也没有 lint 兜
⑪ "未定义类型"的处方是共享实现 semantic_undefined_type_hint()（2026-10-10 收敛：原本八处拷贝各自 if/else，现共用）；调用点含 visit_var.inc、visit_type_def.inc、check_undefined_type 等 US1 的新错误文案必须走它，否则又开一处拷贝 ✓

⚠ 实施中踩到的两个坑（都很隐蔽，值得记住）

  1. 预注册阶段早于 import —— 语义分析开头会先把所有函数签名归一化一遍，那一遍跑在 AST_IMPORT / AST_USE 之前 ⇒ 那时模块别名还没登记，动手只会得到假错误「模块 'm' 未导入」（实测一个探针里 3 个位置全报）。 修法：加显式阶段标志 in_type_prepass，那一遍原样留着，主阶段再解析 ✓ （不猜"是不是预注册"—— 猜错就是假报错或漏报 ✓）。
  2. 两个"静默错"（都靠套件才暴露，光看输出看不出来）： - 抽取时把 native 成功出口改成了失败：原 case 里那一句 break; 位于 if (!semantic_import_native_type(…)) 之外（= 成功出口 ✓），我按行号映射时当成失败分支 ⇒ 所有 native 限定名（d.DirEntry）静默变成 any ✗。 为什么难发现：局部变量 / 形参 / 顶层变量的 any 是合法的 ⇒ 那几格"看起来正常"，只有 struct 字段位置报「字段不能使用 any」才把它顶出来 ✓。 ⇒ 教训：搬代码必须按语法层级看，不能只按行号映射 ✓。 - semantic_init 不是整体 memset（本仓注释里专门警告过 ✓）：新加的 in_type_prepass 漏了显式清零 ⇒ 模块模式下读到栈上垃圾（非零）⇒ 归一化整段被跳过 ⇒ 模块里写 m.Pt 报"未定义的类型" ✗（入口脚本模式恰好是 0，所以只有模块模式红 ✓）。

症状

import "./_mod.leno" as m
m.Pt p = m.mk()          // ✗ error: 不支持带模块前缀的类型名（如 'a.Point'）：请先 use a.Point…
func show(m.Pt x) { }    // ✗ 同上（parse_type_internal 收尾拒绝）
var q = new m.Pt()       // ✓ 表达式位置一直合法

⇒ 用户被迫给每个用到类型的文件都写 use，且必须列全（§0.2）；库的中间层还得替下游 use（§8.3）。

根因

  • 类型位置：parse_type_internal 只吃一个标识符，收尾调 parser_reject_module_qualified_type() 主动报错（parser_func.c:662）。 注释交代了动机（parser_func.c:653-661 的 2026-09-16 实测）： 不支持时如果不管，会静默 misparse —— if v is a.Point { 报"if 语句体必须用大括号"、 v as a.Point 语法通过、运行期才炸。⇒ 当年的选择是"友好拒绝"而不是"支持" ✓ 这个决定本身是对的 （比静默错好），本表要做的只是把"拒绝"升级成"支持"。
  • 声明位置：parser.c:225-231 同款友好拒绝。
  • 表达式位置：parser_expr.c:732 已支持 ⇒ 三处口径不一致才是问题的本质。

可用的地基（为什么现在成本可控）

  1. 归一化单一入口：resolve_alias_in_type 是递归的，且已被所有类型位置调用 （var 声明 / 函数形参与返回 / struct 字段 / destruct 槽 ✓ 见 §1-⑤） ⇒ 在它里面做"限定名 → 本地类型名"的解析，下游校验点（check_undefined_type、 semantic_check_undefined_subtypes、visit_var.inc、visit_type_def.inc）全都不用动 ✓。
  2. 解析单一入口：parse_type_internal 一处加分支即可覆盖全部类型位置 ✓。
  3. 查名链路已存在：表达式位置早就靠模块符号表查 m.X（M8/M9 的报错即由它产出） ⇒ 复用同一条链路，不另造一套 ✓。
  4. 诊断有共享实现：semantic_undefined_type_hint ✓（新文案走它，不再开拷贝 ✓）。

方案（两步，都在"入口"上）

  1. 解析侧（parser_func.c + parser.c） - parse_type_internal：识别 IDENT . IDENT ⇒ 把模块前缀与类型名一起存进 TypeInfo （备选 A：新增 char* module_name 字段；备选 B：struct_name 存 "m.Pt"）。 推荐 A：语义清楚、type_to_string 好写、不会与真正的嵌套名混淆。 - 撤掉/改写 parser_reject_module_qualified_type：保留它作为"其余非法点号"的兜底 （如 m.Pt.Sub），但不再拦 IDENT.IDENT。 - parser.c:225-231 的声明路径：从"报错"改为"交给类型解析"。
  2. 语义侧（resolve_alias_in_type） - 遇到带模块前缀的类型 ⇒ 在该模块已导入的前提下，去它的符号表查导出类型：
    • 命中 ⇒ 就地替换成不带前缀的 TypeInfo（后续流程完全不知情 ✓）；
    • 未 import / 未导出 / 名字错 ⇒ 走 semantic_undefined_type_hint 同口径处方 ✓。
    • ⚠ 替换后不要留着 module_name（否则 type_equal 会把 m.Pt 与 Pt 判成不同类型 ✗）。

实施前必须先回答（别猜）

  1. TypeInfo 加字段的连带面：type_copy / type_free / type_equal / type_to_string 全要跟着改（漏一个就是泄漏或误判）—— 先数清这四处。
  2. is / as / case is 的解析是不是也走 parse_type？（§1-① 的实测里它们曾经静默 misparse ⇒ 必须确认它们现在都经过 parse_type_internal，否则 US1 覆盖不全、又留一个位置不一致 ✗）
  3. 前瞻冲突（唯一的真语法风险）：语句开头的 IDENT . IDENT 现在是表达式语句 （m.func()）⇒ 改成"也可能是类型声明"后，要看 parser.c:225 那段的前瞻够不够， 会不会把 m.func() 误判成类型声明。
  4. 模块解析的时机：resolve_alias_in_type 跑的时候，模块符号表一定已经加载了吗？ （import 是否总是先于类型解析？若不是，"限定名"就得两遍解析或推迟到查名阶段。）

验收判据（按位置矩阵钉全，这是 US1 的核心风险）

4. 明确不做（想清楚了，不再反复）

不做 为什么
给 use 加 func / var 运行期实体走模块名（m.func() / m.var）是正确的边界（否则名字冲突、初始化顺序都成问题）✓ 见 import使用指南 §8.2
反向收紧（要求所有类型都 use，连 native 规格也强制） 与 §1-⑧ 的既有兜底冲突，且增加摩擦、零收益 ✗
限制 new m.Pt() 这类表达式位置写法 它是正确的那一半 ✓ 要补的是类型位置，不是砍表达式位置
use m.* 通配（原 US3） ★ 2026-10-12 定：不做（US1 落地后重估的结论）。三条理由：① 逃生阀已经有了 —— 类型位置直接写 m.Pt 即可，通配解决的那个痛点（"懒得列全"）已经有了更精确的解法 ✓；② 通配是"收进一批看不见的名字" ⇒ 与"显式优先 / 少报不误报"的既有风格反向 ✓；③ 它还会带来一条新的要回答的规则（通配进来的名字与 use m.C 同名时谁赢）⇒ 用多一条规则换更差的可见性，不划算 ✗（细节见 US1 的"顺带收益"：US3 的必要性被 US1 直接消掉了 ✓）
在解析器里做类型名解析（拿模块符号表） 解析器不该知道模块加载状态 ⇒ 归一化放语义侧 resolve_alias_in_type（§1-⑤ 的单一入口）
