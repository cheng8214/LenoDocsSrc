LenoQR v0.3.0

Leno 的二维码模块。形态与 LenoCrypto 一致：编码端纯 Leno、解码端 FFI。

当前进度 - ✅ 生成（encode）：纯 Leno —— 版本 1–40 自动选择、L/M/Q/H、数字/字母数字/字节(UTF-8) 三种模式、8 个掩码 + 4 条罚分、format/version 的 BCH、GF(256)/Reed-Solomon（0x11D） - ✅ 识别（decode）：quirc 后端（ISC），gray / ARGB8888 / RGB24 三种像素入口 - 两端不互相依赖：编码不需要原生库；解码不依赖编码器

生成（encode，纯 Leno）

import "QR" as qr

var r = qr.encode("https://gitee.com/cheng8214/LenoLang", "M")   // 纠错档 L/M/Q/H，默认 M
if not r.ok { print(r.err); return }

print("v" + _str(r.version) + "/" + r.eccName + " mask=" + _str(r.mask))
var rows = r["rows"] as Array[string]      // size 行，每行 '0'/'1'（'1' = 黑）

返回 Dict：

键 类型 含义
ok / err bool / string 失败原因（如"内容超出该版本容量：101 字节，v1/H 只能装 7 字节"）
version / ecc / eccName / mask / size int / string 实际选中的规格（版本、纠错档、掩码、边长模块数）
mode int 0=数字 / 1=字母数字 / 2=字节(UTF-8)
rows Array[string] 矩阵（'0'/'1' 文本，便于直接打印/对拍）
cw Array[int] 交织后的完整码字流（数据 + 纠错）—— 仅对拍/诊断用

配套：

// 矩阵 → 像素（scale 像素/模块，quiet 模块静区；静区不足 4 格很多识别器会扫不到）
string gray = qr.toGray(r, 4, 4)     // 1 字节/像素，0=黑 255=白（可直接喂 decodeGray）
string argb = qr.toARGB(r, 4, 4)     // ARGB8888（B,G,R,A）

// 指定版本 / 查容量
var r2 = qr.encodeVersion(text, "H", 10)   // 不做自动选择；装不下就 ok=false
qr.capacityBytes(1, 0)                      // v1/L 字节模式 = 17
qr.dataCodewords(1, 0)                      // v1/L 数据码字 = 19
qr.gfMul(a, b)                              // GF(256)/0x11D 乘法（自测用）

ECI 26（UTF-8 显式声明）：少数老扫码器会按 Latin-1 解释未声明编码的字节， 显式声明能避免乱码（代价 +12 bit 容量）：

var r = qr.encodeEci("你好，Leno", "M")     // r.eci == 1

Kanji 模式（Shift-JIS 字节 → 每字 13 bit；本库不做转码）：

import strings
// "こんにちは" 的 SJIS 字节
string sjis = strings.from_bytes([130, 177, 130, 241, 130, 201, 130, 191, 130, 205])
var r = qr.encodeKanjiSJIS(sjis, "M")       // r.mode == 3

不做自动转码的理由：Leno 没有 iconv，跨平台转码要么加原生依赖、要么维护大表； 调用方通常本来就在处理 SJIS 数据（从文件/网络拿到的就是字节）。

存成 PNG 的完整例子：examples/gen_png.leno（编码纯 Leno，只有"写 PNG"借 LenoSDL3 的 IMG_SavePNG）。 不想依赖 SDL 的场合，直接拿 rows 自己画即可。

识别（decode，quirc）

import "QR" as qr

// ① 灰度缓冲（每像素 1 字节，0=黑 255=白）
var r = qr.decodeGray(grayPtr, w, h, stride)

// ② ARGB8888（内存序 B,G,R,A —— SDL 的 PIXELFORMAT_ARGB8888 / pngFileToPixels / 截屏都是它）
var r = qr.decodeARGB(pxPtr, w, h, pitch)

// ③ RGB24（内存序 B,G,R）
var r = qr.decodeRGB24(pxPtr, w, h, pitch)

if r.found { print(r.text) }

三者都返回同一种 Dict：

键 类型 含义
found bool 是否识别到二维码
text string 载荷（UTF-8/ASCII 字节原样转成 Leno string）
len int 载荷字节数
err string 空串 = 正常；非空 = 真错误（库没编 / ABI 不符 / 参数非法）

found=false 且 err="" 表示"图里没有二维码" —— 扫一张截图没扫到码是日常，不是异常， 所以这里不抛异常（与 LenoSDL3 的 capture 系列返回 Dict 是同一口径）。

多码（一张图里多枚码：海报拼图、成对贴纸、界面截图）—— 检测只做一次， 按 index 逐个解：

var all = qr.decodeAllARGB(px, w, h, pitch)
// {found, count, texts: Array[string], metas: Array[int], err}
//   count = 检测到的枚数（含解不开的）
//   texts = 成功解开的载荷
//   metas = 每枚 4 个整数 [version, ecc_level, mask, data_type]
//           ecc_level 是 quirc 口径：M=0 L=1 H=2 Q=3；data_type：1=数字 2=字母 4=字节 8=Kanji
print(_str(all.count) + " 枚")
for (all.texts as Array[string]) to t { print("  - " + t) }

单码接口（decodeGray/ARGB/RGB24）在多码图上只返回第一枚能解开的 —— 不确定图里有几枚时用 decodeAll*。

其它诊断/元信息：

函数 说明
qr.version() quirc 自身版本串（当前 1.0）
qr.abi() 原生库 ABI 版本（当前 1，用于和 .leno 侧握手）
qr.maxPayload() 单枚码的最大载荷字节数（quirc 给的是 8896）
qr.libName() / qr.libPath() / qr.available() 加载诊断

示例：examples/decode_png.leno（用 LenoSDL3 解 PNG → 交给 LenoQR 识别）； 屏幕框选识别可直接把 SDL3.captureScreen() / Win32.captureScreen() 返回的 {w,h,pitch,pixels} 喂给 decodeARGB。

原生库怎么来的

src/
  quirc.h quirc_internal.h quirc.c decode.c identify.c version_db.c   ← 上游原样（ISC）
  leno_qr.c      ← 我们唯一的 C 入口（包装层）
  build_dll.bat  ← Windows：产出 lib\quirc.dll
  build_so.sh    ← Linux / macOS：产出 lib\quirc.so

为什么要包装层（而不是让 Leno 直接调 quirc_*）：

  1. quirc_code / quirc_data 各带 ~9KB 内嵌数组，交给 Leno 用 cstruct 严格对齐 = 把 quirc 的 ABI 抄进 .leno，换版本就静默错位；
  2. quirc 只吃紧凑灰度缓冲（w×h，无 stride），而调用方给的是带 pitch 的 ARGB8888 —— 逐行拷贝与灰度转换（BT.601 luma）都放在 C 里做一次。

对外只有 5 个导出：leno_qr_abi / leno_qr_version / leno_qr_max_payload / leno_qr_scan_gray / leno_qr_scan_argb（返回 >=0 字节数、0 没找到、-2 参数、-3 内存）。

ABI 握手：.leno 侧启动时比对 leno_qr_abi() 与 qr_native.leno 里的 ABI 常量。 dlopen 成功 ≠ 签名一致（旧 DLL 配新 .leno 在 x64 上不会崩，只会读出垃圾）⇒ 不一致直接报 "请重跑 build 脚本"。

库的查找：只把裸文件名交给 ffi.load，由 FFI 层按 模块目录/bin → 模块目录 → 已加载模块目录 → 单文件打包资源目录 → exe 目录 → PATH 去找。quirc.dll 与 qr_native.leno 同在 lib/ ⇒ 走"模块目录"这条即命中。

⚠ 不要自己用 dirs.script_dir() 拼路径：它给的是入口脚本所在目录（不是模块目录）， 从 test/ 跑时会拼出 leno_module/lib/ 这种不存在的路径（第一版踩过）。

构建

cd build\leno_module\LenoQR\src
build_dll.bat          :: Windows → ..\lib\win\quirc.dll（-static-libgcc，自包含）

cd build/leno_module/LenoQR/src
./build_so.sh          # Linux → ../lib/linux/quirc.so
OUT_DIR=../lib/mac ./build_so.sh   # macOS（同一脚本，换个输出目录）
  • 上游 quirc 源不加 -Wall（它本身不是零告警，不为消告警去 fork）； 我们自己的 leno_qr.c 用 -Wall -Wextra（当前0 warning）。
  • 产物落 lib/<平台>/，src/ 只放源码（2026-11-19 起；此前是平铺在 lib/）。

打包（-p）

leno.toml 里声明：

[native-libs.quirc]
win   = "lib/win/quirc.dll"
linux = "lib/linux/quirc.so"

-p --onefile 会把它内嵌进 exe，首次运行时解包到用户缓存目录（实测：897KB 单文件产物， [pack] 内嵌 1 个原生库，运行后能正常调 qr.abi()）。

⚠ 打包器只取文件名落盘（collector_add 把 lib/win/quirc.dll 复制成 exe 同目录下的 quirc.dll）⇒ qr_native.leno 的 lib() 里"子目录路径失败后退回裸文件名"那一路正是 为这个场景准备的，两边配合得上。

⚠ macOS 那行还没加：随包的 .so 是 Linux ELF（macOS dlopen 必失败），写上 mac = "..." 会让"文件不存在就报错"的检查变成假通过。要在 macOS 分发时， 先 OUT_DIR=../lib/mac ./build_so.sh 产出 Mach-O，再补一行 mac = "lib/mac/quirc.so"，同时在 qr_native.leno 的 lib_name() 里加 mac 分支。

实测（Windows x64 · gcc 15.2.0）

  • 编码耗时（纯 Leno，含 8 掩码评分）—— 优化前后：
内容 优化前 优化后
15B（v1/M） 1.6 ms 0.68 ms
300B（v10/M） 16.2 ms 5.0 ms
1200B（v25/L） 69 ms 21.4 ms

优化点：① 罚分单遍扫描（原 6 遍）；② 掩码就地切/撤（原每掩码复制整张矩阵）； ③ 掩码条件表按 size 缓存（批量生成同版本时零重算）；④ RS 生成多项式按 n 缓存； ⑤ 计数循环统一用 for a:b to i（实测 100 万次空转：for 4.2ms vs while 6.4ms）。

⚠ 用 for 时记两条（本库踩过）： - 闭区间：for 0:n-1 to i 走 0..n-1 共 n 轮；空区间（n=0）执行 0 次，不必为它退回 while； - 倒序要显式步长：for 3:0 是空区间（0 次），倒着扫要写 for 3:0:-1 to i。 本库的 bits_push（高位先写）与 zigzag 放置（右列→左列）都用这种写法 ✓ - 识别耗时：一张 328×328 PNG（v4/Q）从读盘到出文本 ≈ 5 ms；多码检测与单码同量级 （检测只做一次，逐枚解码另算） - 生成的 PNG 头/尺寸经独立解析核对（328×328 / 360×360，5–6 KB）

边界与已知限制

  • 不做：Structured Append、Micro QR、ECI 分配号 ≥128（只支持单字节分配号， 足够覆盖 UTF-8/ISO-8859/SJIS 等常见值）、Kanji 的自动转码（要调用方给 SJIS 字节）。
  • 编码只吃 string（UTF-8 字节）：二进制载荷请先自己转成字符串载体。
  • 单码接口在多码图上只返回第一枚；需要全部用 decodeAll*。
  • 二维码四周必须留 ≥4 模块静区，否则定位图案认不出来（这是 QR 规范，不是库的毛病）。
  • text 是 quirc 给出的原始载荷字节：UTF-8 载荷（绝大多数生成器）直接用； Kanji/Shift-JIS 或 ECI 声明了别的编码时，需要调用方自行转码（quirc 里 eci / data_type 暂时没往上暴露 —— 需要时在 leno_qr.c 里加一个 meta 出口）。
  • 低质量拍照的鲁棒性弱于 zxing-cpp（quirc 的定位/纠错更简单）；截图与清晰照片够用。 真要压拍照场景，再考虑加 zxing-cpp 兜底（C++ 构建链代价另算）。
  • POSIX 分支未在本机验证（本机无 WSL/Docker）。脚本与 Windows 同构，需在 Linux/macOS 上跑一遍测试才算收口。

规格表从哪来

lib/qr_tables.leno 不要手改：它由 src/gen_tables.py 从 python qrcode 的 RS_BLOCK_TABLE / PATTERN_POSITION_TABLE 导出（python src/gen_tables.py 重新生成）。 手抄 PDF 的 160 组容量表+分块结构，错一位的症状是"某些版本扫不出来"，且很难肉眼发现。

配套窗口示例（看得见的那种）

leno_gui/应用/二维码生成器/qr_maker.leno：输入框实时生成二维码、Ctrl+S 存 PNG。 它把 qr.encode() 的 rows 矩阵用 LenoImage 画成像素图（4 格静区 + 整数倍缩放）， 再经 SDL3 贴到窗口上 —— 正好演示三个模块怎么串起来。

:: 开窗口（ESC 退出，Ctrl+S 存 qr_out.png）
build\leno.exe leno_gui\应用\二维码生成器\qr_maker.leno
:: 不开窗口，直接出图（CI / 无显示器）
build\leno.exe leno_gui\应用\二维码生成器\qr_maker.leno save "要编码的文字"
:: 开窗口并在 0.8s 后把**窗口内容**回读成 window.png（核对"窗口真实长相"）
build\leno.exe leno_gui\应用\二维码生成器\qr_maker.leno shot

自测口径（不靠肉眼）：生成的 PNG 再喂给本模块的 decode_png 示例，识别结果必须与原文一致 （实测中英文混排 UTF-8 也一致）。

后续可选（都不阻塞现在）

  • 性能：v10 已从 16ms 降到 5.4ms；若还要更快，下一步是把矩阵按"每行一个 int 位图" 表示（罚分与掩码都用整型位运算），预计能再快 3–5 倍，但要重写放置与罚分。
  • 识别增强：多码的坐标（quirc 的 corners 已有，只是没往上暴露）、ECI 编号 透传（quirc_data.eci）。
  • 编码增强：ECI 分配号 ≥128（GB18030 等）、SVG 输出（不需要 SDL）。
  • POSIX：在 Linux/macOS 上跑 build_so.sh + 五个测试，再往 leno.toml 补 linux/mac。
