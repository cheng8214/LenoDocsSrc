F2 非可空 / 可空：语义设计与迁移方案（2026-11-18）

状态：L0 + L1 + L2 + L3 已落地（2026-11-18）：T x = null 已是编译错误， 仓内 1313 文件 + 11 个同级项目全部迁移干净。仅 L4（struct == null 升错误）未做 —— 见第八节。 上游台账：docs/待修_2026-11-17_实测发现.md 的 F2 条目。 结论先行：? 今天只是"声明意图"，没有任何强制力；只禁 T x = null 是无效的 （可从 T? 隐式流回去）。要做就按 L1→L4 分层上线，且必须先给"天然可空"的类型开豁免， 否则一次性返工 149 处语义上本来正确的句柄写法。

一、要解决的两个现场

现场 症状 根因
Aria 桌面歌词 Window dlWin = null 之后 dlWin != null 恒真 ⇒ 用 bool dlOpen 伴生字段兜 非可空类型接受 null，且比较不报错（只在"确定非空"时警告）
Aria 托盘 Tray trayObj = null 同理（trayOn 伴生） 同上

两个 bug 的共性："有没有"这件事靠人手维护一个 bool 伴生字段，忘同步就静默错。

二、现状实测（v0.2.4 + 2026-11-17 的编译产物）

struct P { int x = 0 }
写法 编译期 运行期
P g = null（非可空 ← null） 静默通过 g 就是 null
P? g2 = null 通过 null
P w = q（q: P?，可空 → 非可空） 静默通过 w 是 null
take(q)（形参 P，实参 P?） 静默通过 形参是 null
func f(): P { return null } 静默通过 返回 null
q.x（q 为 null，不用 ?.） 通过 运行期报错：字段访问需要结构体对象
q?.x / q ?? new P() 通过 null / 兜底值
n + 1（n: int? 且确定为 null） 报错（"确定为 null 不能参与算术"） —
p == null（p 确定非空） 警告（WARN_STRUCT_EQ_NULL，2026-11-17 修过误报） 恒 false

关键事实 1：P 与 P? 运行期同构（struct 是堆对象引用，null 是合法值）。 ⇒ ? 若要"有保证"，只能靠静态检查，不可能靠运行时表示。

关键事实 2：只禁 T x = null 无效 —— P? q = null; P w = q; 两行就把 null 洗成非空类型。 ⇒ 必须同时管住四条通路：赋值 / 实参 / return / 字段写入（读侧另有 while/for 条件）。

关键事实 3（决定分期方式）：存量里"显式类型 = null"的分布（口径：排除 var， 统计 类型 名字 = null；已带 ? 的单独算）：

仓库 显式 = null 已写 ? 非可空 其中句柄类（L0 豁免） 真正要改
Aria 16 8 8 4（Ptr ×2、Channel） 4（Window/Font/Tray/PopMenu）
LenoSDL3 + leno_gui 152 39 113 78（Ptr / cLib / sdl3 / sdl3_ttf …） 35
合计 168 47 121 82 39

真正要改的 39 处里，绝大多数是懒初始化缓存与测试夹具，不是"概念错了"：

  • Dict lineWCache = null（sdl_edit.leno:114）、Array[string] _phLines = null（sdl_edit.leno:128） → Dict? / Array[string]?，判空后懒建
  • Font g_fontBig = null（test_filedialog.leno:25）、Window a = null（test_mark_attribution.leno:25） → Font? / Window?（测试里本来就是"稍后创建"）
  • FFI 懒加载句柄（kernel32 _krnl = null、sdl3 g_lib = null）属于 L0 豁免，不用改

⇒ 一刀切禁止会把 82 处语义正确的句柄写法一起判红，而真正的迁移面只有 39 处。 这就是必须先有 L0 豁免清单的原因。

现有的 ? 声明基数：LenoSDL3/gui 160 处、Aria 9 处（说明 ? 已经在用，只是没人强制）。

三、规则设计（分层上线，每层独立可回退）

L0 定义"天然可空"（豁免清单，先定死）

下列类型的变量允许 = null，且不参与 L1/L2 的检查（它们的存在意义就是"可能没有"）：

Ptr[...] / Ptr / cLib 句柄（kernel32 这类）/ Channel / Thread / Future / File / Socket / func(...) / cstruct 指针

判据写在编译器一处（kind_accepts_null_ref 已有类似清单，复用它 + 补 cstruct）， 不再逐处特判。struct / face / enum / 数值 / string / Array / Dict 不豁免。

为什么 string 不豁免：string s = null 是"空字符串"的假象，用 "" 才对。

L1 非可空类型 ← null 字面量 ⇒ 警告（不是错误）

覆盖 5 个位置：变量声明 / 赋值 / 实参 / return / struct 字段默认值。

[警告] 'dlWin' 声明为 Window（非可空），却赋了 null
        提示: 这个值之后取字段会运行期报错（"字段访问需要结构体对象"）
        提示: 要表达"可能没有"请写 `Window? dlWin = null`，并用 `if dlWin != null { … }` 收窄
        提示: 句柄类（Ptr / cLib / Channel / File …）不受此限

先警告不报错的理由：存量 121 处要按 L0 分类过一遍 —— 82 处句柄类自动豁免， 剩下 39 处（Aria 4 / SDL3+gui 35）里既有真问题（Window dlWin = null），也有该顺手改成 ? 的 懒初始化缓存。先跑一段警告、确认"剩下的都是真问题"，再升错误，比一次性断掉存量安全得多。

L2 T? → T 的隐式流失 ⇒ 警告

四条通路（赋值 / 实参 / return / 字段写入）。没有这一层，L1 就是纸糊的（关键事实 2）。

[警告] 'q' 是 P?（可能为 null），却直接传给了要求非可空的形参 'p'
        提示: 三种修法 —— ① `if q != null { take(q) }`（分支内收窄）
                          ② `take(q ?? 默认值)`
                          ③ 形参本身改成 `P?`，在函数内部判空

前置条件：if x != null 的收窄要真的能收（is 守卫已有收窄机制，null 守卫要补上同等能力）， 否则 L2 会逼用户到处写 ?? 默认值。

L3 L1 升错误

只把"非可空 ← null 字面量"升成错误（L0 豁免不变）。这时 T x = null 彻底写不出来。

L4 struct == null 升错误

必须排在 L1+L2 之后 —— 只有"非可空真的非空、可空不会偷偷流回去"成立， "p == null 恒为 false"才是一个永远的逻辑错误而不是碰运气。

L4 之前的过渡态：维持现在的 WARN_STRUCT_EQ_NULL（已修过误报：初值是 null 的变量不再被警告）。

版本与逃生阀

层 版本 形态
L1 + L2 + 收窄 0.3.0（minor） 警告，可用 @allow_null 局部豁免（可选）
L3 0.4.0（minor） 错误
L4 0.4.0 同上 错误

不做 LENO_ALLOW_NULL=1 这类全局运行时开关：编译期规则不该有环境变量后门（与"单一事实来源"冲突）。 需要豁免就写 T? 或加段级注解。

四、迁移范式（真实代码，前后对照）

A. Aria 桌面歌词：Window + bool 伴生 → Window?

// 现在（desktop_lyric.leno:64 附近）
Window dlWin = null
bool   dlOpen = false
…
if not dlOpen { dlWin = … ; dlOpen = true }
if dlOpen { dlWin.set_always_on_top(true) }     // ← 忘同步就静默错

// L1/L2 之后
Window? dlWin = null
…
if dlWin == null { dlWin = … }
if dlWin != null { dlWin.set_always_on_top(true) }   // 收窄，不用再维护 dlOpen

收益：删掉 dlOpen 这个手工 Option；if dlWin != null 由编译器保证收窄（L2 只会在这里放行）。

B. Aria 托盘：同上

Tray    trayObj  = null        // tray.leno:44
PopMenu trayMenu = null        // tray.leno:45
bool    trayOn   = false

→ Tray? / PopMenu?，删 trayOn，用 if trayObj != null 收窄。

C. LenoSDL3 FFI 懒加载：保持原样（L0 豁免）

kernel32 _krnl = null                       // w32_memory.leno:103
if _krnl == null { _krnl = ffi.load("kernel32") }

→ 不动。cLib 句柄天然可空。如果将来想把"加载失败"也建模进去，再写 kernel32?； 但没必要 —— ffi.load 失败本身就会报错，句柄只有"加载过/没加载过"两态。

D. 非可空返回 null

func findUser(int id): User { return null }        // 现在：静默

func findUser(int id): User? { return null }       // L1 之后：必须这样写
…
var u = findUser(7)
if u != null { … }

E. 可空传非可空形参

P? q = someMaybe()
var a = take(q)                                     // 现在：静默把 null 传进去

if q != null { var a = take(q) }                    // L2 认这条（分支内收窄）
// 或
var a = take(q ?? new P())                          // 明确兜底

F. （可选，不推荐大面积用）显式抉择

Option[T]（LenoResult 已有 Option / some / none）适合"错误通道"场景（Result[Option[T]] 组合）， 不建议用来替代 T?：多一层装箱、写法更长，而且 T? 已经在 169 处存量里用着了。

五、判据与回归（每层落地时必须带的用例）

层 正向 误报守卫
L1 P g = null 报警告；P? g = null 不报 kernel32 _k = null、Ptr[u8] p = null、Channel c = null、Window? w = null 全不报
L2 P w = q / take(q) / return q / obj.f = q 各报一条 if q != null { take(q) } 不报；take(q ?? d) 不报；q?.f 不报；q ??= 之后不报
L3 P g = null 报错；文案含 P? 改法 豁免类仍编译通过
L4 p == null（p 非可空）报错 q == null（q 可空）不报；p == null 里 p 来自 x as P（可能 null）不报

另需一条跨仓回归：Aria --check aria.leno + LenoSDL3 全量 --check（本轮 F3 用的同一套）， 要求 0 错误、警告数可解释（每条都能对上"真问题"）。

六、未决问题（需要拍板）

  1. 收窄能力：if x != null 之后要不要把 x 视为非空（L2 的前提）。 现有 is 守卫有收窄、??= 有"之后非空"，null 守卫补齐是一致的做法 —— 但要处理 while/and/or 的组合（or 条件下不收窄，与 is 的既有口径一致）。
  2. 数组/字典元素：Array[P] 的 arr[i] 是否算"可能为空"？ 建议不算（与今天一致，避免给所有容器访问加噪声）；要严格就写 Array[P?]。
  3. 泛型：func f[T](T v) 里的 T 是否可空？建议：跟随实参，不做额外约束。
  4. 非空断言：要不要 p!？建议不做（与"不发明运算符"原则一致）； 需要"我知道它不会为空"时用 p ?? 兜底 或把类型改成非可空并保证赋值路径。
  5. string 的豁免：string s = null 现在是合法的（运行时当空串？还是 null？）—— L1 要不要管它？建议管（写成 ""），但要先确认现有代码里没有依赖 null 字符串的地方。
  6. 迁移谁来写：Aria 只有 4 处（Window/Font/Tray/PopMenu），我可以直接给 patch； LenoSDL3 的 82 处按 L0 豁免不动，剩下 35 处多是测试夹具与懒缓存，可随下个版本顺手改。

八、迁移与 L2 现状（2026-11-18 第二轮）

8.1 自身代码迁移：已完成（69 处 → 0，仅剩 1 条有意保留）

一次性脚本（变量/字段 ⇒ 类型后加 ?、return null ⇒ 改签名）改了 37 个文件 / 63 处， 其余 6 处人工处理。结果：全仓 1313 个 .leno 编译检查 0 失败、L1 警告 仅 1 条 （examples/工具/leno-replace.leno 的 read_raw，它需要"早退收窄"才敢写 string?）。

迁移中踩到的两点（都已修）：

  1. 字段赋值被误判成"宿主对象赋 null"：a.raw = null 的目标是字段访问， 而我的检查对 targets[] 为空时回退到 names[0]（拿到 a）⇒ 报"变量 'a'（Anim）赋了 null"。 修法：targets[0] 存在且不是裸变量时不再回退（3 条误报消失）。
  2. catch e { inner = null } 被插成了 catch e {? inner = null }：脚本按行尾 name = null 插 ?，撞上单行 try/catch。⇒ 迁移脚本只适合"声明行"，遇到单行复合语句要人工核。

8.2 L2（T? → T 的流失）：已开启（2026-11-18 修完崩溃根因）

实现内容（代码都在，留着待定位后一行打开）：

位置 挂点

崩溃根因（2026-11-18 已修）：打开后 391 个文件编译期崩 0xC0000005。 真凶不在检查函数里，而是：

semantic_init() 没有清 s->null_narrow_count

Semantic 是 main.c 的栈变量、semantic_init 逐字段初始化（不是整体 memset）—— 漏了这个新字段 ⇒ 计数是栈上垃圾（实测读数 291879179）⇒ sem_null_narrowed() 的循环 按 2.9 亿次越界读 null_narrow_names[]，在 strcmp 上炸。

排查路径（记录下来省下一次）：把崩溃文件按行数排序找到 3 行的最小样例 → 在 warn_nullable_flow 入口打印 s / s->current / s->null_narrow_count ⇒ 一眼看到垃圾计数。 中途误判过 scope_resolve／infer_expr_type／类型名悬垂（都已顺手加固，但不是根因）。

修法两条： 1. semantic_init() 里 s->null_narrow_count = 0;（根因）； 2. sem_null_narrowed() 里再夹一道 count ∈ [0, 8]（坏状态最多退化成"不收窄"，绝不越界）。

顺带修的真 bug：semantic_check_native_arg() 的 5 个调用点全都传整个调用节点 （AST_MODULE_CALL / AST_CALL），而不是出问题的那个实参 ⇒ 报错位置指向调用的列、 而且"值是不是裸变量"永远判不出来（收窄豁免失效）。现在传 args.items[i]： 报错指到实参、收窄能认出变量、examples/工具/leno-replace.leno 的 if raw == null { return } + strings.byte_slice(raw, …) 也终于编得过 ✓

验证：assert/test_nullable_flow.leno（5 组：三条通路各报一条 / 分支收窄放行 / 早退收窄放行 / 早退后 native 实参放行 / 没有 if 的文件不崩）。 全仓 1313 文件 0 失败 0 警告（自身代码已按 L1/L2 迁移干净）；断言 646/0、 模块测试 52/0；Aria --check 0 错误。

8.3 L3（T x = null 升错误）：已开启（2026-11-18）

前置迁移（升错误之前先清零存量）：仓内 1313 文件早已 0 警告；同级目录的 5 个项目 另有 25 处，按 L1 的告警逐条迁移：

升错误本身：warn_null_literal() → check_null_literal()，改发 ERR_TYPE_MISMATCH； WARN_NULL_LITERAL 从 WarnType 里删掉（枚举值不落盘，删除安全）。5 个位置全覆盖， 豁免口径不变（T? / any / 未标注 / 泛型形参 / 句柄类）。

顺带修的两处"编译器自己生成 null"（否则 L3 会把编译器产物判红）：

  1. 带载荷 enum 的槽位：降级出的 struct 字段 p0/p6/... 默认值是 null，但字段类型照抄 载荷类型（Pt）⇒ L3 报"字段 p0 是 Pt，不能赋 null" ⇒ 所有带 struct 载荷的 enum 编不过 ✗。 修法：semantic.c（AST 侧）与 enum_payload.inc（符号表侧）同时把这些槽的类型标成 nullable = 1（只标"要造 null 默认值"的那几类 kind：struct/face/Ptr/cstruct/泛型形参； int/float/bool/string 槽仍走零值、保持非可空）。
  2. 断言用例：9 个用例原来用 P g = null / string s = null / Array a = null 演示 "旧语义"，已改成 ? 并更新注释（test_var_null_semantics 的教程口径同步改为 "引用型也要 ? 才能清空"）。

验证：断言 646/0、模块测试 52/0、仓库 1313 文件 0 失败、11 个项目 203 文件 L3 失败 0、编译器 0 warning。
