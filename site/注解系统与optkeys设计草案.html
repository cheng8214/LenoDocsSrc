注解系统 & @optkeys（设计 + 实现说明）

状态：✅ 已实现（2026-10-31 落地）—— 实现见 src/semantic/semantic_annotations.c： @optkeys(["visible:bool", "w:num", "align"]) 带类型后缀（int/float/num/bool/string/Array， 冒号后不写 = 不查）、同模块与跨模块都查（跨模块经模块符号表 / .lenosymc v39 往返）。 本文因此保留为设计与口径说明（为什么放在"参数检查"这个阶段查、三处尝试的结论）， 而不当"待做计划"看。 ⚠ 历史标题曾写「草案（未实现）」，2026-11-21 核对源码后订正 ✓ —— 别再照着标题判断状态。

起因：docs/语言与框架问题_Aria实战_2026-10-31.md 的 L5 —— LenoSDL3 各控件用 dochk.check(who, opts, _opts_keys()) 在运行时对账选项键， 传错键只 print 一行警告：

  • 没有文件:行号（who 只有控件名，看不出是哪个 createHBox）；
  • 打包后完全看不见（单文件 exe 走 -mwindows，没有控制台，print 丢进虚空）；
  • 每个控件创建都要遍历一遍 opts，纯浪费。

本方案：给语言加一套注解语法，让框架把"这个构造函数接受哪些键"声明成 编译器可消费的元数据，把检查提前到编译期。

⚠ 核心约束：编译器不需要知道 LenoSDL3 的存在。注解是语言特性，框架只是使用者。

G3 运行时零开销（dochk.check 可整套删掉）

2. 语法设计

2.1 注解的基本形态

注解 := '@' 标识符 [ '(' 参数字面量 ')' ]

@deprecated                                  // 无参
export func old_api() { ... }

@deprecated("改用 createBox")                 // 一个字符串
export func old_api() { ... }

@optkeys(["w", "h", "pad_x", "spacing"])     // 字符串数组
export func createHBox(Dict opts): HBox { ... }

@optkeys("*")                                // 通配：接受任意键，不检查
export func createCustom(Dict opts): HBox { ... }

参数只允许字面量：string / int / float / bool / 由它们组成的数组。 不允许表达式、不允许 identifier、不允许跨行。

理由：注解是编译期数据，一旦允许表达式就要引入"注解求值"，失败语义、 循环依赖、求值顺序全得设计。一期把口子收死，报错文案写"注解参数必须是字面量"即可。

2.2 多个注解可叠加

@optkeys(["w", "h", "pad_x"])
@deprecated("改用 createBox")
export func createHBox(Dict opts): HBox { ... }

收集成有序列表挂在声明上。同名注解出现多次 ⇒ 参数并集（见 2.4）。

2.3 @optkeys 挂在函数上，不是类型

// LenoSDL3/lib/sdl_layout.leno
@optkeys(["w", "h", "pad_x", "pad_y", "spacing", "bg_color", "bg_radius",
          "clip", "justify", "align", "visible"])
export func createHBox(Dict opts): HBox {
    // dochk.check("HBox", opts, _opts_keys())   ← 一期之后再删
    ...
}

为什么不挂在 struct HBox 上：

  1. HBox 是 struct，但 opts 不是它的字段，而是构造参数 —— 语义上属于构造函数；
  2. 同一类型可能有多个构造函数（createHBox / createHBoxFrom），键表可以不同；
  3. 挂在函数上，检查时不需要"从返回类型反查类型表"，直接看 callee 的注解即可（实现更简单）。

语义定义为："本函数的 Dict 参数接受这些键"。函数有多个 Dict 参数时，一期只认第一个，并在文档里写明。

2.4 并集语义

@optkeys(["w", "h"])
export func createHBox(Dict opts): HBox { ... }

@optkeys(["justify"])            // 同一个函数上的第二个 optkeys ⇒ 并集
@optkeys(["w", "h"])
export func createHBox(Dict opts): HBox { ... }

为什么需要并集：框架里"基础布局键"和"主题相关键"可能由不同模块/不同作者追加， 合并比"后覆盖前"更符合直觉（也不会因为声明顺序不同产生不同结果）。

2.5 未知注解直接报错

编译器维护一张已知注解表（一期只有 optkeys）：

[错误] aria.leno:42: 不认识的注解 '@optkey'
  [提示] 你是不是想要 '@optkeys'？

比"静默忽略"好：注解拼错等于没写，而且最难发现（代码看着是对的）。

3. 词法与 AST

3.1 词法

新增一个 token：

TOK_AT        // '@'

@ 在 Leno 里当前未被占用（字符串插值 $"..."、可切片 arr[a:b]、可空 T?、 空合并 ?? 都不冲突），不会引入歧义。

3.2 AST

// 注解节点（挂在任意声明上的链）
typedef struct {
    char*  name;          // "optkeys" / "deprecated"
    int    line;          // 注解所在行（诊断用）
    // 参数：一期只支持 0 或 1 个字面量
    int    arg_kind;      // 0=无参 / 1=string / 2=int / 3=float / 4=bool / 5=字符串数组
    char*  arg_str;
    double arg_num;
    int    arg_bool;
    char** arg_list;      // 字符串数组
    int    arg_list_len;
} AstAnno;

// 声明侧挂链（不新建声明节点，只在现有节点的 u.xxx 里加两个字段）
AstAnno* annos;           // 注解数组
int      anno_count;

挂在 AST_FUNC_DECL / AST_STRUCT_DECL / AST_VAR_DECL 上。

为什么不做一个 AST_ANNOTATED { annos, decl } 包装节点：那会让所有消费声明的 地方（semantic / codegen / 模块符号表）都要多拆一层。直接给声明加字段，改动面最小。

4. parser 落点

主入口：src/parser/parser.c 的模块级 declaration()（当前 switch 在 :160 起）。

在 switch 之前 插入注解收集：

// 伪代码
static Ast* declaration(Parser* p) {
    AstAnno* annos = NULL;
    int anno_n = 0;

    // ① 先把所有 @xxx 收完
    while (p->lex.current.type == TOK_AT) {
        lexer_next(&p->lex);                       // 吃掉 '@'
        if (p->lex.current.type != TOK_IDENT) {
            error_add_at_fmt(ERR_SYNTAX, line, col, "'@' 后面必须跟注解名");
            return NULL;
        }
        AstAnno a = parse_anno_args(p);            // 名字 + 可选 (字面量)
        annos = realloc_add(annos, &anno_n, &a);
    }

    Ast* stmt = parse_decl_core(p);                // 原来的 switch

    // ② 挂到声明上（允许挂的声明类型有限）
    if (anno_n > 0) {
        if (!decl_can_be_annotated(stmt)) {
            error_add_at_fmt(ERR_SYNTAX, ...,
                "注解只能用在模块级声明（func / struct / var / const）之前");
        } else {
            attach_annos(stmt, annos, anno_n);
        }
    }
    return stmt;
}

注意 export 的顺序：现在的写法是 export func ...。注解要在最外层：

@optkeys([...])
export func createHBox(...) { }        // ✓ 注解在最前
export @optkeys([...]) func ...        // ✗ 不支持（不给自己挖坑）

因为 parser_module.c:414 的 TOK_EXPORT 分支会递归调回 declaration()， 所以只要注解收集在 declaration() 顶部，@x export func ... 天然可用 ✓

参数解析：

static AstAnno parse_anno_args(Parser* p) {
    // 名字
    // 可选 '('
    //   TOK_STRING → 一个字符串
    //   TOK_LBRACKET → 字符串数组（只允许 string 元素）
    //   TOK_INT/FLOAT/TRUE/FALSE → 标量
    // ')'
    // 其它 token ⇒ "注解参数必须是字面量"
}

5. semantic 检查

5.1 收集

在遍历声明时把 @optkeys 记到函数符号上：

// 全局（每编译单元一份）
typedef struct {
    const char* func_name;     // 全限定或模块内唯一名
    char** keys; int n;        // 已合并（并集）
    bool wildcard;             // '*' ⇒ 不检查
    int decl_line, decl_file;  // 诊断里指"去哪看"
} OptKeySet;

5.2 检查

在 AST_CALL 的处理里（src/semantic/visitinc/visit_expr.inc）：

// ① callee 解析到具体函数符号，且它带 @optkeys
// ② 排除 wildcard
// ③ 找到"第一个 Dict 参数"对应的实参
// ④ 该实参必须是 AST_DICT_LITERAL（字面量）—— 否则放行
// ⑤ 逐个键：不在集合里 ⇒ 报

for (每个键 k in dict_literal) {
    if (key_in_set(k)) continue;
    const char* hint = nearest_key(k, set.keys, set.n);   // 编辑距离 ≤2
    if (hint)
        error_add_at_fmt(ERR_*_UNKNOWN_OPT, call_line, col,
            "%s 的 opts 不认识键 '%s'\n"
            "  提示: 你是不是想要 '%s'？\n"
            "  提示: 接受的键见 %s:%d 的 @optkeys",
            func_name, k, hint, set.decl_file, set.decl_line);
    else
        error_add_at_fmt(... 同上，无"是不是想要"一行 ...);
}

编辑距离工具：semantic_method_hint 那套（semantic_type_utils.c:1439 附近） 已经有"相似名"的实现，可以直接复用/抽出通用版本。

5.3 为什么只查字面量

createHBox({w: 30, tip: "x"})     // ✓ 查
var o = {w: 30, tip: "x"}
createHBox(o)                      // ✗ 放行（静态不可知）
createHBox(buildOpts())            // ✗ 放行

这是 threads.start 那条教训的直接应用（见 docs/语言与框架问题_Aria实战_2026-10-31.md L3）：宁漏勿误报。 "有时查得到、有时查不到"如果还伴随误报，用户会直接关掉这个特性。

6. codegen

注解不产生任何字节码。AST_* 上的 annos 字段在 codegen 里被忽略即可。

一期不需要 AST_ANNO 这个独立节点（见 3.2），所以 codegen 甚至不用改。

9. 对账用例（必须做）

风险最高的地方不是检查逻辑，而是声明和实现不同步：

export func createHBox(Dict opts): HBox {
    float w = opts.get("w", 0.0)          // ← 实现读了 "w"
    ...
}
@optkeys(["w", "h"])                      // ← 声明漏了 "h"？

一旦声明漏键，正常代码编译不过 —— 比运行时静默更让人恼火。

兜底用例（放 assert/，CI 跑）：

扫描 LenoSDL3/lib/sdl_*.leno 里所有
    opts.get("X") / opts.has("X") / opts["X"]
与同文件的 @optkeys 声明比对：
    实现读到的键 ⊆ 声明集合      （漏声明 ⇒ 失败）
    声明集合 ⊆ 实现读到的键 + 白名单（多声明 ⇒ 警告，不算失败）

这条用例是整套机制能不能长期用的关键，一期就要带上。

12. 实现踩坑记录（2026-10-31，都实测过）

13.1 注解必须加在门面层，不是实现层

LenoSDL3 是"门面 + 实现"两层：

// SDL3.leno（门面，应用 import 的是这个）
export func createHBox(Dict opts): HBox { return lay.createHBox(opts) }

// sdl_layout.leno（实现）
export func createHBox(Dict opts): HBox { HBox b = new HBox(); b.set(opts); return b }

把 @optkeys 加到实现层时，应用里的 SDL3.createHBox({...}) 一个都不报——因为符号表里 它看到的是门面那个函数（无注解），门面转发给实现时传的是 opts 变量（非字面量 ⇒ 按规则放行）。

⇒ 门面与实现两处都要加（实现层那份覆盖"模块内部互相调用"）。

13.2 检查落点：挂在"参数个数检查"旁边

先后试过三个位置，都收不到控件构造调用：

位置 结果
visit_expr.inc 的 case AST_CALL 开头 调用是 AST_MODULE_CALL，不进这个分支 ✗
infer_expr_type 的 case AST_MODULE_CALL 该分支只处理 native 模块，用户模块的构造调用不来 ✗
visit_module.inc 的 case AST_MODULE_CALL 开头 实测只收到模块内部的转发调用（mod=lay fn=createHBox）✗

可行的位置：visit_expr.inc 里 func_def 已解析出来、正要报"参数数量不足"的那一处—— 那里跨模块也能拿到被调函数的 AST（否则报不出参数个数）⇒ 直接读 func_def->annos， 连符号表都不需要 ✓

13.3 符号表缓存会丢键表

ModuleFuncSymbol.optkeys 是 v39 新增字段。注意两点：

  • add_func 里必须显式置空 func->optkeys（table->funcs 是 realloc 扩容的， 新槽位是垃圾值，不置空会读野指针 ✗ —— 与 param_types 那几条注释同一个坑）
  • 写缓存的顺序是「读源码 → AST 填充 → 写缓存」（sym_table_entry.inc:351/376）⇒ optkeys 能进缓存 ✓；升版本号（v38 → v39）让旧缓存失效重扫 ✓

实测：连续两次 --check（第二次命中缓存）都能正常报出，说明缓存往返是通的。

13.4 ✅ 运行时白名单已整套删除（2026-10-31 收尾）

补齐注解后，_opts_keys() 那套已删（提交 8f6d523，41 个文件、-326 行）：

删掉 保留
41 处 dochk.check(..., _opts_keys()/_set_keys()/label_keys()/alert_keys()) add(c, opts) 的 dochk.check(..., _add_keys())
39 个白名单函数定义 popmenu / tray / window 三处（内部控件，未加注解）

为什么要删——不只是"重复"，而是已经实际漂移过：

sdl_gridlayout.leno 的 set() 读了 min_col_width，但它的 _opts_keys() 白名单里没有 ⇒ 影视海报墙传 min_col_width 一直被运行时误报"不认识的选项"（全量扫 --check 才发现）。

这正是"两份数据"的必然后果。删完只剩注解一份，改选项时只改一个地方。

验证：533 passed / 0 failed；47 个 GUI 主程序 --check 零误报；Aria 实跑界面正常、运行时零 [ui] 告警。

13.5 补注解时的两种来源

  • 没有白名单的（Label / Alert / VirtualGrid）：扫描实现里的 opts.get("…") / opts.has("…") 反推键表，再补通用几何键（w/h）。这类最容易漏，必须靠全量应用验证兜底。

14. 键值类型检查（2026-11-01）

14.1 目标

键名检查只能抓"选项不生效"，值类型写错是逻辑静默走反：

createXxx({visible: "false"})    // 多了一对引号

实测：编译通过；bool v = opts["visible"] ?? false 里 v 装的是字符串（?? 只做空值兜底， 不转换类型）；运行时非空字符串判定为真 ⇒ 界面行为反了，却没有任何报错。

目标：只对声明了类型的键，在编译期把这类错误报出来；没写类型的键行为完全不变。

14.2 语法

类型跟在键名后面，用冒号分隔，仍在同一个 @optkeys 里（不新增 @opttypes—— 键名与类型本来就该在一起，改键名时类型跟着走；多一个注解只会多一套"漏写/对不上"）：

@optkeys(["visible:bool", "enabled:bool", "w:float", "h:float",
          "tip:string", "headers:Array",
          "align", "label"])          // 后两个不写类型 = 不查

14.3 类型词表

只用 Leno 自己的类型名，不发明缩写（曾经想过 fn / arr / dict / num，全部废弃）：

词 接受的实参
int 整数（bigint 也算整数，走 type_is_integer_kind）
float 浮点 和整数（int→float 是本语言允许的隐式转换）
num 数字：int 或 float 都收（注解专用记号，语言里没有这个类型名）
bool true / false
string 字符串
Array 数组
color 颜色字面量 #RRGGBBAA（#RGB / #RRGGBB 也收）—— 见下面的精度说明
不写 不查（默认，占绝大多数）

color 的特殊之处（2026-11-17 加）：它不按"类型兼容"判，因为颜色在语言里仍然是 int （运行期零开销），与 int 的差别在写法而不在类型 ⇒ 判据是"这个字面量是不是颜色字面量" （AST_NUM.is_color，lexer 的 read_color 置位）。 精度刻意收窄（宁漏勿误报）：只有 alpha 字节 == 0 且颜色分量 != 0 的裸 int 才告警 —— bg_color: 0（要透明底色）与 hover_color: 0xCCFFFFFF（本来就写对的 ARGB）一律不报； 变量 / 函数调用 / props 也不报（判不出用法）。

@optkeys(["border_color:color", "bg_color:color"])
func box(Dict opts) { }

box({border_color: #00000088})    // ✅ 53% 黑
box({border_color: 0x00000088})   // ⚠️ 这是"全透明 + 0x88 的蓝"，不是半透明黑
box({bg_color: 0})                // ✅ 既有"不要底色"写法，不报
  • 大小写不敏感（Bool / BOOL 都认），文档写规范形式
  • num 与 float 的检查行为完全一样（float 本来就收 int），差别只在语义表达： 控件的 x / y / w / h / item_h 这类尺寸键内部有时按 float 取、有时按 int 取， 标 num 比标 float 准确，也不会让人误以为"这里必须写 0.5 这种浮点字面量"。 报错文案显示用户写的原词（写 num 就报"期望 num"，不会擅自改成 float）
  • Array[...] 只认外层：Array[int]、Array[Array[int]] 都等价于 Array（见 14.6）
  • 认不出的词（拼错成 bolean）⇒ 退化成"不查"，不报错（宁漏勿误报）

14.4 检查口径：复用现有类型系统，不另立规则

不自己写"AST 形状 → 类型"的映射，全部复用语义分析现有的两个入口：

TypeInfo* got = infer_expr_type(s, value);                       // semantic_type.c:1071
if (got && got->kind != TYPE_ANY && !type_is_compatible(&want, got))
    警告;                                                        // leno_types.h:513
if (got) type_free(got);                                         // 返回值是新分配 ⇒ 必须 free

want 由类型词构造（TYPE_INT / TYPE_FLOAT / TYPE_BOOL / TYPE_STRING / TYPE_ARRAY）。

这样做的好处：

  1. 兼容规则与语言一致（int→float、bigint 当整数、null 可给 any…），不存在"两套规则各说各话"
  2. 覆盖范围从"只有字面量"扩展到任何类型可推断的值（变量也算）： createXxx({visible: flag}) 里 flag 是 string 也能抓到
  3. 改动量小

14.5 落点与改动面

文件 改动
src/semantic/semantic_annotations.c 类型词解析、声明解析、键名比较忽略冒号、值检查、警告文案
src/semantic/visitinc/visit_expr.inc 调用点传 s（annos_check_call_def 加 Semantic* 参数）
src/semantic/semantic_visit_ast.c 同上，extern 声明同步

不动：parser、VM、codegen、序列化（注解本来就是字符串，.lenosymc 不用升版本）。

14.6 已知限制（明确不做）

限制 原因
不查数组元素类型 需要递归解析 + 递归检查 + 空数组/混合数组规则；收益低（17 个数组键，元素多是 string）
Dict[...] 带参数不支持 逗号与注解的 CSV 分隔符冲突（Dict[string, int] 会被裂成两段）
非字面量实参（createXxx(o)）放行 沿用 5.3 的口径，静态不可知
自定义 struct / face 类型暂不支持 opts 里没有这种值；要支持得先解决"跨模块名字比对"

14.7 验收清单

  • @optkeys(["visible:bool"]) + createXxx({visible: "yes"}) ⇒ 编译期警告（期望 bool，实际 string）
  • {visible: flag}（flag 是 string 变量）⇒ 同样报
  • {w: 30} 对着 "w:float" ⇒ 不报（int→float 合法）
  • {padding: 0} 对着 "padding:int" ⇒ 不报；{padding: 0.5} 对着 "padding:int" ⇒ 报
  • 不写类型的键（"align"）⇒ 传什么都不报
  • "headers:Array" + {headers: ["a"]} ⇒ 不报；{headers: "a,b"} ⇒ 报
  • 拼错类型词（"visible:bolean"）⇒ 不报错、退化成不查
  • --check 全量套件零误报；Aria（5000+ 行、大量控件调用）零误报
  • 断言用例 assert/test_anno_optkeys_type.leno

14.8 实现检查清单（防漏）

  1. 类型词解析：anno_type_of_word()（裸词 → 枚举）
  2. 声明解析：anno_key_type_of("visible:bool")、anno_csv_type(csv, key)（CSV 项不以 \0 结尾，不能直接复用前者）
  3. 键名比较要忽略冒号：anno_csv_has / anno_csv_nearest / anno_has_key / anno_nearest 四处都要改——只改一处会出现"键名拼错时提示 align:int"这种怪现象 ✗
  4. 值检查接入两条路径：同模块（AnnoOptKeys 表）与跨模块（CSV 串）
  5. annos_check_call_def 加 Semantic*，两个调用点同步
  6. type_free() 不能漏（infer_expr_type 返回新分配）
  7. 断言用例 + 全量 --check + Aria 零误报
