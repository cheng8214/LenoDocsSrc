区间口径约定（下标 / 整数一律闭区间）

一句话：凡是"下标 / 整数区间"，两端都算（含 b）。 这条规则 2026-10-10 在切片族上定下来，2026-11-20 收尾：把最后两处"半开"也改掉了 （RegexMatch.end ⇒ last、strings.rfind 的 before ⇒ last）。 本文是全仓唯一的口径来源；模块文档里各自重复的那一句只是为了就近可查。

一、规则

用法 语义 例
arr[a : b] / s[a : b] 闭区间，含 b [10,20,30,40][1:2] ⇒ [20, 30]
strings.slice(s, a, b) / s.slice(a, b) 闭区间（与语法切片同口径） "hello".slice(0, 2) ⇒ "hel"
strings.byte_slice(s, a, b) 闭区间（字节下标） ——
for a : b to i 闭区间，a、b 都跑到 for 0 : 3 to i ⇒ 4 轮
switch case a : b 闭区间 case 1:4 命中 1..4
rands.ints(min, max) / rands.int_array(...) 闭区间 rands.ints(1, 6) ⇒ 1..6
RegexMatch.start / .last 闭区间两端（last = 末位） s[m.start : m.last] ⇒ 整段
strings.rfind(pat, last?) last = 允许的匹配起点上界（含） "a.b.c".rfind(".", 2) ⇒ 1
rands.floats(min, max) 按 [min, max] 表述 ⚠ 连续分布，max 命中概率为 0（见下）

负下标

  • 起点负数 ⇒ 从末尾数（arr[-3 : 2] = 倒数第 3 个到下标 2）✓
  • 终点负数 ⇒ 结果恒为空（不是"从末尾数"✗）⇒ 编译器给 [切片负终点] 警告。 要"去掉最后 N 个"写 arr[0 : arr.len() - N - 1] ✓

不是"区间"的长度参数（不参与本条规则）

参数名是 n / len 的，一律是长度，不是端点：

strings.take(s, start, n)        // 从 start 起取 n 个字符
files.read(n)                    // 读 n 字节
ffi.read_bytes(ptr, off, len)    // 从 off 起读 len 字节

判断方法：看参数名 —— end / last 是端点，len / n / count 是长度。

浮点随机：表述为闭区间

rands.floats(min, max) 按 [min, max] 表述。实现是 min + r*(max-min)、r ∈ [0,1) ⇒ max 恰好取到的概率是 0；连续分布下这与闭区间等价，所以口径统一写成闭区间 ✓ （别据此以为 max 会以某个小概率出现 —— 它取不到。要"一定含端点"的离散语义用 ints ✓）

二、2026-11-20 的收尾（breaking）

1. RegexMatch.end（半开）⇒ RegexMatch.last（闭区间末位）

// ❌ 旧（v3.2.43 及以前）
"abc123def"[m.start : m.end - 1]     // 要记得 -1
var n = m.end - m.start              // 长度

// ✅ 新（v3.2.44 起）
"abc123def"[m.start : m.last]        // 与切片同一口径，不用算术
var n = m.last - m.start + 1         // 长度（或直接 m.text.len()）
  • 为什么删字段、而不是把 end 的语义改成"含"：改语义不报错 ⇒ 旧代码 s[m.start : m.end - 1] 会静默少取最后一个字符、end - start 算长度会静默差 1 ✓ 删掉 ⇒ 旧代码在编译期报错并给出改名提示（不会静默错一格）✓
  • 旧 end 的值 = 新 last + 1；空匹配时 last = start - 1（s[a : a-1] 得空串 ✓）
  • 字节码 v3.2.43 → v3.2.44、模块缓存 v58 → v59：字段号含义变了 ⇒ 旧 .lenb / .lenomc 整体失效重编（旧的 1 号位会读到 last，静默差一格 ✗）

2. strings.rfind(pattern, before?) ⇒ rfind(pattern, last?)

// ❌ 旧：before 不含 ⇒ 只在 [0, before) 里找
"a.b.c".rfind(".", 3)      // 1

// ✅ 新：last 含 ⇒ 起点 ≤ last
"a.b.c".rfind(".", 3)      // 3     想保持旧结果写 2
  • 换算：旧 before = n ⇔ 新 last = n - 1 ✓
  • 负数照旧从末尾数（-1 = 末位）✓

3. 编译器怎么兜

  • m.end ⇒ error: struct 'RegexMatch' 没有字段 'end' —— 它**改名**了…（附新名字与换算）
  • arr[i].end / arr[i].nope 这种索引接收者形态也一起兜住了 （此前这条"索引路"只查脚本 struct 的字段表，native struct 整块跳过 ⇒ 运行期才炸 ✗）
  • 迁移提示表在 src/semantic/semantic_type_utils.c 的 semantic_renamed_field_hint()； 仓内 + 下游项目都迁移完后可以删（删前 grep 一遍 \.end\b）✓

三、为什么要统一

  1. 同一个符号 a : b 出现在切片、for、switch case 里 —— 它们早就都是闭区间。 若某个字段/参数是半开，就会出现"同一个 a : b 写法，一处含、一处不含"，只能靠记忆 ✓
  2. 半开的错法是静默差一格（多一个字符 / 少一个字符），结果"看着像对的"， 是排查成本最高的一类 ✗
  3. .len()、strings.find、切片、for 全在一个口径上 ⇒ 一个偏移量可以直接用于另一处， 不需要 -1/+1 中转 ✓
