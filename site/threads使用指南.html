Leno Threads 线程使用指南

简介

Leno 提供基于 隔离 VM + Channel 的多线程支持，参考 Go 语言的 goroutine + channel 设计。每个线程拥有独立的 VM 实例、GC 和内存空间，线程之间通过 Channel 传递消息，不共享内存，零数据竞争。

⚠ "不共享内存"指的是用户数据：vm.globals（入口脚本的顶层变量）、局部变量、 堆上对象都是每线程一份。模块对象（ObjModule）是进程级共享的例外 —— 见下一节。

共享数据模型（先看这一节）

什么共享、什么隔离

东西 主线程 / 子线程 说明
局部变量、参数 各一份 寄存器/栈，天然私有
入口脚本的顶层变量 var x = 1 各一份 子线程启动时深拷贝（对象也克隆，TH8）
模块对象（ObjModule）本身 共享同一份 loaded_modules 是进程级缓存（有意不隔离）
模块级 var（ObjModule.globals） 共享同一份槽 并发写 = 数据竞争；子线程写对象 = 跨堆引用（见下）
thread_local var 每线程一份 语言特性，推荐用于"每线程状态"
threads.local_* 字典 每线程一份 运行期字符串 key 的版本
const 声明 / 模块常量 共享，只读 运行期还带只读标记（OP_LOCK_REF）
Channel / Thread 共享句柄 引用语义，内部有锁

模块顶层语句什么时候执行？

模块顶层（lib/xxx.leno 里不在任何 func 中的语句，包括 var x = …、thread_local var …、 顶层 print(...)）的执行时机是确定的：

  • 谁执行：触发 import 的那个线程（绝大多数情况就是主线程）。
  • 执行几次：整个进程一次。模块对象挂在进程级 loaded_modules 上，第二次 import 直接复用，顶层语句不会重跑。
  • 子线程会不会执行：不会 —— 除非子线程是第一个 import 它的线程（这种情况本身有 风险：模块对象会分配在子线程堆上，而模块表是进程共享的 ⇒ 该线程结束后别的线程访问 这个模块会读到残值。编译器/运行期会打一条「子线程首次加载模块」警告）。

⇒ 所以"主线程 import 时构建一次、之后所有线程只读"是受支持的用法，LenoQR 的 GF 表（g_exp = _gf_build_exp()）就是靠这条。但注意它依赖"主线程先 import"这个前提 —— 如果某个子线程可能先 load 这个模块，就改用 thread_local var 或 threads.local_*。

只读跨堆访问安全吗？

安全。GC 的根集合里包含 loaded_modules 的全部模块对象（loaded_modules_mark_all）， 任何线程的 GC 都会顺着模块对象标记它的 globals；而每个线程的 GC 只会清扫自己堆里的对象 ⇒ 主线程建的表不会被子线程的 GC 回收，子线程正常读它没有问题。

反过来"子线程写模块级 var"就不安全，而且分两种情况：

写法 结果
子线程写标量（m.n = 5） 值复制，安全（但仍是并发写同一槽 ⇒ 语义上要自己保证只有一个人写）
子线程写本线程堆上的对象（m.g = [1,2]） ✗ 跨堆引用：该线程退出/GC 后槽里是悬空指针，读到 185 / -1 / 0 这类残值

第二种现在会打警告（见「注意事项 2. 全局变量」末尾），根治写法是 thread_local var。

核心概念

概念 说明
Thread 线程对象，由 threads.start() 创建
Channel 通道对象，线程间安全通讯的桥梁
threads.start(func, args...) 启动新线程，可传递参数
t.join() 等待线程结束，获取返回值
t.join_for(ms) 带超时的等待：true=已结束，false=超时（线程继续跑）
t.error() 线程的错误文案（空串 = 没出错；不用 join 也能看到）
threads.current_id() 当前 OS 线程 id（诊断/日志用，别做业务判断）
ch.send(value) 向通道发送值（阻塞）
ch.send_for(v, ms) 带超时的发送：满了最多等 ms，超时 false（不写入）
threads.select([ch…], ms) 多路等待：返回第一个有数据的通道 {index, value}，超时 null
ch.receive() 从通道接收值（阻塞）
ch.try_send(value) 非阻塞发送，成功返回 true
ch.try_receive() 非阻塞接收，成功返回值，失败返回 null
ch.close() 关闭通道
ch.is_closed() 检查通道是否已关闭，返回 bool
ch.len() 获取缓冲区当前消息数量
threads.sleep(ms) 当前线程休眠指定毫秒数

Channel 通讯

Channel 是线程间安全通讯的核心机制，参考 Go 语言的 channel 设计。

创建 Channel

// 有缓冲通道（异步）— 缓冲区大小为 N
var ch = threads.channel(10)

// 无缓冲通道（同步）— send 阻塞直到有人 receive
var ch = threads.channel(0)

基本发送与接收

import threads

func sender(var ch) {
    ch.send("hello")
    ch.send(42)
    ch.send(3.14)
    ch.close()
}

main() {
    var ch = threads.channel(10)
    var t = threads.start(sender, ch)

    print(ch.receive())    // hello
    print(ch.receive())    // 42
    print(ch.receive())    // 3.14

    t.join()
}

非阻塞操作

try_send() 和 try_receive() 提供非阻塞的 Channel 操作：

import threads

main() {
    var ch = threads.channel(2)

    // try_send: 成功返回 true，失败（满/关闭）返回 false
    assert_eq(ch.try_send("A"), true)
    assert_eq(ch.try_send("B"), true)
    assert_eq(ch.try_send("C"), false)  // 缓冲区已满

    // try_receive: 成功返回值，失败（空）返回 null
    assert_eq(ch.try_receive(), "A")
    assert_eq(ch.try_receive(), "B")
    assert_eq(ch.try_receive(), null)   // 缓冲区已空

    ch.close()
    assert_eq(ch.try_send("D"), false)  // 已关闭
}

Channel 关闭

  • ch.close() 关闭通道，不再接受新消息
  • ch.receive() 在通道关闭且缓冲区为空后返回 null
  • 向已关闭的通道 send() 会抛出异常
  • 向已关闭的通道 try_send() 返回 false（不抛异常）
import threads

func producer(var ch) {
    for 5 to var i {
        ch.send(i)
    }
    ch.close()
}

main() {
    var ch = threads.channel(10)
    var t = threads.start(producer, ch)

    while true {
        var msg = ch.receive()
        if msg == null {
            print("通道已关闭")
            break
        }
        print("收到: " + msg)
    }

    t.join()
}

输出：

收到: 0
收到: 1
收到: 2
收到: 3
收到: 4
通道已关闭

生产者-消费者模式

import threads

func producer(var ch) {
    for 10 to var i {
        ch.send(i)
        print("生产: " + i)
    }
    ch.close()
}

func consumer(var ch) {
    while true {
        var msg = ch.receive()
        if msg == null {
            print("消费者结束")
            break
        }
        print("消费: " + msg)
    }
}

main() {
    var ch = threads.channel(5)
    var tp = threads.start(producer, ch)
    var tc = threads.start(consumer, ch)
    tp.join()
    tc.join()
}

双线程通讯

import threads

func sender(var ch) {
    for 3 to var i {
        ch.send("消息" + (i + 1))
    }
    ch.send("结束")
    ch.close()
}

func receiver(var ch) {
    while true {
        var msg = ch.receive()
        print("接收: " + msg)
        if msg == "结束" {
            break
        }
    }
}

main() {
    var ch = threads.channel(10)
    var ts = threads.start(sender, ch)
    var tr = threads.start(receiver, ch)
    ts.join()
    tr.join()
}

可传递的类型

Channel 支持的类型

类型 说明 传递方式
int 整数 直接复制
float 浮点数 直接复制
bool 布尔值 直接复制
string 字符串 深拷贝
null 空值 直接复制
Array 数组 深拷贝（递归复制每个元素）
Dict 字典 深拷贝（递归复制每个键值对）
Channel 通道 引用计数共享（可传递 channel 本身）

不支持传递的类型

类型 原因
Ptr 指针不能跨 VM 共享
File 文件句柄不能跨 VM
cstruct 实例 每个线程独立 malloc（定义可以共享，见下节）
闭包/函数 能 send 过去，但收到后 type() 是 func、不能调用 ⇒ 等于没用

★ 2026-11-09 更正：struct 实例 这一行原来写的是「需要序列化，暂不支持」， 那是 2026-10-12 之前的状态。现在 struct 实例（含 Array[struct]）可以过 Channel， 走深拷贝，收到后 type() 仍是原类型、字段可读。实测： 

// 子线程
P p = new P(n = "原", v = 1)
ch.send(p)
p.n = "子改过"          // 发送后再改原对象
// 主线程收到 n="原" ⇒ 是深拷贝，不受影响

⚠ 但闭包捕获仍然一律是副本：子线程里改 self.cnt / 局部变量， 父线程看不到改动（不报错）。要回传结果请用 Channel。

cstruct 在线程中的使用

cstruct 定义可以在线程中安全使用。子线程会继承主线程的 cstruct 定义，且由于 cstruct 定义是只读的类型元数据，多个线程可以安全共享：

import ffi
import threads

cstruct MEMORYSTATUS {
    u32 dwLength
    u32 dwMemoryLoad
    u64 dwTotalPhys
}

func get_memory_info(var ch) {
    // 在子线程中使用 cstruct
    var kernel32 = ffi.load("kernel32.dll")
    var mem = MEMORYSTATUS.malloc()

    mem.dwLength = MEMORYSTATUS.size()
    ffi.call(kernel32, "GlobalMemoryStatus", mem.to_ptr())

    ch.send(mem.dwTotalPhys)
    mem.free()
    ffi.free(kernel32)
}

main() {
    var ch = threads.channel(1)
    var t = threads.start(get_memory_info, ch)
    var total_mem = ch.receive()
    print("总物理内存: " + total_mem)
    t.join()
}

注意事项： - cstruct 定义（如 MEMORYSTATUS）在线程间共享，是安全的 - cstruct 实例（如 mem）是每个线程独立的，不能跨线程传递 - 每个线程需要独立进行 malloc() 和 free()

完整示例：并行排序

import threads
import times as ti
import rands

func bubble_sort(var arr) {
    var n = arr.len()
    for n - 1 to var i {
        for n - i - 1 to var j {
            if arr[j] > arr[j + 1] {
                var temp = arr[j]
                arr[j] = arr[j + 1]
                arr[j + 1] = temp
            }
        }
    }
    return arr
}

func sort_worker(var ch) {
    var arr = rands.int_array(1, 1000)
    var s = ti.ms()
    var result = bubble_sort(arr)
    var e = ti.ms()
    ch.send(e - s)
}

main() {
    var ch = threads.channel(4)

    // 启动 4 个排序线程
    for 4 to var i {
        threads.start(sort_worker, ch)
    }

    // 收集结果
    var total = 0
    for 4 to var i {
        var ms = ch.receive()
        print("线程" + (i + 1) + ": " + ms + "毫秒")
        total = total + ms
    }
    print("平均: " + (total / 4) + "毫秒")
}

注意事项

1. 闭包捕获变量（深拷贝）

threads.start() 支持闭包捕获外部变量，捕获的值会深拷贝到子线程，各线程拥有独立副本：

var x = 10
var t = threads.start(func() {
    print(x)    // ✅ 输出: 10（深拷贝）
})
t.join()

多个线程捕获同一变量时，各自拥有独立副本，互不影响：

var shared = 100
var t1 = threads.start(func(){ return shared })
var t2 = threads.start(func(){ return shared })
print(t1.join())  // 100
print(t2.join())  // 100

闭包捕获 + 参数传递：

var prefix = "hello"
var t = threads.start(func(int n){ return prefix + " " + n }, 42)
print(t.join())  // hello 42

2. 全局变量：每线程一份（对象也深拷贝，2026-10-20 起）

子线程启动时把全局变量表复制一份：

值 子线程拿到的是
标量（int / float / bool / null） 独立副本 ✓
string / Array / Dict / struct / 闭包 克隆进子线程堆（TH8，2026-10-20）✓ 改内容主线程看不见
module / 函数 / socket / 文件句柄 / Channel / Thread 共享（只读元数据或引用语义） 
var count = 0
var arr = [1, 2, 3]

func worker() {
    count = count + 1
    arr.add(4)
}

main() {
    count = 100
    arr = [1, 2, 3]
    var t = threads.start(worker)
    t.join()
    print(count)       // 100 —— 标量各一份
    print(arr.len())   // 3   —— 数组是副本（旧版这里会是 4 ✗）
}

结果要带回来请用 join() 的返回值或 Channel（别指望改全局对象）。

历史注记：2026-10-20 之前这里是"只抄指针、对象共享"——子线程写全局 Array/Dict 会走子线程的写屏障去改主线程堆，偶发 0xC0000374 堆损坏。已修（TH8）。

⚠ 模块级 var（ObjModule.globals）仍然是所有线程同一份、且无锁 —— 那是另一件事 （loaded_modules 是进程级缓存，见 TH5 的「明确不做」）。并发写模块级可变状态依旧不安全， 要么只读，要么走 Channel 单点化。

★ 2026-11-15 起：往模块级 var 里写"本线程堆上的对象"会打一条警告（只提示一次）： 

[警告] 子线程把**本线程堆上的对象**写进了模块级变量（模块 'm' 槽 1，线程序号 1 / 模块属于 0）——
       模块级 var 是所有线程**共享的同一份槽**，而对象属于写它的那个线程堆：
       该线程退出/GC 之后这个槽会指向已回收内存（读到 185 / -1 / 0 这类残值）。
       建议：① 每线程状态改用 threads.local_set/get；② 或由主线程构建后**只读**。

为什么这条非有不可：那种错不报错、也不崩，只是"跑一阵值就没了"。实测（Aria 服务端） CRC 表的 table_entry(1) 返回 185 / -1 / 0 —— 看起来像算法错，实际是跨堆对象被回收后的残值。 根治写法见下面的 thread_local var。

3. Channel 的缓冲大小

  • 有缓冲 threads.channel(N)：缓冲区满时 send() 阻塞，适合异步通讯
  • 无缓冲 threads.channel(0)：send() 阻塞直到有人 receive()，适合同步通讯

4. 线程安全

  • 每个线程拥有独立的 GC，无需担心 GC 冲突
  • Channel 内部使用互斥锁和条件变量，线程安全
  • send() 和 receive() 可以安全地在不同线程中并发调用
  • ✅ 入口脚本的全局对象是每线程一份（TH8，2026-10-20）⇒ 并发写它不会互相影响
  • ⚠ 但模块级 var（ObjModule.globals）仍是所有线程同一份、且无锁 ⇒ 并发写它就是数据竞争， 只读或改走 Channel 单点化（见第 2 条末尾）
  • ⚠ 目前没有 Mutex / 原子变量（threads 只提供 start/channel/sleep/join_all/parallel_for/map/local_*）， 共享可变状态的正确写法是 Channel 汇到单点线程，或 threads.local_* 每线程一份

5. 跨线程能传什么（传值即深拷贝）

值 能传吗 行为
int / float / bool / null / string ✅ 按值 / 复制
Array / Dict ✅ 深克隆（连字典的键一起）
struct 实例 ✅ 深克隆 + 接收侧按定义重建（2026-10-12 起；嵌套 struct / face 声明也一并带上）
闭包 / 函数 ✅ 2026-10-20 起：字节码共享、捕获值递归克隆 ⇒ 子线程调用时用的是副本（环形捕获超 64 层报错）
Channel ✅ 按引用共享（同一把句柄）
cstruct，或字段里装了 cstruct / Ptr 的 struct ❌ 报「不能跨线程传递此类型（来自 结构体.字段）」—— cstruct 是裸 C 内存，错的是给它克隆出假句柄
自引用（环形）struct ❌ 报「嵌套层数超过 64」而不是挂死

因为是深拷贝，子线程改了字段主线程看不见 —— 结果要靠 join() 的返回值或 Channel 带回来：

struct P { int x = 0 }
func work(P p): int {
    p.x = 100        // 改的是**副本**
    return p.x       // ✓ 结果从返回值走
}
main() {
    var p = new P()
    var t = threads.start(work, p)
    print(t.join())  // 100
    print(p.x)       // 0 —— 主线程的原件没被改到
}

详细约束（含 Ptr 字段、环形引用这些拒绝面）见 docs/module_threads_api.md 的 「跨线程传值的硬约束」，改动与判据见 docs/线程并发能力修复追踪.md 的 TH1。

6. ⚠ 同一条通道上"边收边发"会把自己发出去的消息收回来

通道语义是"谁先 receive 谁拿"，不区分发送者。所以"父线程发 N 条 → 子线程收 N 条 → 子线程再发回 N 条"这种在同一个通道上的写法，子线程会先收到自己刚发出去的那条：

// ✗ 同一条通道收发混用：子线程第 2 轮收到的是自己发回的 q，循环次数就对不上了
for 0 : 2 to var i {
    var v = ch.receive()
    if v is Point => q { ch.send(q) }
}

做法：收发各用一条通道（in_ch / out_ch），或让方向单一（只发或只收）。 ⚠ 附带一条容易踩的：for A : B 是闭区间（for 0 : 3 跑 0、1、2、3 共 4 轮） —— 循环次数与消息条数对不上时，receive() 会永久阻塞、join() 也就永远等下去 （表现是"程序卡死且无输出"）。

7. FFI 回调与原生线程的关系

Leno 提供两种并行机制，它们工作在不同层面：

机制 实现方式 线程安全 适用场景
threads.start() 独立 VM 实例，完全隔离 ✅ 安全 Leno 原生多线程计算
ffi.callback() 分两条路：Leno 线程上直接执行；无 VM 的外部线程编组到主线程执行 ✅ 见下 C 库回调 Leno

关键区别：

  • threads.start() 创建的线程拥有独立的 VM、GC 和内存空间，通过 Channel 通讯，互不干扰
  • ffi.callback() 注册的回调运行在外部线程（如 Windows 线程池、C 库工作线程）—— 这些线程没有 VM ⇒ 不能在它们上面直接跑 Leno 字节码 ✓

回调被并发触发时会怎样（★ 2026-10-12 订正：旧版说"会覆盖主 VM 栈"，已不成立）

src/module/ffi/ffi.c 的 callback_dispatch() 按调用方是谁分两条路：

  1. 调用方是 Leno 线程（threads.start() 起的子线程，或主线程）⇒ 直接在该线程自己的 VM 上执行 ✓ （每个 Leno 线程一套栈与 GC ⇒ 并发回调天然各跑各的，不共享栈 ✓）；
  2. 调用方是没有 VM 的外部 C 工作线程（SDL3 对话框线程、Windows 线程池…）⇒ 编组 （marshalling）：把参数快照塞进线程安全队列，阻塞该外部线程，由主线程 ffi.pump_callbacks() 取出、在同一个 VM 上逐个执行、完成后唤醒它 ✓ （ffi_call_impl 末尾会自动泵一次；事件循环里也会泵 ✓） ⇒ 多个外部线程并发回调会被串行化到主线程上执行 ✓，不存在"多线程同时写同一个 VM 栈" ✗ （旧版那段"全局变量竞态 / GC 冲突 / sp·frame_cnt 相互覆盖"描述的是编组机制落地之前的行为 ✓）

⚠ 因此现在仍然成立的三条约束（都实测过 ✓）：

  • 主线程不泵就死锁：外部线程回调期间主线程必须能走到泵点。所以 不要在主线程里"阻塞等待外部线程结束"（如 WaitForThreadpoolWorkCallbacks）—— 会死锁 ✓ （见 examples/ffi/test_callback_threadpool.leno 的说明 ✓）
  • 回调里的 Leno 代码仍要当"共享状态"看：编组解决的是"栈不共享"，不是"数据不共享" ✓ （模块级 var 依然所有线程同一份 ✓）
  • 不要在回调里起 Leno 线程/做重活：那是在主线程的泵里同步执行的，会把泵堵住 ✓

建议：

  • 需要 Leno 原生多线程并行 → 使用 threads.start() + Channel
  • 需要 C 库回调 Leno → 单线程回调最省心；多线程回调可用（会被串行化），但别在主线程里阻塞等待

8. print 是线程安全的

单次 print() 调用是原子的，不会与其他线程的输出交错。但多次 print() 调用之间可能被其他线程插入：

// 线程1
print("A")  // 原子，不会交错
print("B")  // 原子，但 B 可能在其他线程输出之后

// 线程2
print("C")

可能输出：A C B 或 A B C，但不会出现 AC 这样的交错。

9. 避免忙等待

使用 ch.receive()（阻塞）而非 ch.try_receive() + 循环轮询：

// ❌ 忙等待，浪费 CPU
while not ch.is_closed() or ch.len() > 0 {
    var val = ch.try_receive()
    ...
}

// ✅ 阻塞等待，不浪费 CPU
while true {
    var val = ch.receive()
    if val == null { break }
    ...
}

10. 线程生命周期

  • 线程函数返回后，线程自动结束
  • t.join() 会阻塞等待线程结束
  • 未 join() 的线程在主线程退出时可能被强制终止

11. 子线程异常与 join() 行为

子线程中的异常不会自动传播到主线程，但会在 join() 时体现：

  • 子线程正常运行：t.join() 返回线程函数的返回值
  • 子线程抛出异常：t.state() 返回 "error"，t.join() 会在主线程抛出异常，错误信息格式为 "Thread error: <子线程错误信息>"
  • 不想 join 又想看错误：t.error()（空串 = 没出错）。fire-and-forget 的线程出错时， 没人 join 就只剩这一个入口能看见（throw "x" 的原文能正确带出，TH11）
var t = threads.start(func(){
    throw "子线程出错"
})

try {
    t.join()  // 抛出: Thread error: 子线程出错
} catch e {
    print("捕获: " + e)  // 捕获: Thread error: 子线程出错
}

注意：state() 是快照，不是锁。 在 state() 和 join() 之间存在竞态窗口——线程状态可能在检查后立即改变。因此不建议依赖 state() 来决定是否 join()，更安全的做法是直接用 try-catch 包裹 join()：

// ❌ 依赖 state() 快照，存在竞态窗口
if t.state() == "done" {
    var result = t.join()  // state() 返回后线程可能已变为 "error"
}

// ✅ 直接 try-catch，无竞态问题
try {
    var result = t.join()
} catch e {
    print("线程出错: " + e)
}

11.5 线程池（任务 = 闭包）

完整可跑示例：examples/threads/pool.leno（4 worker / 20 任务，实测平方和 2470）。骨架：

func worker(Channel tasks, Channel results): int {
    var done = 0
    while true {
        var job = tasks.receive()
        if job == null { break }                    // 停机信号
        try {
            results.send({ok: true, value: _str((job as any)())})
        } catch e {
            results.send({ok: false, value: _str(e)})
        }
        done = done + 1
    }
    return done
}

三个要点： 1. 背压：tasks / results 都设容量，满了 send 阻塞（自然限流，不会无限堆任务） 2. 异常别静默：worker 里 try/catch 把错误当结果回传 —— 线程池最怕"任务没结果也没报错" 3. 循环变量先拷局部：for N to i { int x = i; tasks.send(func(){ return x*x }) } （直接捕获 i 会让所有闭包看到同一个槽）

12. threads 与 async 的交互规则

Leno 提供两种并发机制，不应混用：

机制 模型 调度方式 内存模型
threads.start() OS 线程 + 隔离 VM 抢占式，真正并行 独立内存，Channel 通信
async func + await 协程 + 事件循环 协作式，单线程内调度 共享内存，无数据竞争

交互规则：

  • 不要在子线程中使用 async/await：子线程有独立 VM 和事件循环，asyncs.run() 不会跨线程调度
  • 不要在 async 函数中调用 threads.start()：协程是协作式调度，启动 OS 线程会打破协程的执行假设
  • 需要 CPU 并行 → 用 threads.start() + Channel
  • 需要 I/O 并发 → 用 async func + await + asyncs.run()

关于 async 的完整边界定义（返回值类型、不 await 行为、异常传播、事件循环语义），参见 src/module/asyncs/asyncs.md。

// ❌ 错误：混用 threads 和 async
async func bad() {
    var t = threads.start(func(){ ... })  // 不要这样做
    await asyncs.sleep(100)
}

// ✅ 正确：选择一种模型
// 方案1：纯线程
func worker(var ch) { ... }
var t = threads.start(worker, ch)

// 方案2：纯协程
async func worker() { ... }
var f = worker()
asyncs.run()

13. type() 的语义约定

type() 返回的是运行时值的类型，而非变量的声明类型：

int? a = null
print(type(a))  // "null"（不是 "int?"）

var b = 42
print(type(b))  // "int"

b = "hello"
print(type(b))  // "string"（类型随值变化）

Leno 的变量是动态类型的，声明类型（如 int）只是编译期提示，type() 反映的是运行时实际值的类型。这意味着：

  • null 值的 type() 始终返回 "null"，无论变量声明为什么类型
  • BigInt 和普通 int 的 type() 都返回 "int"（对外统一）
  • 子线程中 type() 的行为与主线程一致

线程入口：模块函数也能用（★ 2026-10-12 起）

模块里的函数现在可以直接当线程入口 ✓ —— 库可以自己封装并发：

// 模块 side（lib/worker.leno）
import threads
export func do_work(int n): int { return n * 2 }
export func run_parallel(int a, int b): int {
    var t1 = threads.start(do_work, a)          // ✓ 模块开线程跑自己的函数
    var t2 = threads.start(do_work, b)
    return t1.join() + t2.join()
}

// 入口脚本
import "./lib/worker.leno" as w
var t = threads.start(w.do_work, 21)            // ✓ 直接拿模块函数当入口
print(t.join())                                 // 42
print(w.run_parallel(1, 2))                     // 6

以前为什么不行（历史记录，写在这儿免得再踩）：threads.start 会硬拦"入口必须是入口脚本 里的具名全局函数"✗，根因是协程首帧漏设 frame->module，而模块字节码（读写模块级 var、 取模块函数）全部经 frame->module 寻址 ⇒ 进函数体后第一条模块符号指令就报 「不在模块上下文中」（症状是 join() 只给 Thread error: unknown error，连函数体都进不去 ✗）。 补上那一行之后模块函数直接可用 ✓（改动与判据见 docs/线程并发能力修复追踪.md 的 TH2 ✓）。

⚠ 两个仍然成立的注意点：

  1. 模块级可变 var 是跨线程共享的（模块对象由进程级缓存共享，不按线程隔离 ⇒ 不这么做是有意的， 见 docs/线程并发能力修复追踪.md 的「明确不做」表）。并发写同一个模块级变量就是数据竞争 —— 库要么把状态收进实例（_ParseCtx 那种写法），要么用 Channel 同步。
  2. 入口函数的实参个数必须严格对上 ✓ —— 线程入口由 VM 直接调用，默认参数不会被补齐 ✗。 另：入口函数所属模块必须在入口脚本的 import 链上（否则模块的 var 还没初始化， 会明确报「所属的模块尚未初始化」✓）。

并行原语（★ 2026-10-12 起）

手写"起 N 个线程 + 收 N 条结果"的样板以前每个项目都要抄一遍 ⇒ 现在有三个现成的模块函数 （没有新增对象类型 / 关键字，就是普通函数 ✓ 见 docs/线程并发能力修复追踪.md 的 TH3）：

原语 作用 回调形态 返回
threads.join_all(Array[Thread]) 等一组线程结束（“WaitGroup”的等价物） — int（真正等完的个数）
threads.parallel_for(n, f) 分 n 份并行：f(index) 在 n 个线程上各跑一次，等全部结束 f(int index) int（真正起来的线程数）
threads.map(arr, f) 并行 map，结果按输入顺序收回 f(item, index) Array[回调返回类型] 
import threads

// 分 4 份并行；回调是闭包 ⇒ 可以用捕获的 channel 把结果带回来
var ch = threads.channel(8)
var started = threads.parallel_for(4, func(int i) {
    ch.send(i * 10)
})
var sum = 0
for 0 : 3 to var k { sum = sum + _int(ch.receive()) }
print(sum)          // 60（0+10+20+30）

// 并行 map：结果顺序与输入一致，静态类型直接是 Array[int]
var doubled = threads.map([1, 2, 3, 4], func(int x, int idx): int {
    return x * 10 + idx
})
print(doubled[3])   // 43（4*10+3）

// 手工起的线程可以一次等完
var ts = []
ts.add(threads.start(work, 1))
ts.add(threads.start(work, 2))
print(threads.join_all(ts))   // 2

⚠ 三条注意： 1. n 要自己控（parallel_for 不会自动按核数分）—— 说几份就几份。 2. map 的线程数 = 元素数（每个元素一个线程）⇒ 元素多时线程开销会盖过收益； 重活请用 parallel_for 自己分块 ✓ 3. 回调的形参个数是硬校验（线程入口由 VM 直接调用，默认参数不会被补齐 ✓）： parallel_for 要 f(int)，map 要 f(item, index)（与 arrays.map 同口径 ✓）。

通道元素类型（Channel[T]，★ 2026-10-12 起）

给通道写上元素类型，receive() 就直接是那个类型，不用再 _int(...) / is 收窄：

import threads

struct Pt { int x = 0; string tag = "" }

main() {
    Channel[int] ch = threads.channel(4)   // ← 工厂返回裸 Channel，靠标注拿到元素类型
    ch.send(7)
    int v = ch.receive()                   // ✓ 直接是 int

    Channel[Pt] pc = threads.channel(4)
    var p = new Pt()
    p.x = 9
    pc.send(p)
    Pt got = pc.receive()                  // ✓ 直接是 Pt（跨线程的 struct 是深拷贝）
    print(got.x + v)
}
写法 receive() 的静态类型
Channel[int] ch int ✓
Channel[Pt] ch Pt ✓（可再取字段）
var ch = threads.channel(1)（裸 Channel） any（回落，仍可用但需 _int(...) / 收窄）
ch.try_receive() 恒为 any ✓ 这是有意的：空通道它给 null，说它是 T 就是撒谎（要精确得先有"可空元素"的表示）

⚠ 两条口径： 1. 元素未知的一侧一律放行 —— 裸 Channel 能赋给 Channel[int]，Channel[int] 也能传给 形参写成 Channel 的函数（运行期本来就不携带元素类型 ⇒ 写窄了只会误报）； 2. threads.channel(n) 推不出 T（工厂没有元素信息）⇒ 想看精确类型就写标注。 顺带：Thread[T] 标注现在也能写了（Thread[int] t = threads.start(f, 1) ✓）。

线程局部存储（threads.local_*，★ 2026-10-12 起）

模块级可变 var 是所有线程同一份（故意不隔离 ⇒ 并发写就是数据竞争）。库想"每个线程一份 状态"时，用这三个函数 —— 它们按线程隔离，不需要锁：

函数 说明
threads.local_get(key, default) 本线程存过 key ⇒ 给它；没存过 ⇒ 给 default（不写）
threads.local_has(key) 本线程是否存过 key（⇒ "存过 null" 与 "没存过" 是两回事 ✓）
threads.local_set(key, value) 只写本线程那份 
import threads

func worker(int id): string {
    threads.local_set("hits", id * 100)                 // 每个线程各写各的
    var n = _int(threads.local_get("hits", -1))
    threads.local_set("hits", n + 1)
    return _str(_int(threads.local_get("hits", -1)))    // 101
}

main() {
    threads.local_set("hits", 7)
    print(threads.start(worker, 1).join())              // 101
    print(threads.start(worker, 2).join())              // 201
    print(_int(threads.local_get("hits", -1)))          // 7 —— 子线程动不到主线程那份
    print(threads.local_has("nope"))                    // false
}

⚠ 四条口径别混（各有不同语义）：

状态放在哪 主/子线程之间 并发写
模块级 var（lib/xxx.leno 顶层） 同一份（共享） 数据竞争 ✗ ⇒ 要么收进实例，要么用 threads.local_* / thread_local var
入口脚本顶层标量（var count = 0） 各一份（子线程里重新赋值主线程看不见） 安全 ✓（但要靠 join() 返回值汇总）
入口脚本顶层的对象（Array / Dict / struct） 槽各一份，但对象本身共享 改内容会互相看见 ✗
threads.local_* 每线程一份（子线程读不到主线程写的） 安全 ✓
thread_local var（模块顶层，2026-11-15 起） 每线程一份（编译期定位槽位、无字符串 key） 安全 ✓（推荐）

每线程状态：thread_local var（★ 2026-11-15 起）

模块顶层写 thread_local var 名字 = 初值 ⇒ 每个线程各一份。编译器给每个声明分配一个 进程内唯一的槽位号，值放在 VM.tls_slots（随 VM 走 ⇒ 天然每线程一份），GC 把它当根。

// lib/crc.leno
thread_local var counter = 0                 // 类型按初值推断
thread_local Array[int] table = []           // 显式类型也行（类型前置，与其它声明一致）
thread_local var cache = {}                  // 空字典

export func crc_init() {
    if table.len() == 0 {
        for 0 : 255 to n { table.add(n) }    // 每个线程建自己那份，互不影响
    }
}

export func hits(): int {
    counter += 1
    return counter
}

要点：

  • 初值只能是字面量或空容器（0 / "" / true / null / [] / {}）。 为什么：声明处的代码只在主线程执行一次，别的线程没机会跑它 ⇒ 它们按"声明的初值" 惰性新建一份（Array/Dict 每线程新建空容器，不会共享同一个对象）。 要在别的线程跑一段初始化代码，写成可空 + 首次访问赋值： leno thread_local var tbl = null func table(): Array[int] { if tbl == null { tbl = _build() } // 每个线程各建一次 return tbl }
  • 只能在模块顶层（脚本顶层本来就每线程一份；函数内的局部变量天然线程私有 ⇒ 都不需要它）。
  • 不能 export（每个线程各一份 ⇒ 别的模块读到哪个值取决于"哪个线程在读"）。 要跨模块用，导出访问函数。
  • 复合赋值 / 自增 / for 循环都照常（读走 OP_GET_MODULE_VAR、写走 OP_SET_MODULE_VAR， VM 按槽位表分流到本线程 —— 不需要额外写法）。

与 threads.local_* 的分工：新的库代码优先用 thread_local var（有类型、无字符串 key、 不会撞名）；threads.local_* 保留给"键是运行期才知道的"场景（如按配置名缓存）。
