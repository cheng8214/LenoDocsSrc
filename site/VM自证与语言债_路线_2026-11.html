VM 自证与语言债 · 下一阶段路线（2026-11）

这份文档是"待办清单 + 进度表"，不是论文。 规矩：做完一项就把表里那一行改成 ✅ 并写上实测数字，没做的保持 ⬜（不要提前打勾）。

一、为什么是这四件事

本轮（2026-11-25）修的那个 0xC0000005 说明了问题所在：单次 encodePNG 正常、纯 zlib 连压三次正常、缓存清干净仍然崩 —— 真正的根因是 VM 的原地帧没清非参槽位，GC 把悬空指针 当根扫进去，而崩溃现场报在 LenoCompress.deflate_level 的 OP_LOADK 上，指错了三个模块。 靠人工从"报错位置"反推到"真正根因"花了整整一轮。

结论：这个项目的瓶颈不是"再加功能"，而是"能跑对"还没变成"能被证明跑对"。 所以下面四项按"不做会持续流血"排序，而不是按"做起来爽"排序。

语言断言 668 passed / 0 failed
模块测试 65 passed / 0 failed（25 个模块）
文档站 137 篇 / 9 组

三、P0 详情（已完成）

做了什么

① --gc-stress[=N]（命令行）与 LENO_GC_STRESS=N（环境变量）

build\leno.exe --gc-stress=512 assert\run_tests.leno build\leno.exe assert      :: 旗标
set LENO_GC_STRESS=512 && build\leno.exe assert\test_x.leno                     :: 环境变量
  • 每 N 次分配强制挂一次回收请求（默认 64）—— 复用既有钩子 gc.force_every；
  • 环境变量那条是必须的：断言套件是逐个子进程跑的，子进程不继承命令行旗标；
  • 实现：gc_request_stress()（参数解析时登记，gc_init 应用）+ gc_set_stress()。

② 两处校验（每次回收自动跑，默认零开销）

校验 时机 抓什么
悬空根校验 标记之前 帧寄存器里的对象指针必须真的在 young/old 堆链上。不在 ⇒ 就是"槽位没清、残留上一轮已回收对象"
标记完整性校验 标记之后、sweep 之前 活对象（marked）的每个子引用，该被标记的（年轻代 / FULL 模式全部）必须也 marked。否则它马上会被 sweep 掉，而持有者还留着指针

命中就 abort() 并打印持有者/子对象的类型、代数、marked 位（型号名而不是数字）。

它抓到了什么（实证）

把"原地帧清非参槽位"那行临时回退（模拟旧代码）后，同一条命令给出的就是根因：

[GC-VERIFY] 悬空根：帧 6 的寄存器 10 指向**不在堆上**的对象 0x…（type=Array owner_thread=0 本VM serial=0）
            （典型原因：这段寄存器槽没被初始化/清理，残留着上一轮已回收对象的指针）
            该帧 func=zlib local_count=11

而修复版同一条命令全绿。这就是本节的价值：同样的 bug，人工定位花了一轮，工具 1 行。

已知边界（写清楚，别当它万能）

场景 处理 原因
子线程 VM（vm.thread_serial != 0） 照常校验（P0.1 已放开） 跨堆指针靠"owner_thread 是否等于本 VM 的 serial"逐值判掉，不需要全局堆注册表，也就不会去走别人正在改的堆链
Channel / Thread / ffi 库对象 白名单跳过 Channel 是 malloc 的、不进堆链表；Thread 由线程系统跨 VM 交接；ffi 库对象有意永不回收
owner_thread 与当前 VM 不同的对象 跳过 跨堆引用合法（Channel 载荷、threads.start 返回值）
test_async_io_limit / test_async_sockets 压力下超时（120 s 上限） I/O 计时用例，回收频率放大后跑不完 ⇒ 不是 GC 缺陷

P0.1 的真实收获：先修的是工具自己的 bug。 放开子线程后 test_threads_native_state 间歇报"悬空根"，而报告里 young=… 与那个对象地址完全相同 —— 说明对象明明在堆上。 根因是三份"本线程状态"用了普通 static（开关 gc_verify_graph_on 除外）： 两个子线程同时 GC 时，A 刚建好索引、B 就把 cnt 清 0 重建 ⇒ A 在自己的堆里"查不到"对象。 改成 THREAD_LOCAL 后 4/4 稳定通过。 教训与 P0 本身一致：校验器自己也要能被信任 —— 假阳性的工具会让人把它关掉。

四、后面三项的第一步（还没做）

P0.1 子线程 VM 的完整性校验 —— ✅ 已完成（2026-11-25）

原计划是"建一张 thread_serial → {young_heap, old_heap} 的全局注册表"。实际不需要： Object.owner_thread 在分配时就记下了"这个对象属于哪个 VM 的堆"，所以只要 逐值比较 owner_thread 与本 VM 的 thread_serial 就能把"跨堆引用（合法）"和 "悬空指针（缺陷）"分开，而且完全不用去遍历别的线程正在改动的堆链（那才是数据竞争）。

真正要修的是校验器自己的三个 static：它们记的是"本线程正在做什么" （索引指针/计数/容量、pass_active、"当前持有者"），必须 THREAD_LOCAL。 两个子线程同时 GC 时，A 刚建好索引、B 就把 cnt 清 0 重建 ⇒ A 在自己的堆里"查不到"对象， 报出假的悬空根（报告里 young= 与那个对象地址一模一样，正是破案线索）。 gc_verify_graph_on 则不能 TLS —— 新线程的 TLS 会初始化成 0，那样子线程根本不开校验。

验证：test_threads_native_state / test_reflect_stress / test_thread_heap_reclaim 在 LENO_GC_STRESS=512 下各连跑 4 次，12/12 全过；全量压力套件仍是 666/2（只剩两条 async IO 超时，与 P0 时一致）。

P1 迭代协议 —— 库级 ✅（2026-11-25）+ 编译器接入 ⬜（P1.1）

现状：for c to v 是语义期改写成 c.to_array()（见 semantic_rewrite_for_iterable）⇒ 每轮遍历分配一个快照数组。

已完成（库级协议）：Iter[T] / DequeIter[T] 游标 + Stack/Queue/Deque/PriorityQueue.iter()、 LRU.keys_iter()。用法 while it.has_next() { if it.next() is int => v { … } }，零数组复制。

实测（N=1,000,000，本机）：

写法 时间 每轮分配
for st to v（快照） 55 ns/op 8 MB
iter() 游标 100–106 ns/op ~0（实测 808 B / 20 万项）
for st.items to v（Stack 专用，走公开字段） ~51 ns/op ~0

这张表是 P1.1 的前置情报：快照是"一次复制 + 数组顺序扫"，复制成本被整轮摊薄 ⇒ 单趟遍历它反而更快。所以"把 for 改成走协议"不是白捡的： 必须先让 codegen 把 len()/at(i) 内联成数组下标（否则每元素两次方法调用 ≈ +50 ns）， 否则只是把 8 MB 垃圾换成 2× 时间。P1.1 的判据因此写成"分配为 0 且不慢于 55 ns/op"。

第一条候选实现（不新增字节码）：语义期把 for c to v 降级成 for 0 : c.len()-1 to i { v = c.at(i); <body> }，前提是 len/at 能被窥孔优化成 OP_LEN + OP_INDEX_ARRAY_*（同类优化已有先例：for 计数器原始减一、比较+跳转融合）。

语义差异要先拍板：快照版在循环体里改容器不影响本轮；协议版是实时视图。 容器 README 已经把两者都写清（"想两者兼得：热路径用 iter()，循环体别改容器"）。

P3 PGO（约 1 天出结论）

待办与路线图.md 的 T18 已实测：fib(30) 从 41.9ms 退到 54~60ms 是 vm_run 机器码布局问题， PGO 能找回约 85%（54.0 → 44.7），但训练集不当会让 400k 排序 +7%。 第一步：用现有基准（fib / 排序 / pbkdf2 / SDL3 三个 bench）做训练集，测"找回多少、伤不伤排序"。
