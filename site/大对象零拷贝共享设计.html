大对象零拷贝跨线程共享（frozen + 引用计数）设计稿

状态：已实现（S0–S4 全部落地，2026-11-27） —— 落地记录、踩坑与偏差见 §14。 第二稿：按"能编译期拦就不留运行期"改成 Frozen[T] 静态类型。 前置：并发这一轮已收尾 —— shared-nothing 深克隆 + 拒绝面、Atomic、Channel、池的起跑屏障与收尾 pool_shutdown()。 本文只解决一个遗留项：数据跨线程每次都深拷贝。不碰共享可写堆、不加锁、不改线程模型。

0. 一句话

_freeze(x) 把对象图一次性深拷贝到堆外共享区、打上 FROZEN 位、静态类型变成 Frozen[T]； 此后跨线程传递只做引用计数加减（O(1)），不再拷贝。 写 frozen 在编译期就报错（本作用域、传成参数、方法调用全覆盖），运行期 FROZEN 位只做 any 路径的兜底。

关键实现取舍：Frozen[T] 不是新的 TypeKind，而是 TypeInfo 上的一个 frozen 位。 这样 Array[int] 的所有读特化（OP_INDEX_ARRAY_INT/_IMM、OP_ITER_GET、方法 IC）一行都不用改、一点都不会变慢；

1. 现状成本（为什么值得做）

传输物 现状 出处
128 KB string 过 Channel 514 µs/条，有效带宽 243 MB/s（同数据 ffi.memcpy 22 GB/s） 线程并发能力修复追踪.md:156-165
Array[int] 克隆 67 ns/元素（10 万元素 7 ms；元素拷贝本身 ~2 ns） src/object/object_thread.c:367-369
threads.map 1 万元素 17~27 ms（大头是线程启动，不是拷贝） 语言摩擦与隐式契约清单.md:783
Channel 一次传输 两次深拷贝：send 克隆进发送堆、receive 再克隆进接收堆（模型使然，见 :77） 同上

数据越大越亏，而且是每一次跨界都亏。frozen 把「每次 O(n)」变成「一次 O(n) + 每次 O(1)」。

3. 语义

3.1 三个内建（照 _gc / _mem 的命名口径，sys.c:1729-1733）

var big = []
for 0 : 999999 to i { big.add(i) }

Frozen[Array[int]] snap = _freeze(big)   // 一次性 O(n)：深拷贝到共享区 + FROZEN 位
ch.send(snap)                            // O(1)：引用计数 +1
var v = snap[123]                        // 读：仍是 OP_INDEX_ARRAY_INT 特化（静态 kind 仍是 ARRAY）
for x in snap { ... }                    // 读：OP_LEN + OP_ITER_GET，一字不改
var copy = _thaw(snap)                   // 深拷贝回本线程堆，类型回到 Array[int]（可写）
_is_frozen(snap)                         // true（给 any/动态场景用）
  • 静态类型是 Frozen[T]：_freeze(Array[int]) → Frozen[Array[int]]，_thaw(Frozen[Array[int]]) → Array[int]。
  • 快照语义：冻结返回新图，原对象一个字不动、照常可写（§3.4）。
  • 深：整图（数组元素、字典键与值、struct 字段）一起冻。
  • 幂等：_freeze(已冻结) 直接返回同一对象（引用 +1），不重复拷贝。

3.2 谁能冻 / 谁不能 —— 默认在编译期拒

类别 结论
✅ 标量 / string / Array / Dict / struct（任意嵌套） 允许
❌ Ptr / Ptr[T] / cstruct / FFI 回调 / File / Socket 编译期报错（静态类型可判），点名类型
❌ Channel / Channel[T] / Atomic / Thread 编译期报错 —— 本来就是"共享可变"，与不可变语义冲突
❌ func / 闭包 / 模块 编译期报错（S4 前；S4 只放开"堆归属"问题，不放开闭包）
⚠ 实参静态类型是 any 编译期判不了 ⇒ 运行期检查并报错（唯一保留的运行期口子）

理由：这些判断只看静态类型，没有一项依赖数据——没有任何理由拖到运行期。

3.3 环

_freeze 检测到环 ⇒ 运行期抛错："冻结对象不能包含环（引用计数无法回收环）"。 这条必须留在运行期：环是数据形状，不是类型。检测复用构建时那张 ptr → 已访问 表，不额外扫。

3.4 为什么不做"原地冻结"

原地冻结省一次拷贝，但别名不可控：var a = big; var f = _freeze(big) 之后 a.add(x) 会撞上"只读错误"， 报错点离肇事点十万八千里。快照语义把不可变性收敛到"冻的那一刻"。这条不讨论。

3.5 Frozen[T] 怎么落地：TypeInfo 上一个位，不是新 kind

struct TypeInfo {
    TypeKind kind;        // ← 仍是 TYPE_ARRAY / TYPE_DICT / TYPE_STRUCT / TYPE_STRING / 标量
    int frozen;           // ★ 新增：这一位就代表 Frozen[...]
    ...
};

为什么不是新 TypeKind（这是本稿唯一的大决定，有实测判据）：

  1. 读特化的判据是静态 kind：codegen_expr.c:782-783 的 arr_spec、codegen_stmt.c:1790-1791 的写特化。 一旦静态类型成了新 kind，ot->kind != TYPE_ARRAY ⇒ 大数组下标读全部回落通用 OP_INDEX （07_collections.inc:193：val_is_obj + obj->type 分支 + val_is_num + value_to_double）， 恰好把我们想优化的大对象读变慢。用 frozen 位 ⇒ codegen 零改动。
  2. for / print / _str / jsons.encode / type(x) / 方法查找全都按 kind 或运行期对象标签分派 （codegen_stmt.c:938-968、io.c:375、types.c:829、jsons.c:1526-1592、vm_ic.inc:20） ⇒ 只要 kind 不变，这些地方一行都不用改。
  3. is / as 的规格编码只认 kind（vm.c:408-411 对未知 kind fail-closed）。 用新 kind 会让 x is Frozen[...] 静默恒假；用 frozen 位则问题变成"显式禁止"（见下）。

代价（必须付的）： - type.c 四处（type_copy / type_equal / type_to_string / type_free）各加 1~3 行，渲染成 Frozen[Array[int]]； - type_is_compatible：frozen → 可变 不兼容、可变 → frozen 也不兼容（必须显式 _freeze， 否则"静态说是不可变、运行期其实可变"——静态保证立刻变假）； - .lenosymc：TypeInfo 序列化加 1 字节，LENOSYMC_VERSION 0x2D → 0x2E（v46）（写 sym_table_cache.inc:108-160、读 :183-230 严格镜像）； - parser 认 Frozen[ 前缀（照 Channel[ / Ptr[ 的写法，parser_func.c:129-198）； - is / as 的目标类型为 Frozen[...] ⇒ 编译期报错："frozen 是静态类型、运行期只有对象标签； 要判冻结请用 _is_frozen()"。这条是"宁报错不静默恒假"。

3.6 拦截分层（回答"哪些能编译期拦"）

场景 拦截点 层级
snap[0] = 1 / snap.add(x) / snap.f = 1 / snap += x 根符号类型带 frozen ⇒ 复用 const 那 4 条通道 编译期
func f(Frozen[Array[int]] a) 体内写 a[0]=1 形参类型带 frozen ⇒ 同上 编译期
把 frozen 传给 Array[int] 形参 / 赋给 Array[int] 变量 type_is_compatible 拒绝 编译期
snap.someMutMethod()（struct 的 mut func） 复用 mut_names（semantic_type_utils.c:2130-2147） 编译期
_freeze(ptr) / _freeze(ch) / _freeze(atomic) / _freeze(闭包) 静态 kind 判定 编译期
x is Frozen[T] / x as Frozen[T] 显式禁令 编译期
any 里装着 frozen → 写 FROZEN 位 + 现有 6 个 readonly 检查点 运行期（兜底）
冻结含环 / 跨线程 def 归属 / _freeze(any) 数据相关 运行期

设计原则：编译期能判的全在编译期；运行期只剩"类型系统看不见"的那一类。绝不"编译期放过、运行期也不管"。

4. 对象模型（frozen 图的内存形态）

4.1 头部：白嫖 4 字节，sizeof(Object) 保持 32

typedef struct Object {
    ObjType type;            // @0
    int32_t refcnt;          // @4  ★ 新增：只用对齐空洞，对象不长大
    struct Object* next;     // @8
    int marked;              // @16
    uint8_t flags;           // @20  0x01 改名为 OBJ_FLAG_FROZEN
    ...
} Object;
  • sizeof(Object) 仍是 32（4+4+8+4+4+8）。仓里现在没有任何 sizeof(Object) 断言 ⇒ S0 补一条 offsetof typedef 断言。
  • 0x01 现在叫 OBJ_FLAG_INTERNED，leno_value.h:60 定义、全仓 0 处使用 ⇒ 改名 OBJ_FLAG_FROZEN。
  • owner_thread 对 frozen 无意义，固定填 0xFF（0 = 主线程）。

4.2 分配：绕开 gc_alloc，不进任何堆链

static Object* frozen_alloc(size_t size, ObjType type);  // calloc + 填头，不挂 young/old_heap、不池化
  • 不能走 gc_alloc()：会把对象挂进当前线程的堆，随线程退出被 free。
  • 不能池化：gc_free_object() 的池化路径会 memset 32 B 再挂回 free_list（gc.c:462-478），与 refcount 冲突。
  • 不进 gc_track_memory()：否则大 frozen 顶高 GC 阈值却永远回收不掉。

4.3 释放：归零 → 显式栈迭代释放整图

void frozen_unref(Value v);   // 原子减一；归零 ⇒ frozen_free_graph()，显式栈（照 gc_drain_mark_stack）
  • 必须迭代：100 万层的链递归会爆栈。
  • 图内边也计数：父持有子 1 份（构建时 refcnt++），父释放时释放子 ⇒ 整图生命周期自然成立。

4.4 记账

全局原子 g_frozen_bytes / g_frozen_objs；_mem() / _gc_stats() 各加 2 个字段； 不并入 gc.young_allocated / old_allocated（否则 GC 被触发但永远收不回 ⇒ 抖动）。

5. 引用计数挂在哪

5.1 位置

不在任何线程堆上。 frozen 图是独立所有权区域（malloc 出来的对象图），跨堆引用靠：

  1. 图内：refcnt（父→子边 + 外部引用）；
  2. 图外：每个 VM 一张 frozen 注册表（VM.frozen_reg），记录"本 VM 持有过哪些 frozen 对象"。

5.2 为什么不在每次赋值上计数

逐变量计数要覆盖：局部变量、栈、寄存器、容器元素、struct 字段、闭包 upvalue、帧槽复用…… 容器元素级增减会把 O(1) 的 add 变成"可能触发释放"的路径，还要配写屏障 —— 成本比深拷贝还高。

所以采用"VM 级持有"：frozen 对象进入某 VM 视野时登记一次（按指针去重），VM 活多久持多久； 任何局部变量/容器里的同一个指针都天然被保活。 代价：对象会比"实际最后引用"多活一段时间（池任务用 §5.5 的 scope 修补）。

由此得到一条硬规矩（写进 value_clone_for_channel 注释与文档）：

任何 frozen 指针必须先登记进当前 VM 的注册表，才允许被持有。

5.3 注册表结构

开放寻址 ptr → count，容量 2 的幂、装载因子 0.5；按 VM 一份（VM.frozen_reg），不参与 GC 扫描。

5.4 什么时候 acquire / release

事件 动作 持有者
_freeze 在本线程创建 当前 VM acquire 当前 VM
Channel send 槽位 acquire（buffer_owner 旁记 frozen，槽位出清时 release） 槽位（跨线程安全）
Channel receive 接收 VM acquire（去重）→ 再放掉槽位那份 接收 VM
threads.start 参数 / 池任务参数 子线程 VM acquire；池任务走 scope 子线程 VM
join 取结果 父 VM acquire 父 VM
入口 globals 快照（TH8） 子线程 VM acquire 子线程 VM
模块 globals（每线程克隆） 同 globals 各 VM
线程退出 / gc_free_all 注册表全量 release —

所有 acquire 都发生在已有克隆点（§6 闸门里那一行），不新增调用路径。

5.5 池任务必须有 scope

worker VM 长期存活 ⇒ 只按 VM 记账的话，注册表会涨成"所有历史任务的并集"。任务边界加一对：

int  frozen_scope_mark(VM* vm);
void frozen_scope_release(VM* vm, int mark);   // 只放本任务新增的条目

thread_exec_task() 前后各一次。文档写清："池任务别把 frozen 存进 worker 的长期状态"。

5.6 ObjStructDef / ObjFunction 的堆归属（最容易出血的地方）

frozen struct 里存 ObjStructDef*，冻结闭包里存 ObjFunction* —— 这两类对象分配在创建它的线程的 GC 堆上 （object_struct.c:100、codegen_func.c:106），靠 struct_def_table（THREAD_LOCAL）标记存活。 那个线程退出、堆被摘除释放后，frozen 图里的指针就悬空。

对策分两步： - S1~S3：_freeze 只接受可解析的 def（主导入模块的定义），其它情况明确报错 "该 struct 的定义所属线程可能已退出，暂不支持冻结" —— 先保证不悬空。 - S4：frozen 图对它指向的堆外对象（def / function）所属堆取一个 gc_dead_heap_ref()（机制已存在 gc.c:586-595）， 图释放时 unref。验收：子线程 _freeze(new S(...)) → 子线程退出 → 主线程读字段仍是原值。

6. 与 value_clone_for_channel() 唯一闸门的衔接

闸门只加一个前置分支（channel_clone_value() 最前面，object_thread.c:334）：

static Value channel_clone_value(Value val, int depth) {
    if (val_is_obj(val) && (((Object*)val_as_obj(val))->flags & OBJ_FLAG_FROZEN)) {
        frozen_acquire(gc.vm, val);      // O(1)：哈希查找 + 计数
        return val;                       // ★ 不拷贝、不进深度递归
    }
    ... 原有的白名单分支一个字都不改 ...
}

六个调用点（send/receive/try_send/try_receive/send_for + 线程侧三处）零改动。

6.1 组合规则（一条规则覆盖两种用法）

递归克隆时，遇到 frozen 节点就停（acquire 后原样返回），遇到可变节点照旧深拷贝。

于是：整个大数组冻结后 send ⇒ 全零拷贝；只冻结其中某个大子数组 ⇒ 外层克隆、子数组零拷贝（部分冻结自动成立）。

6.2 拒绝面

Ptr / cstruct / FFI / File 仍由闸门拒绝（object_thread.c:243-268）； 但 _freeze 在编译期先拒一遍（§3.2），闸门文案只补一句"frozen 对象按共享传递"。

7. GC 要改的地方（5 处，全部是"看到 frozen 就停"）

位置 改法 理由
gc_mark_object() gc.c:1554 最前面 if (flags & FROZEN) return; frozen 不归任何堆管，不能进标记栈
gc_scan_children() gc.c:920 同样早退 图内子引用由 refcount 负责
gc_free_object() gc.c:462-478 断言 !FROZEN 防止被当普通对象 free 进池
sweep 不用改 frozen 从不进 young_heap/old_heap 链，扫不到
gc_free_all() gc.c:2875 堆释放之后 frozen_reg_release_all()；顺序在 pool_shutdown()+join 之后（现状已保证） 唯一"主动放光"的地方

附带三件小事： - intern：frozen string 不进每线程 intern 表（string_table.c:11-12）；intern_remove 不得对 frozen 调用（gc.c:2094）。 - 写屏障：frozen 不可写 ⇒ 永不进 remembered set（§8 在写指令处先抛错，屏障不用改）。 - 子线程退出：走 gc_detach_heap（不自调 gc_free_all）⇒ thread_entry_point 收尾（object_thread.c:1011-1037） 加一次 frozen_reg_release_all(&child_vm)，放在 gc_detach_heap_finish 之前。

8. 不可变执法：编译期为主，运行期只兜底

8.1 编译期（主）

现有 const 的 4 条通道直接复用，只把判据从"根是 const"扩成"根是 const 或根的静态类型带 frozen"：

通道 现状位置

mutator 方法调用 A.add(x) visit_expr.inc:722-734、:752-767、visit_module.inc:1582-1587（名表 semantic_type_utils.c:968-976、:1131-1135）

风险 对策

12. 明确不做

不做 为什么
共享可写堆 / 锁 / GIL 模型的价值就是隔离；要共享可变走 Atomic / Channel
引用计数下沉到普通对象 那才是"重做 GC 所有权"（每次赋值计数 + 写屏障）；本方案收益正来自"只在跨界计数"
新 TypeKind 表示 Frozen 会掉读特化（§3.5 第 1 条），且 for/print/jsons 全部要改
Channel 移动语义（move） 语义分叉（buffered 时发送方可能活得比接收方久），收益与 frozen 重叠
自动冻结（send 时按大小自动 freeze） 隐式 O(n) 开销，用户看不见；显式 _freeze 才算得清
环回收（trial deletion） S5 之后的事；拒绝环已覆盖"只读大表"场景

13. 已按"编译期优先"定的路线（不再需要拍板，除非你否掉）

原问题 决定 一句话理由
语法形式 Frozen[T] 泛型写法 + _freeze/_thaw/_is_frozen 内建 Ptr[T]/Channel[T] 已是这个写法，用户零学习成本；Frozen 一旦进函数签名，编译期闭环
写的拦截时机 编译期为主（4 条 const 通道 + 兼容规则），运行期 FROZEN 位只兜 any 你要求"能编译期拦就别留运行期"；且 const 那套机制已存在，扩判据即可
环 运行期拒绝 环是数据形状，类型系统看不见
冻结语义 快照（_freeze 一次 O(n)） 原地冻结会让别名被误冻，语义不可控
记账 frozen_bytes 只统计、不计入 GC 阈值 计入会让 GC 空转
Frozen 的实现形态 TypeInfo.frozen 一位，不新增 TypeKind 新增 kind 会掉 OP_INDEX_ARRAY_INT 等读特化（实测判据 codegen_expr.c:782），恰好拖慢大对象读

如果你否掉"TypeInfo 位、不加 kind"，唯一替代是新 TypeKind，代价：所有读特化要加 unwrap、is/as 要新增编码、 序列化同样 bump，估计多 300~500 行且多一次性能回归风险。我的建议是维持现方案。

你说"按路线走"，我就从 S0 开始：只加 4 字节 + 一条断言 + 基准脚本，跑 677/677 与 fib(30)/pbkdf2 确认 ≤1% 波动，再进 S1a。

14.2 踩到的两个真坑（都不在算法上，在"谁先死"上）

  1. 注册表登记进了错误的 VM（症状：整套用例卡死十几分钟） thread_vm_init 结束时会把 current_exec_vm 还原成父线程的 VM（object_thread.c:1007）， 于是子线程收到 frozen 时登记进了主线程的注册表 ⇒ 两条线程并发改同一张开放寻址表， frozen_cnt 超过 cap 后每次插入都再扩容，表现为永远跑不完。 修：一律用 gc.vm（THREAD_LOCAL，gc_init 时就指向本线程 VM）。

  2. 退出阶段解引用已释放的堆对象（症状：test_channel_struct 30 次崩 3 次） 最初 channel_free_all() 用 obj_is_frozen(buffer[i]) 找要 unpin 的槽位 —— 但进程收尾时 gc_free_all() 可能先把堆释放掉，那些 Value 已经悬空 ⇒ 0xC0000005。 修：Channel 里加一条与 buffer 平行的 Object** frozen_slots，put 时记指针、take/收尾时按指针 unref， 绝不在收尾路径解引用 buffer 里的 Value。二分定位过程：禁用闸门 ⇒ 仍崩；禁用 slot 读写 ⇒ 不崩。

14.3 与设计稿的偏差（有意为之，都有注释）

设计稿 实际 为什么
池任务用 frozen_scope_mark/release 逐任务放 暂未做（按 VM 持有到 worker 退出） 逐任务 release 与"任务把 frozen 发到未消费的 channel"冲突；Channel 槽位 pin 只保护顶层 frozen 值，半冻结值仍靠注册表 ⇒ 先保证不悬空。代价：长期存活的 worker 会多持一些冻结图（同一张图重复传不会叠加，按指针去重）
半冻结（可变容器夹 frozen 子对象）完全自动 支持读/传递；子对象存活依赖发送方注册表 逐元素 pin 要两次 O(n) 扫描 + 记账；已列为后续可做项
槽位只按"顶层是否 frozen"pin 同左（frozen_slots） 顶层就是冻结图时 O(1)，覆盖推荐用法
