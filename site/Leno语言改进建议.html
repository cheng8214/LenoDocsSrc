Leno 语言特性评估总结

结论：Leno 语法和特性已足够且稳定。 以下是对各项建议的评估结果，大部分已实现或经评估后决定不实现。语言层面不再追加新特性，重心放在库生态和稳定性上。

已实现的特性

1. struct 可空类型 Type? ✅

Type? 可空类型已完整实现，支持 int?、string?、Point? 等所有类型。可空 struct 字段初始为 null，无需 bool 伴生字段。

Font? _font                    // 可空 Font，初始为 null

func _ensure_font() {
    if _font == null or not _font.ok {
        if _font != null { fnt.releaseFont(_font) }
        _font = fnt.acquireFontAuto(_fontSize)
    }
}

2. struct 构造函数 / 析构函数 / 命名参数初始化 ✅

已完整支持：

struct cs {
    int x
    int y

    func cs() {       // 构造函数，new 时自动调用
        // 初始化逻辑
    }

    func ~cs() {       // 析构函数，GC 回收时自动调用
        // 清理逻辑
    }
}

// 命名参数初始化
var c = new cs(x = 1, y = 2)

// 也支持默认值 + 部分参数
struct Point {
    int x = 0
    int y = 0
}
var p = new Point(x = 10)  // y 自动为 0

3. 字符串插值 $"..." ✅

var name = "Leno"
print($"Hello {name}!")   // 自动转换，无需 _str()

4. switch case is 类型匹配与收窄 ✅

switch w {
    case is Panel { w._bind_window(handle) }
    case is Edit  { w.set_window(handle) }
}

5. 泛型约束 func f[T: Face](...) ✅

6. try-catch-finally 异常安全 ✅

7. GC 兜底机制 ✅

FFI 资源（ffi.malloc/ffi.load/ffi.callback）由 GC 自动追踪，忘记 ffi.free() 时 GC 自动回收不会泄漏。

8. format 全局函数 ✅

format("%.2f", 3.14159)      // "3.14"
format("%05d", 42)           // "00042"
format("%s: %d", "Leno", 5)  // "Leno: 5"

9. ?. 安全访问 / ?? 空值合并 ✅

root?.set_size(w, h)
var font = _font ?? defaultFont

10. for-in 遍历 / 泛型数组字典 / 数组切片 / 原始字符串 ✅

经评估后不实现的特性

defer 延迟执行 — 已回退

defer 引入的 try-finally 包裹与内联优化的 OP_CLEAR_LOCAL_RANGE 有架构级冲突。去掉后零影响——FFI 手动内存管理 + GC 兜底 + try-catch-finally 功能等价。defer 引入太多不确定性和漏洞，得不偿失。

替代方案：try-catch-finally + GC 兜底。

运算符重载 — 暂不实现

现有功能已足够： - struct 方法：a.add(b) - 普通函数：vec_add(a, b) - 直接字段运算：a.x + b.x（UI 库实际写法，最常见，性能最优）

实现代价过高（parser/codegen/vm/semantic 四层 ~500-800 行改动），且破坏 OP_ADD_INT/OP_ADD_FLOAT 类型特化快速路径。收益有限——UI 库中不存在 Vec2 + Vec2 整体运算场景。

match 表达式 — 不需要

switch case is 已具备类型匹配和收窄能力，功能等价。不需要额外引入 match 语法。

访问控制关键字 — 暂不实现

当前用下划线前缀约定"私有"（如 _font、_bind_window），实际使用中已足够。编译器强制的 private/public 引入语义复杂度，收益不大。

数组解构 — 暂不实现

// 当前写法已经足够
var arr = parseColor(...)
r = arr[0]; g = arr[1]; b = arr[2]

收益太小，不值得增加语法复杂度。

case is 逗号合并 — ✅ 已实现

switch case is 支持逗号合并多个类型共享同一个 body：

switch w {
    case is Panel, ScrollView, HBox, VBox, AnchorBox, TabControl, SpinBox {
        w._bind_window(hwnd)
    }
    case is Edit { w.set_window(hwnd) }
}

Dict 解构初始化 — 暂不实现

当前 opts.get("key", default) 模式虽然重复，但清晰直观，且已在整个 UI 库中稳定使用。

待斟酌（有争议，暂缓决定）

① 漏写 return 是否升级为编译错误

现状：声明返回 int 的函数漏写 return 只给警告，运行时静默返回 null、exit=0。

该管的理由：null 静默流向调用点 —— 报错要到"参与运算/调用方法"时才出现， 而且指向的是症状（null 不能参与运算），不是病因（这个函数漏了 return）。

不能直接升级的三个顾虑：

顾虑 说明
存量代码 全仓有多少函数靠"隐式返回 null"在跑，没统计过；一升就一片红
返回 any / 无标注 它们本来就该返回 null，不能算错
有些"漏写"是故意的 比如某些提前退出的辅助函数，返回值根本没人用

建议分三步，不要一步到位：

步 做法 风险
1 纯统计：扫全仓"声明了具体返回类型 + 函数体末尾可达"的函数，出清单 零（不改编译器）
2 调用点运行时警告：拿到 null 而声明类型非 T? 时报一条（带函数名） 低（只警告）
3 观察一段时间后，只对"显式声明具体返回类型 + 非 any + 非可空" 升级为 error 中

还没定的关键点：int 和 Dict 要不要区别对待。 int 漏写几乎必然出错；Dict/Array 漏写却可能是"空结果"的合法表达。 真要升级，很可能得按返回类型分类，而不是一刀切。

结论：暂不动。等第 1 步的统计结果出来，再决定要不要走第 2、3 步。

② >>> 对负数按 48 位语义（已决定：不改，2026-10-24）

现状（同一运算符两种口径）：

-16 >>> 2   = 70368744177660          // 2^46-4，按 48 位
-1  >>> 1   = 140737488355327         // 2^47-1，按 48 位
m   >>> 1   = 4611686018427387903     // 正数大值，按 64 位

为什么这不是 bug：Leno 的 int 本身就是 48 位 payload（NaN-boxing）， 超出部分走 bigint。48 位正是它的真实位宽，与类型容量一致 —— 负数 >>> 填 48 个 0， 正是因为那个值只有 48 位有效数据。

已决定不改，理由：

理由 说明
与类型容量一致 强行 64 位反而和 int 的实际位宽脱节
真实使用者不受影响 examples/crypto/ 的 xxtea / speck / rc5 全部是 (_int32(x) & 0xFFFFFFFF) >>> n —— 32 位正数，两种语义结果完全相同
改动有回归风险 assert/test_ushr.leno 有 4 条断言锁定 48 位（-1 >>> 0 == 0xFFFFFFFFFFFF 等）

如果将来真要改：先改 test_ushr.leno 那 4 条断言，并确认没有别处依赖负数的 >>> 结果 （比如哈希/序列化里对负数做逻辑右移）。改完必须重跑 examples/crypto/ 的全套用例。

顺带记一笔：这个“口径不一致”在第三轮扩展测试里被当成疑似 bug 提出来， 但它是有意设计。已在此留档，避免重复讨论。

③ 无初值变量在赋值前使用 —— 暂不做（2026-10-24 评估）

现象：int x; print(x + 1) 编译通过，运行时才报「加法运算: null 不能参与运算」。

容易混淆的一点：var a, b, c = 1 有警告（[部分初值声明]），但那是 "一次声明多个变量、只有部分带初值"的场景，和本条不是同一个问题。 单变量无初值（int x / var x）两种写法都不警告。

为什么暂不做：要做对，必须跟踪"每个局部变量在当前控制流点是否已赋值"。 但下面这种是合法的：

int x
if cond { x = 1 } else { x = 2 }
print(x + 1)          // 两条分支都赋值了，不该警告

⇒ 需要数据流分析（每个分支都要走完才能确认），误报率会很高。 "没有警告"虽然不理想，但比"大量误报"好 —— 用户会直接关掉警告。

如果将来要做，前提是： 1. 先有"局部变量赋值状态"的流分析框架（或者只做最保守的一种： 声明后同一条直线语句序列内、首次使用前就赋值 ⇒ 不警告，其余一律警告） 2. 警告而非错误（WARN_ 而非 ERR_），且 --Wlevel 可控

现状的可接受性：运行时错误信息已经带 type=null, value=null， 加上 defer/??/字典解构默认值这些新特性，写"忘记初始化"的机会在减少。

④ 泛型函数返回类型与 T 不符 —— 暂不做（2026-10-24 评估）

现象：

func id[T](T x): T {
    return "i am a string"      // 不管 T 是什么都返回 string
}

int a = id(42)                   // 编译通过
                                 // 运行时：类型转换 int: 操作数必须是数字

为什么难修：定义处无法判断 —— T 可以是 string，所以 return "..." 对 id[string] 是合法的。只能在实例化时检查，而实例化时编译器认为返回类型就是 T（= int），静态看没矛盾 ⇒ 要拦只能做泛型的运行时类型校验（每次返回都比对 实际值与 T 的实参），这是个大工程，且会给所有泛型调用加开销。

现状的可接受性：错误不是静默的 —— 运行时会在"把 string 当 int 用"的第一处 报出来（带完整操作数类型和调用栈），只是位置离开了定义处。

如果将来要做：只对"返回类型标注为 T、且函数体 return 的字面量类型与 T 不可能兼容"的极窄场景报错（如 T: int 约束下返回 string）。有约束的泛型可以判， 无约束的不行。

⑤ face 方法签名 —— 不是缺口（已核实，2026-10-24）

第三轮报告说"face 方法签名不匹配静默通过"，实测不成立：

检查项 行为
参数数量 ✅ 拦：struct 'Circle' 的方法 'area' 参数数量与 face 'Shape' 不匹配: 期望 0, 实际 1
返回类型 ✅ 拦：返回类型与 face 'Shape' 不匹配: 期望 int, 实际 string

唯一会被放行的情况是 int → float，这是语言有意允许的隐式加宽 （func f(int a): float { return a } 也合法），不是 bug。

报告之所以认为"静默通过"，很可能就是用 float face + int 实现测的。

附：外部使用者实录（LenoSDL3「数据看板」示例，2026-09-25）

一次外部使用者（AI 代理）实写界面的踩坑记录：复刻 4 张 TraeTools 页面、给控件库补 3 个控件、修平滑滚动。 结论与正文一致：没有一条需要新增语法 ✓ —— 全都落在错误信息 / 文档可见度 / lint 三个层面 ✓。 每条都带可复现证据（探针 / 报错原文 ✓）。

一、真正的棱角（建议动，成本都极小）

1. split() 的元素是 any，会污染 var 推断 ✗

var raw = text.replace("\r", "").split("\n")   // raw 的元素是 any ✗
string ln = raw[i]                              // 编译报错：期望 string，实际 any

报错原文（提示本身很好，但这一行"看着明显能编译"✗）：

错误: [类型不匹配] 变量 'ln' 声明类型与初始化值类型不匹配
  期望类型: string
  实际类型: any
  提示：使用 _str(value) 进行显式转换

建议：split() 的返回类型静态已知 ⇒ 直接给 Array[string] ✓ （与 sdl_edit.leno 中 Array[string] _lines = text...split("\n") 的写法对齐 ✓）。 收益：消除"新手卡在门口"的一类报错 ✓。

2. for A : B 闭区间 + arr.len() 上界 ⇒ 建议加 lint ✗

for 0 : 3 to ci { ... }   // 闭区间 ⇒ ci = 0,1,2,3（四个角 ✓ 有意为之）
for 0 : 4 to ci { ... }   // 误以为左闭右开 ⇒ ci=4 不匹配任何 case ⇒ 空指针崩溃 ✗

（sdl_renderer.leno 里那条注释就是这个崩溃的现场记录 ✓）

建议：上界表达式形如 xxx.len() 时给一条编译期提示（"闭区间：这会多跑一轮" ✓）。 收益：能编译、能跑、跑到崩 ✗ —— 这类默认值最值得编译器兜一手 ✓。

3. struct 字段默认值不能是 new X() ⇒ 报错文案可以再补一句

export struct Badge impl Widget {
    Label _lbl = new Label()   // ✗ 报错
}

报错原文：

error: [语义错误] struct 字段 '_lbl' 的默认值不是常量表达式，请使用构造器初始化

实际正解（语法文档里有，但报错没给 ✓）：

    Label _lbl
    func Badge() { _lbl = new Label() }   // 构造函数：new 时自动调用 ✓

建议：在报错里直接附这 3 行 ✓（现在只说"请使用构造器初始化"，使用者得翻文档 ✗ —— 我就翻了 ✓）。 收益：这是复合控件（持子控件）的必经之路 ✓，而 UI 库里复合控件遍地都是 ✓。

二、我没发现的既有特性（说明"可发现性"比"有没有"更关键）

以下全在文档里 ✓，但我一个都没用上 ✗，全程用最笨的写法硬拼：

特性 我的笨写法 ✗ 本该这么写 ✓
字符串插值 "y=" + _str(y) + " / " + _str(max) $"y={y} / {max}"
空安全 / 空合并 if _lbl != null { _lbl.set_text(t) } _lbl?.set_text(t) / ??
构造函数 + 命名参数 X x = new X(); x.set(opts) new X(w = 10, h = 20)
遍历 for arr.len() to i { var a = arr[i] ... } for a in arr { ... }
