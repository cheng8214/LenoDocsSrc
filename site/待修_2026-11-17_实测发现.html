F1 any as func(...) 恒产出 null ✅

已修（2026-11-17）

  • 根因：src/vm/vm.c 的 vm_as_cast() switch 没有 TYPE_FUNCTION 分支 ⇒ 落 default ⇒ matches = 0 ⇒ 返回 null（静默）。语义层的"as 恒失败"清单里也没有函数类型，所以编译期没拦。
  • 修法（两步）：
    1. vm_as_cast 补 TYPE_FUNCTION：值确实是闭包 / 原生函数 ⇒ 透传（不复制、保留 upvalue）；
    2. emit_type_op（src/codegen/codegen_expr.c）对函数类型把 C 操作数改记形参个数 （255 = 裸 func，不检查）⇒ vm_as_cast 比 arity，不符 ⇒ null； OP_AS_CAST 处理器（src/vm/vminc/run/13_async_ffi.inc）在"值本来是函数、但签名不符"时 打一条带行号的警告： 警告: as func(...) 签名不符（第 N 行）：闭包有 1 个参数，目标签名有 0 个 ⇒ 结果是 null
  • 第二阶段（2026-11-17 同日补完）：形参类型也能校验了
    • 类型规格新增 TYPE_FUNCTION 变体：param_count(u8) + spec(形参)* + spec(返回)， 255 = 不校验形参（裸 func）。发射端 codegen_expr.c 的 emit_type_spec、 执行端 vm.c 的 type_spec_size_impl / type_spec_match、校验器 bytecode_verify.c 的 spec_scan 三处同构（漏一处就会"校验器把合法字节码判成损坏"）。 → 同日已单源化：spec_scan 只剩指针薄壳，长度与合法性统一走 vm.c 的 type_spec_verify()；发射端每发一条规格还会自检一次（不一致当场报内部错误）。 详见 leno_vm.h 的 type_spec_verify 注释与 bytecode_verify.c 的 spec_scan。
    • as func(...) / is func(...) 现在走 OP_AS_CAST_SPEC / OP_TYPE_CHECK_SPEC； 判据在 fn_params_match()：只比形参个数 + 标量形参类型（int/float/string/bool）—— 复合（Array/Dict/Ptr）与 struct/face/enum 在运行期只有 kind、没有名字与元素类型， 硬比会误杀；返回类型不比（func():int 可当 func():void 用，与静态侧一致）。
    • 失败文案现在带两边签名： 警告: as func(int):void 失败（第 62 行）：实际拿到 func(string)（形参不符）⇒ 结果是 null
    • 格式变了：LENO_BIN_VERSION v3.2.42 → v3.2.43、LENO_MODCACHE_VERSION v57 → v58 （变长尾随字节，旧 VM 会把签名当指令）⇒ 旧缓存整体失效重编，打包产物要重打。
  • 仍未做：返回类型与复合形参的精确比对（需要把完整类型树也存进 ObjFunction， 且 param_types 目前只记 kind）。
  • 回归：assert/test_as_func_cast.leno（4 条）。断言套件 642 / 0；模块测试 52 / 0。
  • 副作用（已确认是改善）：签名不符时不再"缺参当 null 传进去"（修前实测 func(int n) 当 func():void 调会打出 "cb" + 空值、不报错），现在是 null + 警告 ⇒ 应用侧 if f != null 的 守卫重新有意义。

现象（最小复现）

Dict d = ["cb": func(int n) { print("cb " + _str(n) + "\n") }]
var raw = d.get("cb", null)
print("raw 是 null ? " + _str(raw == null) + "\n")        // false —— Dict 里确实存着闭包
var f = raw as func(int):void
print("cast 后是 null ? " + _str(f == null) + "\n")      // true  ← BUG
print("cast 后 is func ? " + _str(f is func(int):void) + "\n")   // false

实测（v0.2.4）：

表达式 实测
raw 的原生类型 func
raw == null false
raw as func(int):void 的类型 null
as func(int):void 后 is func false
零参版本 as func():void 同样是 null

⚠ 零参版本也不能用。此前有一处误判（"零参恰好能工作"）源于读 sdl_menu.leno:70 的代码猜出来的，实测已被否掉。

为什么危害大

转换不报错、不抛异常、只是变 null。症状是"回调永远不触发"：

// Aria 桌面歌词配色：点「确定」后颜色不变、也不报错
func(Color):void onPick = opts.get("onPick", null) as func(Color):void
if onPick != null { onPick(out) }     // 恒 false ⇒ 永远不会调用

已存在的受害路径（修完 F1 要顺手回归）

build/leno_module/LenoSDL3/lib/sdl_menu.leno:70：

mi.action = d.get("action", null) as func():void

⇒ 用 Dict 构造的 MenuBar 菜单项，动作从来没触发过（菜单能弹、点了没反应）。 使用面很小（createMenuBar|addMenu(|action: 在 Aria + LenoTrae 合计 2 处命中）， 所以一直没被报上来 —— 属"沉默死代码"。

修法（建议，按成本从低到高）

  1. 运行时：as 到函数类型时永不产出 null
    • 签名匹配 ⇒ 透传原闭包（保留捕获环境，别复制）；
    • 签名不匹配 ⇒ 抛可捕获错误并带行号：期望 func(int):void，实际 func():void。
  2. 编译期：源为 any、目标为函数类型时，生成 rt_as_fn(v, sig_hash, line)，而不是裸转换 （sig_hash 可由形参个数 + 各参数类型 hash 得到，闭包本身已带 arity 信息）。
  3. 不要"直接禁掉 any as func(...)"：那只是把成本转嫁给所有使用者（每个回调都得写具名形参）。

位置

  • 行为定位在 cast 的语义兼容判定 + codegen 的 AST_CAST 生成这两处 （src/type.c 的 cast/兼容路径、src/codegen/ 里处理 AST_CAST 的地方）。
  • 本条只定位到行为，未定位到具体函数行 —— 动手前先 grep TYPE_FUNCTION 在 cast 分支的处理。

判据（回归用例）

新增 assert/test_as_func_cast.leno：

  1. Dict 存 func(int) → as func(int):void → 调用，必须真的执行；
  2. Dict 存 func() → as func(int):void → 必须抛错（带行号），而不是 null；
  3. 零参往返 as func():void 同样成立；
  4. sdl_menu 路径：createMenuBar 建一项带 action: 的菜单，clickItem 后动作必须执行。

已修（2026-11-17）：误报

现有 warning 的误报（先修这个）

WARN_STRUCT_EQ_NULL 的判据是声明形态（"P p 默认被立即分配"），不是"这个变量是否可能为 null"：

P g = null
print(_str(g == null))       // 运行期 true，但 warning 仍报"默认被立即分配（不为 null）" ← 误报

位置： - src/semantic/visitinc/visit_expr.inc:280 - src/semantic/semantic_visit_ast.c:1492

正确顺序

  1. 修误报：引入最简 null 状态（definite_null / non_null / unknown，按初始值与赋值传播），只在"比较不可能为 null"时才报；
  2. 禁字面量：非可空 T 不接受 null 字面量（T x = null 报错）；
  3. 升错误：此时 struct == null 才真的永远无意义 ⇒ 把 warning 升成 error。

迁移规模（先量过再动手）

    1. @optkeys 增加 :color 键类型 + set() 侧校验；
    2. 新增告警：Color 类型的形参 / 字段被裸 int 字面量赋值时提示（0x00000088 会被点名）。 只对字面量生效 ⇒ 零误伤存量代码。
  • 阶段二：Color 从 alias 变 distinct type，#RRGGBBAA 字面量直接产出 Color， 与 int 之间要显式 as（成本：alias 语义、# 字面量、@optkeys 键类型三处一起动）。

判据

  • 阶段一：createButton({border_color: 0x00000088}) 期望出告警；border_color: #00000088 期望安静；
  • 阶段二：Color c = 0x00000088 期望编译错误。

⛔ 结案（2026-11-18）：颜色不做成类型，阶段一即最终形态

决定：保持 alias Color = int（C 生态 / Android @ColorInt 那一派）， 阶段一（字面量身份 + @optkeys(...:color)，SDL3 门面 154 个键）就是终态； 阶段二（distinct Color / struct Color）明确不做，也不做"按名字猜"的启发式告警。

三条理由（都是硬约束，不是偏好）：

  1. Leno 的 struct 是堆引用（要 new、有生命周期、== 按引用）⇒ 照 Rust Color32 / C# Color 那套 "值类型包装"要付：Color 出现 782 处签名改 + 每次传颜色一次分配 + == 语义变化 （主题表里同一颜色判不等、Array[Color] 去重失效）。收益是拦几个误用，不值。
  2. 事故形态已堵：bg_color: 0x00000088 这类"想写 53% 黑、实际全透明"现在编译期就告警， 且误报面实测为 0（仓库 2718 个 .leno + Aria 75 个文件命中 0）。
  3. 剩下的坑类型系统也管不到：int n = 0x00000088; set_bg_color(n) —— C#/Rust 之外的 int+lint 派（C/SDL、Win32 COLORREF、TS、Android）全都拦不住，只能靠 review。

为什么不加"命名启发"（形参名/字段名含 color 就按同一判据查）：它把判据从显式标注 （@optkeys(...:color)）降级成猜名字，误报面随项目代码风格漂移；现在 0 误报的干净状态更值钱。

以后若真要类型安全：先做"值类型 struct"这项语言能力（那是独立的一轮工作），再谈 Color； 在那之前不要再给 Color 加特例（distinct 也一并搁置，2026-11-18 讨论后否决）。

现状留证（便于将来复查）：distinct 关键字全仓 0 处；Color 仍是 export alias Color = int（sdl_core.leno:150、sdl_theme.leno:25）； :color 键 154 个；用例 assert/test_optkeys_color.leno（5 例）。
