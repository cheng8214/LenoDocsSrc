M1【高】threads.start 的入口判据是"module 必须为空"，报错文案却说"当前文件" —— ✅ 已修（2026-10-12）

结论：限制本身已撤（不是只改文案） —— 模块函数现在可以直接作线程入口 ✓。 实施记录见 docs/线程并发能力修复追踪.md 的 TH2；下面的原文保留，用来记住两层坑 （文案与判据不一致、契约查不到）是怎么来的。

隐式契约（原源码判据 src/module/threads/threads.c 的前置校验）：线程入口函数 f 必须 不属于任何模块——子 VM 只继承调用方 VM 的 globals ⇒ 模块函数进不了线程函数体。

实测复现（LenoMusic 拆分当天 ✓）：把 bang_menu_worker 搬进模块 bang_page.leno 后：

threads.start(): 线程入口必须是**当前文件**的函数 ✗ 收到的是模块 'bangpg' 里的 'bang_menu_worker'

两层问题： - 文案说"当前文件"，实现判的是"入口脚本"——同一次运行里"当前文件"有好几个 （每个被 import 的模块都是当前文件之一）⇒ 照着文案改不出对的结果； - threads使用指南.md 查不到这条契约 ⇒ 模块化重构第一次起线程必撞，撞完还看不懂。

当时的可行解（已实测 ✓，现在仍然能用 ✓）：宿主把 worker 当函数值传进模块，模块里存成 func(...):... 字段再 threads.start(字段, …)——此时 f 仍是入口脚本的函数 （module == NULL）✓，子线程 globals 正常 ✓（探针实测 join 回值正确 ✓）。 LenoMusic 三个页面模块全部按此落地 ✓。

实际修法（2026-10-12 落地，比当年的三条建议更彻底）： 1. 治本：协程首帧漏设 frame->module（src/vm/vm.c 的 vm_run_coroutine_with_vm）， 而模块字节码全走 frame->module 寻址 ⇒ 补上那一行，模块函数直接可用 ✓ （连带修好了主线程 async 协程里调模块函数的同一处缺口 ✓）； 2. 文案/拦截：threads.start 撤掉那条硬拦，只保留"模块尚未初始化"这一种情况的明确报错 ✓； 3. 文档：threads使用指南.md 的该节从"限制"改写成"模块函数也能用 + 两个仍然成立的注意点" ✓。

M2【高】调用"函数类型字段"的返回值是 any（声明的返回类型没生效）

实测复现（探针，2026-10-11 ✓）：

// 模块里
pri func():string outdirOf
pri func outdir(): string {
    return outdirOf()        // ✗ error: [类型不匹配] 返回类型不匹配：期望 string，实际 any
}

哪怕字段声明是 func():string，通过字段调用的返回值在类型系统里仍是 any ⇒ 必须手动收窄：var d = outdirOf() return d as string ✓（as 收窄后可用）。 普通函数调用不受影响（返回类型正常）⇒ 洞只在"函数值当字段/变量再调"这一形态。

为什么疼：函数值是本语言"跨模块传行为"的正路（M1 的解法就靠它）⇒ 用得越多， 这个洞越常撞；而且报错只说"实际 any"，看不出"明明声明了返回类型"。

修法建议：函数类型字段的调用按声明签名推返回类型（签名就在那，信息是现成的）； 顺带把 M1 的解法场景跑一遍回归（函数值 → threads.start 不受影响 ✓）。

M3【中】this 不存在、自引用叫 self——但误用 this 的报错不提示

实测（2026-10-11 ✓，两支探针）： - 方法里写 return this ⇒ error: [未定义变量] 未定义的变量: this（无任何提示）✗； - 方法里写 return self ⇒ 完全可用 ✓：经返回的引用写字段，原对象同步变 （引用语义，探针 m.v = 42 ⇒ h.v == 42 ✓）——"返回自己"这件事做得到 ✓。

所以这条的本质是报错质量小项：this 是最常见的顺手词，报"未定义变量"却不带 "是否想用 'self'？"（仓里已有同款先例：contains() 写错提示 has() ✓）。

修法建议：未定义变量报错对 this / self / This 这几个高频误拼给纠错提示； Leno入门教程.md（struct 一节）补一句"方法内自引用用 self"。

M4【中】模块别名与 struct 字段同名 ⇒ 静默遮蔽，报错指到别处

实测复现（LenoMusic 拆分当天 ✓）：入口脚本里

import "./bang_page.leno" as bang      // 模块别名
struct App { BangPage? bang = null }   // 恰好也有个字段叫 bang

// 方法里：
bang = bang.create_bang_page(...)      // ✗ 后一个 bang 被解析成"字段"

报错是"在字段 bang 上找不到方法 create_bang_page"之类——看不出是遮蔽 （字段把模块名遮了）⇒ 排查烧掉好几轮编译循环。改名 as bangpg 后当场通过 ✓。

修法建议：语义阶段检测"模块别名 vs 同作用域字段/变量同名"并直接报错 （哪怕只给 warning：「别名 'bang' 被同名字段遮蔽，模块成员将不可达」）—— 这种冲突几乎从不合法，报出来没有误伤成本。

M5【低】三件小摩擦（每个都吃掉一次编译循环）

# 摩擦 实测 建议
5a 内建类型进不了 use 模块.(…) 批量导入：use SDL3.(…, Thread) 报"期望类型名" 2026-10-11 ✓（Thread 是内建类型，不是 SDL3 导出的） 报错说清"X 是内建类型，无需 use"即可（内建类型本来就不该放进来，但报错要指路）
5b 保留字撞名无提示：Outer alias = o（alias 是关键字）报的是普通语法错，看不出"这是保留字" 2026-10-11 探针 ✓ 保留字位置报错统一带一句"'alias' 是保留字，换个名字"
5c pri 字段逼出成套 setter 样板：模块工厂没法直填 pri 字段 ⇒ 每个都写 set_xxx（LenoMusic 两个页面模块各 5+ 个） 2026-10-11 ✓ 已决：不修（2026-10-12 ✓）—— 理由与官方绕法见本节末的决定块；一句话：改用本 struct 自己的方法（构造函数 / init(Dict) / 析构）把 N 个 setter 收成 1 个 ✓

✅ M5c 已决：不修（2026-10-12）

结论：保持 pri 的字段级（struct 级）边界，不加 new T() { field: v, … } 字面初始化。

为什么（按权重排序）：

  1. pri 是有实际作用的严格边界，不是多余 —— 实测（2026-10-12）： · 同一模块里的普通函数碰它 ⇒ 'T.x' 是 pri 私有字段… ✓ · 兄弟 struct 的方法碰它 ⇒ 同样被拦 ✓（struct U { func poke(T t) { t.x = 1 } }） ⇒ 它挡的是"同一模块内、除本 struct 方法以外的一切"。放宽成"同模块可见"是削弱既有封装保证， 而收益只是"少写几个 setter" —— 与本仓近两轮"把静默问题往编译期收"（as 恒失败报错、--check 自报范围、 M6 的截断审计）方向相反 ✗
  2. 那套 setter 多数不是纯样板：GUI 控件里 set_value 常带 clamp / 标脏 / 重排（如 Slider.set_value） ⇒ 创建式直填等于绕过不变量（new T() { value: 999 } 这种越界值最容易写出来 ✗）； "可读性收益"与"绕过校验"是同一枚硬币 ✓
  3. 字面初始化是新增语法，且会造出第二条构造路径（与"工厂 + init"并存）⇒ 与《Leno语言改进建议》的 "不再追加特性"、以及本仓反复收敛的"单一事实来源"两条口径都冲突 ✗
  4. 关键：痛点有零语言改动的替代 —— 走结构体自己的方法（这一族本来就允许直填 pri ✓）：
场景 写法 说明
固定初值 func T() { x = 7 } 构造函数：new T() 后自动跑；不能有参数 ✓
参数化初值 func init(Dict o) { x = o.get("x", 0) … } 一次填完所有 pri 字段 ⇒ 工厂只剩两行 ✓
释放资源 func ~T() { … } 析构函数：与上面成对（不能有参数/返回值 ✓）

⇒ N 个 setter → 1 个方法，而且校验/夹紧留在类型自己的代码里、构造入口唯一 ✓

实测（构造函数 + init(Dict) + 析构三件套，2026-10-12 ✓）：make({x: 7, name: "abc"}) ⇒ 7/abc； new 后 alive = 1、离开作用域回 0 ✓（探针临时文件，已删）。

落地：Leno入门教程.md 的「构造函数与析构函数」一节新增子节 「pri 字段怎么填：工厂不必写一套 setter」（三行场景表 + 可跑例子 + 两条"不存在的写法"提示 ✓）； 语言陷阱速查.md 新增 ㉜（用户侧同款 + "struct 方法不需要 export"那条易混点 ✓）。

M6【高，已修 2026-10-12】C 侧宽值塞进 Value 的截断面：val_int vs val_int_safe

隐式契约：int 是 48 位，而"把 C 的整数塞进 Leno Value"有两条路 ——

// src/include/leno_value.h:183
static inline Value val_int(int64_t n) { return … | ((uint64_t)n & PAYLOAD_MASK); }   // 只留低 48 位，静默
// src/bigint.c:253
Value val_int_safe(int64_t v) { … int48 内给 int、超出给 BigInt … }

⇒ 凡是"值域可能超 int32"的地方写了 val_int((int)…)，就会静默截成低 32 位 （不是 48 位—— (int) 先砍一刀 ✗）。它与 val_int_safe 的选择没有编译期护栏， 所以只能一处一处审（语言层看不出差别：type() 一律报 "int" ✓）。

出处（同一天两次踩）：① LenoTrae 的托盘窗口过程 —— ffi.callback 的 64 位实参被截， lParam 转交回 SDL 后崩在 SDL3.dll（10-03~10-11 共 5 次，见 assert/test_ffi_callback_i64.leno）； ② 由①引起的全仓审计（2026-10-12）。

审计结果（本轮修的 6 处）：

# 位置 症结
A1 src/vm/vm.c as i64/as u64 四分支 64 位目标却 (int)：4294967296.0 as i64 = 0、281474976710657 as i64 = 1
A2 src/module/ffi/ffi.c ffi.sizeof ptr->size 是 size_t ⇒ >2GB 缓冲给错值
A3 src/module/files/files.c f.tell() / f.len() long 在 LP64 是 64 位 ⇒ >2GB 文件错值（Windows 上 long 本就 32 位）
A4 src/module/types/types.c _int(FFI 指针) 走 val_int（静默截 48 位），与 ffi.ptr_to_int 的 val_int_safe 口径不一
B1 src/module/ffi/ffi.c read_uint64 / read_at(u64) 按 INT32 判界 ⇒ 2^32 出来是内部 BigInt，而 read_int64 同值给 int（同值不同型 ✗）
B2 src/module/types/types.c _int(bigint) 单 limb 同上按 INT32 判界（该值 < 2^32 ⊂ int48，本来就该给 int）

回归：assert/test_wide_int_convert.leno（as i64/u64 × 6、as i32 截断不许变宽 × 3、 高地址 _int(ptr)、read_uint64/read_int64 同值同型）。

没纳入自动套件的三处（要 >2GB 的缓冲/文件、或语言层造不出的中间态）：A2 / A3 / B2 —— 只靠改动注释与本表钉住 ✓。未改的：as i8/i16/i32/u8/u16/u32 的截断是语义本身 ✓。

建议护城河：给这类转换加一条 lint/脚本（grep val_int((int) 与 val_int((int64_t) 白名单）， 或在 val_int 上加 __attribute__((deprecated)) 风格的口径提示 —— 不然下次照样漏 ✗。

M7【中，✅ 已修 2026-10-12】指数字面量曾只有 enum 成员值那条路能用（两条路两种结果 ✗）

实测矩阵（2026-10-12 ✓）：

上下文 1e10 / 1.0e10 / 1.5e-3

实测边界（6 个探针 build/_probe_new_*.leno，2026-10-13）：

写法 结果
方法里 new B(k = 隐式自字段) ✗ 未定义的变量
方法里 new B(k = self.id) ✓
方法里 new B(k = 局部变量) / new B(k = 外层函数()) ✓
方法里 new B(k = 1)，之后的语句再读 id ✓（只坏在参数那一段，self 没被永久切走）
普通函数里 new B(k = 参数) ✓（只在 struct 方法里犯）
B 有同名字段（Inner.id = 99） ✗ 仍响亮报错，不会静默取到 99

⚠ 最后一行把严重度钉住了：不是"self 被切成 B"（那样同名字段会静默错值，性质完全不同 ✗）， 而是"参数值那一段看不见隐式 self" ⇒ 裸名只按变量解析（所以同名字段也不会被误取 ✓）。

疑似病因（⏳ 未钉死，动手前先按探针确认现状）：src/semantic/visitinc/visit_struct_init.inc:137 对每个字段值调 visit(s, field_value) —— 该 case AST_STRUCT_INIT 整段不压/不弹作用域 （scope_resolve(s->current, struct_name) 只是查找，不是切换点）⇒ 嫌疑落在隐式 self 字段的 解析判据上：它在"构造参数"这条路径下拿不到外层方法的 self 上下文。 建议的排查入口：semantic_type.c 里 scope_resolve(s->current, "self") 那几处（639 / 2555） 与裸名分支（831 / 1221），对比"方法体语句"与"构造参数"两条路径传进去的上下文差异。

临时绕法（零成本，两条都行 ⇒ 所以它只值"中"）：

  1. 值里写显式 self.：new Inner(k = self.id) ✓；
  2. 先建空壳再逐字段赋值（LenoSDL3 的 sdl_card.leno:237 就照这条写的 ✓）：
BadgeSpec b0 = new BadgeSpec()
b0.text = badge          // 这里读本结构体的字段完全正常 ✓

为什么值得修：这是"代码看着像自己写错了，其实是编译器看不见 self"那一类 —— 人会先怀疑名字写错 / 字段私有 / 漏了 use，一次编译循环就这么没了 ✗； 而判据明明现成（外层方法的 self 就在上下文里）⇒ 参数值应当按"在调用方上下文里求值"处理 ✓。 同族的隐式契约见 M4（模块别名 vs 同名字段）。

修好之后的判据：6 个探针（build/_probe_new_*.leno）应全绿； 建议同时补一颗 assert/ 用例（"方法里构造 + 参数用隐式自字段"）， 因为 walk 语料里这类写法本来就该是常态，只是大家一直在默默写 self. 绕它 ✓。

M6 · alias 跨模块（2026-11-25 修完，原症状保留作记录）

原症状（三个探针，全部实测）：

写法 修前 修后
本文件 export alias Stack[T] = ct.Stack[T] ✅ 本文件里可用 ✅
另一个文件 use gen.Stack 后 new Stack[int]() ❌「struct 'Stack' 不是泛型类型，不能写类型参数」（类型参数丢了） ✅
另一个文件 new gen.Stack[int]() ❌「未定义的 struct 类型 'gen.Stack'」 ✅
另一个文件 Stack[int] s = …（类型注解） ❌ 类型对不上 ✅

根因：别名存在解析器每文件一张的 alias 表里（add_alias_with_params）， 而模块符号表里的别名条目（ModuleAliasSymbol）只存 body、不存形参名 ⇒ 消费端 拿到的别名"没有类型参数"；限定名更是直接在符号表里找不到 struct。

修法（2026-11-25，四处）：

  1. ModuleAliasSymbol 增 type_params / type_param_count，module_symbol_table_add_alias 带参， AST 填充（ast_fill_one_alias）与两处跨模块传导一起带上； .lenosymc 升到 v60（旧缓存里的别名条目少这段 ⇒ 必须重编）。
  2. Symbol 增 is_type_alias / alias_type_params / alias_type_param_count； 本文件 alias 注册（semantic.c）与 use m.X 导入（semantic_visit_ast.c）都置上。
  3. visit_struct_init：名字若指向别名 ⇒ 用调用点实参代入形参，把 new Stack[int]() 就地改写成 new ct.Stack[int]() 再重新解析（带 8 次跳数保险）。 模块限定写法（new gen.Stack[int]()）走同一实现的"裸类型信息"版。
  4. resolve_alias_in_type：展开泛型别名时按使用处的实参替换形参 （否则声明类型停在 Stack[T]，与构造出来的类型对不上 ⇒ 误报类型不匹配）。

顺带修的解析器 bug（就是当初让人以为"alias 根本不能用"的那两个）：

  1. 值别名探测（parser_func.c 的 IDENT DOT IDENT）把 alias X[T] = m.Y[T] 误判成 alias X = Enum.member ⇒ 后面的 [T] 被当作下标表达式 ⇒ 报「未定义的变量: T」。 修法：带类型参数的一律不是值别名；成员名后面跟 [ 也回退按类型解析。
  2. new 处按别名替换 struct_name 时（parser_expr.c）只取 struct_name、丢了 module_qualifier ⇒ new StackAlias[int]() 报「未定义的 struct 类型 'Stack'」。

回归用例：assert/test_alias_generic_cross.leno（本地泛型 / Array[T] / 跨模块限定名 / 已实例化 / 值别名 / use 导入 / 再导出 共 8 条路径）+ assert/helpers/alias_box_mod.leno。

实际收益：LenoWeb.web_generic.Stack 从"只能删掉（破坏性）"变成 export alias Stack[T] = ct.Stack[T] —— use web.Stack 保住，实现只剩容器那份。

顺带修掉的两个真 bug（2026-11-25，让"文件内 + 限定名"这条能跑；上游已改 + 用例已加）：

  1. 值别名探测（parser_func.c 的 IDENT DOT IDENT）把 alias X[T] = m.Y[T] 误判成 alias X = Enum.member ⇒ 后面的 [T] 被当作下标表达式 ⇒ 报「未定义的变量: T」 （完全指错靶子）。修法：带类型参数的一律不是值别名；成员名后面跟 [ 也回退按类型解析。
  2. new 处按别名替换 struct_name 时（parser_expr.c）只取 struct_name、丢了 module_qualifier ⇒ new StackAlias[int]() 报「未定义的 struct 类型 'Stack'」。 修法：限定名拼成 qual.name 再往下传。

回归用例：assert/test_alias_generic_cross.leno（本地泛型 alias / Array[T] / 跨模块限定名 / 已实例化 / 值别名 五条路径）。

注：原计划里写的"还差：模块符号表加别名表 + bump 缓存"，就是上面修法第 1 条 —— 已落地 （.lenosymc v59 → v60）。
