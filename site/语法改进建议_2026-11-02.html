语法改进建议（2026-11-02）

本文是建议与对照，代码块是示意（含故意写错的反例），不可直接运行。

目的：把"能改、值得改、改了不会伤现有代码"的语法层建议集中成一份， 供作者按优先级取用。每条都写清：现状（实测）→ 动机 → 建议语法 → 实现落点 → 风险。

复核说明（2026-11-02 二次核对，11-03 更正 ASAN 一条）：本文每条"现状"都用 build/leno.exe 现场跑过。 第一版有 3 处数据不可复现（断言 537、样例 788、maths 基准 ns）和 3 处技术判断错误（C4 的"自动二分"、C1 的"没有赋值表达式"、D1 的"没有 this 提示"）， 已按实测改正，逐条对照见 §F 核对记录。请不要沿用旧版本的这些数字。

⚠ 11-03 更正：原先把"ASAN 0 泄漏"也列为"不可复现"，那是错的 —— 那份报告是在 Linux（glibc + gcc/clang） 上跑出来的，Windows/MinGW-w64 才没有 libasan。 ASAN 报告本身有效，只是换平台就没法在同一台机器上复现。详见下面的"内存正确性"。

本轮实测基线（下列命令都在本机跑过，可复现）： - 语言断言：build\leno.exe assert\run_tests.leno build\leno.exe assert ⇒ 564 passed / 0 failed - 模块测试：build\leno_module\* 下 test\test_*.leno 共 29 个 （本次只核对了数量与路径口径，未逐个跑；跑法：进各模块目录用 build\leno.exe 执行） - 样例：examples 递归 812 个 .leno ⇒ --check 812/812 零错误（含 GUI 样例，--check 不需要显示器） - 内存正确性（分平台）： - Linux：-fsanitize=address 可用，断言套件与模块测试能跑出 0 泄漏 （2026-11-03 在其中抓到过"箭头投机解析每次失败漏 120B"并已修，见 69c3f9d3）； - Windows + MinGW-w64：没有 libasan，-fsanitize=address 链接失败 （cannot find -lasan，见 docs/编译器崩溃排查手册.md）⇒ 本机只能用 -O0 -g + gdb。 ⇒ 结论：ASAN 结果有效，但只能在 Linux 侧复跑；Windows 侧的内存问题靠 gdb 与代码审查。

换句话说：下面这些不是 bug，是"语言形状"层面的改进机会。 已修/已纠错的几条见 §A，其余按优先级列在 §B–§E。

A. 本轮已处理（留作记录）

A1 ✅ arr[:] 双侧全省略切片（原路线图 T28）

  • 修前：arr[:3] / arr[5:] / arr[-3:] 都合法，唯独 arr[:] 报 期望表达式 + 期望 ']' ⇒ 解析器不对称。
  • 修法：src/parser/parser_expr.c 的 arr[:end] 分支（消费 : 之后）先判 ]， 紧随 ] ⇒ end = NULL。语义 / codegen / VM 本来就按 null = 省略 处理 （OP_SLICE），所以改动只在解析器。
  • 语义：等价整段浅拷贝（与 arr[0:arr.len() - 1] 一致，且是副本不是别名）。 字符串同样可用："hello"[:]。
  • 回归：assert/test_array_slice.leno 测试 4b（副本非别名，full[0] = 99 后 arr[0] 仍为 1）/ 4c（字符串）。
  • 文档：module_arrays / 入门教程 / 语言陷阱速查 / INDEX / 路线图 T28 共 5 处已同步。

A2 ✅ 文档纠错三处

  1. 入门教程原写 print(arr[:-3]) // [1,2,3,4,5]，实测是 [] （Leno 的负下标只对起点生效；负终点恒为空，且编译期有 [切片负终点] 警告）。 已改成 [] 并注明警告。
  2. docs/语言陷阱速查.md ⑳ 说"源码浮点字面量不支持科学计数法"，已过期： 实测 1e3 / 1.5e-2 / 1.5e17 都通过。只有前导小数点 .5 仍不合法。已更新。
  3. docs/import使用指南.md §7.1 曾把"函数内条件 import"写成可用 —— 实测 "m" 永远是 null（codegen 只在 root_scope 解析别名）。现在编译器直接拒绝 嵌套的 .leno import（见 A3），文档与示例已同步。

A3 ✅ 源码模块 import 必须写在模块顶层（编译期强制）

  • 修前：main() { import "x.leno" as m; print(m) } 编译通过、运行输出 null， m.foo() 报「下标访问: 对象不支持索引」——根因完全看不出。
  • 修法：语义阶段检测 .leno import 的 s->current != s->root_scope ⇒ 直接报 「源码模块 import 只能写在模块顶层……」。原生模块（ffi/maths…） 不绑定变量，写在函数里仍合法（仓内回调大量 import ffi）⇒ 不拦。
  • 文档：import 使用指南 §7.1 改成"顶层 import + 按条件选引用"；两个 boundary 示例同步修正；diag 断言钉住报错。

A4 ✅ cstruct 数组字段切片（不是语法，但和切片这一族相关）

  • ObjCStructArrayView 只支持逐元素索引，OP_SLICE 不认识它 ⇒ obj.values[2:5]、obj.values[:] 运行期报「切片: 对象必须是数组或字符串」， 而 docs/module_cstructs.md 明确承诺支持。
  • 已在 OP_SLICE 增加视图分支，按普通数组的闭区间/负起点/钳位规则物化成 Array （嵌套 cstruct 元素给非拥有视图）；新增 assert/test_cstruct_array_slice.leno。
  • 遗留（类型推断小项）：语义侧把「cstruct 数组字段切片」的静态类型从 any 改成 Array[元素类型]。实测确认现状：var s = d.values[:] 后 s.len() 直接报 「不能在 any 类型上调用方法 'len'」，必须先 if s is Array 收窄。可排在 C1 之后。

A6 ✅ ??= 空值合并赋值（B1，2026-11-02 完成）

  • 现状→结果：a ??= 3 以前报「期望表达式」，现在合法。
  • 实现（4 处）：
    1. src/lexer.c 的 '?' 分支加三字符前瞻：? ? = ⇒ TOK_COALESCE_ASSIGN （⚠ 该 token 追加在枚举末尾，避免挪动既有 token 数值）；

    3. src/codegen/codegen_stmt.c：新增 gen_coalesce_assign_var()（局部/形参/全局/upvalue/模块/ __self_field__）+ gen_index_assign 的判空分支 —— 都是 emit_is_null → emit_jmp_if_false 跳过右值 → 写回，右值只在该写时求值；
    4. src/semantic：豁免 T11「确定是 null 还参与运算」的报错（int? a = null; a ??= 3 正是它的头号用法），并新增"目标不可空 ⇒ 恒不生效"的编译错误。

A7 ✅ 箭头函数 x => expr / (a, b) => expr / (int x) => expr / () => expr（C2，2026-11-02 完成）

  • 实现：纯语法糖，直接 desugar 成 func(参数) { return expr }（AST 仍是 AST_FUNC_DEF）， 语义 / 闭包 / 类型推断零改动。两个入口：
    1. TOK_FAT_ARROW 的中缀规则（src/parser/parser_expr.c 的 rules[] + parse_arrow_infix）；
    2. (…) => 用投机解析：parse_grouping 先开静默段 + 保存词法状态试一遍参数表， 失败就回滚成普通括号表达式 —— (a + b) / (pr.sum()) 照旧。
  • 与既有 => 的关系（关键）：=> 原本只用于类型绑定 （if x is T => v / case is A => v）。两者共存靠两条：
    • is 的优先级（PREC_IN）比箭头（PREC_ASSIGNMENT）高 ⇒ 解析到 AST_TYPE_CHECK 时 parse_arrow_infix 发现 left 不是裸变量、原样返回不消费 token，=> 留给绑定语法；
    • 新护栏 check_arrow_in_cond()：条件位置/case 值出现箭头函数 ⇒ 编译错误。 否则 if x => 1 { }（以前是语法错误）会变成"条件 = 函数值"⇒ 恒真且一声不吭。
  • 口径：省略类型的参数是 any；函数类型按完整签名比较，所以传给 func(int):int 形参时要写 (int x) => …。
  • 回归：assert/test_arrow_func.leno（9 项：单参/零参/多参/带类型/当实参/括号表达式不受影响/ if 表达式体/嵌套箭头）+ assert/test_diag_arrow_func.leno（if / while / case 三处护栏 + "if x is T => v 绑定不被误伤"的对照）。examples 812 个 --check 全过、断言 543 全过。
  • 文档：入门教程「匿名函数」一节后新增「箭头函数」小节 + 语法速查表一行。

A8 ✅ 实参位置禁止裸赋值（C1 的前置闸门，2026-11-02 完成）

  • 实测的旧行为：f(a = 1, 2) ⇒ 返回 12，且事后 a == 1 —— 因为 = 是优先级最低的 中缀运算符（parser_expr.c 的 rules[TOK_EQ] = parse_assignment），实参位置会先真的赋值 再把值当实参传，全程无错无警告。而 new Point(x = 10) 里同样长相的 x = 10 是字段名 （parse_new 的 AST_STRUCT_INIT 路径）⇒ 一个写法两种语义。
  • 修法：新增 parse_call_arg()（src/parser/parser_expr.c），6 处实参解析循环统一走它 （普通调用 / 泛型调用 / 模块调用 / obj.m(...) / (expr).m(...) / ?.m(...)）： 实参若是 AST_ASSIGN / AST_COMPOUND_ASSIGN / AST_INDEX_ASSIGN ⇒ 报 「实参位置不能写「名 = 值」……」。判据用起始列差区分"裸赋值"与"用户显式加括号"： f(a = 1) 拦、f((a = 1)) 放行（既有 assert_eq((c += 5), 6) 靠这条）。
  • 不动的部分：(a = 1) / 1 or (a = 1) / var b = (a = 1) 全部照旧； new Point(x = 10) 照旧。
  • 回归：assert/test_diag_arg_assign.leno（裸赋值 ×2 报错 + 括号赋值 / new 字段名 / or 短路三个对照）。仓内全量扫描：examples + assert + 20 个模块库， 实参位置赋值 0 处（仅 test_operator_precedence.leno 的 2 处括号内赋值，不受影响）。
  • 意义：C1 现在可以直接做了 —— 实参里的 名 = 值 不再有第二种解释。

A9 ✅ 命名实参 f(b = 2, a = 1)（C1，2026-11-02 完成，第一版）

  • 口径：只对本模块的脚本函数生效（能查到 AST_FUNC_DEF 的形参名）。 位置实参必须在命名实参之前；同一形参不许既位置又命名；名字写错列出可用形参； 中间形参可跳过，前提是它有字面量默认值（= 2 / = "" / = false / = null）。
  • ✅ 2026-11-03 补丁：求值顺序 = 书写顺序。第一版把实参按形参名重排后交给 codegen， 导致 f(b = sideB(), a = sideA()) 先执行 sideA（静默换序 ✗）。 现在语义阶段额外生成 Ast::call.arg_eval（书写顺序的「表达式节点 → 形参槽」表）， codegen 用 gen_call_args_to() 按书写顺序求值、直接写进对应形参槽； 没有命名实参时该表为 NULL，仍走原循环（字节码零变化）。 回归进 assert/test_named_args.leno ⑨（全命名 / 位置+命名两组副作用顺序）。
  • 实现：
    1. src/parser/parser_expr.c：parse_call_arg(p, allow_named) 多了个参数 —— 裸标识符调用（f(...)）里形如 名字 = 值 的实参不再报错，留给语义阶段判定； 方法 / 模块 / ?. 调用仍然当场报「实参位置不能写「名 = 值」」（本期不支持）。 用新增的 Ast::arg_paren 标记区分 f(a = 1) 与 f((a = 1))。
    2. src/semantic/semantic_visit_func.c：新增 sem_normalize_named_args() —— 按形参名把实参重排成纯位置实参，然后整条链路（类型检查 / 默认参数补齐 / codegen）完全不用改，字节码与按位置传参逐字节一致。
    3. src/semantic/visitinc/visit_expr.inc：case AST_CALL 最前面调用它 （必须在任何"逐个访问实参"之前，否则会先把它当赋值表达式处理）。
  • 缺口（第一版故意留的）：方法调用 / 跨模块 / 内置 native 函数不支持命名实参 （拿不到形参名），会给出定向报错；跳过中间形参只支持字面量默认值。
  • 回归：assert/test_named_args.leno（重排 / 位置+命名 / 默认参数 / 跳过中间 / 嵌套 / 泛型函数 / 方法体内 / 递归，共 8 组）+ assert/test_diag_arg_assign.leno 重写为命名实参的错误路径（名字写错、重复、命名后写位置、方法调用不支持、括号对照）。
  • 文档：入门教程新增「命名实参」小节（含 4 条规则与限制）。

A10 ✅ 数字分隔符 1_000_000（B3，2026-11-02 完成）

  • 实现（src/lexer.c 的 read_number）：十进制 / 十六进制 / 二进制 / 小数部分 / 指数部分 五个扫描循环都允许 _，但只允许夹在两个该进制的数字之间 （1_ / 1__0 / 0x_FF 都不吞 ⇒ 照旧报语法错，不会静默接受）。
  • 关键点：token 的 text/len 保留原文（诊断与高亮要看原样）， 但做数值转换前把下划线剥掉成 numtext/nlen 再交给 strtod / strtoull / bigint 文本 —— 否则 strtod("1_000") 会在 _ 处停下，静默得到 1。 bigint 的长度判据（>15 / >18）也改用 nlen，否则 1_000 会被误判成 bigint。
  • 回归：assert/test_number_separator.leno（十进制 / 0x / 0b / 小数 / 指数 / 等值对照 / bigint / _1 仍是标识符）。

  • 动机：UI / 日志里最常见的需求就是"保留 N 位小数"；现在要么写 format（格式串 与参数分离、容易错位），要么 _str(_round(...))（还得自己补 0）。
  • 建议：{expr:spec} 内的 spec 复用现有 format 的转换子集（%d/%f/%.Nf/%x/%s）， desugar 成 format("%.<spec>", expr)。
  • 落点：src/parser/parser_expr.c 的 parse_interp_string（解析 { 内表达式后直接 if current != TOK_RBRACE ⇒ 期望 '}'，当前 : 就死在这里）+ 语义/代码生成侧复用 format 内建。
  • 风险：中。插值里出现 : 的既有写法（Leno 三元是 if，所以没有 a ? b : c； 字典/类型注解一般不在表达式内）需盘点；建议只在 { 后顶层 : 识别。

C4 switch 区间 / 条件 case（P2，约 2 天）

  • 现状：case 1:3 { } 报 [语法错误] case 语句体必须用大括号 {} 包裹 （1:3 被当成表达式，逗号/冒号在 case 头没有专用语法）；只能一个个列 case 1 … case 3。
  • ⚠ 第一版的动机写错了：原文说"switch 已有同类型 ≥4 个自动二分"，实测不成立。
    • src/codegen/codegen_stmt.c 的 gen_switch 只有线性比较链：逐 case emit_eq + emit_jmp_if_true + 跳板区，没有任何"≥4 个就换查找"的分支；
    • 全仓 codegen 没有一处发 OP_SWITCH_LOOKUP；
    • VM 侧那条指令是空动作：src/vm/vminc/run/14_switch_for.inc 里 LABEL(OP_SWITCH_LOOKUP): DISPATCH();；
    • switch_lookup_index()（src/vm/vm.c）没有任何调用方，是死代码；
    • 实测：6 个 int case 的 --debug 反汇编是 6 条连续的 OP_EQ，无 SWITCH_LOOKUP。

⇒ 所以"与二分优化兼容"这个成本项不存在；反过来，"switch 没有查找优化"本身 是个可选的性能项（要做就得先让 codegen 发指令 + VM 实现，工作量独立于本条目）。 - 动机（改后）：分数段 / 时间片 / 字符区间分类是常见写法；区间 case 能把 "长 if 链"收进 switch，至少省掉重复的 x >= a and x <= b。 - 建议语法（11-03 修正）：case 1:3 { } —— 与切片 arr[2:8]、范围 x in 0:9 同符号同口径（闭区间）。 - 第一版曾建议 case 1 to 3（复用 for 的 to），理由是": 已被切片/类型标注/字典占用"。 这条理由不成立：case 头里 : 后面只可能跟区间右端，没有第二种解释，不存在歧义； 而另造 to 会让 Leno 有两套等价的区间写法，与"单一事实来源"冲突。 - 11-03 已按 : 实现，case 1 to 3 保留为"报错 + 提示改成 :"（不静默兼容）。 - 落点：parser 的 case 头（case 后表达式若紧跟 to ⇒ 造区间节点）； codegen 在 gen_switch 比较链里生成两次比较（>= lo and <= hi）， 现在有 OP_CMPJMP_* 可直接用。 - 风险：中。主要成本在语义/代码生成与"case is Type 混合"的排序， 以及区间 + 常量的重复/重叠检测（可选）。

C5 for x in arr 作为 for arr to x 的别名（P2，约 1 天 —— 建议不做）

  • 现状：for x in a { } 会报一条很好的错（实测原文）： 「for 头的 x in 集合 不是遍历写法（in 是成员测试运算符，而 for 是区间循环 ⇒ 循环体不会执行），且 x 未定义；遍历请写 for 集合 to x（集合在前）」。
  • 动机：几乎所有主流语言都是 for x in arr；Leno 的"集合在前"（for arr to item） 是独有语序，跨语言用户每天都会写反。诊断虽好，但每条都要手改。
  • 建议（若做）：只在 for 头把 for IDENT in EXPR 识别为遍历 （in 在 for 头不可能是成员测试）⇒ desugar 成 for EXPR to IDENT。 这样不动 in 运算符在其它位置的语义。
  • 为什么不建议做：与 B4、D1 选项② 同属"给已有概念加第二套写法"，而 D3 已用 "单一事实来源"否掉三元运算符。真要降低摩擦，把这条诊断的文案（已经很好） 再往前推一步即可 —— 例如在 IDE/LSP 侧做 quick-fix，成本是零语法变更。
  • 风险（若做）：中。除了 for 头前瞻，还要定"for 里的 x 是已声明变量时算遍历还是 成员测试"，并决定 for (x in a) 这种带括号形态是否保留（建议明确不支持 + 给文案）。

C6 批量导入 / 批量 use（P3）

  • 现状（2026-11-02 复核更正）：
    • 批量 use 其实早就有了，只是语法是 use m.(A, B, C)（圆括号，不是花括号）—— 实测 use m.(A, B) 正常（tmp_c6 验证）。原条目说"一行一个"是错的。
    • import io, times 仍然报 [语法错误] 期望表达式 ⇒ 只有批量 import 是真缺口。
  • 若要做批量 import：src/parser/parser_module.c 的 parse_import_stmt 是单条实现 （400+ 行，里面还夹着"预扫描模块的 use 行 / 包名解析 / 版本校验"）， 要支持 import a, b 得先把它拆成 parse_one_import() + 循环（返回 AST_BLOCK 包多条， 与 parse_var_decl 多变量同款）。属于结构性重构，不是"加个循环"那么简单， 收益（省几行 import）与风险不匹配 ⇒ 建议继续搁置。
  • 替代方案：模块头部继续一行一个；真要压缩，用包（leno.toml）或 use module.(A, B)。

D. 低优先级 / 需作者拍板

"别名类"统一立场（本轮的评审结论）：B4（elif）、C5（for x in arr）、 D1 选项②（this）本质相同 —— 都是给已有概念加第二套写法；而 D3 用 "两套等价语法与单一事实来源冲突"否掉了三元运算符。两条立场不能同时成立。 建议统一为不加别名、只改诊断（诊断已经普遍写得很好）， 否则就三处一起加、一起写进语法文档。这个取舍需要作者拍板。

D1 this → self 的纠错提示（已完成，见 A5）

  • 选项①（只加提示）已落地；选项②（把 this 当 self 同义关键字）属"别名类"， 立场见上面的统一说明 —— 与 B4 / C5 一起决定，不要单独加。

D2 负终点切片语义（不建议改，仅记录）

  • 现状（实测）：arr[:-3] == []（负终点恒为空），arr[-3:] 正常从末尾数（得 3 个元素）； 负常量终点在编译期给 [切片负终点] 警告（WARN_SLICE_NEG_END）。
  • 改成 Python 语义（负终点 = len + end）很诱人但破坏兼容：仓里已有代码/测试依赖 当前口径。建议保持现状 + 文档（本轮已纠错）。

D3 三元 cond ? a : b（不建议加）

  • 现状：明确报错并推荐 if cond then a else b / eif 链。
  • 理由：Leno 已有"if 表达式"，再加 ? : 会形成两套等价语法（与"单一事实来源"纪律冲突）。 保持现状，诊断文案已经足够好。

D4 trim() 只认 ASCII 空白（可选，P3）

  • 现状（实测）："　你好　".trim().len() 仍是 4（全角空格 U+3000 不修剪）， trim() 结果仍是 "　你好　"。
  • 动机：中文内容里全角空格很常见，用户会直觉认为 trim 应处理它。
  • 建议（改后的方案）：不要改 trim 的默认语义，另加 trim_unicode() / trim_start_unicode()（或 trim(chars) 重载）， 边界扫描按 UTF-8 空白集（至少 U+3000、U+00A0；与 Python str.strip / Rust char::is_whitespace 同口径）。
  • 理由：改默认行为会静默影响"故意保留 NBSP/全角空格"的数据清洗代码； 新增方法零破坏，用户按需选择。
  • 风险：低（纯新增）。
