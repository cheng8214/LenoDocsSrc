待修：编译 / 语义问题清单

记录在开发过程中真实踩到、但当下不阻塞、留待后续修的语言/编译器问题。 每条都写清：现象、最小复现、当前绕过方式、影响面。

1. var 接收可空返回值时，被推断成非可空

状态：已修（2026-10-28）。修的是 native 规格通道；当初记的 face 形态经复核并未丢可空。

当初的现象：函数声明返回 Widget?（可空接口），用 var 接收后，!= null 判断被怀疑恒为真：

// 声明
pri func(int, int, float, float): Widget? cellBuilder

// 当时的写法
var ucw = cellBuilder(ri, c, cw, rowH)   // 怀疑被推断成 Widget（非可空）
if ucw != null {                          // 怀疑恒真
    ucw.render(r)
    continue                              // 返回 null 时若也走进来，后面的内建绘制被跳过
}

// 当时的绕过写法（现已非必需，但留着更直观）
Widget? ucw = cellBuilder(ri, c, cw, rowH)
if ucw != null { ... }

复核结论（2026-10-28，探针 + 回归用例）：

  1. 脚本函数 / face 方法 / 函数类型字段（func(...): Widget?）三条返回路径的可空性 一直是保留的，运行期判空也正确。已用覆盖真实形态的探针验证（同模块、跨模块、 pri 字段、方法体内调用、数组元素 struct 实现跨模块 face、if ... continue 的写法）， 全部判空正确。⇒ 当时"该列整列不绘制"的根因不是可空性推断（var 与 Widget? 两种写法的静态类型相同、运行期逐字同义），真实原因待复现时再记。
  2. 真正丢可空性的是 native 规格通道：NativeTypeSpec 原先只能表达"非可空 T" ⇒ 返回值明明可能是 null，调用点拿到的静态类型却不带 ?。可直接复现：
   var r = _exec("cmd /c echo hi", 5000)   // 静态类型曾是非可空 struct ExecResult
   if r != null { ... }                    // ⇒ 误报「struct 值类型默认被立即分配（不为 null）」

这正是 sdl_capture.leno / screenshot_hotkey.leno 里手写 ExecResult? r = _exec(...) 并留注释绕开的那条坑。

修法（src/include/leno_types.h + src/native.c + src/module/sys/sys.c）：

  • 规格层新增 NTYPE_NULLABLE 包装标签：{ NTYPE_NULLABLE, NULL, &S_EXECRESULT_SPEC, ... } 表示"内层规格的类型是可空的"。
    • 为什么用 tag 而不是给 NativeTypeSpec 加 int nullable 字段：全仓 40+ 处规格都是 位置式初始化，加字段会让它们全部触发 -Wmissing-field-initializers（实测 40 条噪音）， 而"没写就是非可空"本就是需要的默认值 ⇒ 用包装 tag 表达，既有规格逐字不变。
    • native_type_spec_to_info_impl() 先剥壳解析内层再打 nullable（驻留实例先 type_copy 再改，避免污染全局缓存）；native_spec_kind() 取内层 kind； native_type_spec_to_string() 渲染成 内层?（LSP hover / 诊断与实际类型同形）。
  • _exec 的返回规格包成 ExecResult?（native_exec 在首参不是 string / 分配失败时 确实 return val_null()）。其它 native 不顺手标可空：dirs.stat 之类正常路径必返回 结构体，误标可空只会让 st.size 这类访问凭空多出"可能空"的噪音。
  • 只影响编译期推断，规格不进字节码 ⇒ 不需要升 LENO_BIN_VERSION。

回归用例：assert/test_var_nullable_infer.leno（① struct/face 可空返回值判空 ② sdl_table 那种"pri func(...): W? 字段 + 方法体内 var + continue"的形态 ③ var r = _exec(...) 不再误报 null 比较）。

影响面：所有"native 返回可空"的调用点（var 推断不再撒谎）；规格里将来若还有 "确实可能返回 null"的 native，包一层 NTYPE_NULLABLE 即可。

2. 全局文本替换类重构没有编译期保护（工程问题，非语言 bug）

状态：备忘

批量把 xxx( 重命名成 mod.xxx( 时，用 String.Replace 会命中字符串字面量与 其它上下文。本次出现过： - 替换 "resizable", 时误改到 opts.get("resizable", true) → 变成 opts.get("radius", "resizable", true)，报"参数过多 / 类型不匹配"。

规避：批量替换带引号的片段时，必须加更长的上下文（含 opts.get( 前缀）， 或者先 --check 再逐条看错误行号。

3. 成员方法不能直接当函数值用

状态：已修（2026-10-28）—— 现在三种写法都能用，不必再套 lambda。

当初的现象：把同一个 struct 里的成员方法赋给一个函数类型字段，报 "未定义的变量" （不是"方法不能作为值"这种能看懂的提示）：

// struct 内
pri func track_row_like(Song sg, Button b) { ... }

// 调用处（修前报错：未定义的变量: track_row_like）
hk.onTrack = track_row_like

// 当时的绕过：lambda 包一层（现在**不再需要**，留着也能跑）
hk.onTrack = func(Song sg2, Button b) { track_row_like(sg2, b) }

修后的三种写法（都可用）：

// ① 方法体内裸写方法名 —— 编译器自动改写成 `self["方法名"]`
hk.onTrack = track_row_like

// ② 显式给接收者（同模块 / 跨模块都行）
hk.onTrack = hk.track_row_like

// ③ 顶层（无接收者）裸写 —— 仍然报错，但文案说清原因与出路：
//   未定义的变量: track_row_like —— 它是 struct 'Hk' 的**成员方法**，不能脱离接收者当值用。
//   在方法体内直接写方法名即可（编译器自动绑定 self）；方法体外请写 `对象.track_row_like`

为什么能跑（实现要点，都在语义层，VM/字节码没动）：

  • 运行期本来就支持：OP_INDEX 对 struct + 字符串下标在字段查不到时按方法名兜底， 返回一个 已绑定接收者的 bound closure（vm/vminc/run/07_collections.inc 的 struct 分支）。 此前只是语义层不认这条路：裸名落进"未定义变量"，obj.方法名 落进"没有字段"。
  • semantic_visit_method.c：transform_method_body_ex 的 AST_VAR 分支新增一段 —— 裸名命中本 struct 的方法表 ⇒ 就地改写成 AST_INDEX{ self, "方法名" }。 顺序是字段优先（字段与方法同名时取字段；裸调用仍是方法优先，两者取向不同是刻意的）。
  • visit_field_access.inc + semantic_type.c：字段查不到时用统一判据 semantic_struct_has_method()（func_table 的 "Struct::method" 键 + struct 定义的方法表） 放行，并在推断侧用 infer_method_value_type() 给出不含 self 的函数签名 （bound method 已绑接收者 ⇒ 调用点只传业务实参）。
    • 跨模块占位符的形参名不叫 self（符号表只存类型）⇒ 判"第 0 个形参类型就是这个 struct" 来识别 self，否则签名会多一个参数。
    • 无返回值注解的方法 ⇒ 签名返回类型是 void（TYPE_NULL）而不是 any， 否则 func(Song):void 会签名不等而误报类型不匹配。
    • ⚠ type_function() 的所有权不对称：返回类型直接接管、参数表深拷贝 ⇒ 只能释放参数表。
  • codegen_expr.c：AST_FIELD_ACCESS 的通用 OP_INDEX 路径补记 dce_note_method_ref —— 否则"只被取值、从不直接调用"的方法会被 DCE 当死代码剪掉（取到 null，静默错值）。

回归用例：assert/test_method_value.leno（裸名/显式/跨模块/默认参数/返回值/当实参/ 存进 Array[func(...)]/字段优先/顶层裸名报错文案六件事）+ fixture assert/method_value_mod.leno。

影响面：hk.onTrack = track_row_like 这类"回调字段 = 本类方法"的写法从"必须套 lambda" 变成"直接写"；Aria / LenoMusic 里已有的 lambda 包装无需改动，想简化可去掉。

4. 截图探针（*_SHOT）有时让 UI 卡住 / 退出码异常

状态：已知限制，非框架 bug（2026-10-28 更正）

现象：带 ARIA_SHOT=xxx.png 跑无头验证时，偶尔出现： - 界面卡住（帧不再推进）； - 进程退出码 -805306369（截图本身通常是成功的）。

原因：探针在 on_tick 里"截图 → 立刻 _exit()"，截图（读回像素 + 写 PNG）与 当帧的渲染/事件循环没有解耦，读回期间又来一帧就会撞上。

结论：早期曾误判为"Canvas 作为单元格控件导致的崩溃"，实测 Canvas 用在单元格里 是正常的（同样的表、同样的探针，有时 exit=0 有时不是）⇒ 不是 Canvas 的锅。

规避：探针里截图后不要立刻退出，先让出两拍再 _exit（本仓库的 ARIA_AT 与 test_table_cell_widget.leno 已按此写法：留 6 秒窗口）。

待办（低优先）：给 saveImagePNG 加"读回像素后强制 markFrameRedraw 一帧"的 收尾逻辑，从根上消除这个竞态。

5. Widget 接口没有命中测试

状态：待增强（2026-10-28 记录）

face Widget 只有 get_w/get_h/set_pos/set_size/process/render/dispose。 在"表格单元格里放按钮"这类场景，宿主无法判断"这次点击是否落在子控件上"， 只能把事件广播给子控件，同时自己也处理行选择 ⇒ 点按钮会连带触发行双击。

建议：face Widget 增加 func hit_test(float x, float y): bool （默认实现 = 点在 [x, y, x+w, y+h] 内），宿主的转发逻辑变成： "命中才转发、命中则吞掉事件"。
