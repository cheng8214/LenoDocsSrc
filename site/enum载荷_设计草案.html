enum 载荷（case Progress(done, total)）设计草案

状态：已实现并收官（2026-11-10）：步 1~4 + 断言 + 跨模块 + == 按值 + jsons.encode。 目标：把"enum 只能当 int 常量用"补成"enum 成员可以带数据"，且不破坏现有 int 枚举。 ⚠ 实现与本文初稿有三处偏离（都是为了不退回 any、不让类型名对不上）， 见文末 §7「实现记录」——读 §2/§3 时以 §7 为准。

1. 现状与痛点

现在：

enum State { idle; running; done }
  • 成员是 int 常量（State.running 在语义阶段被改写成 AST_NUM，见 visit_module.inc）；
  • 想带数据只能退回 struct + tag：
struct Msg { int kind; int done; int total }   // kind 用 "0".."5" 或裸 int

痛点：kind 与 done/total 的有效性耦合没有任何检查（kind=0 时 done 该是 0 还是没意义？）， 这正是评估报告 §3.5「enum 半能用」的落点。

2. 语言形态（提案）

enum Msg {
    progress(int done, int total)      // 带载荷成员
    finished(string path)
    failed(string why, int code)
}

Msg m = Msg.progress(3, 10)            // 构造

switch m {
    case Msg.progress(d, t) { print(_str(d) + "/" + _str(t)) }
    case Msg.finished(p)    { print(p) }
    case Msg.failed(w, c)   { throw w }
}

规则（刻意窄）：

  1. 成员要么全带载荷、要么全不带。同一个 enum 里混用 ⇒ 编译错误。 （理由：混用会让"值是 int"和"值是对象"两种表示并存，switch 与 == 的语义立刻分叉。）
  2. 同一 enum 内成员名唯一，参数个数/类型按成员各自声明，不做重载。
  3. 没有载荷的 enum 完全保持现状（int 常量），既有代码与字节码零变化。
  4. E.m(...) 只能用于带载荷的 enum；带载荷 enum 的成员不能当 int 用 （int x = Msg.progress(1,2) ⇒ 编译错误，避免"看起来是数字"）。

3. 降级（lowering）：一个隐藏 struct + tag

不为"带载荷 enum"发明新运行时对象，直接降级成编译器合成的 同名 struct：

// 编译器为 enum Msg 合成（与 enum **同名** —— 见 §7-① 为什么不用 __Msg）
struct Msg {
    int tag          // 成员序号（声明顺序，0-based）
    int p0           // progress 第 1 个参数
    int p1           // progress 第 2 个参数
    string p2        // finished 的第 1 个参数
    string p3        // failed 的第 1 个参数
    int p4           // failed 的第 2 个参数
}
  • 槽位布局（§7-② 改过）：按成员分段 —— 成员 m 的参数占用从 base(m) = Σ_{j<m} 参数个数(j) 开始的连续几个槽。于是每个槽的静态类型就是 该参数声明的类型，一个 any 都不用；progress(int,int) 与 finished(string) 这类最常见的组合也不再冲突。 代价：字段数 = 1 + 所有参数个数之和（实例里多几个恒为 null 的槽）。
  • 构造：Msg.progress(3, 10) ⇒ AST_STRUCT_INIT(Msg, {tag: 0, p0: 3, p1: 10})。 codegen 复用现有 struct 构造路径（零新指令）。
  • 匹配：switch m { case Msg.progress(d, t) { … } } ⇒ switch m.tag { case 0 { var d = m.p0; var t = m.p1; … } }。 主题被换成 m.tag（int 比较链，复用 OP_CMPJMP_EQ），绑定变量是注入 case 体 最前面的 AST_VAR_DECL（初值就是 m.p0/p1）。codegen 完全不知道 enum 载荷存在。 ⚠ 因此主题必须是变量（m），表达式会被求值两次。
  • 穷尽性：tag 取值集合 = 成员序号，沿用 WARN_SWITCH_NOT_EXHAUSTIVE （老 enum 那条只认 TYPE_ENUM，降级后主题是 int ⇒ 由 enum_payload.inc 单独补一份）。

为什么用 tag + 位置槽，而不是"每个成员一个 struct 类型"

  • 每个成员一个 struct ⇒ 变量类型得写成 any 或 union，switch 只能靠 case is 逐个试， 且穷尽性检查退化成"运行期判定"，静态阶段无法给出"漏了谁"。
  • tag + 槽位 ⇒ 变量有单一具体类型 Msg，字段访问、赋值、传参全部沿用现有规则， switch 仍是对 int 的比较链（与今天 int enum 的字节码形态一致）。

5. 兼容性与迁移

  • 现有 int 枚举一个字节都不变：成员仍改写为 AST_NUM，OP_* 指令不增不减。
  • 新特性只对"声明了参数的成员"生效 ⇒ 四个项目现有 enum（Aria 的 Source、LenoMusic 的 State 等）不需要改。
  • 想立刻用上"带数据 + 穷尽检查"的项目，可以把 struct+tag 改成带载荷 enum； 不强制，两条路并存一段时间，等草案实现稳定后再在 AGENTS.md 里推荐。

7. 实现记录（2026-11-10）—— 与初稿的三处偏离

初稿有三处在实现时被否掉了，原因都是"照草案写会退回 any 或让类型名对不上"：

① 隐藏 struct 用 enum 同名，不是 __Msg

初稿：__Msg + 在类型解析处做名字映射。 实现：直接叫 Msg。理由：类型名一旦对不上，Msg m = Msg.progress(...)、形参/返回/字段 声明、m.tag 的字段索引、OP_STRUCT_INIT 的运行时名字查找 —— 每处都要多一条映射规则， 漏一处就是静默错配（本仓最怕的失效形态）。同名则整条链路零改动。 代价：Msg 不能再被别的同名类型占用（合成阶段直接报"与第 N 行声明的同名类型冲突"）； 显式 new Msg(...) 要在 visit_struct_init.inc 里拦掉（那是实现细节，不是用户 API）。

② 载荷槽 按成员分段，不是"按位置取共同类型"

初稿：第 k 个槽取所有成员第 k 个参数的"最宽共同类型"，不可统一就不支持。 问题是初稿 §2 自己的例子（progress(int,int) + finished(string) + failed(string,int)） 第 1 个位置就是 int vs string —— 照初稿要么不支持、要么退回 any。 实现：base(m) = Σ_{j<m} 参数个数(j)，成员 m 的第 k 个参数落在 p<base(m)+k>， 类型就是这个参数自己声明的类型。一个 any 都没有，初稿那个例子原样能用。 代价：字段数 = 1 + 所有参数个数之和（多几个恒为 null 的槽）。

③ switch 是"换主题 + 注入绑定"，不是"展开成多个 case is"

初稿说"整段改写成若干个 case is 形态"。实现更简单且保住 break/default 语义： 把主题换成 m.tag（AST_FIELD_ACCESS，复用原 AST_VAR 节点），case 值换成 tag 常量， 绑定变成注入 case 体最前面的 AST_VAR_DECL（var d = m.p0）。 因此主题必须是变量 —— 表达式会被求值两次（副作用 + 两次取值可能不同）。

顺手补的两处

  • 穷尽性：老的那段只认 sw_expr_type->kind == TYPE_ENUM，降级后主题是 int ⇒ 在 enum_payload.inc 里按成员序号集合另补一份 WARN_SWITCH_NOT_EXHAUSTIVE（文案同口径）。
  • 合成产物不打扰用户：struct_def.is_synthetic / var_decl.is_synthetic 两个标记 用来跳过"字段未初始化"、"与 native/导入模块同名"、"绑定变量未使用"这类面向用户源码的诊断 —— 用户没写这些声明，报给他也无处可改。

三处缺口：已补齐（2026-11-10 第二轮）

缺口 做法 落点

  • == 跨不同 enum 比较：类型不同 ⇒ 不等；switch 里混用两个 enum 的成员也在编译期就拦。

8. 压力测试记录（2026-11-10）—— 测出 3 个 bug，已修

用例固化在 assert/test_enum_payload_stress.leno（8 组：载荷类型 / 零参数变体 / 容器相等 / 5 层嵌套 / 名字撞车 / 322 槽宽索引 / 跨模块 / JSON）。三处都是收官提交里没覆盖到的：

① a == b 为真，arr.has(b) 为假（值比较有两条路，结论不一致）

  • 现象：5 层嵌套载荷 == 给 true、has 给 false；载荷里装 Array[int] 时同样打架。
  • 根因：== 走 vm.c 的 value_eq_depth（深度上限 8、容器逐元素）， Array.has / index_of / Dict 键 走 leno_value.h 的 value_shallow_equal（上限 4、 并且不递归容器 —— 它对 Array/Dict 一律按指针比）。
  • 修法：抽出唯一实现 value_payload_field_equal_depth()（leno_value.h，不分配、 覆盖数值/字符串/数组/字典/嵌套载荷），两条路都调它；深度上限统一成 LENO_VALUE_EQ_MAX_DEPTH = 8。普通 struct 仍是引用语义（零变化）。

② enum Cmd { add(int n) stop() } 被判成"混用带载荷与不带载荷"

  • 现象：零参数变体（Option 的 None、命令的 Stop）根本写不出来，直接报混用。
  • 根因：判据是"参数个数 > 0"，而 stop() 的参数个数也是 0，与老写法的 stop 不可区分。
  • 修法：AST 加 member_payload_flags（写没写括号），parser / enum_payload_synthesize / visit_enum.inc 的判据全改成它。stop() 现在能构造、能 case Cmd.stop() 匹配、能进 JSON（{"tick":{}}）。
  • 顺带堵一个洞：export 一个全部成员零参数的带载荷 enum 会明确报错 （模块符号表靠"参数总数 > 0"决定存不存载荷表，全零会静默退化）—— 报错而不是错值。

③ 只要 enum 里有一个 struct 载荷，整条 enum 的 == 全部变 false

  • 现象：enum P { num(int v) pt(Pt p) }，P.num(5) == P.num(5) 是 false。 4 个成员时正常、加到第 5 个（含 struct 成员）就崩 —— 非常像"随机"。
  • 根因：合成 struct 的载荷槽没写默认值时，struct / face / Ptr / cstruct 类型的槽会被自动 造成一个新实例（实测 P.num(5) 的 p1 是 Pt{x=1} 而不是 null）⇒ 两次构造的 p1 是 两个不同对象 ⇒ 逐字段比较必不等。
  • 修法：合成时给引用类载荷槽显式默认 null（标量槽不能写 null，交给原零值默认）。

④ 两个模块导出同名但不同形的带载荷 enum：运行期才报（已改成编译期）

  • 现象：import a + import b，两边都 export enum Ev（成员不同），消费端 use a.Ev + use b.Ev ⇒ 编译通过，程序先跑完 main（打印了 "ok"），然后在收尾时报 「跨模块同名 struct 'Ev' …… 请给其中一个改名」。
  • 根因：semantic_import_payload_enum 把"同名且已是带载荷 enum"当幂等直接放行， 于是编译期默默挑了先导入的那份；形状冲突只有运行期的 def_owner_conflict 才查， 而它是在两份 OP_STRUCT_DEF 都注册时才触发 —— 那时 main 可能已经拿其中一份跑过了。
  • 修法：导入时按成员名 + 参数个数比形状（与 def_owner_conflict 同口径），一致才幂等放行， 不一致就在编译期报错并点名"给其中一个改名 / 别 use、用限定名 a.Ev / b.Ev"。

⑤ 泛型 / 并发 / JSON 往返：压测通过，无 bug

场景 结果
Box[Ev]（泛型 struct 的字段是跨模块导入的带载荷 enum）、Pair[Ev,string]、idOf[Ev](…) ✅ 取出来能 switch、能按值比较、标量字段不受影响
带载荷 enum 过 Channel（send/receive）、threads.start 入参 ✅ 跨线程是深拷贝，收回来能 switch；== / Array.has / index_of 仍按值成立
jsons.encode 单值 / 零参数成员 / 数组 / struct 字段 / 再 encode ✅ 形状稳定：{"done":{"code":7,"who":"me"}}、{"quit":{}}、[{"text":{"s":"a"}},{"quit":{}}]、{"name":"box","msg":null}
jsons.decode(… ) as Ev（反填） 仍返回 null（设计上未做，见上文"仍未做"）—— 需要时用 switch 分派

回归用例：assert/test_enum_payload_interop.leno（泛型/跨模块/JSON）、 assert/test_enum_payload_threads.leno（Channel 双向 + 深拷贝后按值比较）。

已知边界（不是 bug，写在这里免得下次又踩）

  • switch 的主题必须是变量（降级后要读 m.tag / m.p0，表达式会被重复求值）—— 语义阶段有定向报错。
  • 一个 switch 里每个 case 的绑定各占一个寄存器 ⇒ 80 个 case × 4 绑定会撞 255 上限； 与手写 80 个 case 各声明 4 个局部量完全同价（实测对照：两者报同样的错），不是载荷特有。
  • 300 成员 × 零参数的同模块 enum 可用（带载荷 enum 不发 OP_ENUM_DEF，255 成员上限不适用）。

9. 泛型载荷 enum（2026-11-10 起，进度 2/3）

决定：走擦除，与泛型 struct 同一条路

依据（实测，不是猜的）：

  • struct Box[T] { T v } 现在的表示是"类型系统记住实参、运行期只有一份同名定义"： type(new Box[int]()) 打印 Box[int]、is Box[int] 为真，但字段按 any 存。
  • 泛型载荷 enum 只要沿用同一模型即可：载荷槽里跟类型参数同名的注解在解析期就转成 TYPE_GENERIC_PARAM（convert_to_generic_params，struct/func/face 三处早就在用）， 合成出来的隐藏 struct 带上同样一份 type_params ⇒ 实例化时按实参替换。
  • 不选单态化（每个实参组合造一份 __R_int）：要动 struct 定义表、字段索引、 .lenb 与模块缓存版本策略，而收益只是"字段不做 any"——现有泛型 struct 也没这么做， 为 enum 单独破例会让两套泛型语义并存。

已完成（步 1 + 步 2）

  1. 解析器：enum Name[T, U] { … } 接受类型参数列表（重复参数有诊断）， 载荷参数类型里的 T 转成 TYPE_GENERIC_PARAM（与 struct 字段同款）。
  2. 降级合成：合成出的隐藏 struct 继承同一份 type_params； TYPE_GENERIC_PARAM 载荷槽显式默认 null（与压测 §8 那条同一个理由）。

现在这些都能编译且零诊断：

leno enum Res[T] { ok(T v); err(int code, string msg) } func sig(Res[int] r): string { return "x" }

已完成（步 3/3）：构造的类型实参推断

五条来源，优先级从高到低：

  1. 显式写法 Res[int].ok(42)（2026-11-10 补 —— parser 在 parse_index 里识别 类型名[类型实参].成员(…) 并建成 AST_MODULE_CALL，语义侧直接取实参）。 可以出现在任意表达式位置，是"没有上下文"时的万能写法。
  2. 带类型的声明：Res[int] a = Res.ok(42)
  3. return（函数签名写了返回类型）：func f(): Res[int] { return Res.ok(1) }
  4. 给已声明变量赋值：a = Res.ok(9)
  5. expr as Res[int]

外加 载荷实参推断（2026-11-10 补）：成员载荷声明里出现了 T 时，按实参类型绑定 （Res.ok(1) ⇒ T = int），与泛型函数共用 infer_generic_bindings。 于是 show(Res.ok(1)) / arr.add(Res.ok(1)) / d.set(k, Res.ok(1)) / b.val = Res.ok(5) 这些没有 expected_type 的位置也都成立 —— 此前它们一律报「推不出类型实参」，要求用户先绑一个带类型的局部量。

推断顺序是"先绑定的优先"：期望类型先占住，实参类型只补空缺（不会互相覆盖）。

全都推不出（典型：Res.err(1, "x") —— 该成员的载荷里根本没有 T）⇒ 定向报错， 文案会点名缺哪个类型参数，并区分两种真因（"载荷声明里没有它" / "实参类型不够确定"）， 同时给出显式写法作为出路。

实现坑（已修，钉在 assert/test_enum_payload_generic_infer.leno 的用例 ②）： 改写后的 new Res(...) 交给正常 struct 初始化路径时，必须清掉外层 expected_type， 否则 Res[Res[int]] x = Res.ok(Res.ok(5)) 里的内层构造会误用外层的 Res[Res[int]] （同名 + generic_count 相同 ⇒ 判"匹配"）⇒ 内层被绑成 T = Res[int]，报 「成员 ok 第 1 个参数: 期望 Res[int]，实际 int」。

另一个实现坑（parser）：显式写法分支只认大写开头的裸变量。实测 _runRens[_qi].destroy() （下划线开头 + 下划线下标）会撞进来，被当成 _runRens 模块的成员调用 ⇒ AST 错乱、 模块编译期 ast_free 直接 0xC0000005（sdl_window.leno）。数组下标 + 方法调用必须继续走原路径。

回归钉子：assert/test_enum_payload_generic.leno（构造三通道 / 匹配绑定 / 双实参共存 / 多类型参数 / 按值比较）+ assert/test_enum_payload_generic_infer.leno （载荷推断 / 显式实参 / 嵌套 / 下标记法回归 / 三条诊断）。

已知边界

  • 类型参数暂不支持约束/默认值（enum R[T: Face]）：解析器只认名字列表。
  • 显式写法只支持裸类型名：Res[int].ok(…) ✓；gm.Res[int].ok(…)（限定名）仍走原路径 —— 跨模块类型在消费端本来就不带类型参数（擦除模型），需要显式实参时先 use gm.Res。
  • 载荷里没有 T 的成员（err(int, string)）在完全无上下文时仍推不出，必须写显式形式 或给带类型的声明 —— 这是信息论上的边界，不是实现缺口。

跨模块（2026-11-10 补齐，已支持）

export enum Res[T] { ok(T v) … } + 消费端 use m.Res 现在完整可用： 跨模块返回、switch 匹配、消费端自己构造、按值相等都通 （钉子：assert/test_enum_payload_generic_mod.leno + assert/helpers/enum_generic_mod.leno）。

实现上只有一个关键点：类型实参要从"看起来像 int"的旧标签里救回来。 载荷 enum 在生产端降级成同名 struct，但导出的函数签名里那一处类型仍是 TYPE_ENUM （export func make(): Res[int] 就是这样）⇒ 消费端 Res[int] r = m.make(5) 会报 「期望 Res[int]，实际 int」（TYPE_ENUM 的显示名就是 int，看不出真因）。 修法是在 type_is_compatible 里放行同名的 STRUCT ↔ ENUM（运行期本来就是同一个对象， 只是类型标签不同）—— 只按同名放行，不同名的照旧不兼容，兼容面没有放大。

过程记录：这条我先做过一版"给模块符号表加类型参数"的大改（ModuleEnumSymbol、 .lenosymc v45、导出/导入三处 + 消费端重建），把同模块主路径改回归了（'(null)' 里没有成员）， 全量回滚后才发现真正缺的只是上面那一处兼容判断。教训：这类改动要先看最小复现， 别一上来动符号表格式 —— 版本号一 bump，所有模块缓存失效，定位成本翻倍。

  • enum 不能挂方法（extend Res { … } 会报"extend 只能给 struct 加方法"）⇒ 即使载荷 enum 运行期就是个 struct，isOk/orElse/… 这类方法也挂不上去。这正是 LenoResult 的 Result[T] / Option[T] 必须保持 struct 的决定性理由（不是"不能泛型"了 —— 那个已经支持）。

显示：_str / print 用成员式（2026-11-10）

此前打印带载荷 enum 会暴露降级布局：Msg{tag=0, p0=7, p1=null, p2=null}。 现在 value.c（_str）与 io.c（print / print_value / print_value_quoted）都走 同一份签名遍历 enum_sig_member_at()（leno_value.h）⇒ Msg.a(7)：

print(Msg.b("hi", 2.5))    // Msg.b("hi", 2.5)   —— print 的字符串带引号
_str(Msg.b("hi", 2.5))     // Msg.b(hi, 2.5)     —— _str 的字符串不带（与 _str("hi") 一致）
_str([Msg.a(1), Msg.c()])  // [Msg.a(1), Msg.c()]

签名缺失 / tag 越界 / tag 不是 int ⇒ 退回通用 Name{field=value} 显示（宁可多暴露字段，不崩）。 钉子：assert/test_enum_payload.leno 的 ④ 段。
