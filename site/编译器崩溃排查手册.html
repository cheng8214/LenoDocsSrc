编译器崩溃排查手册

起因：2026-10-24 支持「下标复合赋值」时，遇到"直接跑没事、换个方式跑就崩"， 绕了很久才发现是一个既有的双重释放 bug。此文档把当时的排查路径固化下来， 下次遇到同类症状直接照做，不要重新摸索。

一、先认症状：这些是崩溃，不是报错

在 cmd 里运行 build\leno.exe xxx.leno，如果没有任何输出、又没有 [错误] 行， 先看退出码：

build\leno.exe xxx.leno & echo EXIT=%errorlevel%
退出码（cmd 显示） 十六进制 含义
-1073740940 0xC0000374 堆损坏（重复释放 / 越界写）。堆管理器在 free 时才发现
-1073741819 0xC0000005 访问违例（空指针 / 已释放后继续用）
-1073741571 0xC00000FD 栈溢出（递归过深）

⚠ 这类崩溃经常伴随 --check 通过：语法、类型都对，坏在内存。

二、最重要的教训：「环境不同」是假象

这次踩的坑：同一个文件

跑法 结果
命令行直接跑 ✅ 正常
被 Leno 父进程用 _exec 拉起 ❌ 0xC0000374
有 .lenocache 缓存 ✅ 正常
全新编译 ❌ 崩溃
小文件 ✅ 正常
文件里语句多了 ❌ 崩溃

这不是环境问题，是堆损坏在不同堆布局下的可见性差异。 分配器不一定每次都检查到，所以"有时好有时坏"本身就是堆损坏的典型特征。

⇒ 不要花时间做"环境矩阵"对比。第一次见到"换个跑法就崩"，直接上 gdb。

三、定位流程（按顺序做，别跳）

第 1 步：判断崩在编译期还是运行期

rmdir /s /q <用例目录>\.lenocache
build\leno.exe <用例>.leno
if exist <用例目录>\.lenocache (echo 编译完成，崩在运行/退出) else (echo 崩在编译期)

.lenocache 生成了 ⇒ 编译成功，问题在 VM 或析构阶段。

第 2 步：二分到最小用例

把一个文件拆成只含单一构造的小文件逐个跑。这次就是靠这步发现 「11 种运算符全过、组合起来才崩、真正触发的是表达式位置的 (f[0] += 3)」。

第 3 步：编调试版 + gdb（核心一步）

build.bat 是 -O2、无 -g，gdb 只能给函数名。先编一个调试版：

:: check_dbg.bat —— 内容与 build.bat 相同，只改两处：
::   -O2  ->  -O0 -g
::   build\leno.exe  ->  build\leno_dbg.exe

然后：

gdb --batch -ex run -ex "bt 20" --args build\leno_dbg.exe <用例>.leno

这次拿到的关键输出：

SIGSEGV in type_free (type=0xfeeefeeefeeefeee) at src\type.c:171
#0 type_free   src\type.c:171
#1 ast_free    src\ast.c:452      ← type_free(ast->cached_type)
#2 ast_free    src\ast.c:121      ← AST_INDEX: ast_free(u.index.obj)
...

第 4 步：认"毒值"

指针里出现这些填充图案，就是在读已释放/未初始化的堆：

值 含义
0xFEEEFEEE Windows 堆：已释放的内存
0xCDCDCDCD MSVC Debug：未初始化的堆
0xDDDDDDDD MSVC Debug：已释放的堆
0xBAADF00D 已分配未初始化

⇒ 看到 0xFEEEFEEE 就说明同一块内存被释放了两次（第二次读到的已经是填充值）。

第 5 步：顺着栈找"第二个所有者"

双重释放的本质一定是同一块内存有两个所有者。本仓库最容易出的三处：

  1. 同一个子节点挂到两个父节点上（共享 obj / index / value）
  2. 就地改 kind：ast->kind = AST_X 后只改了部分 union 字段，其余是旧字节
  3. free 之后还被别处引用

四、本仓库的已知高危模式（写新代码时避开）

① 共享子节点 —— 这次的真凶

// ❌ 错：两个节点拥有同一对子节点 ⇒ 析构时释放两遍
Ast* read = ast_new(AST_INDEX, line);
read->u.index.obj   = left->u.index.obj;
read->u.index.index = left->u.index.index;
assign->u.index_assign.obj   = left->u.index.obj;      // 同一对，又给了一份
assign->u.index_assign.index = left->u.index.index;
free(left);   // 只 free 了壳，子节点被两个节点共享

// ✅ 对：子节点只交给一处，用 op 字段把"读-改-写"下推到 codegen
assign->u.index_assign.obj   = left->u.index.obj;
assign->u.index_assign.index = left->u.index.index;
assign->u.index_assign.op    = op;      // 让 codegen 读旧值 → 算 → 写回
left->u.index.obj   = NULL;             // 转交后置空，避免壳被别处再释放时二次释放子节点
left->u.index.index = NULL;
free(left);                             // 壳用普通 free，不递归

规则：ast_free 对每种节点都会递归释放子节点 ⇒ 任何子节点只能有一个父节点。 要"两处用同一个表达式"，只能深拷贝（见下），不能共享指针。

② 就地改 kind

ast->kind = AST_INDEX_ASSIGN;    // ⚠ union 里还留着 AST_ASSIGN 的旧字节

实测后果：新加的 op 字段读到旧字节的非零值，被误判成"复合赋值"， 18 个测试同时挂（值全错但不崩，更难查）。

规则：改 kind 后逐个字段显式赋值，不要依赖"其他字段是 0"。

③ 固定数组无上限

// 原来：只判了 r，没判 freetop —— free_regs[] 只有 MAX_REG(256) 个槽
gen->free_regs[gen->freetop++] = r;

压栈次数超容量 = 堆越界写。现在 reg_free 已加 gen->freetop < MAX_REG。

规则：往固定数组里写之前，先判容量。

五、工具可用性（本机实测）

工具 状态
gcc 15.2.0（MinGW-w64） ✅ 可用
gdb ✅ 可用（C:\Program Files (x86)\mingw64\bin\gdb.exe）
ASan（-fsanitize=address） ❌ 链接失败（collect2: ld returned 1 exit status）
gflags / PageHeap ❌ 未安装

⇒ 在 Windows/MinGW 上排查只能靠 -O0 -g + gdb，不要浪费时间试 ASan。

★ 2026-11-03 更正（重要）：上面这条"ASan 不可用"只是 Windows/MinGW 的结论， 不是 Leno 的问题。Linux（glibc + gcc/clang）上 -fsanitize=address 完全可用， 断言套件与模块测试能跑出 0 泄漏 —— 实测已用它抓到过两类真问题： - 箭头函数投机解析每次失败漏 120B TypeInfo（parse_type 成功但下一 token 不是标识符时 直接 goto fail，没释放刚建的类型）； - x => { … } 错误分支已分配的 params/types 没释放。

所以内存问题的最佳路径是：Windows 写代码 → Linux 跑 ASAN。 本机的 gdb 只用于"已经崩了"的现场；ASAN 用于"还没崩但已经漏了"的预防。 具体跑法（Linux）：

# 一次性构建带 ASan 的编译器（不要覆盖 build/leno.exe）
gcc -std=c11 -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer \
    src/*.c src/*/*.c src/*/*/*.c -o build/leno_asan.exe -lm -lpthread

# 跑断言套件（ASAN_OPTIONS 让泄漏在退出时以非零码暴露）
ASAN_OPTIONS=detect_leaks=1:halt_on_error=1 \
  ./build/leno_asan.exe assert/run_tests.leno ./build/leno_asan.exe assert

看到一个 SUMMARY: AddressSanitizer: … leaked in N allocation(s) 就说明有漏， 堆栈里的 #0 … #1 … 直接指到分配点。（源文件清单按实际构建脚本调整。）

六、修复后的验证清单

  1. 最小复现用例：修复前崩、修复后 EXIT=0
  2. 原崩溃路径：如果是"某种跑法才崩"，用同一跑法复跑
  3. 单测：build\leno.exe assert\<新测试>.leno
  4. 全量：build\leno.exe tools\run_timeout.leno 400000 build\leno.exe assert\run_tests.leno build\leno.exe assert
  5. 改动面大时（如动 parse_assignment 这种所有人都会走到的函数）： 额外 --check 几个重模块（build\leno_module\LenoSDL3\lib\sdl_tab.leno 等）

⚠ 全量里如果只有一条挂，且它挂的原因是"钉住了旧行为"，那是测试该更新， 不是回归 —— 但必须在提交信息里写明，并单独验证该用例。

七、一句话速查

无输出 + 退出码是负数 ⇒ 崩溃； 先看 .lenocache 判断编译期还是运行期； -O0 -g 编调试版，gdb bt 拿行号； 看到 0xFEEEFEEE ⇒ 双重释放 ⇒ 找"谁还拥有这块内存"； 修复后跑最小复现 + 单测 + 全量。
