LenoSDL3 三个疑难排查复盘（裁剪闪烁 / 打包静默失效 / 方法表断裂）

合并说明（2026-11-22）：本文由三篇排查记录合并压缩而来 —— LenoSDL3_裁剪过多导致闪烁排查记录（398 行）、 LenoSDL3_打包后窗口句柄下发静默失效排查记录（266 行）、 LenoSDL3_Table方法表断裂编译器bug排查记录（133 行）。 三篇原文已归档到 archive/（含完整的分步排查过程与插桩输出）。 这里只留结论、机制、以及"下次怎么快速判断" —— 具体到某一行代码的取证过程看归档原文。

三件事的共同点：都表现为"只有特定产物 / 特定界面上才犯的怪现象"，而根因都不在 GUI 层 （分别是渲染调用成本、DCE 误剪、符号表截断）。这类问题的价值全在"排查路径"上。

0. 三条一句话结论

# 现象 根因（一句话） 状态
1 新加的界面整页闪 pushClipRect/popClipRect 每次调用都 flush，嵌套还要 malloc 交集 rect；叠加 clip 按 _int() 截断丢亚像素 ⇒ 边缘一帧有一帧无 ✅ 机制已查清 + 大部分修复（残留部分复现不出）
2 打包后窗口句柄整条下发失效（IME / 右击菜单 / 弹层全哑），.leno 直跑正常 合并 case is A, B, C 的动态派发被 DCE 判成死代码，写成 <dce-cut> 空桩（一条 OP_RETURN）⇒ 静默 no-op ✅ 编译器侧已治本（2026-10-10）
3 Table 的两个方法突然"不存在" 模块符号表扫描器用固定 128 个槽收方法，Table 有 149 个 ⇒ 超出部分静默丢弃 ✅ 已修（三层防御）

1. 裁剪（clip）过多导致闪烁

1.1 机制：裁剪层数 = 每帧 flush 次数 + 分配次数

每帧成本 来源
1 次 batch flush（把已入队图元提交掉） 每个 pushClipRect 和 popClipRect 各一次
1 次 SDL_Rect.malloc() + free() 嵌套 push 时的交集 rect；只要控件 render 就分配
1 次 SDL_SetRenderClipRect 每次 push/pop

再叠加"clip 矩形按 _int() 截断 ⇒ 丢亚像素"，表现就是边缘/局部一帧有一帧无 = 闪。

1.2 规则（写新界面时照这个来）

  • 能裁的才裁：子控件按构造不会溢出父容器的一律 clip:false；
  • 别为"保险"层层嵌套裁剪 —— 层级越少越好（Tab 内容区原本 4 层，改成 2 层后明显好转）；
  • 注意 _int() 截断：亚像素的边界会抖，必要时把矩形取整一次再传下去。

1.3 另外三条独立的闪烁源（都不是裁剪，别混在一起查）

  1. 文字纹理缓存淘汰 —— 缓存满了淘汰，下一帧重新生成 ⇒ 该文字闪一下；
  2. 不必要的整窗重绘 —— 一处改红就整窗重画，会放大上面所有问题；
  3. 圆角图片"每帧每卡"离屏合成（2026-10-13 抓到并修）—— 一张圆角图每帧新建纹理 ⇒ 整卡闪。

2026-10-25 又把"嵌套裁剪"的每帧成本压到接近零（避免每次都真 flush）。

1.4 现在的状态

按上面改造后"明显变好"，残留闪烁在无头（dummy）与真实驱动（D3D）下连续帧逐像素比对均为 0 差异 ⇒ 未能复现，属于待观察项（不是已知未修 bug）。

2. 打包后「窗口句柄下发」整条静默失效

2.1 五分钟复现法（不必真打包）

build\leno.exe -c app.leno          :: 只产出单文件 .lenb（等价打包的编译单元）
build\leno_vm.exe app.lenb          :: 用 VM 跑 .lenb —— 打包专属 bug 在这里就能看到

关键：.leno 直跑正常、.lenb 出问题 ⇒ 立刻怀疑"合并成一个编译单元"带来的差异（DCE / 同名解析），而不是 GUI 代码。

2.2 根因：合并 case is A, B, C 的动态派发被 DCE 剪成空桩

句柄下发路径上到处是合并 case：

switch c {
    case is HBox, VBox, AnchorBox { c._bind_window(hwnd); return }
    case is Table, TreeView, ListBox { c.set_window_handle(hwnd); return }
}

合并 case 下变量收窄不出具体类型（等价 any）⇒ c._bind_window(...) 退化成按名动态派发 ⇒ src/dce.c 只在"名字被通配引用 且 所属类型也被引用"时才保活，于是入口 .lenb（唯一开 DCE 的产物） 把这些方法判成死代码，写成 <dce-cut> 空桩：

CONST_TAG_DEAD_FUNCTION = 空常量池 + 一条 OP_RETURN      // 语义 = 调用方拿到 null、静默 no-op

⇒ 整条链路"不报错、不执行"。这是本项目最不能接受的一类：静默错值。

2.3 一次误诊（留档，因为它很典型）

最初判成"跨模块同名符号在合并单元里串了"（sdl_layout 的自由函数 _passWindowHandle 与 sdl_window 的 Window._passWindowHandle 撞名）。2026-10-10 复核未能复现：两个最小复现 （.leno 直跑 / 单文件 .lenb）行为都正确，而且那条路径若真命中，编译器会当场报"参数过多" （响的）而不是静默 —— 与观测矛盾。

教训："改了就好的那个改动"不等于"根因"。当时真正治好打包态的是 2.2 的 DCE 修复； 改名只是顺带掩盖。所以复核时要能构造最小复现，复现不出就要怀疑原诊断。

不过复核时另外抓到一个真·同名 bug 并修掉了：形参个数相同时的裸调用仍按"方法优先"解析 ⇒ 现在编译器会给「同名歧义」/「疑似无限递归」告警；形参个数不同的撞车已能正确区分到自由函数。

2.4 治本（编译器侧，2026-10-10）

  • codegen_stmt.c 的 gen_switch：case is 对每个类型都 dce_note_type_ref（让 DCE 知道类型被引用）； 合并 case（match_type_count > 1）的 case 体内打开"多类型"区间 ⇒ 动态派发不再被误剪；
  • 配套：空桩语义（CONST_TAG_DEAD_FUNCTION）保留，但不该被用到的位置绝不能再出现（见回归用例）。

2.5 自查清单（再遇到"只有打包才犯"的怪事，照这个顺序走）

  1. leno.exe -c + leno_vm.exe 先复现（2.1）；
  2. LENO_DCE_VERBOSE=2 打包，grep cut:，看你依赖的函数/方法有没有被剪；
  3. LENO_NO_DCE=1 / LENO_DCE_WILD_SAFE=1 做 A/B：一开就好 ⇒ DCE 误剪；
  4. 全模块扫「顶层函数名 = 某类型的方法名」的撞车（尤其形参个数相同的）；
  5. 涉及 IME / 右击菜单 / 弹层这类"要窗口句柄"的能力：在 Edit.set_window 与 SDL_SetTextInputArea 调用点临时插桩，先确认 hwnd 是不是 null（本 bug 的现象全由它派生）。

3. Table 方法表断裂（符号表 128 上限）

3.1 现象与根因

改了 sdl_table.leno（新增排序功能）后，file_manager.leno 报：

error: [语义错误] 类型 'struct Table' 没有方法 'on_dbl_click'
error: [语义错误] 类型 'struct Table' 没有方法 'contains'

两个方法确实存在，且 Table 的其他方法（on_select / set_editable …）都不报错。

根因：模块符号表文本扫描器（src/module_symbol_table/inc/scan/scan_struct.inc）用固定栈数组 methods[MOD_MAX_METHODS]（128）收集 struct 方法；Table 有 149 个方法 ⇒ 超出 128 的 被静默丢弃。contains 是第 132 个、on_dbl_click 第 130 个 ⇒ 跨模块调用时报"没有方法"。

3.2 为什么它看起来"与内容无关、与位置强相关"

  • 基线 143 个方法时，两者索引 125/123 < 128 ⇒ 编译通过；
  • 新方法插在它们之前 ⇒ 索引变 131/129 ⇒ 被截断 ⇒ 编译失败；
  • 把新方法挪到 struct 末尾 ⇒ 两者索引不变 ⇒ 又编译通过。

⇒ 当时做了大量"删注释 / 改返回类型 / 加引号"的实验全部无效，因为唯一的变量是方法在 struct 内的序号。

3.3 修复：三层防御

  1. 扫描器不再用固定 128 槽（容量按需增长）；
  2. 超限时响亮报错而不是静默丢弃；
  3. 回归用例覆盖"方法数 > 128 的 struct 跨模块调用"。

4. 共同教训（三条，都是"静默"惹的祸）

  1. 静默丢弃 / 静默 no-op 是最贵的 bug：这三件事里两件（DCE 空桩、符号表截断）都是"不报错、不执行/少一半"。 ⇒ 项目口径：能判就判，判不了也要在运行到那一刻响亮报错，绝不静默。
  2. "只有特定产物才犯" ⇒ 先怀疑编译器/构建差异（DCE / 合并单元 / 缓存），不要一头扎进业务代码。 -c + leno_vm 这个五分钟复现法值得记住。
  3. "改了就好的改动"不等于根因：复核要能给出最小复现；复现不出就诚实标注"误诊"，别让它继续误导下一个人。
