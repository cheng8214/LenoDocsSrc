线程 / 并发能力修复追踪

用途：Leno 的并发模型（每线程独立 VM + Channel 传值）本身是定案，不再讨论要不要换。 本文档只追踪它做不到的事一条条补齐：一件事一条，带症状 / 根因证据 / 方案 / 验收判据。

与既有文档的分工（别混）： - docs/threads使用指南.md：面向使用者的用法（现行 API 怎么写）。 - docs/module_threads_api.md：API 参考 + 跨线程传值硬约束。 - docs/多线程struct与模块全局变量问题记录.md：已完结的排查记录（struct 定义跨线程、模块 globals 串台、FFI 回调三修）。历史事实看它，待做事项看本文。 - 本文 = 待做台账：优先级、判据、成本、状态。做完一项 → 在该文补事实 + 此处标 ✅ 并写 commit。

最后更新：2026-10-20（TH8–TH13 线程能力；TH14/TH15 async 实战暴露的并发上限与超时取消）。 可能挂死的用例必须走超时壳（async / 网络 / 线程类，禁止裸跑）： build\leno.exe tools\run_timeout.leno 15000 build\leno.exe assert\test_xxx.leno —— 超时由 _exec(cmd, timeout_ms) 杀掉子进程树、退出码 124。本仓已经因为裸跑被挂住过三次。

回归方式（已定）：只跑断言套件，不与栈式差分： .\build\leno.exe assert\run_tests.leno build\leno.exe assert ⚠ 文档里不写死断言总数（历史上有十个版本）—— 一律以实跑为准。

测量/重编译：改运行时需重编 VM。build.bat 用 cmd /c 会失败；直接在 PowerShell 里调 gcc （源文件 = sources_core.txt + sources_compiler.txt + src\module\ffi\leno_ffi_win64.c，参数 -Isrc -Wall -Wextra -std=c99 -O2 -lm -municode -lws2_32，约 86 个源文件 / 70 秒）。

三、明确不做（避免反复讨论）

不做的事 为什么
共享堆 / 拆掉线程堆隔离 要重写 GC 与所有写屏障，收益为零：模型的价值就在隔离
threads.Mutex / atomic / Semaphore 立项前提是"堆隔离下没有可被两线程同时访问的普通对象"，该前提 2026-10-20 被实测推翻（入口脚本的全局 Array/Dict 是跨堆共享的，见 TH8）。但结论仍是"不做锁"：共享对象挂在创建者堆上，子线程写它会走自己的写屏障去改别人的堆 ⇒ 锁能挡逻辑竞态，挡不住 0xC0000374 堆损坏。正确解法是 ① TH8 深拷贝消除隐式共享 ② 真要共享可变状态就走 Channel 单点化，或用 threads.local_* 每线程一份
让模块 globals 按线程深拷贝隔离（旧"方案 C"） ObjModule 由 loaded_modules 全局缓存共享，强行隔离破坏模块缓存一致性 + 模块全局语义 + GC 的 module mark 逻辑（见 archive/多线程struct与模块全局变量问题记录.md §五）
统一 threads 与 async 的调度器 大工程；当前两者定位清晰（算得慢 / 等得久），先各自补短板
去掉 Channel 的"两次深拷贝" 看着像浪费（send 克隆到发送堆、receive 再克隆到接收堆），实际是模型使然：buffer 里的值必须挂在发送线程堆上（否则发送方 OP_RETURN 后可能被 GC 回收，接收方 UAF），而接收方只能在自己的堆上用 ⇒ 换手时必须再克隆一次。真要去掉得引入"共享堆/所有权转移 + 跨堆根注册"，等于重做 GC 边界，风险远大于收益
threads.start 补齐默认参数 默认参数是编译期在调用点补的（fill_default_args），而 ObjFunction 里没有默认值表 ⇒ 线程入口由 VM 直接调用，拿不到默认值。要做只能在调用点特判 threads.start(f, ...)（编译器/semantic 改动），收益只是"少写几个实参"
async IO 后端换 IOCP / epoll 已评估并留待办（docs/待办与路线图.md §九 / T35）：select 在 1024 挂起以内够用，换后端只省"等待"、不加速协程里的字节码，成本 600–1000 行且属并发核心。触发条件：常驻 >2000 连接 / 挂起 IO 经常 >1024 / select 自身 CPU >30%

附带纪律：value_clone_for_channel() 是全模型正确性的唯一闸门。每加一个可克隆类型， 必须同时加"拒绝面"（不支持的类型明确报错，不许静默传引用）+ 一条回归用例。 历史出血点：dict 的 key 漏克隆（object_thread.c:110-139）、channel 重入克隆（:836-840）。

四、逐条详述

TH18（P0）spawn 时并发克隆 globals 会崩 —— ✅ 已修（2026-11-14 压测）

症状 - 脚本里有个较大的模块级全局数组（实测 4000 元素即可），threads.start() 起线程时 偶发 0xC0000005，约 1/4 概率；崩的位置在主线程：vm_ffi_end / thread_reap。 看着像"native 调用 / join 的锅"，与 clone 毫无关联。

根因（gdb 实测） - 崩时全局 vm 结构体的字段被写成了文本（vm.ffi_args = 0x5b5d31345b5d3034 = "40]["）。 - 来源：object_thread.c 的 g_channel_clone_ctx（192 字节诊断上下文，形如 数组[3]） 原来是进程级 static，而克隆路径本来就跑在多个线程上（每个子线程启动时克隆 globals、 收消息时克隆值）⇒ 并发 snprintf / strlen 同一个缓冲。 strlen 读到"还没写 NUL"的中间态 ⇒ 返回 > 192 ⇒ sizeof - cl 下溢成巨大值 ⇒ snprintf 无界写，把后面的 .bss（正是全局 vm）整段刷成 ctx 文本。 - 为什么和"数组大小"相关：元素越多 ⇒ 克隆循环里 snprintf 调用越密 ⇒ 撞上并发窗口的概率越高。

修复 1. static THREAD_LOCAL char g_channel_clone_ctx[192]（一行）。 2. cl 上界钳位（防御性，杜绝再次下溢）。 3. 顺带去掉一个纯浪费：原来每个数组元素都要 2×192B memcpy + strlen + snprintf， 而标量 / string 元素根本不可能被拒（永远克隆成功）⇒ 只对 Array/Dict/struct/闭包 这几类可能被拒的元素构造上下文，报错文案一字不变。

A. 截断饥饿（真问题，已修） TH14 把 FD_SETSIZE 提到 1024 并在入集前截断，但每轮都从下标 0 开始 ⇒ 挂起请求超过 1024 且前 1024 个长期不可读时，后面的请求永远轮不到（饿死，无报错）。 修法：g_async_scan_start 环形游标 —— 每轮从上次没查到的位置接着扫， async_compact() 重排后把游标收进新长度内。

B. g_event_loop 多线程覆盖（疑点，实测不成立） 担心：g_event_loop 是进程级全局，而 asyncs_init_globals() 在 native_register_globals() 里 被调用 —— 每个 threads.start() 的子线程都会跑一遍 ⇒ 把全局指针指向子线程的 event_loop， 之后主线程 future_complete() 把协程塞进废弃队列 ⇒ asyncs.run() 卡死。

实测：不会发生。 子线程调 native_register_globals() 时在 vm_run_coroutine_with_vm() 之前，此刻 current_exec_vm == NULL ⇒ get_current_vm() 回退到主 VM ⇒ 看到 vm.event_loop 已存在 ⇒ 不覆盖。 （这条路径依赖调用顺序，比较脆）⇒ 新增 assert\test_async_after_thread.leno 钉住： "先起线程并 join，再跑 async sleep 必须正常完成"。

仍开放（能力缺口，非 bug） - 没有 aconnect：sockets.connect 是阻塞调用，在协程里会卡住整个事件循环 （第一版探针就是被这个卡住的）。高并发客户端只能放线程池，或等服务端化。 - asyncs.run() 没有全局超时：它会等所有协程结束；只要有一个协程永远挂在 一个永不完成的 Future 上，run 就不返回。当前只能对单个 Future 用 asyncs.timeout。

TH17（P1）异步 connect + 事件循环全局超时 —— ✅ 已修（2026-10-20）

A. sockets.aconnect(host, port) -> Future（async 函数里 await） 动机：sockets.connect 是阻塞调用，在协程里会卡住整个事件循环（高并发客户端被串行化， backlog 满时甚至死锁 —— 第一版探针就栽在这里）。

实现：非阻塞 connect → 注册 ASYNC_OP_CONNECT → select 等就绪 → getsockopt(SO_ERROR) 判定。 立即成功时直接返回已完成的 Future。

踩到的坑（值得记）：只把 connect 的 fd 登记到 writefds 时，连接被拒绝的那次永远不会被处理 （实测：aconnect 到关闭端口，8 秒超时被 kill；connect 返回 WSAEWOULDBLOCK=10035 说明请求注册成功）。 根因：Windows 把"连接失败"报在 exceptfds（第三个集合），而不是可写集合。 ⇒ 现在 readfds / writefds / exceptfds 三个都登记，就绪判定取三者之一，再用 SO_ERROR 区分成功/失败 （实测拒绝时 SO_ERROR=10061）。

B. asyncs.run_for(ms) -> bool 动机：asyncs.run() 会等所有协程结束 ⇒ 一个协程挂在永不完成的 Future 上就永远不返回。 实现：event_loop_run_for(loop, deadline) —— 每轮检查 deadline，且把单次 poll 的等待时间 截到"剩余时间"，避免超时精度差一整个 poll 周期；返回 true = 全部完成，false = 超时停下 （协程 / 定时器 / 未完成 IO 状态全部保留，可再次 run）；ms <= 0 = 无限（等价 run）。 协程失败时与 run 一样抛异常（错误比超时更需要看见）。

验收 - assert\test_sockets_aconnect.leno：4 个并发 aconnect + echo 全成功；连没人监听的端口拿到 null （约 2s，Windows 拒绝有点慢，但不卡） - assert\test_async_run_for.leno：有协程永久挂起时 run_for(300) 返回 false（实测 311ms）， 再 run_for(200) 仍 false（204ms），且程序能继续执行到末尾 - ⚠ 用法注意：aconnect 的 Future 没有标注元素类型 ⇒ await 出来是 any， 必须 var c = raw as Socket 收窄（与 arecv 不同，后者标了 string）
