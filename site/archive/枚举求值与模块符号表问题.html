二、ENUM 组：三个计算点实测互不一致

2.1 复现（修复前的实测数据）

md.leno：

export enum E5 {
    P = 2 + 3 * 4
    Q = 2 * (3 + 4)
    BIG = 1 << 40
}
export func fp():int { return E5.P }
export func fq():int { return E5.Q }

三条访问路径各打印一次，修复前输出：

mod_side : P=14 Q=14 BIG=1099511627776     ← 同模块（枚举定义处 / 模块内函数）
use_path : P=20 Q=10 BIG=1099511627776     ← use d.E5 后直接写 E5.P      ← 错！
qual_path: P=14 Q=14 BIG=1099511627776     ← d.E5.P 模块限定

2+3*4 正确是 14，use 路径给 20（当成 (2+3)*4）；2*(3+4) 正确是 14，use 路径给 10（当成 2*3+4，括号被丢弃）。 同一份源码、同一个程序，成员值随访问写法而变，且 use 那条是错的。

隐式成员（无 =）修复前实测：

E1 全隐式 {P,Q,R}      → use 与 qual 都报「枚举 'E1' 中没有成员 'P/Q/R'」
E2 {P=7 Q R=9 S}       → 只有 P、R 可见；Q、S 报「没有成员」
E3 {P=2+3*4 Q}         → P 可见；Q 报「没有成员」
同模块单文件 {A B C}   → A=0 B=1 C=2（正常，说明解析器没问题）

2.2 三个计算点分别在哪

  1. 解析器（权威）：parse_enum_stmt + eval_const_expr，AST 递归求值、有优先级、隐式成员按 next_auto_value = member_value + 1 递增。 值流向：同模块访问（visit_enum.inc → sym->enum_values）与模块字节码（codegen_stmt.c → OP_ENUM_DEF → 运行期 enum_def）。
  2. 符号表扫描器：scan_enum.inc 自己重算一遍（next_auto + 手写解析 + 「最简从左到右」求值器）。 值流向：跨模块 use（visit_module.inc）、成员存在性检查（visit_expr.inc）。
  3. 运行期 enum_def（op_enum.inc / op_utils.inc）：值来自点 1 的字节码。

2.3 ENUM-1 根因：一个错位的括号

scan_enum.inc 中 if (*after_enum == '=') { 于第 73 行开括号，直到第 309 行才闭合， 而「决定最终取值 + member_count++」整段落在它内部：

                                if (has_explicit) {
                                    next_auto = member_values_buf[member_count] + 1;
                                } else {
                                    member_values_buf[member_count] = next_auto;
                                    next_auto += 1;
                                }
                                member_count++;
                                }        // ← 这个 } 才是 if ('=') 的收尾（错位）

后果：只有写了 = 值 的成员才会 member_count++；无 = 的成员名字被写入缓冲区但计数不推进，被下一个成员覆盖。 （用脚本统计全文件花括号深度验证：最终 depth=0，if ('=') 覆盖 73-309 行。）

2.4 ENUM-2 根因：两套求值语义

扫描器的求值器注释里自己写着「不处理优先级」「从左到右」，且把不认识的字符（含括号）直接 cp++ 跳过； 求值失败还会静默退回「无显式值」⇒ 值变成自动递增值。解析器走的是 AST 递归下降（优先级、括号、一元运算都正确）。

三、MOD 组：模块符号表扫描

3.1 MOD-1：一个调用点遍历 3 次

以 main.leno 中 import "M.leno" as m + 一处 m.foo() 为例，M 被完整遍历 3 次：

  1. visit_module.inc：import 时 create + scan（结果存在 info->sym_table，后续复用）。走 create，不查 g_sym_memo ⇒ 被 k 个文件 import 就扫 k 次。
  2. visit_module.inc：每个 m.foo() 调用点又 create + scan + destroy，只为判断「是不是 struct」。纯冗余 —— module_info->sym_table 就在手边（同一分支下面还在用它查函数）。
  3. module_has_method() → extract_module_exports_from_file 再整体读一遍 M 的源码并跑 export 词法统计。

即：一个调用点 = 2 次符号表全扫 + 1 次导出全扫；10 个调用点放大到 21 次。

3.2 MOD-2：记忆化永不失效

g_sym_memo 只有 sym_memo_lookup / sym_memo_store，没有失效与清空入口； 而 module_symbol_table_get_shared 命中时直接返回，根本不进磁盘缓存的哈希校验， 于是 .lenosymc 的「源文件 + 依赖哈希」失效机制被内存 memo 短路。 长驻进程（leno_lsp，消息循环 + 链接同一个 module_symbol_table.c）里，用户改了依赖文件后 hover/signature 仍拿旧符号表；另外 memo 表 shared=1、destroy 是 no-op，内存只增不减。

ENUM-6（P2）枚举迭代变量类型丢失（推断为 any）

  • 测试：assert/test_enum_value_consistency_mod.leno 的 sum_all() 刻意写成 s = s + v （不带 _int）—— 若推断退回 any，该函数直接编译失败，用例即红； 全量套件 303 passed, 0 failed。

七、后续想法（已记录，暂不实施）

本节是设计取舍的备忘，不是待办；等真出现「const/dict 表达不了且样板成本很高」的场景再回来评估。

7.1 字符串值枚举（enum E { A = "a" }）—— 决定：不做

  • 结论：取舍，不是语言限制。字符串常量集合用 export const / dict 可完整表达（含双向查）， 且 dict 更贴近 JSON/配置场景（jsons.parse 直接给 dict）。
  • 代价一侧：枚举现有的增量能力（位运算/位标志、FFI 直传、编译期折叠、for E to v 迭代、按名取值） 对字符串值基本无用；而支持字符串值需要把 6 处「统一 int64」改成 tagged value： 符号表 ModuleEnumSymbol.member_values、.lenosymc 8 字节值布局（还要再 bump 版本）、 OP_ENUM_DEF 常量池、enum_def_lookup_member_value 的 int64 出参、JIT callout、 enum_def_set_member。估算 300~500 行、跨 8 个文件。
  • dict 方案的两个真实代价（记录在案，别忘）：① 成员名写错从「编译期报错」退化为「运行期 null」； ② 名字→值与值→名字的映射要写两份（建议配一条 assert 测试锁住同步）。

7.2 更值得先做的两件（若将来真需要「更硬的 enum」）

两者都是加法，不破坏 int64 布局，也不影响缓存格式：

  1. 值 → 名字反查：E.name(v) 之类（日志/JSON/调试里想看 RED 而不是 1）。 运行期在 enum_def_lookup_member_value 旁加 enum_def_lookup_member_name， 符号表侧 member_names/member_values 现成可用。估 <100 行。
  2. 穷尽性检查（exhaustiveness）：switch 少写成员时报错。 现状确认：全仓 src/ 无任何穷尽性检查；且 enum 成员取值即折叠为 int （semantic_type.c 注释：「enum 成员访问返回 int 或 bigint…统一返回 int」）， 所以这层「类型身份」目前并未真正吃到 —— 要做就得先给 enum 补封闭集合语义。

7.3 设计取向（记下来，以后别再纠结）

enum 有意保持简单：成员值 = int64 常量 + 自动递增 + 编译期常量表达式， 不引入字符串值、不引入 ADT/带数据变体、暂不做穷尽性检查。
