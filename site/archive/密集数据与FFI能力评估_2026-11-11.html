密集数据运算与 FFI 能力评估（2026-11-11）

触发：外部评审看了 LenoSDL3/lib/sdl_renderer.leno（117 KB，大量 ffi.malloc + 手算 off + ffi.write_float）后提出三条建议：① 内置 std::vector / Span<T>； ② 支持 #[repr(C)] 的 struct 布局；③ 把 defer 普及成 Go 那样的强约束。

本文结论全部基于本仓库源码与 build\leno.exe 实测，不依据"别的语言有什么"。 文末的问题清单按 P0→P3 排，P0 / P1 / P2 本轮已修（状态与验收数据见各条）。

0. 实测数据（先看数）

基准：20 万个顶点 × 4 个 float（= 80 万次字段写；等价于一次 SDL_RenderGeometry 的顶点缓冲重建）。单进程、times.ms()（1 ms 精度）、重复三次取稳定值。

写法 修复前 修复后 内存形态 能否直接喂 C
ffi.malloc + ffi.write_float（sdl_renderer 现状） 9 ms 9~10 ms 3.2 MB 连续 ✅
Ptr[f32] + ffi.write_at 10 ms 10 ms 3.2 MB 连续 ✅
Vertex.malloc_array(N) + a[i].x = … 52 ms 5 ms 3.2 MB 连续 ✅
Array[struct] + new + add 68 ms 62 ms 20 万独立 GC 对象（约 20 MB） ❌ 元素是 8 字节 Value

读侧（acc += a[i].x，20 万次）：4 ms（融合指令，零视图分配）。

三条探针（build\leno.exe 实跑，修复前 → 修复后）：

p[0] = 1.0                 → [错误] 下标赋值: 对象不支持索引   → 正常读写 ✓
ffi.write_at(q, 100, 1.0)  → [错误] 内存访问越界               → 不变 ✓
q[-1] = 1.0                → 0xC0000005 崩溃（静默越界）        → [错误] 内存访问越界 ✓

1. 三条建议的判定

建议 判定 依据
① 内置 Buffer / Span 半个成立：容器已连续，卡的是元素表示 ObjArray{ Value* elements }（leno_value.h:337）+ typedef uint64_t Value（:127）⇒ Array[float] 每个元素 8 字节带标记，永远不能当 float*
② #[repr(C)] 的 struct 已实现，名字叫 cstruct packed / align(N) / 嵌套 / u8 data[1024] / &c.field / malloc_array(n) 连续数组 / ffi.call_* 自动把实例转指针（ffi.c:942）
③ defer / RAII 已实现且比 Go 强，但有一个比 Go 危险的语义 块级作用域、逆序、return/break/continue/throw 全触发（parser_stmt_other.c:22）；参数在块退出时求值，不是注册时

三条建议里唯一"确实缺"的是 ①：不是缺 Span 类型，而是缺打包数值数组（Array[f32] 真正按 4 字节连续存）。这一改造要动 arr_read/arr_write（全热路径 inline）、GC、写屏障、 类型检查与 ObjArray 序列化，收益却与 Ptr[f32] + 下标语法高度重合 ⇒ 本轮不做， 理由见 §3。

2. 真正该修的问题（按优先级，全部已修）

P0 — a[i].field 每次分配一个视图对象 ✅ 已修

现象：Vertex.malloc_array(n) 的连续数组本该是顶点缓冲的默认写法，实测却比手写 ffi.write_float 慢 5.8 倍（52 ms vs 9 ms / 20 万顶点）。

根因：object_cstruct.c:668

ObjCStruct* cstruct_array_get(ObjCStructArray* array, int index) {
    // 创建临时 cstruct 实例（不拥有内存）
    ObjCStruct* obj = (ObjCStruct*)gc_alloc(sizeof(ObjCStruct), OBJ_CSTRUCT);

每一次 a[i] 都 gc_alloc 一个视图。a[i].x = 1.0 这一行 = 1 次索引（分配视图） + 1 次字段写；20 万顶点 × 4 条赋值 = 80 万次 GC 分配。写路径还额外走 OP_INDEX_SET 的字符串下标分支（obj["x"] 形态）⇒ 每次再做一次字段名比较。

修复：新增两条融合指令（追加在 opcode 枚举末尾，序列化版本 bump 到 v3.2.33）

  • OP_CSTRUCT_ARR_GETF A B C + OP_EXTRAARG fi24：R[A] = R[B][R[C]].field(fi)

  • OP_CSTRUCT_ARR_SETF A B C + OP_EXTRAARG fi24：R[B][R[C]].field(fi) = R[A]

  • codegen：codegen_expr.c 的 AST_INDEX 分支（读）、codegen_stmt.c 的 gen_index_assign 与 gen_assign（写）三处发射 —— 语句位置的赋值走 gen_assign，只改 gen_index_assign 时基准一点没变（踩过一次，注释已写明）。

  • VM：12_fields_object.inc。标量字段用 C 栈上临时 ObjCStruct 直接算地址 （零 GC 分配）；"数组字段 / 嵌套 cstruct"仍走真视图对象（视图里存了父对象指针， 父对象必须在 GC 堆上）。f32 / i32 / f64 走 memcpy 快路径，其余类型回落 cstruct_set_field_value。

  • 校验：bytecode_verify.c 必须登记这两条（漏了就是"内存反序列化失败(6)"， 而 --check 全绿 —— 本次实测踩到）。

验收：52 ms → 5 ms（10.4x），反超手写 write_float；assert/test_cstruct_array_field.leno 覆盖读写/类型提升/数组字段视图/普通 struct 不受影响/越界。

P1 — Ptr[T] 不支持 p[i] ✅ 已修

现象（修复前）：

Ptr[f32] q = ffi.malloc(64)
q[0] = 1.0        → [错误] 下标赋值: 对象不支持索引   ← 运行期才报

根因：OP_INDEX / OP_INDEX_SET 没有 OBJ_FFI_POINTER 分支 （src/vm 里 OBJ_FFI_POINTER 只出现在 12_fields_object.inc / vm_exception.inc）。

修复：VM 两条指令里补分支，语义复用 ffi.read_at / write_at（ffi.c 的 ffi_vm_index_read / ffi_vm_index_write 是薄包装）—— 元素宽度、越界口径、装箱拆箱 只有一份实现。报错走 throw_pending_exception（与 OP_CALL_NATIVE 同口径）。

附带发现（真 bug，已修）：CHECK_BOUNDS 只有 (size_t)offset + access_size > size，负偏移会回绕：q[-1]（offset=-4、size=16） 得到 (size_t)(-4)+4 == 0，0 > 16 为假 ⇒ 检查静默放行 ⇒ 往 ptr-4 写 ⇒ 0xC0000005。现在 offset < 0 与正向越界走同一条报错。 ⚠ 这条改动了 assert/test_ffi_inline_widths.leno 里一条旧契约（原注释写着"负偏移 -1 必须回绕成 0，任何实现都必须如此，不许顺手加检查"）—— 那条契约本身就是内存破坏 的口子（读路径 -1 读到 p[0] 只是运气），已在该测试里写明废除理由。

验收：assert/test_ptr_index.leno（f32/i32/u8 读写、与 read_at/write_at 逐值一致、 越界/负下标/释放后使用/非整数下标全部抛异常）。

P2 — defer 的参数"退出时求值"是静默陷阱 ✅ 已加提示

现象（assert/test_defer.leno:58-61 就是这么测的）：

var name = "first"
defer order.add(name)
name = "second"        // ⇒ 实际入队的是 "second"

Go 是注册时求值参数，Leno 是块退出时求值。对 defer ffi.free(p) 来说， 中间若把 p 改指向新缓冲，释放的是新值 ⇒ 旧缓冲泄漏。

修复（只提示、不改语义）：parser 里新增 WARN_DEFER_LATE_WRITE —— 收集 defer 表达式里能静态看到的变量名，扫本块顶层语句里是否有赋值把它改掉。判据极保守 （宁漏勿误报），嵌套块里的赋值不追。

实测踩到的三个坑（都在 parser 阶段，注释已写）：ffi.free(p) 是 AST_MODULE_CALL 不是 AST_CALL；语句位置的赋值被包在 AST_EXPR_STMT 里；赋值的主数据是 assign.targets[]（names[] 可能没填）。

验收：

defer ffi.free(p) 之后 p = ffi.malloc(32)   → 警告 ✓
defer ffi.free(q) 之后没有对 q 赋值         → 不报 ✓
defer ffi.free(saved) 之后改 p              → 不报 ✓

P3 — Buffer 门面（评估后不做）

Ptr[f32] + p[i]（P1）+ ffi.memcpy / ffi.memset 已经覆盖 vector<float> 的 全部实际用法；再包一个 Buffer 只是应用层几十行代码，不值得占标准库命名空间。

3. 为什么不做"打包数值数组"

  • arr_read/arr_write 是 static inline 且被 VM 所有数组指令内联调用， 改表示等于给全语言最热的路径加一次分支；
  • Array[float] 现在能与 Array[int] 互相赋值/切片/map/filter，打包后要处理 "打包数组 ↔ 装箱数组"的边界转换（每处容器操作都要问一句"对面是什么形态"）；
  • 真正需要 C 连续内存的场景已经由 cstruct 数组 + Ptr[T] 覆盖， 而且 P0 修完之后它们比手写 write_float 还快。

4. 结论

外部建议指出的症状（手算 offset、大量 ffi.malloc）是真的，但它推断的病因 （缺 repr(C)、缺 Span、缺 defer）三条里有两条 Leno 早已实现。sdl_renderer.leno 真正卡住的是 a[i].field 的视图分配（P0），其次是 Ptr[T] 缺下标糖（P1）。 两者的共同点：都是"已经能写、但写法丑陋/悄悄变慢"，而不是"写不出来"。

修复后 sdl_renderer.leno 这一类顶点缓冲代码可以放心写成 Vertex.malloc_array(n) + vs[i].x = …（比手工偏移快），Ptr[T] 也可以直接 p[i]。

6. 第二轮压测（2026-11-11，奇葩组合）

五套脚本：融合指令 × 控制流（异常/finally/闭包/异步/break-continue）、Ptr × 闭包/异步/ 嵌套指针/链式、cstruct 视图生命周期、cstruct × 裸 FFI 指针同一块内存、Ptr 元素类型 在字段/返回值/实参处是否存活。又挖出 4 个问题：

现象（实测） 根因 修法
var e = a[0]; a.free_all(); e.x 静默读到 1 元素视图 owns_memory = 0，data 指向数组那块内存；数组 free 后视图毫无察觉（内存没被覆盖时读到旧值，覆盖后就是垃圾） ObjCStruct 回指父数组（owner_arr）+ GC mark；free_all 后 data == NULL ⇒ 字段读写报「cstruct 数组已释放」
var b = makeBuf(8)（func makeBuf(): Ptr[u8]）里 b[0] 报「需要 Ptr[T] 类型指针」 OP_SET_PTR_ELEM_TYPE 只在 var_decl 发射；Ptr[T] 的 T 不在裸 void* 里 ⇒ 函数返回值丢了标注（写成 Ptr[u8] b = … 就正常） return 处按声明返回类型补发；并强制走临时寄存器（标注是就地改对象，落在变量槽会改掉那个变量本身的类型）
useBuf(ffi.malloc(8))（形参 Ptr[u8]）里 p[0] 报同样的错 同上，实参位置也没标注 gen_call_args_to 按形参类型补发（方法调用跳过：形参表含 self、实参槽错开一位）
V3.malloc_array(2000000000) 分配失败时静默返回 null cstruct_array_new 返回 NULL 时没人报 明确抛「malloc_array 分配失败（内存不足，或元素个数过大）」

Ptr[Ptr[T]]（C 的 char**）现状：声明、写入、读回、传参、二级指针出参全部支持 （类型树完整：Ptr[Ptr[u8]] 是 40/40/18，见 type_copy 对 PTR 的递归）； assert/test_ptr_ptr_charpp.leno 是 argv 风格的完整示例（造 char*[] → 遍历 ffi.read_string → 显式标注后按字节访问 → func(char**) 形态的出参 → 逐层 free）。

元素类型的"第二层"已经补上（§7）：原先 ObjFFIPointer.element_type 只有一个 TypeKind（一层），Ptr[Ptr[u8]] 的第二层在运行期丢失 ⇒ 只能靠 codegen 在 5 个 "值落点"补标注，var x = pp[0] 这种纯推断拿不到。现在元素是复合类型时改发 OP_SET_PTR_SPEC（带整棵子类型树），ffi.read_at 读 PTR 元素时剥一层给新对象 ⇒ 逐层自然正确，var x = pp[0]; x[0] 直接可用。

仍存的边界（与本次改动无关）：Ptr[cstruct] 只能存取指针本身（传给 C 用）， p[0].v 按元素解引用还不行 —— ffi.read_at 的元素类型表里没有 CSTRUCT。

验收：断言 600/600（新增 test_cstruct_view_lifetime / test_ptr_elem_type）； 五套压测脚本 ALL PASS；examples 的 cstruct / ffi / clib + LenoSDL3/lib 全目录 --check 0 失败。

7. Ptr[T] 的元素类型：从"一层 TypeKind"到"完整规格"（2026-11-11）

问题

ObjFFIPointer.element_type 是单个 TypeKind，只能表达一层。Ptr[Ptr[u8]] 在运行期 只知道"指向某个指针"，第二层 u8 丢失 ⇒ pp[0] 读出来是"无元素 Ptr"。

后果是标注点必须穷举：OP_SET_PTR_ELEM_TYPE 要散落在 var_decl / 变量赋值 / 结构体字段 / 函数返回 / 调用实参 五处，漏一处就是"静默不可用"（p[0] 报 「需要 Ptr[T] 类型指针」）。var x = pp[0] 这种纯推断更是直接拿不到。

方案

元素是复合类型时，把整棵子类型树写进对象：

  • 新 opcode OP_SET_PTR_SPEC（iABC 头 + 自定界类型规格）—— 复用 OP_TYPE_CHECK_SPEC 的同一套规格格式与 type_spec_size（发射端 / 判定端 / 反汇编端只有一份长度实现）。标量元素仍走紧凑的 OP_SET_PTR_ELEM_TYPE ⇒ 既有字节码逐位不变。
  • ObjFFIPointer 增加 uint8_t* elem_spec（malloc 拷贝，随对象释放； element_type 仍记第一层，所有既有读 element_type 的代码零改动）。
  • ffi.read_at 读 PTR 元素时剥一层：pp 的 elem_spec 描述"元素类型 = Ptr[u8]"， 读出来的指针本身就是那个 Ptr[u8] ⇒ 它的 element_type = spec 的第二层（u8）， 更深的继续挂在自己的 elem_spec 上。三层 Ptr[Ptr[Ptr[u8]]] 也逐层正确。
  • 发射点收敛成一个 emit_ptr_elem_annotation（标量→紧凑版 / 复合→规格版）， var_decl / 返回 / 实参 三处都改调它。

效果

Ptr[Ptr[u8]] pp = ffi.malloc(8)
Ptr[u8] inner = ffi.malloc(4); inner[0] = 65
pp[0] = inner

var auto = pp[0]        // ← 不写 Ptr[u8]
auto[0]                 // 65 ✓（规格随指针传递，不再依赖落点标注）

三层同理：ppp[0] → Ptr[Ptr[u8]]、[0] → Ptr[u8]、[0] → 字节。

改动清单（新增 opcode 的 7 步全走了一遍）

leno_vm.h（枚举末尾）/ 01_prologue.inc（跳转表）/ 12_fields_object.inc（handler）/ debug.c（名字表，顺序必须与枚举一致）/ bytecode_verify.c（登记 + spec_scan 算长）/ leno_serialize.h（v3.2.34 / modcache v49）/ build_vm.bat（打包运行时必须同步重建）。

验收

assert/test_ptr_nested_spec.leno：两层 var 推断、三层逐层剥、Ptr[Node] 字段存取、 显式标注老写法不回归。断言 603/603；examples + build/leno_module 全量 --check 只剩 2 个与本次无关的既存失败（LenoWeb 的 gen 模块类型导入）。

8. 并发与 cstruct / Ptr 的边界（2026-11-12 实测）

结论先行：cstruct / Ptr 这类裸 C 内存在 Leno 里有三条不同的边界， 必须分清，否则会以为"跨线程被禁了"或者"跨线程是安全的"。

通道 行为 时机
threads.start(f, x) 传参 拒绝（cstruct 是裸内存，没有可安全深克隆的语义） 编译期（静态类型确定为 cstruct）
ch.send(x) 通道 拒绝 cstruct / Ptr / 闭包；被拒时不入队（不留幽灵槽） 运行期（channel_clone_reject）
全局变量里的 Ptr[T] / cstruct 共享（同一进程地址空间）—— 线程写、主线程立刻可见 无任何检查

第三条最容易踩：它不是"传递"，所以 clone 闸门根本不经过 —— 实测

cstruct V3 { f32 x  f32 y  f32 z }
Ptr[V3] g_buf = null                      // 全局

func worker(int n): int {
    g_buf[0].x = 1.5                       // 直接写共享内存
    return _int(g_buf[0].x * 10.0)
}

main() {
    g_buf = ffi.malloc(12)
    g_buf[0].x = 0.5
    var t = threads.start(worker, 1)
    print(_str(t.join()))                  // 15
    print(_str(g_buf[0].x))                // 1.5 ← 主线程看到了子线程的写
}

⇒ 同一块裸内存被多个线程写就是数据竞争，Leno 不做检测（也不可能零成本检测）。 可用做法：

  1. 一块内存只归一个线程写（最省事）：worker 各自 ffi.malloc 自己的缓冲， 结果用 Channel 传纯数据（标量 / string / Array / struct）回来；
  2. 需要共享时自己做互斥（Leno 侧暂无 Mutex，把临界区交给 C 侧或串行化）；
  3. 只读共享是安全的（多个线程同时读同一块内存没有竞争）。

回归用例：assert/test_thread_cstruct_boundary.leno（①编译期拒绝、②通道拒绝且逐条对应、 ③全局 Ptr 共享可见）。

9. 收尾三项：越界策略 / union / 位域（2026-11-12）

9.1 Ptr[T] 的越界策略：size 已知就查

原判据是 owned && size > 0，而 cstruct.to_ptr() 早就把 size 填成"实例大小 / 数组总字节数" （owned = 0）⇒ 这份已知大小被完全忽略：Ptr[V3] p = arr.to_ptr(); p[999].x 照样越界读。

  • CHECK_BOUNDS 改为 size > 0 就查（不再要求 owned）；
  • size == 0（C 侧返回的裸指针）无从可查 ⇒ 维持裸指针语义；
  • 新增 ffi.bind_size(ptr, n)：把"已知字节数"挂到指针上，之后 p[i] / read_at / write_at 都走边界检查（返回同一个指针对象，可链式用）。负数被拒。
  • ⚠ 哨兵与 size 分离：ObjFFIPointer 新增 alloc_size（真实分配大小），ffi.free 的尾部 哨兵按它定位 —— 否则 bind_size 收紧 size 后，哨兵会读到缓冲区中间、误报「堆缓冲区溢出」。

用例：assert/test_ptr_bounds_policy.leno。

9.2 union（C 布局联合体）

语法与 cstruct 一致，只是布局不同：所有字段偏移 0，总大小 = 最大字段（按最终对齐取整）。 字段表 / 读写 / 数组字段 / 嵌套 / to_ptr / size / offset_of / malloc_array 全部复用 cstruct 的实现 —— 只有布局那一段分叉。

union U { i32 i  f32 f  u8 bytes[4] }
U.size()          // 4
U.offset_of("f")  // 0
u.i = 1065353216  // 0x3F800000
u.f               // 1.0   ← 类型双关

⚠ union 现在是保留字（与 cstruct 同级）；把它当函数/变量名的代码会报 「union 现在是保留字……请换一个」。仓库内 examples/泛型系统/集合运算/test_set_ops.leno 的 func union 已改名 setUnion。

限制：union 里不支持位域（C 的各编译器对 union 位域布局不一致，明确报错而不是给错布局）。

用例：assert/test_cstruct_union.leno。

9.3 位域（u32 flags : 3）

布局按 C 的常见规则（小端）：

  • 同类型、能塞进当前存储单元 ⇒ 从 LSB 起接着排；
  • 类型变了 / 塞不下 ⇒ 按类型对齐开新单元；
  • 单元大小 = 声明类型大小；field->offset 是单元起始，bit_offset 是单元内位偏移。

读：取单元 → 右移 → 掩码；有符号类型做符号扩展（i32 s : 4 写 -8 读回 -8）。 写：读-改-写，只动自己那几位（邻居不受影响；写超宽按位截断）。

实现要点： - CStructFieldInfo 增加 bit_offset / bit_width； - OP_CSTRUCT_DEF 的字段表每字段 +2 字节（bit_offset / bit_width）⇒ 写端（codegen）、 读端（VM handler）、反汇编（debug）、字节码校验（bytecode_verify 的 scan_cstruct_def） 四处必须同步，LENO_BIN_VERSION v3.2.37 / modcache v52 一并升； - OP_CSTRUCT_ARR_SETF 的 f32/i32/f64 快路径必须绕开位域（它们按整字段宽度 memcpy， 会把同一单元里的相邻位域一起冲掉）。

限制：只支持小端；不支持 union 里的位域；宽度必须 ≤ 声明类型的位数、不能是数组。

大端护栏（2026-11-12）：位域按小端打包，大端平台上位序会反、且没有任何提示 ⇒ 语义层在定义位域时直接编译报错（LENO_HOST_BIG_ENDIAN 编译期宏，运行时零开销）。 LENO_FORCE_BE=1 是测试钩子：小端机器上也能验证这条报错（否则这段代码在所有 CI 上 都永不执行）。

用例：assert/test_cstruct_bitfield.leno。

9.4 深度 ≥3 的 Ptr（决定：不做，但把报错改成"指路"）

现状：Ptr[Ptr[cstruct]]（深度 2）完全可用（var auto = pp[0] 也行）；深度 3 （Ptr[Ptr[Ptr[V3]]]）只有 var x = ppp[0] 这条纯推断路径拿不到最内层的 cstruct 定义，得到的是可控报错，不是静默错值。显式标注后深度 3 照常工作：

Ptr[Ptr[V3]] mid  = ppp[0]     // ✅
Ptr[V3]      leaf = mid[0]     // ✅

为什么不做（评审结论）：

  • C 里 T***（结构体三级指针）基本是"语言没有容器"的补偿写法；Leno 有 Array[T] / Array[Array[T]] / cstruct 数组，没有出现它的理由。真实边界上的 char*** 是 Ptr[Ptr[Ptr[u8]]]，与 cstruct 无关，本来就能用。
  • 要做彻底，缺的是一层运行期类型链（read_at 在 ffi 层没有 chunk，解析不了规格里的 名字常量 ⇒ 得把"指针 → … → cstruct 定义"整条链在标注期预解析成 GC 节点）， 还要动 emit_type_spec / type_spec_size / spec_scan / type_spec_match 四处 同构代码 —— 为一个几乎不存在的写法去改当前工作正常的两层路径，风险大于收益。

本轮只改报错（2026-11-12）：原来只说「Ptr[cstruct] 缺少元素类型信息（请写成 Ptr[类型名]）」，用户不知道该标哪一级。现在：

Ptr[cstruct] 缺少元素类型信息：这一级指针不知道自己指向哪个 cstruct
（常见于**深度 ≥3 的指针**，如 `ppp[0]` 的结果）——
请显式标注一次元素类型：`Ptr[V3] x = ppp[0]`

同一手处理了「无类型 Ptr」那条（read_at / write_at）： 「……当前是无类型 Ptr —— 常见于嵌套指针的下标（如 pp[0]）或 C 函数返回的裸指针； 请显式标注一次元素类型：Ptr[u8] x = pp[0]」。

用例钉住：assert/test_ptr_ptr_cstruct.leno 的 ④ 段（断言文案含「深度 ≥3」与 Ptr[V3] x = ppp[0]，并验证显式标注后深度 3 可读）。

验收

断言 615/615；examples + build/leno_module 全量 --check 只剩 2 个既存无关失败； build.bat + build_vm.bat 均已重建（ObjFFIPointer / CStructFieldInfo 布局与字节码格式都变了）。
