Leno 报错提示改进计划

⚠ 局部过时（2026-10-02 注）：文中"已在 op_utils.inc 的 OP_INDEX 增加排查提示" ——op_utils.inc 是栈式文件，已删除（0f0cf52）⇒ 勾选项的落点需按现行 src/vm/vminc/run/*.inc 复核；清单本身（哪些报错该更清楚）仍可作现行待办。

背景：在集成 Blend2D + LenoSDL3 的开发过程中，反复遇到了若干"编译器无提示、运行时才崩溃"或"提示过于模糊"的问题。本文档系统性地梳理这些问题，按优先级给出改进方案并落地实施。

一、问题清单与归类

A1 Blend2D 函数名记错 bl_context_set_stroke_width_d 该函数没有 _d 后缀 已修复
A2 clib 签名漏参数 fill_path_d(self, origin, path) 实际 3 参数 已修复
A3 cstruct 值类型与堆指针错配 用值类型字段存 malloc() 的堆指针 已修复

二、改进方案（按优先级）

改进 1（高）：clib 调用接收方为空时给出明确报错

现状：_b2d.bl_xxx(...) 里 _b2d 若为 null，语义检查不拦（TYPE_CLIB 类型），运行时直接解引用崩溃。

目标：在 codegen 或运行时把"clib 接收方为 null"转为可读错误。

实施位置：clib 调用 codegen（src/codegen）。

改进 2（高）：运行时 null 索引报错补充上下文

现状：op_utils.inc 只输出 value_type_desc(obj_val)。

目标：报错中附加源码行号（已有）+ 尽量提供操作上下文。

实施位置：src/vm/vminc/op_utils.inc（已有行号），增强文案描述。

改进 3（中）：ffi.load 全失败时给出汇总提示

现状：lib() 里 7 个候选路径都失败时 g_b2d 保持 null，无提示。

目标：当 ffi.load 从未被成功调用（或全部候选失败）时，提示"所有候选路径均未找到库"。

实施位置：sdl_blend2d.leno 的 lib()（脚本层包装）+ ffi.c 加载失败文案已有，可补充候选路径汇总。

改进 4（中）：跨模块 clib 增加"空接收方"提示

现状：第 417-420 行"允许任意调用"导致 null.bl_xxx 无编译期提示。

目标：当接收方类型为 clib 但值为 null 时，在语义阶段给出警告或运行时明确报错。

实施位置：src/semantic/visitinc/visit_expr.inc + codegen。

改进 5（高，2026-10-11 登记）：嵌套字段赋值的报错 —— 要么支持它、要么说清"这条路没通"

现象（最小复现 12 行，实测 2026-10-11 ✓）：

struct Inner {
    float value = 0.0
}

struct Outer {
    Inner inner
    func f() { inner.value = 1.0 }     // ← 报的就是这一行
}

error: [类型不匹配] 字段 'inner' 类型不匹配: 期望 'struct Inner'，实际 'float'

为什么误导：报的字段名是外层字段 inner、期望类型是外层字段的类型、实际类型是 右边那个值的类型 —— 读起来像"你把 float 赋给了 struct 字段" ✗，可源码里压根没有 "给 inner 赋值"这回事（写的是 inner.value ✓）。真正的问题是"嵌套成员赋值 （字段.字段 = v）这条路没走通" ✓，报错却把靶子立在别处 ⇒ 照着它去查 RHS 表达式 / 字段声明，查不出所以然（本次就是这么被带偏的：还一度误判成"value 是关键字"✗， 实测 value 当字段名/读/写都完全正常 ✓ —— 换任何名字一样报 ✓）。

边界（同一份探针里逐格实测 2026-10-11 ✓）：

接收者是 写法 结果
本 struct 的字段 inner.value = x ✗ 报上面那条
局部量（new 出来的） o.inner.value = x ✅ 正常编译
参数 func g(Outer o) { o.inner.value = x } ✅ 正常编译
局部量（绕一手 copy） Inner c = inner; c.value = x; inner = c ✅ 正常编译
本 struct 的标量字段 other = x ✅ 正常编译

⇒ 只差"基座是自己的字段"这一格 ✗ ⇒ 更像编译器 bug（不是有意的语言限制： struct 是引用语义，o.inner.value = x 与 inner.value = x 语义上是一回事 ✓）。

两种修法（择一，都能让这条误导消失）：

  • ①（推荐）把它支持起来：字段.字段 = v 按"先取外层字段（引用）⇒ 再写内层字段"处理 ⇒ 与 o.inner.value = v 走同一条路，报错自然没了 ✓（也顺手消掉一类"合法代码被拒" ✓）；
  • ② 若确实不打算支持：报错要说到点上，例如 「嵌套字段赋值暂不支持：'inner.value' —— 可以先取出来改再放回： Inner c = inner; c.value = …; inner = c」✓ ⚠ 且不能再用"字段 'inner' 类型不匹配"这种把外层字段当靶子的文案 ✗。 文案口径照本文档「改进 1 / 改进 2」那两条的先例：说清"差什么" + 顺手给一句"怎么改" ✓。

实施位置（本次只定位到这两处，未逐行走查 ✗ —— 开工前先把这一段补完）：

  • 赋值目标的解析：src/parser/parser_expr.c:1237-1307（左值是 AST_MODULE_ACCESS 时建 AST_ASSIGN{names[0] = module_name, targets[0] = <module_access>} —— 注意 names[0] 取的是 最左边那个名字 ✓ 与报错里的 inner 吻合 ✓）；
  • 报错来源：src/semantic/visitinc/visit_expr.inc:400 （AST_INDEX_ASSIGN 的 struct 分支 "字段 '%s3' 类型不匹配: 期望 '%s1'，实际 '%s2'"， field_name 取自 ast->u.index_assign.index 的字符串 ✓ —— 即那条被脱糖出来的"单层"字段名 ✓）；
  • ⚠ 同一个分支还吃 .field = v / pa["x"] = v / pa.x += v 的脱糖形态（见该段注释 ✓） ⇒ 动它要连带回归 assert/test_diag_static_errors.leno 与 examples 全量扫描 ✓。

✅ 已修（2026-10-11）：按上面的修法 ①（把它支持起来）+ 顺带补了"成员不存在"的编译期诊断

真因不在上面那两处定位里（照那两处查会查空 —— 记一笔，免得下次又绕）：报错确实出自 visit_expr.inc 的 AST_INDEX_ASSIGN struct 分支，但让它"指错靶子"的是前一步： src/semantic/semantic_visit_method.c 的 transform_method_body_ex（case AST_ASSIGN）里那条 "裸字段名 ⇒ self[字段] = 值"的整句重写 —— 它只看 names[i]（最左边那个名字）， 于是把 inner.value = 1.0 改写成 self["inner"] = 1.0：末级成员被丢掉 ⇒ 期望类型变成外层 字段的类型、实际类型变成 RHS 的类型 ⇒ 报出那条假错 ✗。（而 o.inner.value = v 走的是 parser 的 AST_INDEX_ASSIGN 分支，不经这里 ⇒ 才出现"两种写法行为不一致"✓）

改动两处

文件 改动
src/semantic/semantic_visit_method.c case AST_ASSIGN：targets 已被 transform 成嵌套访问（AST_INDEX）时，按"先取外层字段（引用）⇒ 再写内层字段"收尾 —— 直接复用 targets[i] 的 obj/index 建 AST_INDEX_ASSIGN，不再按裸字段名整句重写 ✓（与经局部量/参数走同一条路 ✓）
src/semantic/visitinc/visit_expr.inc 同分支补：字段表已知（struct_def_sym 拿得到、字段数 > 0）却查不到这个名字，且 infer_field_type 也落空 ⇒ 报 struct 'X' 没有字段 'y'（与读路径同一句文案，读写对称 ✓）。加了 field_table_known 闸门 ⇒ "struct 定义不在当前作用域"（跨模块等，两级都查不到）不报，避免误伤 ✓

改进 6（中，2026-10-11 登记）：--check 的检查范围要说清（或补齐）

现象（实测 2026-10-11 ✓，见 语言陷阱速查.md §四 的表）：把带类型错误的模块放进 import，--check 入口 打印「检查通过」✗ —— 哪怕入口真的调用了那个坏函数 ✓； 而同一个坏模块自己当入口时 --check 会报 ✓；真编译/真跑当然也报 ✓。

目标（择一）： - ① 让 --check 也把被引用模块的函数体过一遍（代价：慢一些；好处："改完 check 一下"才名副其实 ✓）； - ② 至少在输出里说清范围 —— 例如结尾打印 「检查通过（仅入口文件；被 import 的模块函数体未检查 ⇒ 发版前请真编译一次 ✓）」 ⇒ 这个更便宜，且能掐掉"我已经 check 过了"这种假安心 ✓（B6 正是这么混过去的 ✓）。

实施位置：src/main.c 的 --check 分支（① = 走完整模块语义；② = 只改收尾文案 ✓）。

✅ 已按 ② 落地（2026-10-11）

src/main.c 的 --check 收尾改两行：第一行把范围写进"检查通过"里，第二行点名边界并给出正解：

检查通过: <入口文件>（仅入口文件；未产出 .lenb）
          ⚠ 被 import 的模块「函数体」未检查 —— 发版前请真编译一次：leno -c <入口>

⚠ ① 当时没做，理由（代价 + 风险，不只是"慢一点"）：要让 --check 真去过模块体，就得把模块编译 管线（parse + 语义）对每个被引用模块跑一遍，同时还得管住 .lenomc 缓存写入（--check 现在 的卖点之一正是"无副作用" ✓）与错误归属（模块编译自己有一套 errors.count 前后差分， 见 module_compiler.c ✓）⇒ 收益不抵风险 ✓ —— 想查模块体时：-c 一次，或对那个模块自己 跑 --check（它自己当入口时，函数体是查的 ✓，本轮 52 个库文件的回归就是这么做的 ✓）。

✅ ① 已落地（2026-10-20）—— 而且比预想的便宜

用户判断：「--check 我认为没啥暖用」——成立。实测：模块里放 int x = "oops"， --check 打印"检查通过"，-c 才报错；而 --check 只比 -c 快 28ms（39 vs 67ms）⇒ 用一个不可信的结论换 28ms，不值。

根因（比原判断简单得多）：模块是在 codegen 遇到 OP_IMPORT 时才真正编译的 （DCE 需要完整引用图，见 main.c 的 compileMode 注释）。旧 --check 早退在语义之后、 codegen 之前 ⇒ 模块根本没被编译 ⇒ 当然查不到。

修法：把早退点从"语义之后"挪到"codegen 之后、serialize 之前"（main.c 的 lenolang_compile）。 不用碰模块加载管线、不用管错误归属 —— 那些担心在"复用现有编译流程"面前都不成立。

代价（实测）：--check 也要跑 codegen ⇒ site.leno 39ms → 38~45ms（-c 是 63ms）。 副作用：模块 .lenomc 缓存照常写（与 -c 一致，缓存可重建）。成功文案改为 「编译检查通过: <入口>（未产出 .lenb）」。

回归：assert/test_check_flag.leno 改成三条 —— ① 好文件退出 0 且不产出 .lenb；② 模块里的类型错误必须被抓（点名模块文件）；③ 入口自身错误 ✓ （原先那条"钉住边界仍然存在"的 ④ 已随 ① 落地改成 ② 的正向断言 ✓）

  • clib 本文件定义时已有参数数量/类型校验（visit_expr.inc:360-378）。

五、2026-10-20：写 LenoHTTP 时撞到的两个报错问题（都已修）

1. if (a) == b then … 报「if 表达式需要使用 'then' 关键字」—— ✅ 已修（解析 bug）

现象：if (id + 1) == 4 then 10 else 20 编译失败，报"if 表达式需要使用 then"； 而 if (id + 1 > 4) then ... 正常。写 out.send(if (r as string) == expect then 1 else -3) 时撞到，第一反应是"我忘写 then 了" ✗

根因（src/parser/parser_expr.c 的 parse_if_expr）：看到 if 后面是 ( 就手工消费 它、再 consume(')')，等于假设"括号正好包住整个条件"。于是解析完 (id + 1) 就去找 then， 撞上 == ⇒ 报「需要使用 then」。而 (a) == b 在普通表达式里完全合法 ⇒ 报错误导 ✗

修法：条件整体交给 parse_expression（括号由分组规则处理），删掉手工消费。 覆盖：(a > b) / (a) == b / and 链 / 嵌套 if 表达式 / eif 链 / 条件里带函数调用。 用例 assert\test_if_expr_paren.leno（7 条断言）。

2. Dict opts = {} 报「默认值必须是字面量常量」—— ✅ 文案已改

现象：{} 明明是字面量，报错却说"必须是字面量常量或编译期常量表达式" ⇒ 自相矛盾， 让人以为是"我写错语法了"，实际是"数组/字典字面量不支持作默认值"。

修法（src/semantic/semantic_visit_func.c）：单独识别 AST_DICT / AST_ARRAY，文案改为

参数 'opts' 的默认值不支持 数组/字典 字面量 —— 请改用 null（函数内判空）或模块级常量

附带影响：http.get(app, path, handler, Dict opts = {}) 因此写成 any opts = null（函数内判空）。 这是受该限制影响的真实写法，见 LenoHTTP/lib/http_app.leno。

3. x.use(...) 报「期望属性名」+「use 语句期望模块名」—— ✅ 已改成说清"保留字"

现象：给 LenoHTTP 加中间件时把方法名起成 use（http.use(app, fn)）：

error: [语法错误] 期望属性名          ← 看不出是 `use` 的问题
error: [语法错误] use 语句期望模块名   ← 更远，因为 `use` 又被当成语句开头

根因（parser_expr.c 的 parse_dot）：. 后面不是标识符时，旧代码只区分 "内建类型关键字"与"其他"两种，后者一律说「期望属性名」；而 use 恰好在"其他"里。 报错后返回也没吞掉这个 token ⇒ 外层又把它当语句开头，再报一条。

修法（与 M5b 的「保留字撞名」同族，parser_func.c 的参数名那处同款）：

error: [语法错误] 'use' 是**保留字** ✗ 不能用作方法名/字段名 —— 换个名字（如 before / apply / with）；
       若确实要用这个键名，写成 x["use"] ✓
  • parse_dot 与 parse_safe_dot（?.）都改
  • 报错后 lexer_next 吞掉非法 token，避免它再被当语句开头
  • 用例：assert\test_diag_static_errors.leno 的 E2 组（f.use(1) ⇒ 文案含"是保留字"，落点行 3）
  • ⚠ 仍会伴随 1–2 条「期望 ')'」之类的级联（解析器恢复的老问题，见 T20）； 但第一条就是真因，不再把人往"忘写属性名"上引
