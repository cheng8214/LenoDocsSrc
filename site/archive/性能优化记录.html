Leno 性能优化记录

⚠ 历史结论（2026-10-02 注）—— 本文描述的是栈式 VM。 文中引用的 src/vm/vminc/op_call.inc、op_jump.inc、op_variables.inc、op_constants.inc、 op_type_specialized.inc、op_arith.inc、op_string.inc、op_for_loop.inc 在寄存器式改造中 已全部删除（0f0cf52），现行解释器是 src/vm/vminc/run/01_prologue.inc … 14_switch_for.inc 与 vm_*.inc；vm.stack[]/vm.sp 在寄存器式下只余少量记账。 部分"已回退"的操作栈优化（如 vm_stack_push_fast 相关）对现行实现已无对应关系。 数据与取舍留作历史对照，现行性能结论见 docs/待办与路线图.md。

优化目标

将 fib(30) 的执行时间从 280ms 优化到 170ms（double 模式下的最佳性能）

当前状态（安全版本）

  • 优化前: 280ms
  • 当前: 187ms (最佳)
  • 目标: 170ms
  • 差距: 17ms

优化进展

阶段 时间 优化内容 状态
初始 280ms - ✅
GC优化 210ms 移除VM循环中的gc_check_safe_point ✅ 保留
栈操作优化 203ms 引入vm_stack_pop/push/peek_fast ⚠️ 部分保留
全面优化 187ms 移除大量不必要的frame更新 ⚠️ 部分回退

优化状态更新

已保留的优化

  1. ✅ gc.c - GC 检查点移到 gc_alloc
  2. ✅ vm_run.inc - 移除操作码合法性检查（性能提升明显，整体变快）
  3. ❌ op_type_specialized.inc - 类型特化指令使用快速栈操作 已回退 (2026-08-14)
  4. ✅ op_arith.inc - 算术指令移除不必要的 frame 更新
  5. ❌ op_jump.inc - 跳转指令优化 已回退 (2026-05-28)
  6. ❌ op_call.inc - 函数调用优化 已回退 (2026-05-28)

回退的优化

由于稳定性问题，以下优化被回退：

  1. ❌ op_constants.inc 中的快速栈操作
  2. ❌ op_variables.inc 中的部分快速栈操作
  3. ❌ 部分快速栈操作 (vm_stack_pop_fast, vm_stack_push_fast, vm_stack_peek_fast) - 2026-05-28 回退
    • 涉及文件: op_call.inc, op_jump.inc, op_variables.inc
    • 原因: 更多排序.leno 测试失败，这些指令中的快速栈操作在复杂场景下导致栈边界错误
    • 例外: op_type_specialized.inc 中的快速栈操作已恢复，因其栈操作确定且由编译器生成，相对安全

当前性能

  • fib(30): 203ms
  • 整体性能: 提升明显（数组测试等变快）

优化详情

1. GC 检查优化 (gc.c)

文件: src/gc.c

修改内容:

  • 将 gc_check_safe_point() 从 VM 主循环移回 gc_alloc 函数
  • 只在内存分配完成后检查，减少检查频率

代码变更:

// 在 gc_alloc 函数末尾添加
if (gc_requested && gc.enabled && !gc.running) {
    gc_check_safe_point();
}

性能影响: 从 280ms 提升到 210ms

风险: 低 - GC 检查点从指令边界移到分配点，对象已初始化，状态相对安全

2. 快速栈操作函数 (leno_vm.h)

文件: src/include/leno_vm.h

新增函数:

vm_stack_pop_fast

// 栈操作：弹出值（不检查下溢，用于性能关键路径）
static inline Value vm_stack_pop_fast(VM* vm) {
    return vm->stack[--vm->sp];
}

vm_stack_push_fast

// 栈操作：压入值（不检查溢出，用于性能关键路径）
static inline void vm_stack_push_fast(VM* vm, Value v) {
    vm->stack[vm->sp++] = v;
}

vm_stack_peek_fast

// 栈操作：查看栈顶值（不检查边界，用于性能关键路径）
static inline Value vm_stack_peek_fast(VM* vm, int distance) {
    return vm->stack[vm->sp - 1 - distance];
}

风险: 中 - 只在确定栈状态安全时使用，否则会导致未定义行为

3. 快速整数运算宏 (vm_helpers.inc)

文件: src/vm/vminc/vm_helpers.inc

新增宏:

  • PUSH_INT64_RESULT_FAST - 使用 vm_stack_push_fast
  • PUSH_SAFE_INT64_ADD_FAST - 使用 vm_stack_push_fast
  • PUSH_SAFE_INT64_SUB_FAST - 使用 vm_stack_push_fast
  • PUSH_SAFE_INT64_MUL_FAST - 使用 vm_stack_push_fast

风险: 中 - 只在类型特化指令中使用

4. 类型特化指令优化 (op_type_specialized.inc)

文件: src/vm/vminc/op_type_specialized.inc

优化内容:

  1. 移除不必要的 frame = &vm.frames[vm.frame_cnt - 1]; 更新
  2. 使用 vm_stack_pop_fast 替代 vm_stack_pop
  3. 使用 vm_stack_push_fast 替代 vm_stack_push
  4. 使用快速整数运算宏

涉及的指令:

  • OP_ADD_INT, OP_SUB_INT, OP_MUL_INT, OP_DIV_INT, OP_MOD_INT
  • OP_ADD_FLOAT, OP_SUB_FLOAT, OP_MUL_FLOAT, OP_DIV_FLOAT
  • OP_NEG_INT, OP_NEG_FLOAT
  • OP_EQ_INT, OP_LT_INT, OP_GT_INT, OP_LE_INT, OP_GE_INT
  • OP_EQ_FLOAT, OP_LT_FLOAT, OP_GT_FLOAT, OP_LE_FLOAT, OP_GE_FLOAT
  • OP_ADD_INT_IMM, OP_SUB_INT_IMM, OP_MUL_INT_IMM
  • OP_LT_INT_IMM, OP_GT_INT_IMM, OP_LE_INT_IMM, OP_GE_INT_IMM, OP_EQ_INT_IMM

性能影响: 从 210ms 提升到 203ms

风险: 中 - 类型特化指令由编译器生成，保证栈状态正确

5. 变量操作指令优化 (op_variables.inc)

文件: src/vm/vminc/op_variables.inc

优化内容:

  1. OP_SET_LOCAL - 移除不必要的 frame 更新
  2. OP_GET_LOCAL - 使用 vm_stack_push_fast

6. 跳转指令优化 (op_jump.inc)

7. 函数调用优化 (op_call.inc)

  2. OP_RETURN - 使用 vm_stack_pop_fast 和 vm_stack_push_fast

16. 快速栈操作部分回退与恢复 (2026-05-28)

问题: 更多排序.leno 测试在副本3中失败，而副本2正常

原因分析: 快速栈操作函数 (vm_stack_pop_fast, vm_stack_push_fast, vm_stack_peek_fast) 不进行边界检查，在复杂排序算法的大量函数调用和返回场景下导致栈下溢或上溢

第一阶段 - 全面回退:

  1. op_call.inc - 使用安全版本
  2. op_jump.inc - 使用安全版本
  3. op_type_specialized.inc - 使用安全版本
  4. op_variables.inc - 使用安全版本
  5. vm_helpers.inc - 移除快速宏

第二阶段 - 恢复类型特化指令优化:

经过测试，op_type_specialized.inc 中的快速栈操作是安全的，已恢复：

  • 所有 vm_stack_pop → vm_stack_pop_fast
  • 所有 vm_stack_push → vm_stack_push_fast
  • 使用 PUSH_SAFE_INT64_*_FAST 宏

最终状态:

文件 使用 fast 原因
op_type_specialized.inc ✅ 栈操作确定（pop 2/push 1 或 pop 1/push 1），由编译器生成，相对安全
op_call.inc ❌ 函数调用和返回涉及复杂的栈帧管理，容易出错
op_jump.inc ❌ 跳转时栈状态不确定
op_variables.inc ❌ 局部变量操作可能涉及边界情况

经验总结: - 快速栈操作虽然能提升性能，但在复杂场景下（如递归调用、大量函数返回）存在栈边界安全风险 - 类型特化指令栈操作确定，由编译器生成，相对安全 - 建议：仅在确定栈状态绝对安全的热点路径使用快速操作，并配合充分的测试

回退原因

  • 断言测试 202 passed, 0 failed（功能正确）
  • 但全量 .leno 测试文件运行后发现整体变慢
  • 回退后恢复到原始速度

根因分析

frame = &vm.frames[vm.frame_cnt - 1]; 虽然看似冗余，但实际上对编译器优化至关重要：

  1. 寄存器分配锚点: frame 赋值给编译器一个明确的“重新加载点”，让 frame 指针保持在寄存器中。移除后，编译器可能无法证明 frame 在跨函数调用后仍然有效，被迫从内存重新加载

  2. 别名分析屏障: frame = &vm.frames[vm.frame_cnt - 1]; 明确告诉编译器 frame 指向 vm.frames 数组的具体位置。没有这行，编译器可能保守地认为 frame 指向的内存可能被任何函数调用修改，从而生成更多的内存读写

  3. 指令调度优化: frame 赋值后的代码块，编译器可以更激进地重排指令。移除后编译器变得保守，指令调度质量下降

  4. 与 #10、#14 一致: 之前移除 OP_CLOSE_UPVALUE、OP_DEFINE_GLOBAL、OP_GET_NATIVE、OP_STRING_ADD 的 frame 更新时也观测到性能下降，这次是大规模验证了这一现象

核心教训

frame = &vm.frames[vm.frame_cnt - 1]; 不能随意移除！

即使从语义上看是冗余的（前一个修改 frame_cnt 的操作已设置了正确的 frame），但编译器需要这行代码作为优化提示。移除它会导致编译器生成更保守、更慢的代码。

这与“死代码消除”直觉相反——某些“死代码”实际上是编译器的优化锚点。

最终结论

  • ❌ 不要移除 opcode handler 开头的 frame 更新
  • ✅ 唯一安全移除 frame 更新的地方是 op_arith.inc（已验证）
  • ❌ op_type_specialized.inc 快速栈操作 已回退 (2026-08-14，详见 #18)
  • ✅ 未来优化方向应转向：JIT、内联缓存深化、超指令合并、字节码内联等

18. 回退 op_type_specialized.inc 快速栈操作 ❌ 已回退 (2026-08-14)

回退内容

将 op_type_specialized.inc 中所有 vm_stack_push_fast → vm_stack_push， 所有 vm_stack_pop_fast → vm_stack_pop。

涉及 ~30 个类型特化指令（OP_ADD_INT, OP_SUB_INT, OP_MUL_INT, OP_DIV_INT, OP_MOD_INT, OP_ADD_FLOAT ~ OP_DIV_FLOAT, OP_NEG_INT, OP_NEG_FLOAT, OP_EQ_INT ~ OP_GE_INT, OP_EQ_FLOAT ~ OP_GE_FLOAT, OP_ADD_INT_IMM ~ OP_EQ_INT_IMM）。

回退原因

开发 LenoNet（libcurl 绑定）时，HttpClient 多次请求触发 FFI 回调， 回调中执行 Leno 字节码使用了 vm_stack_push_fast， 该函数不检查栈溢出，越界写入破坏了堆元数据， 导致程序结束时 gc_free_all() 调用 free() 触发 STATUS_HEAP_CORRUPTION (0xC0000374)。

gdb 堆栈回溯：

#7  gc_free_all () at src\gc.c:1625  ← free(gc.vm->stack) 触发堆损坏检测
#8  lenolang_run () at src\main.c:215

根因链：

FFI 回调 (libcurl write_callback)
  → callback_dispatch_direct → vm_call_value → 执行 Leno 字节码
    → op_type_specialized.inc 中的 vm_stack_push_fast
      → VM 栈已满（FFI 回调复用主线程 VM 栈）
        → 越界写入 vm->stack[vm->sp++] → 破坏相邻堆内存
          → gc_free_all() 时 free() 检测到 STATUS_HEAP_CORRUPTION

详见 archive/LenoNet_崩溃问题排查记录.md

性能影响

从 ~203ms 回退到 ~210ms（约 3% 性能损失）。

核心教训

vm_stack_push_fast / vm_stack_pop_fast 不检查栈边界，在任何可能栈空间不足的场景都不安全。

2026-05-28 曾因 更多排序.leno 失败而部分回退，但保留了 op_type_specialized.inc 中的使用。 当时认为"编译器生成的类型特化指令栈操作确定，相对安全"， 但忽略了 FFI 回调复用主线程 VM 栈时栈空间可能不足的情况。

结论：不要在生产代码中使用不带边界检查的栈操作函数。

19. 回退 op_call.inc 和 vm_helpers.inc 中残留的 vm_stack_push_fast ❌ 已回退 (2026-08-15)

回退内容

将以下文件中残留的 vm_stack_push_fast 调用全部替换为安全的 vm_stack_push：

  1. src/vm/vminc/op_call.inc — OP_CALL_GLOBAL_FUNC 中的 1 处调用
  2. src/vm/vminc/vm_helpers.inc — 5 个 _FAST 宏中共 11 处调用：
    • PUSH_INT_WRAP_FAST (1 处)
    • PUSH_INT64_RESULT_FAST (2 处)
    • PUSH_SAFE_INT64_ADD_FAST (3 处)
    • PUSH_SAFE_INT64_SUB_FAST (3 处)
    • PUSH_SAFE_INT64_MUL_FAST (2 处)

回退原因

继 #18 回退 op_type_specialized.inc 之后，发现 op_call.inc 的 OP_CALL_GLOBAL_FUNC 指令和 vm_helpers.inc 的 _FAST 宏中仍残留 vm_stack_push_fast 调用。

  • OP_CALL_GLOBAL_FUNC 是性能优化提交 51aec011 引入的融合指令，直接用 vm_stack_push_fast 压入 callee
  • vm_helpers.inc 中的 _FAST 宏虽然当前没有被任何操作码文件直接调用（仅有 PUSH_INT64_RESULT_FAST 被 PUSH_SAFE_INT64_MUL_FAST 内部引用），属于死代码，但保留不安全的实现存在未来被误用的风险

当前状态（2026-08-15 修正）

#19 中"全局零调用"和"vm_helpers.inc 已改用安全版本"的描述与实际代码不符，以下为真实状态：

  • vm_stack_push_fast 函数定义保留在 leno_vm.h 中
  • vm_helpers.inc 中的所有宏（PUSH_INT_WRAP、PUSH_INT64_RESULT、PUSH_SAFE_INT64_ADD/SUB/MUL 及对应 _FAST 版本）仍使用 vm_stack_push_fast，被 op_arith.inc 的通用算术指令调用
    • 安全理由：这些宏用于 OP_ADD/OP_SUB/OP_MUL 等通用指令的快速路径，栈操作模式固定（pop 2 → push 1），不会在 FFI 回调中触发栈溢出
    • FFI 回调崩库的根因是 op_type_specialized.inc 中的 vm_stack_push_fast（已在 #18 回退），不是 vm_helpers.inc 的宏
  • vm_stack_pop_fast 和 vm_stack_peek_fast 仍被 op_arith.inc、op_call.inc、op_jump.inc、op_variables.inc、op_stack.inc 等使用
  • op_type_specialized.inc 中已全部使用安全版本（vm_stack_push / vm_stack_pop），不使用任何 _fast 函数

核心教训

vm_stack_push_fast 的安全性取决于使用场景。 op_type_specialized.inc 中不安全是因为 FFI 回调复用 VM 栈时可能栈空间不足。vm_helpers.inc 的宏用于通用算术指令，栈操作模式固定（pop 2 → push 1），且 FFI 回调中不会走到通用算术路径，因此安全。

20. OP_RETURN 快速路径优化 ❌ 已回退 (2026-08-15)

回退原因

A/B 测试证明此优化无实际效果。

对 fib(30) 各跑 30 次的对比结果： - 无优化组（A 组）：中位数 78ms，众数 78ms - 有优化组（B 组）：中位数 78ms，众数 78ms

两组数据分布完全一致，优化没有带来任何可测量的性能提升。之前文档中记录的"94ms → 79ms，提升 16%"是错误的——94ms 是后台任务干扰造成的波动，不是优化前的真实基线。

原优化内容（已移除）

在 OP_RETURN 和 OP_GET_LOCAL 中添加快速路径，跳过异常/协程/upvalue 检查。由于实际无效果，已删除快速路径代码，恢复原始执行路径。

同时回退的优化

OP_GET_LOCAL 的指令顺序调整和快速路径也一并回退（同样无效果）。

回退方法

已执行回退。代码已恢复为原始版本。

21. call() 帧异常字段懒初始化 ❌ 已回退 (2026-08-15)

回退原因

利用 has_try 标志跳过异常字段初始化的优化对 fib(30) 提升仅 ~1-2%（79ms → 78ms），在测量误差范围内，实际收益可以忽略。引入的分支复杂度和潜在风险不值得这点提升。

回退方法

将 vm_call.inc 和 op_call.inc 中的 if (likely(!func->has_try)) 分支替换回无条件初始化全部 7 个异常字段。
