函数调用性能优化：调用帧 locals 阈值与多返回值解构

⚠ 历史结论（2026-10-02 注）—— 本文多处与现状相反，读前必看。 本文产生于栈式 VM 时代，其中「正确路径：保持栈机 → 加 trace-JIT → 至少 2 年内不考虑寄存器机」 这条结论已被取代：本仓库早已是寄存器式 VM（0f0cf52），JIT 也已不在代码中 （git ls-files "*jit*" 为空）。 另外三处按现状重读： ① INLINE_LOCALS_MAX 现为 64（src/include/leno_vm.h:589，本文写作时的 8/32 已过时）； ② 当时的编译器函数内联器（src/codegen/codegen_inline.c，621 行）随寄存器式改造被删除且未移植 —— 这就是今天"空函数调用 578ms vs 栈式 193ms"这类对拍的真正原因（栈式那些数字是内联后剩的空循环）； ③ 现行调用路径实现在 src/vm/vminc/vm_call.inc + src/vm/vminc/run/06_call.inc， 现行结论见 docs/待办与路线图.md 的 ⑤-g / ⑤-y。 结论与数据留作历史对照，不要当现行现状引用。

背景

光线追踪基准测试（examples/性能测试/光线追踪对比.leno vs .py）中，Leno 标量优化版 比 Python 慢 1.31x（3219ms vs 2456ms），而"全部测试"中 Leno 碾压 Python。通过 --debug 字节码分析 + 微基准隔离，定位到两个根因。

每多一个参数 Leno 损失 68ns（约 200 周期）——对搬移一个 8 字节 NaN-boxed Value 而言极不正常。真正的嫌疑是参数数量把函数的局部变量槽位数推过了某个阈值。

根因分析

根因 1（主因）：INLINE_LOCALS_MAX = 8 导致每调用一次 malloc/free

src/include/leno_vm.h:214：

#define INLINE_LOCALS_MAX 8

call()（src/vm/vminc/vm_call.inc:89）中，局部变量槽数超过 8 的函数每次调用都要：

if (likely(local_count <= INLINE_LOCALS_MAX)) {
    locals = frame->inline_locals;      // 栈上内联，零成本
} else {
    locals = (Value*)malloc(local_count * sizeof(Value));  // 每次调用分配！
    ...
}

对应测试函数的实际槽数（--debug 可验证）：

函数 参数 局部变量 总槽数 结果
f1（1参微基准） 1 ~5（for 循环隐藏槽） 6 内联，无分配
f7（7参微基准） 7 ~5 12 每调用 malloc/free
sphereHit 7 9 16 每调用 malloc/free
trace 7 11 18 每调用 malloc/free

Windows 上一次 malloc+free 约 100~200 周期。Phase C 共约 1600 万次调用 （1500万 sphereHit + 100万 trace），仅堆分配开销就达 500~1000ms， 与实测 763ms 差距吻合。这就是 Leno 输给 Python 的全部主因。

CPython 3.11+ 恰好做了 zero-cost frame（帧直接在解释器栈上），无此开销。

根因 2（次因）：多返回值解构的冗余指令

--debug 显示 var[float,int](a, b) = hit(...) 生成：

OP_CALL_GLOBAL_FUNC  func=0 args=3
OP_SET_LOCAL_POP     10      ; 返回值2 → 临时槽（多余）
OP_SET_LOCAL_POP     9       ; 返回值1 → 临时槽（多余）
OP_GET_LOCAL         9       ; 临时槽读回（多余）
OP_CAST_FLOAT                ; 类型已匹配，转换多余
OP_SET_LOCAL_POP     7       ; 最终槽 a
OP_GET_LOCAL         10      ; （多余）
OP_CAST_INT                  ; （多余）
OP_SET_LOCAL_POP     8       ; 最终槽 b

来源：gen_destruct_decl()（src/codegen/codegen_stmt.c:1178）先逆序存入临时槽， 再逐个加载、转换、存入最终槽。每个多返回值调用多出 4 条指令 + 2 个临时槽， 且临时槽还会推高函数 local_count（加剧根因 1 的阈值跨越）。

优化方案

优化 1：INLINE_LOCALS_MAX 8 → 32

一行改动。收益分析：

  • 覆盖典型函数（sphereHit=16、trace=18 均被覆盖）
  • CallFrame 从 ~152B 增长到 ~344B；帧池按需扩容，典型调用深度（<64 帧） 内存增量可忽略；深递归（万级深度）约 3.4MB，可接受
  • 涉及 INLINE_LOCALS_MAX 的所有引用点（vm_call.inc、op_call.inc、vm_init.inc、 vm.c、object_thread_fixed.c）均使用同一宏，自动生效
  • 纯运行时结构变化，不影响字节码格式，无需升级 LENO_BIN_VERSION

优化 2：多返回值解构直接存储

改造 gen_destruct_decl() 的 TYPE_MULTI_RET 分支：

  • 函数调用后 N 个返回值已在栈上（ret0...retN-1，retN-1 在栈顶）
  • 超出 slot_count 的返回值先 POP
  • 逆序处理：CAST（仅当返回类型与槽位类型不一致时发射）→ 直接 OP_SET_LOCAL_POP 到最终槽
  • slot_count > ret_count 时，剩余槽位补 OP_NULL
  • 完全消除临时槽：省 2×SET_LOCAL_POP + 2×GET_LOCAL，类型匹配时省 2×CAST
  • 不再推高 local_count，间接缓解根因 1

语义保持：

  • 部分接收（var[int,string](a,b) = three_ret_func()）→ POP 多余返回值
  • 超量接收（slot_count > ret_count）→ 尾部槽位补 null
  • SYM_GLOBAL / SYM_MODULE 目标同样适用（值在栈顶，操作不变形）

已评估但不实施的方案

  • 编译期参数类型转换消除：实测调用机制本身已快于 Python 2.4x， call() 内的逐参转换检查（每参 2~3 条分支）不是当前瓶颈，收益小于复杂度。 保留为后续方向（配合 float 帧槽 unboxing 一起做更有意义）。
  • OP_RETURN 快速路径 / try 字段惰性初始化：try 相关 4 字段必须由 call() 预清空（OP_TRY 会把当前 catch_ip 存入 prev_catch_ip，残留脏指针会破坏嵌套 try 状态恢复），且 4 次指针写成本极低，不动。

实现中发现的 bug：顶层代码局部槽位记账缺失

优化 2 消除临时槽后，test_destruct_auto_infer.leno 等测试报 "局部变量索引越界"。根因与优化本身无关，是被优化掩盖的既有缺口：

  • 语义分析在顶层代码（非函数内）分配的局部槽位（如 for 循环体内声明的变量、 顶层解构声明）不会自动反映到 chunk->local_count（codegen 中仅 for 内部槽位、 内联槽位会更新它）；
  • 主帧（vm_load）按 chunk->local_count 分配 locals 数组，漏记即越界；
  • 旧实现里解构临时槽恰好把 local_count 推高，"顺便"盖住了真实槽位，消除临时槽后 缺口暴露。

修复：codegen_stmt.c 新增 track_toplevel_local_slot()，在所有不经语义分析 local_count 路径的局部槽位存储点调用，顶层时补齐 chunk->local_count 与 max_local_slot 记账：

  • gen_var_decl：SYM_LOCAL 声明存储（1 处）
  • gen_destruct_decl：多返回值接收、补 null、数组/字典解构（3 处）
  • gen_try：catch 变量 OP_SET_LOCAL_POP（消除临时槽后暴露，test_exception 曾 因此报"局部变量索引越界"）
  • gen_assign：并行赋值临时槽区域（防同类越界）

函数内无需处理（func->local_count 来自语义分析的 local_index，已覆盖全部声明）。

第二轮：数组索引快速路径 + 赋值 CAST 编译期消除

背景

第一轮后剩余差距：Phase A 慢 1.24x、Phase B/B2 慢 1.11~1.15x、Phase C 慢 1.06x。 --debug 分析 index_micro.leno 热点循环字节码发现两个可消除的开销：

  1. OP_INDEX 数组 int 索引走通用路径：val_is_num（三分支 ||，含 bigint 对象 解引用判断）+ value_to_double（int64→double）+ (int) 截断（double→int32） ——一次数组索引做了两次类型判断和一次 64↔32 位往返转换；
  2. 赋值处冗余 CAST：sum += <float表达式> 生成的 OP_CAST_FLOAT 在表达式 静态类型已是 float 时是纯开销（sum = sum + scx[si] + ... 每次循环一条）。

优化实现

优化 3：OP_INDEX / OP_ITER_GET 数组 int 索引快速路径（VM 侧）

src/vm/vminc/op_utils.inc OBJ_ARRAY case 顶部增加快速路径：

  • val_is_int(index_val) 命中时直接 val_as_int 取 int64 索引；
  • (uint64_t)index < (uint64_t)arr->count 无符号比较，一条指令同时覆盖 负索引与上界越界；
  • 越界时落入原通用路径，报错信息与语义完全不变；
  • float/bigint 索引仍走原路径。OP_ITER_GET 的数组分支同样改为无符号比较。

不改字节码格式，所有数组索引访问（含 Phase B/C 中 sphereHit 内的 scx[si] 等） 自动受益。

优化 4：赋值/声明处 CAST 编译期消除（codegen 侧）

src/codegen/codegen_stmt.c 新增 assign_cast_needed()：仅当表达式静态类型 （cached_type）与目标声明类型完全一致时跳过 CAST——此时 CAST 不可能失败， 是纯运行时开销；类型未知（any/无 cached_type）或不一致时保留，维持运行时 类型检查与报错行号语义。应用于 4 处：

  • gen_var_decl：var float x = 1.0（int 字面量 var float x = 1 仍会 CAST 提升）
  • gen_assign 单目标：x = <同类型表达式>
  • gen_assign 多目标并行赋值（保守：右值为 AST_ARRAY 时类型不匹配，CAST 保留）
  • gen_expr_stmt 局部赋值快速路径

与多返回值解构的 CAST 消除（第一轮优化 2）同一原则：能在编译时确定，就不给运行时。

实测（2026-08-29，同机同批）

三轮优化累计（第三轮：方法 IC/分配融合/OP_INVOKE_METHOD_TYPED；第四轮：size-class 池）：

对比标量版（B 1.04x / B2 1.06x / C 1.00x）可见：差距几乎全部来自 对象路径，即方法分派 + 对象分配，而非算术或数组。

为什么对象版比 Python 慢（--debug 字节码 + 源码定位）

  1. 方法查找线性 strcmp：OP_GET_METHOD（op_struct.inc）每次调用 for + strcmp 遍历方法表，未接入 IC_CACHE 内联缓存；CPython 3.11 有 类型版本化的方法缓存 + LOAD_METHOD 专用指令。
  2. 对象分配路径重：OP_STRUCT_INIT 每次 struct_def_find 全局字符串 查找 → gc_alloc 头 → 独立 calloc(field_values) → gc_track_memory → 逐字段类型检查 + gc_write_barrier。Hit（2 字段）一次 new = 2 次 系统分配 + 多层簿记；Python __slots__ 对象 = pymalloc 池 1 次分配。
  3. receiver 双求值/双压栈：方法调用点字节码 recv; args...; recv; OP_GET_METHOD; OP_CALL n，receiver 表达式求值两次（spheres[si].hit() 即两次 OP_INDEX）、call() 再拷贝到 locals[0]。

已实施的优化（第三轮，2026-08-29）

三项全部落地，回归 256/256 通过：

  1. 方法查找内联缓存（op_struct.inc OP_GET_METHOD）：新增 InlineMethodCacheEntry（def 指针 + name_hash + 代数 + closure）， 以指令地址哈希索引，命中 O(1) 取预创建闭包。安全性： - ObjStructDef 由 struct_def_mark_all() 作为 GC 根标记，closure 经 def 可达，缓存裸指针不悬空；GC 非移动（晋升仅翻转 generation 标志） - 新增 struct_def_generation() 代数计数器（struct_def_register 注册/覆盖时递增），缓存校验代数防止同名 def 被重定义后拿到旧方法 - 仅缓存预创建闭包（upvalue_count==0）；需要 upvalue 的方法每次动态 创建，不入缓存
  2. struct 分配单次系统调用（object_struct.c struct_instance_new_depth）： 头 + 字段数组一次 gc_alloc（尾随内联数组），省掉独立 calloc + gc_track_memory；ObjStruct.fields_inline 标记，gc.c 释放路径跳过 单独 free。OP_STRUCT_INIT 的 struct_def_find 同步接入 InlineStructDefCacheEntry 缓存（同代数校验机制）
  3. OP_INVOKE_METHOD_TYPED 融合指令（leno_vm.h / op_struct.inc / codegen_expr.c）：编译期确认 struct 方法（非 async）且接收者静态类型名可解析时发射 recv; args...; OP_INVOKE_METHOD_TYPED name(2) argc(2) type(2)，receiver 只求值一次， 方法查找（IC）+ 调用一条指令完成；async/未知定义走 OP_GET_METHOD 旧路径。 镜像既有 OP_CALL_GLOBAL_FUNC 融合模式，debug.c 反汇编已支持。 （2026-09-13：5 字节旧形态 OP_INVOKE_METHOD 已删除，类型名解析不出来改为编译期报错， 不再有运行时分发回退 —— 见 docs/archive/JIT实现与调试记录.md §8.32）

优化后剩余差距分析

  • B2（734ms）与标量版函数调用（750ms）持平 → 方法分派开销已消除
  • ~~B - B2 差值 114ns/次为 Hit 分配成本~~ 第四轮 size-class 池实施后 B - B2 差值 = 251ms/3M ≈ 84ns/次，与 Python（79ns/次）完全同级， Hit 分配差距已消除（见下节"已实施的优化（第四轮）"）

已实施的优化（第四轮，2026-08-29）：gc_alloc size-class 池

方向 5 落地，回归 256/256 通过，对象版 B 1109→985ms、C 3625→3281ms， 标量版无回退：

  • 实现（gc.c）：[16B, 256B] 小对象按 16B 对齐分 16 个 size-class， 每类 free-list（复用对象头 next 指针串链）；free-list 空时分配新块 （16B 头部 + 64 槽）整块切割；池持有内存上限 4MB（超限回退 malloc， 池化内存不归还 OS，靠上限防常驻膨胀）
  • sweep_young / sweep_old / gc_free_all 的对象释放统一走 gc_free_object()：池化对象清零整个槽后归还 free-list，否则系统 free； gc_free_all 遍历池块列表统一释放
  • 安全性设计：
  • 池类别编码在 Object.flags（0x80=池化位 | 低 4 位=class 索引）， 不按 obj->size 反推 class——gc_track_memory 会改写 size（数组/ 字符串/字典扩容记账），按 size 反推会把槽挂错链导致堆损坏
  • OBJ_ARRAY 不池化：数组有自己的 header 回收列表（arr_try_recycle）， 且 arr_new 复用时将 flags 清零，双重持有会破坏池链
  • GC 非移动（晋升仅翻转 generation 标志），槽地址稳定；分代记账 （young_allocated/old_allocated）按请求 size 计，与池无关，GC 触发 逻辑不变

优化方向

见"方向 1.5"——三项修复（方法 IC、def 免查找、field_values 内联分配） 已全部实施完毕，见上节"已实施的优化"。方向 5（size-class 池）也已实施。

后续优化方向与战略决策（2026-08-29 修订）

修正："栈机到顶了"——不准确

从全量性能测试数据看，Leno 落后 Python 的场景有三个，但都不是栈机 vs 寄存器机的问题，而是具体实现策略的问题：

落后场景 原因 是栈机问题吗
对象版 Phase B/B2 慢 9~17% gc_alloc 走 malloc + 分代簿记，Python 用 pymalloc free-list ❌ 分配器策略问题
经典递归斐波那契慢 36% Python 3.11 zero-cost frame，Leno 每次递归建完整帧 ❌ 帧管理问题
光线追踪 Phase C 持平 递归 + 数组索引混合，边界检查无法消除 ⚠️ 部分相关，非栈机原罪

Lua 5.4 也是栈机，多数场景不输 CPython。Leno 落后的 7~17% 是分配器和 帧管理没优化到位，不是"栈机到头了"。

优化决策分类

❶ 边际优化——停止

继续微调指令编码、IC 容量、内联阈值——投入产出比太低。三轮优化收益递减 （第一轮 25%→第二轮 2%→第三轮对象版 2%），边际优化到此为止。

❷ 结构性优化——顺手修，不立项

从数据中能直接看到三个尚未触及的结构性短板，修好不是挤 2%，可能是 20~50%：

结构短板 A：对象分配器改 bump allocator / free-list（= 方向 5）——已实施

  • 已于 2026-08-29 实施（size-class 池，见"已实施的优化（第四轮）"）： Hit 分配 114ns → 84ns/次，与 Python pymalloc 同级

结构短板 B：递归帧优化（frame pool / zero-cost frame 变体）——已实施（帧复用）

  • 已于 2026-08-29 第五轮优化实施（帧复用部分）： 利用已有的 ObjFunction.has_try 编译期标志，call() 及另两处帧建立点 仅在 has_try 时才初始化 7 个 try 字段（catch_ip/finally_ip/ prev_catch_ip/prev_finally_ip/in_finally/try_return_value/ has_try_return，~50B/次），无 try 的函数（绝大多数）全部跳过
  • 帧槽（vm.frames[]）被复用，跳过初始化时 try 字段是脏值，新增 FRAME_TRY_VALID(frame) 守护宏（leno_vm.h），全部读取点已守护： vm_run.inc 分发宏 ×3、OP_RETURN/OP_RETURN_MULTI 的 finally 跳转、 OP_END_TRY 的上层帧检查、OP_THROW 的 in_finally 检查、 op_property.inc 异常检查 ×3、gc.c/coroutine.c 的 try_return_value GC 扫描 ×3（误扫脏 Value 会崩溃）。异常搜索循环 （vm_exception.inc/op_exception.inc/vm.c/op_coroutine.inc）原本就有 has_try 跳过，天然安全
  • 实测（2026-08-29）：fib(32) 219→203ms（Python 204ms，持平反超）， 对象版 B2 766→750ms、C 3468→3375ms，标量版无回退，回归 256/256
  • frame pool 其余部分（预分配帧池）不再需要：vm.frames[] 本就是预分配 复用的扁平数组，真正的每调用开销就是 try 字段清零（已消除）与参数 拷贝（方向 2 已实验放弃，独立 locals 数组的寄存器友好性优于值栈）

结构短板 C：数组/bytes 切片零拷贝

  • 现状：Python bytearray 切片是零拷贝视图，Leno 的 ffi.copy4 有函数调用
  • 边界检查开销
  • 预期收益：图形类应用（SDL、图像处理）显著受益
  • 工作量：低（1 周内）
  • 策略：遇到数组/FFI 相关代码时顺手做

❸ 寄存器机重写——否决

即使定位高性能脚本语言，也不建议现在做寄存器机重写：

  • 风险极高：几个月重写，可能引入大量 bug，FFI/模块/GC 都要重构
  • 收益不明确：寄存器机对纯计算有提升，但对 FFI 密集型场景帮助有限
  • 替代方案更优：做 trace-JIT（类似 LuaJIT）比寄存器机重写投入产出比高得多。 LuaJIT 强不是因为寄存器机，而是因为 JIT
  • 时机不对：语言还没稳定，语法和语义可能还要变，底层 VM 重写等于 流沙上盖楼
  • 正确路径：保持栈机 VM → 加 trace-JIT → 热点编译到机器码。至少 2 年内 不考虑寄存器机

已实施/已放弃的方向索引

方向 1：专用化算术指令

--debug 发现 codegen 已按操作数静态类型发射 OP_SUB_FLOAT / OP_MUL_FLOAT / OP_LT_FLOAT 等专用指令（浮点路径已覆盖）。 剩余 int/混合组合专用化收益集中在整数热点循环，优先级下调至停止。

方向 1.5：struct 对象路径三大热点——已全部实施

已全部实施（2026-08-29 第三轮优化）：

  1. OP_GET_METHOD 线性 strcmp 查找方法表 → 已接入 InlineMethodCacheEntry 内联缓存（def 指针 + name_hash + 代数校验），命中 O(1)。
  2. OP_STRUCT_INIT 每次分配 struct_def_find 全局字符串查找 → 已接入 InlineStructDefCacheEntry 缓存；field_values 已改为头 + 字段数组一次 gc_alloc 尾随内联分配（不限字段数）。
  3. 方法调用 receiver 双求值/双压栈 → 已实现 OP_INVOKE_METHOD_TYPED 融合 指令（receiver 单次求值，查找 + 调用一条指令）。

实施前实测（300 万次调用）：对象版 Phase B 1329ms vs 标量版 765ms—— 方法分派 + Hit 分配合计多 ~75%。实施后 B2 766ms 与标量版持平（方法 分派开销归零），B 1109ms（剩余为 Hit 分配 ~114ns/次）。

补充（2026-09-16）：JIT 的 OP_STRUCT_INIT callout 那条路没有内联缓存。 解释器的 OP_STRUCT_INIT 有 InlineStructDefCacheEntry（命中即零扫描），但 JIT 把它实现成 jit_callout_struct_init，每次都真查一次定义表 ⇒ 表一大就显形：探针（200 个 struct 声明、 300 万次 new）1 个定义 215ms vs 200 个定义 6252ms（29×）。 已在定义表旁加"名字 → 槽位"的桶索引（链按注册顺序 ⇒ 同名取先注册者的语义不变）， 小表（≤4）仍就地线性扫描（否则辅助函数调用本身每次分配要花 ~8ns），大表才走桶： 实测 6205ms → 330ms（18.8×），1 个定义与基线持平。实现与踩坑记录见 docs/单一事实来源与重复实现收敛.md 第三节 Phase 2 的 2b-2 记录（含四路交错 A/B 数据）。

方向 2：locals 迁移到值栈——已实验放弃

  • 现状：call() 逐参从值栈弹出拷贝到独立 locals 数组；OP_GET_LOCAL 每次 间接寻址 + local_count 边界检查
  • 原方案：参数直接留在值栈帧基之上（CPython 3.11 zero-cost frame 思路）， 返回时整体弹掉，不再 malloc locals / 不再逐参拷贝
  • 预期收益：调用路径再快 ~5%（B/B2 剩余差距的来源）
  • 代价：大——帧结构、闭包 upvalue 捕获（close_upvalues 依赖 locals 数组）、 try-catch 帧恢复、调试器栈遍历全部要改；回归风险高，需专项排期

实验结果（2026-08-29，已放弃）

早上另一个对话实际实施了该方案，结果：大量功能回归 + 性能反而变慢， 已全部回退。原因分析如下，作为永久记录防止重试：

1. 值栈局部变量访问反而更慢

op_variables.inc 中 OP_GET_LOCAL 已有值栈路径（frame->locals == NULL 时 走 vm.stack[frame->stack_base + slot]）。看起来"少一次拷贝"，但：

  • 独立 locals 路径：frame->locals[slot]——locals 指针已在 frame 结构 内，寄存器友好，一条 mov + 一次 lea 取地址
  • 值栈路径：vm.stack[frame->stack_base + slot]——需先加载 frame->stack_base （内存读取），再加载 vm.stack 指针，做两次加法再取值

局部变量读写是最高频操作（热点循环中每条 OP_GET_LOCAL/OP_SET_LOCAL）。 省掉的参数拷贝（7 个 Value = 56 字节，~10-20 周期）远不如每条局部变量 访问多出的开销（数百万次 × 多 1 次加载 + 1 次加法）。实测变慢 5~10%。

CPython 3.11 的 zero-cost frame 能受益，是因为它的 LOAD_FAST 用 frame->localsplus + slot，localsplus 指针缓存在寄存器中。Leno 的栈机 架构下 vm.stack 是全局 VM 状态，每次访问都要经 VM 结构加载，没有 寄存器缓存优势。

2. upvalue 捕获机制彻底破坏

capture_upvalue()（vm_upvalue.inc:75）的核心：

created->location = local;  // 直接指向 locals 数组中的槽

close_upvalues() 按 [locals, locals+local_count) 地址范围扫描链表。

迁移到值栈后：

  • 指针失效：值栈扩容（vm_stack_push 触发 realloc）会移动整个 vm.stack，所有 open upvalue 的 location 指针集体失效。当前帧扩容 逻辑只修 vm_grow_frames 的 inline_locals（vm_upvalue.inc:15）， 对值栈扩容完全没有对应修复路径
  • 地址交错：值栈上多帧的 locals 区域地址不连续（中间夹着操作数栈 临时值），close_upvalues 的范围判断和链表降序假设全部失效

3. 尾调用 memmove 破坏 upvalue

OP_TAIL_CALL（op_call.inc:63）用 memmove 覆盖旧 locals 区域。 值栈模式下旧 locals 区域可能有 open upvalue 指向的槽位，memmove 直接破坏这些指针，导致闭包读取已覆盖的垃圾数据。

4. 异常恢复路径全面引用 frame->locals

op_exception.inc:139 的 finally-return 路径、OP_RETURN 的 upvalue 关闭（op_call.inc:661）、构造函数返回 self（op_call.inc:636 result = frame->locals[0]）——全部直接引用 frame->locals 指针。 值栈模式下需要改为 vm.stack + stack_base，且必须保证在关闭 upvalues （可能修改值栈内容）之前取到 self 值，顺序依赖变复杂。

5. 协程快照复杂化

op_coroutine.inc:168：协程挂起时直接拷贝 CallFrame 数组。 独立 locals 模式下 inline_locals 内嵌在 CallFrame 中，拷贝帧=拷贝 locals。值栈模式下 locals 在值栈上，协程挂起时值栈顶部可能不是当前 帧的 locals（中间有其他帧的临时表达式值），提取和恢复都极复杂。

结论

方向 2 不适用于 Leno 当前架构。CPython 3.11 的收益来自其整体设计 （专用 LOAD_FAST 指令 + 寄存器缓存 localsplus + 不在值栈上放操作数 临时值 + 值栈扩容时集中修复 upvalue）。Leno 栈机架构下，独立 locals 数组 + INLINE_LOCALS_MAX=32 内联方案在性能和复杂度上都是更优解。 B/B2 剩余 4~6% 差距属架构性成本，不再追究。

方向 3：方法调用内联缓存审计

  • IC_CACHE / IC_NATIVE_CACHE 已存在（vm.ic_hits / vm.ic_misses 可查命中率）
  • 若 struct 方法调用热点未命中，再针对性优化；命中率正常则不动
  • 策略：命中率正常则不动，属边际优化

方向 4：寄存器机 VM（架构级重写）——否决

  • 栈机→寄存机（如 Lua 5.x / Dalvik），指令数可减 30~50%
  • 预期收益：20~40%
  • 代价：极大——codegen 与 VM 双双重写，等于第二代 VM
  • 已否决：至少 2 年内不考虑。正确路径是保持栈机 + 加 trace-JIT （详见上方"❸ 寄存器机重写——否决"一节）

方向 5：gc_alloc 小对象 size-class 池（= 结构短板 A）——已实施

已于 2026-08-29 第四轮优化实施完毕（详见"已实施的优化（第四轮）"）。 实测 Hit 分配成本 114ns → 84ns/次，与 Python pymalloc（79ns）同级， 对象版 B 1.22x→1.15x、C 1.19x→1.08x。

P0 生态建设（标准库、包管理、IDE、文档） 全力投入，立即开始
