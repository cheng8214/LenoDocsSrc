0. 总判断

Leno 已经跨过“能写真实产品”的门槛，但还没跨过“规模化维护”的门槛。

正面证据是硬的：四个项目都完成打包分发；Aria 24,614 行，里面是一个真正的 HTTP 服务端（线程池 + SQLite + 鉴权 + 管理后台）；LenoMusic 有 17 个可离线运行的测试并产出 Linux 构建；WorkBuddy 有 doctor、离线 stub 和成体系的错误码；LenoTrae 有黄金样例回归。单文件 exe 约 10–12MB，目标机不需要装运行时（WorkBuddy README:16），这条工程链路是通的。

但成本集中在四个“边界”上，而不是语法：

  1. 数据一旦要跨线程、上表格或落盘，类型就蒸发，退回 Array[Array[string]] / Dict + _str；
  2. 状态要么编码成魔法整数/字符串码（int enum 本可用，但无约定/提示），要么受限于 enum 不能带载荷，逻辑分散到多个文件；
  3. 严格解析和可分类的错误没有标准类型，每个项目自己造一套 Result/Parse——标准库自己也有 8 种错误写法、4 类空值哨兵（§4.5）；
  4. 模块与 VM 的实现细节（extend 模块级、256 字段、255 局部量）直接改写应用的架构。

3.5 用 build\leno.exe 实测：哪些是“没写”，哪些是“没有”

方法：在临时目录（build\_probe，用后删除）用 leno.exe 直接编译运行最小用例，不依赖四个项目的任何代码。本节结论对应 2026-11-08 的 build\leno.exe 快照；src/ 正在并发修改，若源码已变需重测。

① switch —— 能用（但不做穷尽检查）

func classify(int n): string {
    switch n {
        case 1 { return "one" }
        case 2 { return "two" }
        default { return "other" }
    }
}

运行结果：int switch: one,two,other；字符串版 str switch: A,B,?；enum 值版 enum switch: ok,nf,err。 --debug 反汇编显示每个 case 是一条 OP_EQ（OP_EQ A=3 B=1 C=2），确认是线性比较链，但功能正确。 判定：能用。补充：enum 的 switch 不写 default 也能编译、无任何警告（switch c { case Color.red ... case Color.green ... } 输出 red）⇒ 穷尽性检查：没有。

② enum —— 半能用（只有 int 常量）

enum Status { ok = 200 not_found = 404 error = 500 }

_str(Status.not_found) 输出 404，可用于 switch。但带载荷的定义：

enum JobMsg {
    Start(int id)
    Progress(int done, int total)
    Done(int id)
}

直接报 9 条语法错误（期望 enum 成员名称、期望 ')'、期望 '}' 结束 enum 定义 等）。 判定：int 常量能用；载荷没有。 这正是四项目把消息写成 ["progress", 已下, 总长] 的原因之一。

③ map / filter / reduce —— 能用，且类型没有丢

var doubled = nums.map(func(int x, int i) { return x * 2 })
var evens   = nums.filter(func(int x, int i) { return x % 2 == 0 })
var total   = nums.reduce(func(int acc, int x, int i) { return acc + x }, 0)

输出：map type=Array[int] value=[6, 2, 4]、filter type=Array[int] value=[2]、reduce type=int value=6；链式 filter().map().reduce() 输出 13。 判定：能用。注意文档 module_arrays.md:51-52 写“reduce 的返回类型暂为 any”，而实测运行时 type() 是 int；文档说的是类型标注、实测取的是运行时值，不能据此判定文档过时（待确认，静态类型未验证），但该描述确实容易劝退使用者。

④ 自定义比较器 sort —— 没有

nums.sort(func(int a, int b) { return b - a })

报错：[语义错误] 调用方法 'sort' 时参数数量不匹配: 期望 0, 实际 1。 改模块形式 arrays.sort(nums, fn) 同样失败：arrays.sort 参数数量不匹配: 期望 1, 实际 2，并附 参数 2 类型错误: 期望 'int'，但传入 'func(int, int):int'。 ~~判定：没有。~~ ✅ 已补（2026-11-09）：arr.sort(cmp) 现在可用（稳定归并；回调里改数组不会崩）。

arr.sort(func(int a, int b) { return b - a })            // 降序
arr.sort(func(Song x, Song y) { return x.dur - y.dur })  // 按 struct 字段

契约与 C qsort / Java Comparator 同口径（负数⇒a 前、0⇒等、正数⇒b 前）。取消失败时的原话是 “期望 0 参”，现已支持 0 或 1 参。

原文说的两处手写已按此处理：player.leno:269 lrc_sort 与 Aria lib/lyric.leno 的同名函数都改成了 ord.sort(cmp)。 但 player.leno:742 insert_sorted 故意保留 —— 它是"往已排序数组插一个"（二分 + 一次移动，O(log n)），改成全量 sort 会退化成 O(n² log n)。 同理 Aria api_report.top_rank 的 Top-N 选择排序（O(n×lim)）也保留。

7. 明确值得肯定的设计

  • LenoMusic：四个项目里工程化最成熟的。纯逻辑与 UI 分离、17 个离线测试、README 把自检命令与已知坑写得可以直接照做、还产出了 Linux 构建。
  • Aria 服务端：线程池 + 每 worker 独立 SQLite 连接 + 线程局部限流 + 声明式路由表，是在“隔离 VM、Ptr 不能跨线程、模块 var 无锁”这套约束下做出的正确设计（server.leno:23-37）。
  • WorkBuddy：doctor 子命令、离线 stub、人话错误码（AUTH_ERROR / HELPER_TIMEOUT / HELPER_PROTOCOL），说明作者在没有 typed error 的情况下仍把错误面做清楚了。
  • LenoTrae：黄金样例回归 + README 的语言注意事项，等于给编译器写了一份真实用户验收清单。
  • 语言本身的表达力（已实测）：cards 的 hook 结构、routes 的声明式表、cli.spec、use 类型导入、if x is T => binding，以及 §3.5 验证通过的 switch / int enum / map·filter·reduce / 用户泛型，都证明核心语法足以写出“像样”的代码。

最终判断：Leno 的语法已经够用，而且比原报告估计的更够用——switch、map/filter/reduce、泛型都实测可用。短板应分成三类：（A）已存在的能力没有到达作者（无 AGENTS.md、无惯用示例、编译器/LSP 不提示、--init 模板不示范），这是“生成侧引导缺口”；（B）确实缺失的能力：记录类型与编解码、Result、8 位索引、enum 载荷、~~comparator 排序~~（✅ 2026-11-09 已补）；（C）官方模块库有 20 个模块、53,052 行，却没有成为标准形态——37 处内部 web_net import 对 0 处 Web 门面 import，~~README 缺 7 个模块且无 import 名映射~~（✅ 已补），77% 库行数不在测试入口内（🟡 已降到 53.9%）。C 与 A 同源，但修复对象是库本身（目录、门面、错误/空值契约、测试入口），不是编译器提示。A 类不补，未来每一段新代码都会继续绕开已有能力；B 类不补，Aria 这类 24.6k 行项目会继续用字符串数组和魔法数字自我补偿；C 类不补，20 个模块就继续以“内部文件”的形式被零散使用，而不会成为四个项目共享的标准入口。先做 A（含 C 的目录/门面部分），再做 B 的前两项，才谈得上“多人、长期、可测试”的可用性。

7.1 做完一轮之后的再判断（2026-11-09）

按上面的排序动了一轮（P0 的文档/README/测试部分 + P4 的比较器），结论有三点变化：

  1. A 类（引导缺口）的证据更强了。三个独立发现指向同一件事： - Array[struct] 本来就能原地更新，"所以只能用行数组"是误判； - strings.fmt_size / split / lines / pad_start 本来就有，"所以手写 4 份"是绕过； - switch / map / filter 本来就能用，"所以 0 使用"是没人示范。

⇒ 缺口不在语言，在可发现性。补 AGENTS.md + README 的 import 名映射，比加任何语法都便宜。

  1. B 类在缩小。这轮补掉的 comparator 排序是原报告认定的"真缺口"之一；顺带发现 maths 缺 pow_mod（有 pow 有 mod 没有二者结合），也已补。 剩下的大项仍是 记录类型（P1） 和 Result（P2） —— 这两项确实是工程级投入，不是补个 API。

  2. 补测试的性价比最高。LenoWeb 0→3 个测试，第一天就抓到 parseUrl 的静默 bug； 而 LenoCSV / LenoCompress / LenoCrypto（本来就有测试）这轮几十组边界探针 一个 bug 都没找到。 对比很直接：有测试的模块质量好，没测试的模块藏着静默错误。

如果只能再做一件事：~~把 Web 门面（37 : 0）收进正轨~~ ✅ 已做（2026-11-09）。

拆出 WebNet / WebHtml / WebCrawl 三个窄入口后，四个项目 37 处全部改回公共入口 （import "web_net" 0 次 → import "WebNet" 37 次），调用点零改动（别名都是 net）。
