Leno 并发选择指引

Leno 提供三套并发原语：threads（多线程）、async/await（协程）、Channel（通道）。 三者不是三种互相竞争的"并发方案"，而是两条执行路径 + 一种通信方式：

  • 执行路径有两种：threads（OS 级并行，多核同时执行）和 async/await（单线程协作调度）。
  • 通信方式只有一种：Channel，它是线程之间、协程之间、线程与协程之间的统一管道。

一分钟决策表

你的场景 选择 理由
CPU 密集：图像处理、加密、批量计算，想让多个核心同时干活 threads 只有真线程能并行利用多核
IO 密集 + 大量并发：几百个网络请求、批量文件读取 async/await 单线程调度，无线程切换开销，轻松上千并发
跨执行流传数据：工作线程汇报进度、生产者-消费者 Channel 配合任意执行模型使用
GUI 程序 主线程跑事件循环 + 重活开 threads 保持界面响应
顺序后台任务：日志落盘、定时清理 async/await 不值得为几个任务付线程成本
不确定 先问自己：瓶颈是"算得慢"还是"等得久"？算得慢→threads；等得久→async

threads：OS 级并行

import threads

func sum_worker(any n) {
    var sum = 0
    if n is int {
        for n to var i {
            sum = sum + i
        }
    }
    return sum
}

main() {
    var t1 = threads.start(sum_worker, 10)
    var result = t1.join()          // join 等待并取回返回值
    print("结果: " + result)        // 45
}

适用：计算瓶颈在 CPU，任务能拆成互不依赖的块。

注意： - 线程间全局变量是隔离的，不能靠共享变量通信——这正是 Channel 存在的原因。 - 线程数量与核心数同量级即可（如 4~8 个），开几百个线程只会在切换上浪费时间。 - join() 会阻塞当前线程直到子线程完成；子线程抛出的异常也通过 join() 传播到调用方。

async/await：单线程协作调度

import asyncs

async func fetch(string url): string {
    await asyncs.sleep(100)     // 模拟网络请求，挂起时让出控制权
    return "data from " + url
}

main() {
    // 调用 async 函数立即返回 Future，不阻塞
    var f1 = fetch("a")
    var f2 = fetch("b")

    asyncs.run()               // 启动事件循环，驱动所有挂起的协程

    var results = asyncs.all([f1, f2])   // 收集多个 Future 的结果
    print(results[0])
}

适用：瓶颈在等待（网络、磁盘、定时器），且并发量大。

注意： - await 只能出现在 async func 内部。 - 协程是并发（concurrent）不是并行（parallel）：任何时刻只有一个协程在真正执行，挂起的协程不占线程。这既是它的优势（无锁、无数据竞争）也是它的边界（单个协程算得慢会卡住整个事件循环）。 - 协程里的重计算是反模式——那正是该开 threads 的信号。

常用 API：asyncs.sleep(ms)、asyncs.yield()、asyncs.all([f...])、asyncs.timeout(future, ms)（超时返回 null，必须在 async 函数内 await 使用）、asyncs.run_for(ms)（跑一会儿没完成先出来，状态保留）。

// timeout 用法：包裹在 async 函数里
async func with_timeout(): string {
    async func slow(): string {
        await asyncs.sleep(5000)
        return "never"
    }
    var r = await asyncs.timeout(slow(), 50)   // 50ms 超时，返回 null
    return r ?? "超时了"
}

真实用法：并发网络客户端（不是 sleep 玩具）

全部步骤见 examples/async await/async_fetch.leno。 一个进程、一个线程、一个事件循环里同时跑：1 个 aaccept 协程 + N 个连接处理协程 + N 个 aconnect 请求协程。

import sockets

// 客户端：一个请求一个协程
async func fetch_one(int port, int id): string {
    var c = await sockets.aconnect("127.0.0.1", port)   // 非阻塞 connect
    if c is Socket => conn {
        conn.send("GET /ping?id=" + _str(id) + " HTTP/1.1\r\nHost: t\r\nConnection: close\r\n\r\n")
        var buf = ""
        while true {                                     // arecv 只返回一次 recv 的数据
            var d = await conn.arecv(65536)
            if d is string => s { buf = buf + s } else { break }
        }
        conn.close()
        return buf
    }
    return ""
}

实测（Windows 10，本机回环）：150 个连接 × 每个服务端"处理"30ms ⇒ 65ms； 逐个等是 4500ms。服务端一侧同样是一连接一协程（await conn.aaccept() 后不 await 处理函数）。

关键：网络等待期间协程是挂起的，不占线程；协程里做 CPU 计算才会卡住整个循环 ——那种活交给 threads，见下面的"协作"。

已知边界（都是真实上限，不是 bug）：

边界 说明
单轮 select 的 socket 数 FD_SETSIZE = 1024；超过靠游标轮转，能跑但延迟上升
大 body 上传 没有 asend。sock.send 在非阻塞 socket 上自旋重试，会占住事件循环 ⇒ 大上传放进线程
本机回环突发握手 Windows 的 listen 背压约 200：同一瞬间 >200 个 SYN 会触发 TCP 重传（多 ~500ms），与 async 无关
跨线程 事件循环是进程级单例（主线程）⇒ 子线程里不能 asyncs.run()

协作：async 等线程算完的结果

协程负责"等"、线程负责"算"，两者经 Channel 交接。等的时候不要用阻塞的 receive() （那会把整条事件循环卡住），用 try_receive() + await asyncs.sleep(1) 轮询：

import asyncs
import threads

func worker(any ch, int n) {
    threads.sleep(30)                       // 模拟 CPU 活
    if ch is Channel { ch.send(n * 2) }
}

async func await_channel(Channel ch) {
    var got = null
    while got == null {
        got = ch.try_receive()
        if got == null { await asyncs.sleep(1) }   // 让出，其他协程继续跑
    }
    return got
}

async func task(int n): int {
    var ch = threads.channel(1)
    var t = threads.start(worker, ch, n)    // 协程里开线程：实测可用
    var v = await await_channel(ch)
    t.join()                                 // 结果已到，join 立即返回
    return _int(v)
}

实测：10 个协程各开一个 30ms 的线程，总耗时 37ms（真并行），结果全部正确。 轮询粒度 1ms ⇒ 别拿它做微秒级同步；要等很多线程时，按批 try_receive 再睡。

Channel：统一通信管道

import threads

func worker(any ch) {
    if ch is Channel {
        ch.send("进度1")
        ch.send(42)
        ch.close()
    }
}

main() {
    var ch = threads.channel(10)     // 缓冲大小 10；0 = 无缓冲（同步交接）
    var t = threads.start(worker, ch)

    var msg = ch.receive()          // 阻塞直到有数据
    print("收到: " + msg)
    t.join()
}

适用：任何需要跨执行流传值的场景——工作线程向主线程汇报进度（见 leno_module/LenoSDL3/examples/应用示例/文件搜索）、生产者-消费者流水线、任务分发。

注意： - send 在缓冲满时阻塞，try_send 永不阻塞（满了返回失败）——UI 主线程收数据用 try_receive/try_send 避免卡界面。 - close() 之后 receive 不会再阻塞等待新数据。 - Channel 是值传递（跨线程时克隆），不是共享引用——这消除了跨线程数据竞争。

组合模式：GUI + threads + Channel（实战范式）

Leno 自带的文件搜索示例是三套原语的标准组合，值得作为模板：

// 模式骨架（摘自 file_search.leno 的思路）
// 1. 主线程（GUI 事件循环）：发起搜索、创建 Channel
searchChannel = threads.channel(65536)

// 2. 工作线程：分批扫描磁盘，结果通过 Channel 汇报
var t = threads.start(_worker_entry, ch, batch, keyword, i)

// 3. 主线程定时器轮询 Channel（try_send/try_receive 不阻塞 UI）
if ch is Channel {
    ch.try_send(fullpath)   // 工作线程侧：满了就丢弃/稍后重试，不卡线程
}

分工：threads 出算力，Channel 传结果，GUI 主线程只做轮询和渲染。

完成检测：先探后取（state() + join() 组合）

等待工作线程结束有两种方式，适用的场景完全不同：

方式 行为 适用
t.join() 阻塞直到线程结束 命令行程序收尾、已确认线程结束时取返回值
t.state() 非阻塞，返回 "running" / "done" / "error" UI/事件循环里轮询检测

在 GUI 或事件循环里直接 join 会冻结界面。正确姿势是"先探后取"——轮询 state() 检测，确认结束后再 join()（此时立即返回，只取返回值）：

// 模式骨架（摘自 file_search.leno）
// UI 定时器每 50ms 轮询：
func pollThreads() {
    bool allDone = true
    int runningCount = 0
    for threads_list.len() to i {
        if threads_list[i] is Thread => t {
            string st = t.state()          // 非阻塞探测
            if st == "running" {
                allDone = false
                runningCount = runningCount + 1
            }
        }
    }
    countLbl.set_text("线程: " + runningCount + "/" + expectedThreads)

    // 全部结束且 Channel 已排空 → 才 join 取返回值（此时立即返回）
    if allDone {
        if ch is Channel and ch.len() > 0 { return }   // 先等结果收完
        for threads_list.len() to i {
            var t = threads_list[i]
            if t is Thread {
                var result = t.join()      // 已知结束，join 只做取值
                // result 是工作函数的返回值（如 [scanned, found]）
            }
        }
        threads_list = []
    }
}

三个要点：

  1. 探测用 state()，取值用 join()——join 的阻塞语义留给"已知结束"的时刻。
  2. join 前先确认 Channel 排空（ch.len() == 0）——线程"done"到主线程"收完数据"之间有窗口，过早收尾会丢最后一批结果。
  3. 计时器用完就 stop()——空转的定时器会持续触发重绘，白耗 CPU。

两个补充细节：

  • join() 的返回值是 any——取值前需 is Array 收窄才能索引：if result is Array { result[0] }。
  • 轮询必须有节奏——UI 里靠定时器（50ms）天然有间隔；命令行程序里手写 while 轮询务必加 sleep(5) 之类的节流，否则空转循环抢光 CPU，工作线程反而更慢。

线程函数的两条纪律 + 入口形态（来自实战的坑）

工作线程函数（被 threads.start 调用的那个）有两条必须遵守的纪律：

// 1. 每个目录/文件操作独立 try-catch：权限错误只跳过当前项，不炸整个线程
// 2. 定期检查取消信号（channel 被主线程 close 即取消）：
if ch is Channel {
    if ch.is_closed() { return }      // 优雅退出，不再扫描
}

入口形态（★ 2026-10-12 更正）：闭包、模块函数现在都能直接作 threads.start 入口 ✓（根因与判据见 docs/线程并发能力修复追踪.md 的 TH2；入口闭包会在子线程堆上 重建副本，不存在"被主线程 GC 提前回收"的 use-after-free ✗）。用具名全局函数只是 风格选择（可读、可复用）—— 仍然推荐，但不是硬性要求：

func _worker_entry(any ch, Array batch, string kw, int wid): Array[int] {
    return scan_batch_worker(ch, batch, kw, wid)
}

取消协议：主线程 close() → 工作线程 is_closed() 退出 → state() 变 done → 主线程 join。一条链路，每一步都非阻塞。

反模式（避免踩坑）

  1. 协程里跑 CPU 密集计算 —— 会饿死同事件循环上的所有协程。改用 threads。
  2. 线程里共享变量传数据 —— 线程间全局变量隔离，写了也读不到（这是刻意的安全设计）。改用 Channel。
  3. 用几百个 threads 做 IO 并发 —— 线程是昂贵的（每 MB 级栈 + OS 调度）。IO 并发用 async/await。
  4. 忘记 asyncs.run() —— 协程创建后只是挂起状态，事件循环不转起来永远不执行。
  5. 在 async func 里 join() 一个长任务 / receive() 一个空 Channel —— 阻塞事件循环，等价于第 1 条。正确做法是"结果先到、join 后调"：try_receive() + await asyncs.sleep(1) 轮询，拿到结果再 join()（见上面"协作"一节）。

总结：两句话

算得慢用 threads，等得久用 async，两者之间传数据用 Channel。

执行模型有两种，通信模型只有一种。
