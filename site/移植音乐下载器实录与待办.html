A1 ★ mobi.kuwo.cn 按 User-Agent 风控 —— 桌面 Chrome UA 会拿到「HTTP 200 + 空 body」

现象：同一个 URL、同一时刻，只换 UA，响应正文长度差别巨大：

UA 响应正文
不设（curl 默认 curl/8.21.0） 292 字节（正常，含 url= 行）✓
okhttp/3.10.0 292 字节 ✓
test/1.0 292 字节 ✓
Mozilla/5.0 292 字节 ✓
桌面 Chrome 完整 UA（Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/148.0.0.0 Safari/537.36） 0 字节（HTTP 仍 200）✗
同上，把空格全删掉 292 字节 ✓

关键对照：Python(requests) 用同一个 Chrome UA 也是 0 字节，无 UA / okhttp 则 292 字节 ⇒ 与 Leno / LenoWeb 无关，是服务端按 UA 做的策略（musicdl 用 okhttp/3.10.0 正是这个原因）。

判据（可复跑）：同一 mobi.s?...&q=<加密串>，逐个 UA 请求比 len(resp.body)。

本轮处置：kuwo_core.leno 里官方取链单独起一个 client 并设 okhttp/3.10.0，不改调用方（搜索用）的 UA。 ⇒ 也是"顺手排掉一个误判"：一开始我以为是 LenoWeb 的 setUserAgent 把请求头写坏了 （用 httpbin 验过：发出的 UA 干净且完整，只有一条），后来并排复测 Python 才定位到真因。 另一个误判：曾怀疑 officialurl 的参数名 format 遮蔽了内置 format()（改名后仍失败）——不成立，注释已改回。

A2 第三方取链 API 会给"降档"结果

现象：搜索列表标注 mp3 7.73 MB，music.nxinxz.com 实际返回 m4a、3,085,464 字节（≈2.94 MB）。 判据：下载后比 实际字节数 与搜索列表的 size。musicdl 的判据是 file_size_bytes * 8 < 320000 * duration_s ⇒ 判为低质并丢弃。 本轮处置：musicdl.leno 在下载后打印对照，明显偏低时warning： ! 实际体积低于列表标注（列表 7.73 MB）⇒ 直链只给了低档，非无损。

A3 酷我 MINFO / N_MINFO 的档位顺序不固定

现象：同一首歌，MINFO 与 N_MINFO 的档位先后相反（实测都出现过）。 ⇒ "取最后一段即最高档"是错的。 判据：按 ; 切段后逐个解析 size:，按数值比大小取最大那档。 本轮处置：kuwo_core.leno 的 bestfield() 按 size 比大小。

A4 酷我歌词接口（newlyric.kuwo.cn）的三个服务端事实

# 事实 现象 / 判据 处置
1 必须带 Referer 不带 Referer 时回 15 字节 TP=DENY REQUEST（HTTP 仍是 200，不是 4xx！）；只带 Referer、不带 UA 也能拿到正文 ⇒ 这个接口看 Referer，不看 UA（与 A1 的 UA 风控是两回事） kuwo_lyric.leno 的 fetchlyric() 自己起 client 并加 Referer: http://www.kuwo.cn/
2 正文是 zlib + gb18030，且不是 Content-Encoding 响应用 Content-Type: text/html 直接吐二进制："tp=content\r\npath=…\r\nscore=…\r\n\r\n" + zlib（前两字节恒为 78 9C） 头体分隔按 CRLFCRLF 定位（兼容 LFLF），剥掉 2 字节 zlib 头再用 web_gzip.inflateRaw（详见 B8），最后 web_charset.decode(…, "gb18030")
3 &lrcx=1（逐字时间轴）与不加是两种打包 不加：gb18030( 标准 LRC )（带 [ti:]/[ar:] 头、译文行已是独立的 [时间]行）；加了：base64+xor(gb18030( 带逐字标签的 LRC ))，且译文行要自己并 本实现选"不加" ⇒ 少一层解密、省掉上游那条 convertrawlrc 正则转换链；两种都实测过，内容质量对播放器等价

另：同一首歌、同一 rid，两次请求的 path= 字段会变（服务端分配），不影响正文。

A5 ★ 酷我 MINFO 的 size 有四种形态 —— 粗糙解析会让整个搜索失败（"青衣"事故）

现象：搜 青衣 时 Leno 端一条都搜不出来，GUI 只显示"没搜到结果"；同一时刻 Python/浏览器打同一个接口命中 10 条。

真因：MINFO 的 size 实测有 4 种写法，而 kuwo_core.bestfield() 原来只做 to_lower().replace("mb","") 就 _float()：

原文 剥 "mb" 后 _float()
size:43.64Mb 43.64 ✓
size:999.06Kb 999.06kb（单位是千字节，且 "mb" 不匹配 "kb"） ✗ 抛异常
size:365.84Kb 365.84kb ✗ 抛异常
size:zpMb（臻品档的假尺寸） zp ✗ 抛异常

异常在 search() 里抛出 ⇒ 整次搜索空手而归。"青衣"只是第一首带 Kb/zpMb 档的歌 （晴天 的全是 Mb，所以之前一直没暴露）。

判据（可复跑）：-s 青衣 vs -s 周杰伦 晴天——前者崩、后者正常。

本轮处置（kuwo_core.leno）：

  1. 新增 parsecellsize()：按 Kb/Mb/Gb/B 选 1024/1048576/1073741824/1 的系数， 并且先 isnumber() 判数字再转（认不出 ⇒ -1，绝不抛异常）；
  2. bestfield() 改用 parsecellsize 比大小 ⇒ 认不出的档位（zp）自动不参与比较；
  3. normalizeSize() 原样保留单位（999.06Kb → 999.06 KB，不再一律贴 MB）；
  4. parsesongs() 里每条结果各自 try：单条脏数据只丢这一条，不再让一个畸形字段毁掉整次搜索。

教训（两条，都值得复用到别的源）：

  • 服务端 JSON 里"看起来是数字"的字段，必须"先判再转"；_float()/_int() 遇到脏串是抛异常不是返回 0。
  • 别把异常翻译成"没搜到结果"：GUI 的 finishSearch() 原来无条件用"没搜到结果（接口可能被限流…）" 覆盖状态栏，把真因（kuwo_core.leno:104 无法将字符串转换为浮点数）盖掉了 ⇒ 用户只能看到"搜不到"， 排查从"看一行日志"变成"猜"。现已改成 searchErr 记下 worker 报的错，收尾时优先显示 搜索失败：<原因>。

A6 ★ 网易 weapi 的六个服务端事实（2026-10-08 加网易源时逐条实测）

# 事实 判据 / 对策
① 新版搜索端点 /weapi/cloudsearch/get/web 对本客户端一律回 {"code":50000005} 加 Cookie、加 X-Real-IP、csrf 前后一致、去掉 Content-Type 全试过，无效 ✗；老路径 /weapi/search/get 正常 code=200 ✓ ⇒ 用老路径
② 端点返回真数据 = 加密正确的反证 服务端要先用 encSecKey 解出 params 才会给结果 ⇒ 修加密前它一直回同一个错误码，"换端点后突然有数据"就是加密已通的信号 ✓
③ form 体里 base64 的 + 必须转义成 %2B 不转义 ⇒ 响应体 0 字节（不报错、也不是 4xx）⇒ 最容易被误判成"接口下线了" ✗
④ 未登录请求 lossless 会被降级成 320k mp3（br 仍回 320000） ⇒ "档位"字段不可信，要按 type / size 判实际格式 ✓
⑤ 付费/原唱曲没有直链（实测 id=186016 原唱「晴天」⇒ code=404、url=null） 对策：搜索后紧跟一次批量取直链（ids 支持逗号分隔的 JSON 数组）⇒ 体积 / 格式 / 可下性一次补齐，列表里就能标"下不了" ✓
⑥ 批量返回的顺序与请求顺序不一致 必须按 id 归位，不能按下标对齐 ✗

教训：③ 与 ⑥ 都是"不报错但结果错"的坑 —— 遇到"响应体为空/结构不对"时， 先怀疑自己的参数编码，别先怀疑接口下线 ✓

A7 ★ 酷狗的六个服务端事实（2026-10-08 加酷狗源时实测）

# 事实 判据 / 对策
① 取链不必签名：trackercdn.kugou.com/i/v2/ 只认 key = md5(hash + "kgcloudv2") 上游那套 android 签名 + 设备注册（AES+RSA）是给 gateway.kugou.com/v5/url 用的；这条 CDN 路更短 ✓（实测通）
② hash 大小写敏感 小写去问 CDN ⇒ status=0 / Hash not found；按搜索给的形态原样用才 status=1 ✓ ⇒ 别 to_lower ✗

④ 直链字段叫 mp3Url（数组：主链 + 备用 CDN），没有 url 只看 url 会得到"永远拿不到链"的假象 ✗（上游写 ['url'] or ['backup_url'] or ['mp3Url'] 正为此）
⑤ 移动端搜索一次带回三档体积 + 付费标记 filesize/320filesize/sqfilesize + pay_type*/price*/*privilege ⇒ 列表体积与"能不能下"不用额外请求 ✓（比网易省一次往返 ✓）
⑥ PowerShell 会误判：mobilecdn.kugou.com 的证书 .NET 不认（TLS 报错） 同机 libcurl（关校验）正常 ⇒ 别拿 PS 的失败结论宣布接口挂了 ✗

教训：② 与 ④ 都是"看着像接口死了、其实是自己没对齐约定"的坑 —— 先把上游代码读哪个字段、用什么大小写照抄一遍，再谈优化 ✓

A8 ★ 第三方聚合接口的八个事实（2026-10-08 修"拿不到 flac"时逐条实测）

背景：用户在上游 musicdl 上真跑了一轮（无任何 cookie），结论很干脆 —— 上游能拿到 flac，靠的全是第三方聚合接口（上游源码里的 _parsewiththirdpartapis）：

源 上游给出的最高档 抓 1 KB 验魔数
网易云 flac 113 / 59 / 86 MB（含付费原唱「晴天 (原唱 周杰伦)」113 MB） 真 flac ✓
酷狗 flac 30 / 29 MB 真 flac ✓
QQ flac 178 / 205 / 151 MB 真 flac ✓
对照组 网易 mp3 8.7 MB、QQ ogg 12.4 MB 真 mp3 / 真 ogg ✓

而 Leno 这边的官方面（未登录/未开会员）一档无损都拿不到 ⇒ 本次补齐 thirdparty.leno。

# 事实 判据 / 对策
① 官方三类接口在免登录态下都拿不到无损：网易 lossless 被降级 320k、QQ F000 的 purl 为空、酷狗付费曲 status=2 无损只能走第三方 ⇒ 三条源各接一条通路（网易 music.qinglvai.top / QQ api.vkeys.cn / 酷狗 api.baka.plus/meting）✓
② 三条通路的直链都验过魔数 抓前 1 KB ⇒ fLaC（102,76,97,67）✓；QQ 那首 4:29 的曲子拿到 178 MB ≈ 5.5 Mbps（上游 kbps: 5549kbps 一致）⇒ 是臻品母带级，比标准无损还高一档 ✓
③ 网易那条的档位是字符串（jymaster/hires/lossless/exhigh/standard） 上游那套 level=999 会回 {"code":40012,"当前音源不支持所选音质"} ✗（实测）；另：游客每日只给 3 首（code=42903）⇒ 用尽后退 mp3 兜底
④ musicapi.haitangw.net/music/wy.php 会降档：quality 写「超清母带」、直链却是 .mp3（10.33 MB / 320k） 与 A2 同款 ⇒ ext 一律按直链后缀回填，绝不信标签 ✓（酷我那支 kw.php 仍正常给 flac ✓）
⑤ 302 类接口不能开重定向跟随（跟随就会把整个 flac 拉进内存） 关跟随读 Location、读完立刻恢复；且读不到 Location 必须认输 —— 关着跟随时 effectiveUrl 就是接口地址本身，拿它当直链会把接口地址写成直链 ✗（实测：baka 的 br=2000 回 502 正好触发这条）
⑥ 同一接口会按档位单独失败：同一个 hash，baka br=2000 回 502、br=999000 正常 302 ⇒ 逐档降着重试（QQ 的 vkeys 同理，14→9 六档）
⑦ 第三方直链必须随行带着走：网易那条的游客配额在搜索时就用掉了 落盘时再取一次必然 42903 ✗ ⇒ 行里加第 10 项 = 直链（dl_engine.F_URL），下载与试听都用它 ✓
⑧ 酷狗 CDN 证书 Windows 侧不认（A7-⑥ 的翻版） 第三方给的是 fs.youthandroid2.kugou.com：schannel 报 SEC_E_WRONG_PRINCIPAL ⇒ curl/PS 一律测不通，而 libcurl（关校验）照拿 206 ✓

教训：这批接口的共同特征是「不报错但给假结果」（标签与直链格式不符 / 502 时 effectiveUrl 回接口地址 / 配额用尽只回业务码）⇒ 判据一律落到直链本身（后缀 + 抓 1 KB 验魔数）； 并且任何一环失败都保持官方结果（有 mp3 的行照旧可下）⇒ 第三方全挂也不会比以前差 ✓

B14【低】数值转换的报错不带坏值，与同运行时的文件报错风格不一致（诊断的一致性）

项 内容
现象 _float("zp") 的消息是 无法将字符串转换为浮点数 —— 不带坏值、不带类型名（_int("abc") 同理：无法将字符串转换为整数）
内部对照（同一轮实测） files.open("D:\\不存在的目录\\x.txt", "rb") 的消息是 无法打开文件 'D:\\不存在的目录\\x.txt' —— 带值 ✓

为什么这条值得修（成本/收益最划算） 排查时"哪个值坏了"就是核心线索。青衣 事故（A5）里，我是靠回到接口原始 JSON 才看出 size:999.06Kb / size:zpMb 的；如果消息直接写 无法转换为 float："999.06kb"，至少省一轮试错。而这条信息在抛出的那一刻就在手上，取不到是纯浪费
建议 文案统一成 无法转换为 float："<原值>"（Python 的对照口径：could not convert string to float: 'zp'）；_int 同理；若原值很长，截断到 N 字符即可
成本 低（原生函数里把入参拼进消息）；文档零
