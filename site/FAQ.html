Leno 常见问题 (FAQ)

本文件记录 Leno 语言使用过程中的高频问题与经过验证的结论，持续补充。

Q：为什么打包成 exe、或运行 .lenb，比直接运行 .leno 源码更快？

现象

对一段纯计算的「经典斐波那契数列」脚本（fib(30)）分别用三种方式运行，计时只包住 fib(30) 本身：

运行方式 耗时 实际执行路径
打包 exe（嵌入 .lenb） ~190 ms 反序列化 → vm_run_chunk
leno xxx.lenb（预编译字节码） ~195 ms 反序列化 → vm_run_chunk
leno xxx.leno（源码） ~236 ms 编译 → vm_run

关系：.lenb(195ms) ≈ 打包 exe(190ms) << 源码 .leno(236ms)。

约 22%（~45ms）的差距全部来自“编译器内存税”，而不是字节码本身有任何差异——三组最终都在同一个 VM、同一份字节码上执行。

为什么编译器驻留会拖慢 VM？

  1. icache（指令缓存）污染 编译器的词法/语法/语义/codegen 代码与 VM 解释器代码同在进程代码段。即使编译阶段已结束，这些代码页仍留在内存。VM 的指令分派循环（vm_run 的 switch(opcode)）执行时，L1 icache 被编译器代码页挤占，指令预取命中率下降。

  2. dcache（数据缓存）污染 编译器留下的 AST 节点、符号表、类型信息、模块扫描结构——这些活跃内存与 VM 的栈、常量池、对象堆竞争 L1/L2 dcache。斐波那契递归是 cache-sensitive 的密集计算，每一次栈帧访问、每一次常量读取，都可能因 dcache miss 多等几个周期。

  3. TLB 压力 编译器分配的内存页增加了页表遍历开销，虽不如 icache/dcache 明显，但在微秒级 benchmark 里也会累积。

关键证据

src/main.c 中 lenolang_run() 的执行顺序是：先 vm_run()（第 186 行），之后才释放 AST / 语义表 / 字节码块（第 189–194 行）。这说明编译器资源不是“懒释放”，而是在 vm_run 执行期间根本没释放。

如果编译器在 vm_run 之前就被完全清理，那么 .leno 与 .lenb 的差距应当只等于反序列化时间（~5ms），而非 45ms。实测 45ms 印证了“dcache/icache 污染”才是主因。

注：打包 exe 与 leno xxx.lenb 走的是完全相同的执行路径（都是 vm_run_chunk → vm_run），所以两者速度一致；慢的只有“现场编译 + 编译器驻留”的 .leno 直跑方式。

工程层面的建议

场景 建议
纯计算密集型脚本（算法、数据处理） 务必先编译成 .lenb，再运行或打包。22% 的差距在长时间运行中会被放大。
GUI / 游戏 / 带 I/O 的应用 差异可忽略。I/O 等待（16ms 一帧、磁盘读写、网络延迟）会掩盖这 45ms。
打包 exe 分发 有意义，但意义在于保护源码 + 即点即跑，而不是性能优化。
REPL / 开发调试 直接用 .leno，开发效率优先，不在乎那点差距。

如果想进一步压榨性能（待验证方向）

既然瓶颈已确认在「编译器内存驻留」，有几个可选方向：

  1. 编译后主动释放编译器资源 在 main.c 中，compile_source_to_chunk() 生成 chunk 之后、调用 vm_run() 之前，主动释放编译器资源：

c // 伪代码 compile_source_to_chunk(source, &chunk); free_ast(ast); // 释放语法树 free_semantic_tables(); // 释放符号表、类型信息 free_module_scanner(); // 释放模块扫描结构 // 然后再 vm_run(chunk)

如果这 45ms 差距能缩到 5ms 以内，即可确认是 dcache 污染问题。（尚未实现，待验证。）

  1. 编译器与 VM 分离进程（极端方案） 编译阶段把源码编成 .lenb，运行阶段只负责加载执行（leno.exe 一肩挑这两件事）。这就是现在的 .lenb 模式，已经是最优解。

  2. 预热缓存（warmup） 若必须跑 .leno 源码，可在正式计算前跑一段“空转”代码，把 VM 的 hot path 预热进 icache，减少编译器代码页的干扰。收益有限。

一句话总结

打包 exe 不会让你的斐波那契算得更快，它只是让编译器滚出内存，别占着 cache 不干活。

如果发现计算密集型脚本 .leno 直跑比 .lenb 慢一截，不是 VM 有问题，而是编译器还在旁边“看热闹”。

（本条目由实测对比 exe / .lenb / .leno 三种运行方式得出，结论已验证。）
