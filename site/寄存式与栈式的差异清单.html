二、A 类：寄存器式对、栈式错（真实行为差异）

A1. 导出（模块）变量的声明类型规范化（就是你问的 float 那条）

最小复现（两个文件放同一目录）：

// _mod.leno
export float mfLit = 1          // 整数字面量初始化一个声明为 float 的导出变量
export float mfExpr = 1 + 1

// main.leno
import "_mod.leno" as m
main() {
    print("type=", type(m.mfLit), "  /2=", m.mfLit / 2)
}

实测对比（--no-cache，两边的完整形态）：

模块里的写法 寄存器式 栈式
export float mfLit = 1 float / 0.5 ✅ int / 0 ❌
export float mfExpr = 1 + 1 float / 1.0 ✅ int / 1 ❌
export float mfDecimal = 1.5 float / 0.75 ✅ float / 0.75 ✅
export int miLit = 7 int / 3 ✅ int / 3 ✅
export string msLit = "s" / export bool mbLit = true 正确 ✅ 正确 ✅
export Array[int] maLit = [1, 2] Array[int] ✅ Array[int] ✅
脚本内（非导出）的全局 float g = 1 float / 0.5 ✅ float / 0.5 ✅

⇒ 差异只在"导出变量 + 用整数字面量初始化 + 声明为 float"这一格； /2 走 int 除法是静态类型错了，type() 也是错的（运行时值也是 int，两个面一起错）。

根因（src/module_compiler.c 的"编译期预登记导出变量"）：

// 修之前：直接按初始化字面量建值，**完全无视声明类型**
case AST_NUM:
    if (init->u.num.is_bigint) { ... }
    else if (init->u.num.is_float) { var_val = val_float(...); }
    else { var_val = val_int((int)init->u.num.value); }   // ← export float x = 1 登记成 int 1 ✗

登记进去以后，模块初始化收尾那段"从 globals 补填 exports"看到 val_is_null(current_val) 为假就跳过了 ⇒ 错的 int 值一直留在 exports 里。 而模块内部读自己的槽位（已按声明类型 CAST 过）是 float ⇒ 出现"同一个变量，模块内 0.5、模块外 0"的诡异现象。

寄存器式修法（commit 6667a60）：预登记时尊重声明类型 —— 声明是 float 而字面量是整数时也按浮点存。

栈式现状：同一段逻辑、同样的问题（未同步）。按约定：栈式逐步放弃，不追平； 如果哪天要同步，改法与寄存器式一样（decl_kind == TYPE_FLOAT 时走 val_float）。

回归锁定：assert/test_cross_module_types.leno（含 int / string / bool 反向用例， 防止"顺手把所有导出变量都转成 float"）。

A2. async 函数经一等值调用必须返回 Future（原 C 类 C4，已修）

最小复现：

import io
import asyncs
async func work(int n): int {
    await asyncs.sleep(1)
    return n * 2
}
async func driver() {
    var f = work
    io.print("via var=", await f(3))    // 曾经：整段**静默无输出**（exit=0，一行都不打）
}
main() { driver(); asyncs.run() }
写法 寄存器式 栈式
var f = work; await f(3) 6 ✅ 静默无输出（exit=0）❌
var r = work(3); type(r) object（Future）✅ 拿到裸值 ❌
把 async 函数当参数传、函数里 await cb(7) 14 ✅ ❌（静默 / 或类型检查挡下）

根因：编译器只在静态能确定 callee 是 async 时才发 OP_ASYNC_CALL； 经变量 / 当参数传 / 经绑定对象调用时静态判不出来 ⇒ 发普通 CALL ⇒ 函数体被同步执行 （返回值不是 Future；体里若有 await，它还会把当前协程的帧搞乱 ⇒ 静默死亡）。

寄存器式修法：把 async 标记落到函数对象上（ObjFunction.is_async：编译期写入 + 模块缓存往返，缓存版本 v12 → v13，旧缓存必须作废），再由 VM 在 OP_CALL / OP_TAIL_CALL 的运行期兜底 —— 命中 async 闭包就"建协程 + 返回 Future"，与 OP_ASYNC_CALL 共用同一份实现（vm_start_async_call）。语义上这就是对的：async 函数一旦被调用就返回 Future，与写法无关。

回归锁定：assert/test_async.leno 测试9（经变量 / 当参数传）。

A3. 跨模块 async（export async func / export struct 的 async 方法）（原 C 类 C2，已修）

最小复现（两个文件同目录）：

// mod.leno
import asyncs
export async func work(): int {          // ① 导出的 async 函数
    await asyncs.sleep(1)
    return 7
}
export struct Worker {                   // ② 导出 struct 的 async 方法
    int n = 0
    async func run(): int {
        await asyncs.sleep(1)
        return self.n + 1
    }
}
写法 寄存器式 栈式
await m.work() 7 ✅ ❌「模块 'm' 中没有方法 'work'」
var w = new Worker(); await w.run() 42 ✅ ❌ 3 条「struct 的字段 'func'/'asyncs'/'self' 声明类型无法解析」警告 + ❌「内部错误: struct 'Worker' 方法收集不完整…请报告编译器 bug」
普通导出函数 m.plain() 5 ✅ 5 ✅（都对，注意别被 async 化）

根因：整条链路上四处都不认 async（grep async src/module_symbol_table 原来是 0 命中）：

位置 原来会怎样
parser_module.c 的 export 分支 只认 TOK_FUNC ⇒ export async func 直接报「export 后面期望 var、const、func…」
scan_func.inc（模块函数扫描） 只认 func ⇒ async func 落到 scan_var.inc 被当成"类型在前"的变量声明（"async" 当类型、"func" 当变量名）
scan_struct.inc（struct 方法扫描） 只认 func ⇒ async func 落到字段解析，伪造出 func/asyncs/self 三个字段
module_loader.c 的 extract_exports（导出名单） 只跳过 func/var/const/… ⇒ 导出名被登记成 async/func

寄存器式修法：解析器认 TOK_ASYNC；扫描器加 scan_skip_async 前缀剥离（函数 + struct 方法两处）；loader 的导出名单同样跳过；符号表加 ModuleFuncSymbol.is_async / ModuleStructMethod.is_async（随 .lenosymc 往返，缓存版本 v14）；codegen 对跨模块 async 调用发 OP_ASYNC_CALL（与本地路径同口径），OP_ASYNC_CALL 也接受模块导出常见的裸函数对象；跨模块方法的占位 AST 带上该标记。

⚠ 加字段的血泪教训：给 ModuleStructMethod 加 is_async 后， sym_table_add.inc 的 module_symbol_table_add_struct 是逐字段手工深拷贝（malloc + 逐项赋值）， 漏拷这个字段 ⇒ 目标里的 is_async 是未初始化垃圾，偶尔为 1 ⇒ 普通方法被当成 async （返回 Future、打印成 [object]），失败点还随内存布局漂移（test_use_return_edge 等 6 个测试）。 已补上拷贝并把 malloc 换成 calloc —— 以后漏拷至少退化成 0（安全默认），不再是随机行为。 给这类结构体加字段时，务必检查"手工深拷贝"点（add_struct 的方法数组、add_func 的扩容槽位、 缓存往返的三处读写）。

回归锁定：assert/test_async_cross_module.leno（含"普通导出函数不受影响"的反向断言）。

A4. 函数返回值按声明类型规范化（原 C 类 C1，已修）

最小复现：

func f(): float { return 1 }          // 整数字面量
func g(): float { int n = 5; return n }   // int 变量
func h(): float { return 1 + 1 }          // 表达式
检查（main 里 f() / 2…） 寄存器式 栈式
type(f()) / f()/2 float / 0.5 ✅ int / 0 ❌
g()/2 2.5 ✅ 2 ❌
h()/2 1.0 ✅ 1 ❌
跨模块 m.ret_float()/2 0.5 ✅ 0 ❌
struct 方法 b.scale()/2 1.5 ✅ 1 ❌
async func + await af()/2 0.5 ✅ 0 ❌
反向：func i(): int { return 7 } → i()/2 3 ✅（int 除法） 3 ✅
反向：构造函数 / : string / : bool 不受影响 ✅ 不受影响 ✅

根因：gen_return 从来没看过声明的返回类型 —— 求值完直接 emit_return。 变量的声明/赋值早就有 emit_cast_for_target（A1 补齐了全局/模块分支）， 返回值这一处却漏了，于是"函数说好返回 float、实际返回 int"； 跨模块调用点只信声明类型，所以在模块边界暴露得最明显。栈式侧同样如此，是共有缺口。

修法：CodeGen 记住当前函数的 AST（current_func_ast，随嵌套函数保存/恢复； ObjFunction.return_types 在寄存器式里从未被填过，不能依赖它）， gen_return 按 u.func.return_type 插 CAST —— 与变量声明/赋值共用 emit_cast_for_target； 构造函数（返回 self）与多返回值不走这条。

💡 一般规律：凡是有"声明类型"的地方，都要在赋值处做一次规范化。 到目前为止的三处：变量声明（A1 修的模块/全局分支）、赋值（早就有）、 函数返回值（A4）。以后再加新的"带声明类型"的语法，先想想这一处补齐没有。

回归锁定：assert/test_return_type_cast.leno（本地 / 跨模块 / struct 方法 / async / 构造函数 + int·string 反向用例）、assert/xmod_types.leno 补 ret_float_lit / ret_float_var / ret_int / ret_str。

A5. 多个协程同时失败时 run() 汇总抛出（原 C 类 C7，已修）

最小复现：

import io
import asyncs

async func riska(): int { await asyncs.sleep(1); throw "A" }
async func riskb(): int { await asyncs.sleep(1); throw "B" }

main() {
    riska()
    riskb()
    try { asyncs.run() } catch e { io.print("run caught: ", e.msg) }
    io.print("done")
}
侧 输出
寄存器式 run caught: 2 个协程失败: A; B / done、exit=0 ✅（正是文档承诺的汇总格式）
栈式 run caught: A，另外一条 B 的未捕获错误从 main 之外冒出来 ❌

根因 / 修法：这条不是单独修的 —— E15（协程异常屏障）修完后自动正确了。 以前协程里抛的异常会被调用方的 try-catch 半路截走，第二个失败根本没走到 run() 的收集点， 反而在调用方之外冒出来；加上协程边界之后，两个失败都归 asyncs.run() 收集， 于是按文档汇总成 N 个协程失败: …; …。

回归锁定：assert/test_async_exception_barrier.leno 第 ④ 条断言（连跑稳定）。

A6. asyncs 的查询类 API 缺失：current() / is_done() / get_result()（原 C 类 C9，已补）

现象：docs/module_asyncs.md 把这三个 API 当已可用写 —— 有签名、有示例， 甚至有「必须先使用 await 确保 Future 完成，再调用 get_result()」这种注意事项， 但两个引擎的注册表里都只有 sleep / run / yield / all / timeout ⇒ 照文档写必然失败：

[语义错误] 未找到模块方法: asyncs.current（可用: timeout, run, all, yield, sleep）

修法（文档是规范，实现向文档对齐；运行时数据其实基本齐了）： - ObjFuture 早有 completed / result ⇒ is_done / get_result 直接读； - 只缺协程 ID：给 ObjCoroutine 加 int id，在 coroutine_new 里从 VM 的计数器 （next_coroutine_id）递增分配。放 VM 上而不是文件级 static，是因为各线程的 VM 都是 memset(&vm, 0, sizeof(VM)) 出来的 ⇒ 天然线程安全、每个 VM 独立编号； - 三个 native + 注册，参数类型写 TYPE_FUTURE ⇒ 语义层会在编译期就拦住 is_done(123)。

行为（实测）：

调用 结果
main 里 asyncs.current() -1（不在协程里；文档未规定，取这个以免与真实 ID 混淆）
协程里 asyncs.current() 1、2…（每个协程一个，互不相同）
未完成 future：is_done(f) / get_result(f) false / null ✅（文档同此约定）
await f 之后 true / 返回值（实测 42、200） ✅
asyncs.is_done(123) 编译期报「参数 1 类型错误: 期望 'Future'，但传入 'int'」 ✅

栈式仍报「未找到模块方法: asyncs.current」（连提示里列出的可用 API 也只有 5 个）⇒ 有意差异。

回归锁定：assert/test_asyncs_query_api.leno。

三、B 类：两边都错、现象还不一样

B1. 局部函数遮蔽同名全局 async 函数，且调用点在该局部函数之后才被语义分析

async func dup(): int { await asyncs.sleep(5); return 5 }

async func other(): int {
    func dup(): int { return 99 }     // 局部同名（非 async）
    return dup()                       // ← 这行是对的（局部遮蔽）
}

async func later(): int {
    return await dup()                 // ← 这行被"污染"：func_table 里 dup 已是那个局部函数
}
侧 现象
寄存器式 other() 正确返回 99；later() 静默少输出（协程提前结束，无任何报错）
栈式 other() 正确返回 99；later() 报「await 只能等待 Future 对象」

根因：func_table 是按名字的全局表、没有作用域维度；局部函数会覆盖同名全局条目。 两边都用"语义遍历到调用点的时点"来判定 async（寄存器式的 ast->u.call.callee_is_async）， 时点早于污染 → 大部分场景正确；但调用点若在污染之后，时点也救不了。

处置：本轮不修（两边都错、且属边角写法）。要彻底解决需要给 func_table 加作用域维度 （记录函数定义所在作用域，查找时按调用点作用域链过滤）——那是结构性改动，单独排期。

注意：这是"两边都错"，不要照任一侧对齐；也不要把寄存器式的"静默少输出"当成回归 —— 它在修 A1/async 之前就是这样。

C8 仍属实：失败 future 在 all() 里是 [null]、不抛；错延后到 run() 才抛（实测异常值类型 Dict[string, any]） 仍开 ⇒ T4（待拍板）
C10 仍属实：未完成成员给 null，run() 之后再取才是真值（实测 null → 5） 仍开 ⇒ T4（待拍板）
~~C11~~ ✅ 已修（T11 ✅）：int? a = null 参与算术 ⇒ 编译错（另有可空运算警告）；未赋默认值的值类型字段参与算术 ⇒ 运行期报错（不再静默算 0 ✗）。既有用例：test_null_arith_compile_error / test_null_arith_error 已实现

五、D 类：栈式侧潜伏缺陷（当前不崩，但别照抄）

D1. 插值串 parts / exprs 两个数组容量可能不平行

parser_expr.c 的插值串收尾分支只给 parts 扩容、没给 exprs 扩容（前面两处扩容都是成对的）， 而 count = idx + 1 是按 idx 算的 ⇒ exprs 的容量可能小于 count。

  • 寄存器式：曾经因此编译期段错误（$"{a}{b}{c}{d}" 这类 4 段及以上插值必崩， exit=0xC0000005，--debug 一行都打不出来）。已修（commit 3531869）： 解析器两数组一起扩容 + 消费端上界改成 count-1。
  • 栈式：解析器同样只扩 parts，但它的消费端按约定只读 exprs[0..count-2] （codegen_inline.c 注释写明 count = exprs_count + 1）⇒ 侥幸不崩。

⚠ 所以：栈式现在是对的、代码是带雷的。日后若把寄存器式的修法同步过去， 两处要一起改（要么都扩、要么都不读最后一格），否则迟早踩同一个越界。

## 九、反向差异：栈式有、我们缺的优化（性能）

前面几节都是"寄存器式对、栈式错/慢"。这里记反方向的 —— 栈式里已经做了、 寄存器式没做（或没做全）的优化。不要默认"寄存器式一定更优"。

### F1. arr.add(x) 缺融合（已补）

现象（同一轮对照，30 万次 .add()）：寄存器式 4.91ms vs 栈式 3.99ms ⇒ 慢 23% ✗； 连累"原始快速排序"（每元素一次 .add()）在小规模上偏慢。

根因（字节码 dump 对照）：

a.add(i) 的循环体
栈式 GET_LOCAL a / GET_LOCAL i / OP_ARRAY_APPEND_NOPUSH = 3 条
寄存器式（修前） MOV(接收者) / MOV(实参) / GET_METHOD "add" / CALL = 4 条，且走完整方法派发

栈式 codegen 早就把 arr.add(x) 融合成一条专用指令，寄存器式一直走通用方法调用。

修法：在 gen_method_call 入口加融合 —— 方法名 add、恰好 1 个实参、 接收者静态类型是 TYPE_ARRAY ⇒ 直接发 OP_ARRAY_APPEND（求值顺序安全： 接收者与实参各自取新临时寄存器，长度结果再 MOV 到目标）。

同轮 A/B（git stash 前后对照，机器漂移互相抵消）：add 5.32ms → 4.70ms = 0.88x ✓； 排序样例 400k 优化 0.70x、100k 原地 0.80x，正确性 12/12 全 true ✓。

⚠ 顺带补掉一个真隐患：OP_ARRAY_APPEND 缺 GC 写屏障，而原生 arr_add 一直有。 本 GC 是分代 + 记住集（老年代引用年轻代必须入集，见 leno_value.h 的 REMEMBERED 位 与 gc.c 开头）。此前该指令只被大数组字面量用到（young→young，恰好不需要屏障）所以没暴露； 把 arr.add(x) 融合进来之后，"老数组追加年轻值"变成常规路径 ⇒ 必须补。 教训：融合指令必须与它替代的原生函数逐条对齐副作用（这里是写屏障），别只对返回值。
