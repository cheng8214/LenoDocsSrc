错误堆栈追踪改进方案

本文是设计方案，代码块是示意（含故意抛错的反例），不可直接运行。

⚠ 局部过时（2026-10-02 注）—— 正文其余部分仍属现行，只有下面三点请按现状重读： ① §「内联优化对调用栈的影响」说"Leno 编译器实现了函数内联优化（codegen_inline.c）"—— 该文件已随寄存器式改造删除（0f0cf52，621 行）且尚未移植 ⇒ "被内联的函数不会出现在 调用栈中"这条当前不成立（所有脚本函数调用都是真帧，调用栈里都能看到）； ② 文中 LENO_BIN_VERSION v3.2.10 / v3.2.11 是当时值，现为 v3.2.12（src/include/leno_serialize.h:157）； ③ 文中断言数「412/0」是当时值 —— 本仓库不再在文档里钉断言总数，一律以实跑 .\build\leno.exe assert\run_tests.leno build\leno.exe assert 为准。

现状分析

Leno 的异常系统已有基础的调用链支持：

已有能力

throw_runtime_error() 在创建异常对象时，已将调用栈信息存入 e.stack：

try {
    var a = 1 / 0
} catch e {
    print(e.msg)     // "除零错误"
    print(e.file)    // "script.leno"
    print(e.line)    // 2
    print(e.stack)   // ["<main>", "inner", "middle", "outer"]
}

异常对象是一个 Dict，包含：

属性 类型 说明
msg string 错误消息
line int 错误发生的行号
file string 错误发生的文件名
stack array 调用栈（函数名数组）

存在的差距

问题 影响 位置
e.stack 只有函数名，缺少行号 无法定位每层调用的具体位置 vm_exception.inc → throw_runtime_error()
throw "string" 不捕获调用栈 用户手动 throw 的异常无 stack 信息 op_exception.inc → OP_THROW
未捕获异常不打印调用栈 程序崩溃时只显示一行错误，无法追踪调用链 vm_exception.inc → throw_runtime_error() 末尾 + op_exception.inc → OP_THROW 末尾

改进目标

1. 丰富 e.stack 内容：每帧包含 函数名 (文件:行号)

当前：e.stack = ["<main>", "inner", "middle", "outer"]

改进后：e.stack = ["<main> (script.leno:10)", "inner (script.leno:5)", "middle (script.leno:3)", "outer (script.leno:2)"]

2. throw 语句也捕获调用栈

当前：throw "error" 抛出的是裸字符串，catch e 拿到的 e 就是字符串本身，无 .msg/.stack 等属性。

改进后：throw "error" 自动包装为异常对象，包含完整的 .msg/.file/.line/.stack。

兼容性：catch e 中 e 仍然是字符串可用的（通过 e.msg 或直接 print(e) 打印消息）。检查 e 是否为 Dict 来决定如何访问属性。

3. 未捕获异常打印完整调用栈

当前输出：

[错误] script.leno:5: 除零错误

改进后输出：

[错误] script.leno:5: 除零错误
    at inner (script.leno:5)
    at middle (script.leno:3)
    at outer (script.leno:2)
    at <main> (script.leno:10)

实现方案

涉及文件

文件 改动
src/vm/vminc/vm_exception.inc 改进 throw_runtime_error() 的 stack 构建；新增 build_stack_trace() 辅助函数；未捕获异常打印调用栈
src/vm/vminc/op_exception.inc OP_THROW 中对字符串异常包装为异常对象

3.1 新增 build_stack_trace() 辅助函数

在 vm_exception.inc 中新增，用于构建包含文件名和行号的调用栈数组：

// 构建调用栈数组，每帧格式: "func_name (file:line)"
static ObjArray* build_stack_trace(void) {
    ObjArray* stack_arr = arr_new(vm.frame_cnt);
    if (!stack_arr) return NULL;

    for (int i = vm.frame_cnt - 1; i >= 0; i--) {
        CallFrame* f = &vm.frames[i];

        // 获取函数名
        const char* func_name = NULL;
        if (f->closure && f->closure->function && f->closure->function->name) {
            func_name = f->closure->function->name;
        } else if (i == 0) {
            func_name = "<main>";
        } else {
            func_name = "<anonymous>";
        }

        // 获取文件名
        const char* filename = "unknown";
        if (f->chunk && f->chunk->filename) {
            filename = f->chunk->filename;
        }

        // 获取行号（当前 IP 对应的行）
        int line = 0;
        if (f->chunk && f->chunk->lines && f->ip) {
            int offset = (int)(f->ip - f->chunk->code);
            if (offset >= 0 && offset < f->chunk->len) {
                line = f->chunk->lines[offset];
            }
        }

        // 拼接 "func_name (file:line)"
        char frame_desc[BUFFER_XLARGE];
        snprintf(frame_desc, sizeof(frame_desc), "%s (%s:%d)", func_name, filename, line);
        ObjString* frame_str = str_copy(frame_desc, strlen(frame_desc));
        if (frame_str) {
            arr_write(stack_arr, stack_arr->count, val_obj((Object*)frame_str));
        }
    }
    return stack_arr;
}

将现有的 stack 构建逻辑替换为调用 build_stack_trace()：

// 替换原来的 for 循环构建 stack

3.4 OP_THROW 包装字符串异常

在 op_exception.inc 的 OP_THROW 中，当异常是字符串时，自动包装为异常对象：

OPCODE(OP_THROW) {
    frame = &vm.frames[vm.frame_cnt - 1];
    Value exception = vm_stack_pop(&vm);
    if (val_is_null(exception)) {
        exception = vm.exception;
    }

    // 如果 throw 的是字符串，包装为异常对象（含 stack 信息）
    if (val_is_string(exception)) {
        ObjString* str = (ObjString*)val_as_obj(exception);
        ObjDict* err_dict = dict_new(8);
        if (err_dict) {
            // msg
            dict_set(err_dict, val_obj((Object*)str_copy("msg", 3)), exception);
            // line
            dict_set(err_dict, val_obj((Object*)str_copy("line", 4)), val_int(GET_CURRENT_LINE()));
            // file
            const char* filename = frame->chunk->filename ? frame->chunk->filename : "unknown";
            dict_set(err_dict, val_obj((Object*)str_copy("file", 4)),
                     val_obj((Object*)str_copy(filename, strlen(filename))));
            // stack
            ObjArray* stack_arr = build_stack_trace();
            if (stack_arr) {
                dict_set(err_dict, val_obj((Object*)str_copy("stack", 5)),
                         val_obj((Object*)stack_arr));
            }
            exception = val_obj((Object*)err_dict);
        }
    }

    // ... 后续逻辑不变
}

3.5 未捕获异常在 OP_THROW 中也打印调用栈

OP_THROW 末尾，当没有找到 catch/finally 时：

if (vm.has_exception) {
    if (vm.current_coroutine) {
        return -1;
    }
    // 打印调用栈
    if (val_is_obj(vm.exception) && val_as_obj(vm.exception)->type == OBJ_DICT) {
        ObjDict* err = (ObjDict*)val_as_obj(vm.exception);
        // 获取 msg
        Value msg_val = dict_get(err, val_obj((Object*)str_copy("msg", 3)));
        char* msg = val_is_string(msg_val) ? strdup(((ObjString*)val_as_obj(msg_val))->chars) : strdup("未知错误");
        // 获取 file/line
        Value file_val = dict_get(err, val_obj((Object*)str_copy("file", 4)));
        Value line_val = dict_get(err, val_obj((Object*)str_copy("line", 4)));
        const char* fname = val_is_string(file_val) ? ((ObjString*)val_as_obj(file_val))->chars : "unknown";
        int ln = val_is_int(line_val) ? (int)val_as_int(line_val) : 0;

        fprintf(stderr, "[错误] %s:%d: %s\n", fname, ln, msg);
        // 打印 stack
        Value stack_val = dict_get(err, val_obj((Object*)str_copy("stack", 5)));
        if (val_is_obj(stack_val) && val_as_obj(stack_val)->type == OBJ_ARRAY) {
            ObjArray* stack_arr = (ObjArray*)val_as_obj(stack_val);
            fprintf(stderr, "调用栈:\n");
            for (int i = 0; i < stack_arr->count; i++) {
                if (val_is_string(stack_arr->elements[i])) {
                    fprintf(stderr, "    at %s\n", ((ObjString*)val_as_obj(stack_arr->elements[i]))->chars);
                }
            }
        }
        free(msg);
    } else {
        char* msg = value_to_string(exception);
        runtime_error(msg, GET_CURRENT_LINE());
        free(msg);
    }
    return -1;
}

实际实现说明

已实现的改进

  1. e.stack 格式升级：从纯函数名数组 ["inner", "middle", "<main>"] 变为 "func (file:line)" 格式 ["inner (script.leno:3)", "middle (script.leno:6)", "<main> (script.leno:10)"]。仍是字符串数组，不影响遍历。

  2. 未捕获异常打印调用栈：所有未捕获异常路径（throw_runtime_error、OP_THROW、OP_END_TRY）现在都会通过 print_unhandled_exception() 打印完整的调用栈到 stderr。

  3. throw 字符串向后兼容：throw "string" 保持原行为，catch e 拿到的 e 仍然是字符串本身。但未捕获时也会实时构建并打印调用栈。

  4. 未捕获异常消息提取：当异常是 Dict 时，从 e.msg 提取消息字符串传给 runtime_error，避免打印整个 Dict 表示。

内联优化对调用栈的影响

Leno 编译器实现了函数内联优化（codegen_inline.c），满足以下条件的函数会被内联到调用点： - 函数体 ≤ 8 条语句 - 不含 try-catch、switch、循环 - 无 upvalue（闭包捕获） - 非 async、非构造/析构函数 - 无泛型类型参数 - 无默认参数 - 内联深度 ≤ 3 层

被内联的函数不会出现在调用栈中，因为它们没有独立的 CallFrame。这与 C/C++ 的 -O2 内联行为一致。

2026-10-02 更新：报错文案统一（引擎错误一律自带位置）

触发：PvZ 的 _int("12\r") 抛 无法将字符串转换为整数，窗外层 catch 打出来的那行 完全没有位置。查下来不是"位置丢了"，而是两个口径：

来源 异常值 e.msg 里带位置吗
原生模块 native_throw_error()（_int、越界…） Dict{msg,line,file,stack} ✗ 只有一句裸消息
VM 操作码错误（除零等，走 _with_operand(s)） Dict ✓ 自带 [操作]/[内部]/[位置]/[操作数]/[调用栈]
用户 throw "x"（wrap_string_exception） Dict ✗（msg 就是用户那句话，本就不该改写）

而 print(e) / "…" + e 只渲染 e.msg ⇒ 前两类看着"有位置"、后两类看着"凭空"。

改法（src/vm/vminc/vm_exception.inc）：

  1. throw_runtime_error() 在 msg 里没有 [位置] 时，补 [位置] file:line (func: 名) + [调用栈] …（有则原样保留 ⇒ 富文案不会被二次追加）。 行号取调用方传入的 line（即 GET_CURRENT_LINE()），保证与 e.line 同源。 覆盖：原生模块错误 + 所有裸 throw_runtime_error("…") 的操作码错误。
  2. 行号 off-by-one 修复：get_current_context() / append_stack_trace() / build_stack_trace() 原先按 lines[ip] 取行，而 ip 指向下一条指令 （约定见 run/01_prologue.inc）⇒ [位置] 与栈帧行号整体偏一行，与 e.line 自相矛盾 （实测：var q = 1 / z 在第 20 行，[位置]/#0 却报 21）。现统一按 ip-4 取。
  3. 用户 throw "x" 不改写：那是用户数据（也有一批断言在比 e.msg 原文）；位置照旧从 e.file / e.line / e.stack 读。
  4. 未捕获路径去重：print_unhandled_exception() 原先无条件再列一遍 调用栈:， 而 msg 现在自带 [调用栈] ⇒ 同一份帧会打两遍。现加守卫 !strstr(msg, "[调用栈]") ⇒ 未捕获输出恰好一份位置 + 一份调用栈。

影响面：e.msg 的正文不变，只是尾部多了位置块 —— 业务代码里 _dlog("… " + e.msg) 这类日志因此自动带上位置（更好）。精确比 e.msg 的两个断言改了口径（改比首行）： assert/test_array_bounds.leno（两条越界路径本来就在不同行）、 assert/test_async_exception_barrier.leno。 新增护栏 assert/test_error_msg_position.leno（引擎错误带位置、行号与 e.line 同源、 只补一次、用户 throw 原文不动）。全套断言 410/0。

不 bump LENO_BIN_VERSION：只改运行期文案，不涉及常量折叠/指令发射/产物布局 （与登记表 v3.2.9 那条"native 求值语义变化"判据不同）。

第二批（同日）：异常跨边界不再被"重造"

问题：原生调用返回处那几段 if (vm.has_exception) 一律把异常 value_to_string() 成字符串，再按"原生调用点"造一个新异常 ⇒ 已经是异常对象的异常 （协程的失败经 asyncs.run() 抛回、FFI 回调带回来的）被降级成字符串，原始 msg/line/file/stack 全丢。实测：协程里 throw "inner-boom"（第 6 行）经 asyncs.run() 抛回，e.line 变成 asyncs.run() 那一行（27），e.msg 还被追加了 一个"位置块"。同类分叉共 7 处（06_call.inc ×3、10_vars_module.inc（模块方法， asyncs.run() 走这里）、12_fields_object.inc、13_async_ffi.inc ×2（clib / cfunc）、 vm_call.inc ×2）—— 同一条规则写了 9 遍，正是"不统一"的温床。

改法：

  1. 把 throw_runtime_error() 里"向上找 catch/finally + 未捕获报告"整段抽成 dispatch_exception(line)（只此一份走法；⚠ 这段以前分叉过就导致过死循环， 所以是"先抽再扩展"，不是"复制一份改改"）。
  2. 新增 throw_existing_exception(Value, line)：已是异常对象就原样派发（位置听 它自己的 line 字段），字符串/裸值才按统一文案处理。
  3. 新增 throw_pending_exception(line)：原生边界的唯一入口，上面 9 处一律改成 if (!throw_pending_exception(line)) return -1;；vm_call.inc 两处保持原来的 return 0（那两处是"回到调用方重新派发"的语义）。
  4. OP_AWAIT 遇已完成但失败的 Future：原来包成 await: 异步任务失败 + [操作数]（其实是被 value_to_short_str 截到 32 字符的原文）， 而"未完成 → 挂起 → 恢复"那条路（vm.c 恢复分支）走的是原样抛出 ⇒ 同一件事两种 文案、命中哪条看调度时机。现在两条都走"原样抛出"（assert/test_async.leno 的 await risky(-1) 断言 e.msg == "negative" 顺便把这条锁住了）。
  5. vm.c 协程恢复路径"没人接"时：原来写死 未捕获的异步异常（位置取协程首行、原文 全丢，而且这条记录基本从不打印）；现在登记原始异常的 msg + 它自己的行号， 仍然只登记不即时打印（保持"谁捕获谁报"，避免与调用方 catch 形成双重报告）。
  6. OP_THROW 的未捕获报告改用 report_unhandled_exception()（与 dispatch_exception 同一份实现，删掉重复的 14 行）。

实测（探针 .probe_pvz/probe_async.leno）：协程内 throw（第 6 行）经 asyncs.run() 抛回 ⇒ e.msg == "inner-boom"（一字不改）、e.line == 6（错误发生地，不再是 run() 那行）； await 一个已失败 Future 同理（e.line == 15）。

护栏：assert/test_error_msg_position.leno 加 ④ 场景（跨原生边界必须原样保留： e.msg 一字不改 + 行号指向 throw 处）。全套断言 410/0。

第三批（同日）：回调调用点不再传 line = 0

全仓只有两处 vm_call_value(callee, argc, 0)（arrays.c 的数组回调、ffi.c 的 FFI 回调）， 写死 0 ⇒ 回调里 native_throw_error 抛出的裸消息异常会带上 line=0，报错打成 file:0:，而 msg 里的 [位置] 块退回"当前指令行" ⇒ 同一条报错里两个位置对不上：

[错误] …probe_swallow3.leno:0: 闭包 upvalue 索引越界      ← 记录前缀（line=0）
  [位置] …probe_swallow3.leno:2 (func: <main>)            ← msg 内（退回上下文行）

现在两处都传 native_get_current_line()（= 触发回调的那一行脚本）⇒ 两处都是 :4（脚本行）， 位置口径真正一致。

第四批（同日）：宿主回调边界的异常展开下界（f6，修崩溃）

症状：原生回调里抛异常，外层 try/catch 能正确接住并打印，随后进程崩 （0xC0000409 / 0xC0000005，非确定性 —— 同一脚本连跑 3 次崩 2 次）。最小复现：

var a = [1, 2, 3]
try {
    var c = a.filter(func(int x, int y): bool { if x == 3 { throw "filter-boom" } return true })
} catch e { print("抛了: " + e.msg) }
print("收尾正常")        // ← 先打印成功，然后进程崩

根因：回调经 vm_call_value → vm_run_with_vm 嵌套进解释器；异常派发只认 "协程边界"，一路扫到调用方（主脚本）的 catch 就跳过去 ⇒ catch 在内层循环里执行完， 内层返回后外层又在同一批帧上继续跑，arr_filter 还接着用已经失效的帧/返回值 ⇒ 状态写坏。 （arrays.c 里那句 has_exception = 0; exception = null; 正是给这个现象"擦屁股"， 顺带把异常也吞了。）

改法：

  1. VM.host_floor（新字段）：vm_call_value 在跑嵌套解释器期间设成"调用前的帧数" （与 stop_frame_cnt 同值、但语义是"异常展开下界"，保存/恢复 ⇒ 支持嵌套回调）。
  2. dispatch_exception() / OP_THROW 的下界取 max(协程边界, host_floor)； 撞界时不派发、也不报"未捕获"，只保持 has_exception 返回 0/-1 —— 接它的人在外层。
  3. C 侧宿主（arrays.c 的 call_closure、ffi.c 的 FFI 回调）失败时不再清异常： 恢复帧数/栈后立刻 return，异常沿 C 栈回到原生边界；OP_MODULE_CALL / OP_CLIB_CALL 调 throw_pending_exception 重新派发（那时 host_floor 已恢复，就能找到调用方的 catch ✓）。
  4. arrays.c 的 call_closure 改成返回状态码 + 出参（map/filter/reduce 拿到 0 立刻上抛）， 不再"失败就给个 null 接着跑"。

验证：filter/map/reduce 回调抛异常 + 组合场景，各连跑 5 次全部 exit 0 （修前 5 次里崩 3~4 次）；新增护栏 assert/test_callback_throw_unwind.leno（退出码即判据） 与 assert/test_ffi_abi.leno 的 G3/G4（C→Leno 回调里 throw ⇒ 必须在 ffi 调用点抛出、 不许吞、不许崩；抛过之后 FFI 仍可用）。全套断言 411/0；PvZ 冒烟正常。

第五批（同日）：try { … } finally { … }（无 catch）静默吞掉异常（f7）

症状（比崩溃更隐蔽：报错整条消失）：

func f(): int {
    try {
        throw "boom"
    } finally {
        print("finally 跑了")
    }
    return 0
}
main() {
    try { f() } catch e { print("catch: " + e.msg) }   // ← 修前**根本不进**这里
    print("程序照常往下跑")
}

修前：只打 finally 跑了 + 程序照常往下跑，没有 catch、没有报错、退出码 0 ✗ （旧二进制 aacb70b 同样如此 ⇒ 老 bug。）

根因：gen_try 一律发 OP_TRY A=0 Bx→catch_pos。没有 catch 体时 catch_pos 指向的 其实是 finally 区（准确说是指向那条为 catch 体准备的 OP_END_TRY A=1）⇒ VM 把 finally 块登记成了 catch handler ⇒ 异常派发按"被 catch 住了"处理（has_exception = 0、不标 pending）跳进 finally，OP_FINALLY 又按"非 pending"把 vm.exception 清成 null ⇒ 异常蒸发。 另一个帮凶：OP_END_TRY 收尾处原本 throw_runtime_error("未捕获的异常", …)，即使能抛出来 也会换掉原文案。

改法：

  1. gen_try：无 catch 体、有 finally 时发 OP_TRY **A=1**（Bx 指向 finally 块）；并且不再 发那条"catch 块入口"的 OP_END_TRY（无 catch 体时它是死代码，还会把 catch_pos 顶到 finally 前面 ⇒ 跳进去先撞上它、finally 体被跳过）。
  2. OP_TRY：A=1 ⇒ 登记成 finally handler（finally_ip = try_start + bx、catch_ip = NULL）。 于是异常派发走既有的"有 finally、无 catch ⇒ pending_exception = 1 先跑 finally"那一支 ✓
  3. OP_END_TRY 收尾的 else 分支：把当前异常原样继续向外抛（dispatch_exception）， 不再换成"未捕获的异常" ⇒ 调用方 catch 到的是真正的 msg / line / file / stack ✓
  4. LENO_BIN_VERSION v3.2.10 → v3.2.11、LENO_MODCACHE_VERSION v26 → v27 （同源码发射的 A 字节不同 ⇒ 按登记表判据整体失效重编译）。

验证：形状探针 4 种写法（单层 / 双层 finally / catch 内 rethrow / 无 finally 对照）全部 正确；回调里的 try/finally（f6 叠加）也正常上抛；正常 return 路径不受影响 （finally 照跑、返回值不变）。新增护栏 assert/test_try_finally_rethrow.leno。全套断言 412/0； PvZ 冒烟正常。

第五批补充：finally 里 return 的"覆盖"语义与泄漏

改完上面 4 条之后，边角探针发现一个新引入的问题：try { throw "x" } finally { return 5 } 里 return 本该覆盖在飞异常（JS/Python 同语义，旧行为也正是"返回 5、无异常"），但 pending 标记会泄漏到调用方 —— 在调用方自己的 END_TRY 处被重新抛出，于是变成 "未捕获的 x"直接终止程序（连调用方的 catch 都进不去 ✗）。

修法：OP_RETURN（06_call.inc）与 REG_FINISH_RETURN（run/01_prologue.inc）在 frame->in_finally 时清掉 vm.pending_exception / vm.exception —— "return 覆盖在飞异常"， 且不再跨帧泄漏。

第五批补充之二：finally 体内的 break/continue 跳出

同一条"pending 泄漏"的路子还有一处：while { try { throw } finally { break } } —— break/continue 都只是 OP_JMP，跳出时既不丢在飞异常、也不注销 try 注册 ⇒ 异常会 泄漏到别处（在不相干的 END_TRY 处被重新抛出，甚至跳回已经跑完的 finally 块 ✗）。 JS/Python 的语义是：break/continue 覆盖在飞异常（丢弃它）。

改法：

  1. CodeGen.finally_depth（生成 finally 体期间 ++/--）+ LoopContext.finally_depth （建循环/switch 时登记的深度）⇒ break/continue 时算出"要跨出几层 finally"， 每层补发一条 OP_END_TRY A=2。
  2. OP_END_TRY 新增 A=2 分支（在原有 A=0/A=1 之前处理）：注销本层 try 注册 + 丢弃在飞异常，不做任何跳转（控制流交给紧随其后的 OP_JMP）。
  3. LENO_BIN_VERSION v3.2.11 → v3.2.12、LENO_MODCACHE_VERSION v27 → v28。

实测（探针）：break 丢弃异常并跳出（返回 0、finally 只跑一次）；continue 每轮都丢弃 异常（finally 跑三轮、循环靠 continue 推进、循环体后半段不执行）；跳出后再抛一次只上抛 新异常且行号指向新 throw（证明注册确实注销了）。护栏用例扩到 10 组断言； 全套断言 412/0（JIT 开 / LENO_NO_JIT=1 各一轮）。

如果需要完整的调用栈信息用于调试，可以： - 在函数中添加 try-catch（会使函数不被内联） - 或使用 --no-inline 编译选项（如已实现）
