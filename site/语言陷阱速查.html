一、先看这四条（最省时间的）

① 明明改了代码，行为 / 性能却一点没变？

先别急着删 .lenocache —— 现在的入口缓存会自动失效：同目录的 entry_<hash>.lenb.deps 是依赖清单，第 2 行 BIN <指纹> 是编译器二进制身份，之后每个被引用文件一行 （§8.112 / 2026-09-17 起，见 src/main.c 的 ENTRY_DEPS_MAGIC）。

实测（2026-10-09）：入口脚本一个字不动、只把被引用的 lib.leno 返回值从 "A" 改成 "B"， 不删缓存再跑一次 ⇒ 输出跟着变成 B（自动重编译 ✓）。

所以按这个顺序排查：

  1. 是不是改了另一个副本的模块 —— 模块是按 leno.exe 所在目录找的（见 §五 ①）✗ 最常见
  2. IDE / lint 没重载 ⇒ 编译一次（--check 就够）就见真章
  3. 真怀疑缓存 ⇒ 删一次对照（这本身也是"证明缓存无辜 / 有罪"最快的办法 ✓）

⚠ 老笔记里"改了 src/ 必须手删 .lenocache"是 2026-09-17 之前的经验（那时 .deps 里还没有 BIN） ⇒ archive/GC与分配优化.md 那条现已加注 ✓ ⚠ 这套依赖清单只在本仓这条线里实现（LENODEPS 只出现在本仓 src/main.c） ⇒ 若你用的是别处的旧构建产物，"改了没生效"，仍按老办法手删 .lenocache 对照一次 ✓

② 跨线程传 struct：2026-10-12 起打通 ✓（只剩 cstruct 仍然拦 ✓）

见 §三 ② —— struct 实例现在能跨线程了（深克隆 + 接收侧按定义重建 ✓，改动见 docs/线程并发能力修复追踪.md 的 TH1 ✓）。⚠ 原来"编译期就拦 struct"那条是误报 ✓， 已撤掉；cstruct 仍然编译期拦 ✓（裸 C 内存，没有可安全克隆的语义 ✓）。

③ use 列表漏类型：报错点在使用处，不在 import 那行

见 §二 ② —— 而且静态检查 / IDE 不一定标出来（编译才报 ✓）。 ★ 2026-10-10 起报错会直接点名"它其实是哪个模块导出的" ✓（不再让人猜 ✓ 见 §二 ②）

④ 双击打包好的 exe：闪一下就没 / 看不清任何提示

症状 ⇒ 双击运行、没开终端 ⇒ 程序直接退出，屏幕上什么都没有 ✗ （最容易误判成"程序坏了 / 环境不对" ✗）。 病因 ⇒ 无控制台产物（_console(false) 或 -p --no-console ✓）在没有控制台的环境里 stderr 没有去处 ⇒ 报错全部消失 ✗ —— 不是"没报错"，是没地方报 ✗。 怎么办 ⇒ 两条路 ✓： 1. 想立刻看到输出（最直接 ✓）：用 -p --console 重新打包 ✓（覆盖 _console(false) ✓ ⇒ 变成控制台程序 ✓ 双击会开个窗口把错误打全 ✓）； 2. 想留下日志（发布版推荐 ✓）：设环境变量 LENO_LOG=<路径> ✓ ⇒ 产物的 stdout/stderr 会写进那个文件 ✓（里面既有 print 也有 [错误] … 与 [崩溃] … 0xC0000005 ✓）， 把整个文件发给作者即可定位 ✓；致命错误还会弹框提示日志在哪 ✓ （LENO_NO_DIALOG=1 关掉弹框 ✓）。 ⚠ 不设 LENO_LOG 时只有"标准流句柄真没有"的极端现场才会自动落日志 ✗ —— 实测里"重定向到文件"和"没人接"在平台层分不开（都报 CHAR ✗）⇒ 判据故意取保守方向 ✓ （宁可少记一次，也绝不冲掉/抢走你已经接好的输出 ✓ 这两处都踩过真 bug ✗）。 完整行为与边界见《单文件打包使用指南》的「无控制台产物出错时，错误去哪了」✓

二、模块与可见性

① 模块级函数不加 export 就是文件私有；pri 只能用于 struct 成员

pri func helper(): int { return 1 }      // ✗ 文件顶层

报错（照抄）：

error: [语法错误] pri 只能用于 struct 成员；模块级不加 'export' 就是文件私有，请去掉 'pri'

✅ 新版本的提示已经直接给出结论与改法（实测 2026-10-09）—— 见到"期望表达式"那种指不到病因的老报错， 说明用的是老编译器 ✓

② use M.(A, B, …)：源码里出现的每个类型都要列

漏一个（例：Label 没进列表）报：

error: [未定义变量] 未定义的类型: Label（它其实是模块 'SDL3' 导出的 struct ⇒ 请补一句 `use SDL3.Label` ✓；
      源码里**出现它的每一处**都要在 use 列表里 —— 泛型参数里（如 Array[Label]）也算 ✓）

★ 2026-10-10 起：报错会去已导入模块的符号表里按名字找（struct / face / enum / 别名 / clib ✓） ⇒ 命中就点名模块与类型种类 ✓；一个都没命中才退回老话术（请检查是否已通过 use 语句导入该类型… ✓） —— 实测：double 仍是专门话术 ✓、真未知类型不会乱指模块 ✓（回归：test_native_module_resolve.leno ✓）。

⚠ 三个容易吃亏的点： - 报错位置在使用那一行（不是 import / use 那行）⇒ 看到它先往回找 use 列表 ✓ - 只出现在泛型参数 / 返回类型里的类型也要列（例：Array[Button] 里的 Button）✗ 最容易漏 - lint 常抓不到（它不跑完整模块符号表）⇒ 改完 use 列表一定要编译一次 ✓

③ 跨模块用到的 struct 类型要能"传导"出去 ⇒ 子模块 import 必须带别名

import "./web_html.leno" as html      // ✓ 带别名
import "./web_html.leno"              // ✗ 不带别名：外层 use 不到它的类型

不带别名时，外层 use 拿不到该模块的 struct/face 类型（表现为"类型未解析"或参数对不上）✓

④ 每个入口目录一份 .lenocache

缓存目录 = 入口文件所在目录（不是 cwd、也不是 exe 目录）⇒ 同目录多个入口脚本共享 一个缓存目录，清理时别只删当前键（src/main.c 的注释里写明了"保留最新 K 个"的理由 ✓）

三、类型与值

① struct 要 new

struct P { int x = 7 }
P p = P()        // ✗
P p = new P()    // ✓

报错（照抄）：

error: [语义错误] struct 'P' 需要使用 new 关键字实例化，例如: new P()

（报错很清楚 ✓，但从别的语言过来第一下最容易忘 ✗）

② 跨线程传值：标量 / string / Array / Dict / struct / Channel ✓（cstruct 不行 ✗）

struct P { int x = 7 }
func work(P p): int { return p.x }
Thread t = threads.start(work, new P())     // ✓ 2026-10-12 起合法（TH1）

过线规则（2026-10-12 实测 ✓ —— 本文旧版写的是"struct 不行 ✗"，已随 TH1 翻案 ✓）：

实参类型 能过吗 行为
int / float / bool / null ✓ 按值 ✓
string ✓ 复制 ✓
Array[...]（任意元素类型 ✓） ✓ 深克隆 ✓
Dict ✓ 深克隆 ✓（连键一起 ✓）
struct（含嵌套 struct、face 声明、泛型实参 ✓） ✓ 深克隆 + 接收侧按定义重建 ✓
Channel ✓ 按引用共享 ✓（同步句柄本就该共享 ✓）
cstruct ✗ 编译期报「跨线程不能传 cstruct」✓（裸 C 内存 ✓）
字段里装了 Ptr / 闭包 / cstruct 的 struct ✗ 运行期报「不能跨线程传递此类型（来自 结构体.字段）」✓

判据（少报不误报 ✓）：编译期只拦静态类型确定为 cstruct 的实参 ✓； any 放行 ✓（静态看不出来时，运行期那条兜底 ✓）。Channel.send(...) 那条通道 不做编译期拦截 ✓（运行期同一个闸门照管 ✓）。

// 运行期拒绝面：报错会**指认到具体字段**（不是干巴巴一句"不能传"）
struct Holder { int v = 1  Raw raw }        // Raw 是 cstruct
var h = new Holder()
h.raw = Raw.malloc()
ch.send(h)   // error: 不能跨线程传递此类型（来自 Holder.raw，类型标记 17）—— 跨线程只支持 …

为什么 cstruct 不行、struct 行（这两个决定的边界在哪）：

  • 跨线程实现是 value_clone_for_channel 深克隆 ✓；而跨堆引用会让收尾时同一块内存 被两个堆各释放一次 ⇒ 0xC0000374 堆损坏 ✓（src/object/object_thread.c 那段注释自带 实测对照：跳过接收侧克隆 0/8、保留克隆 6/8 ✓）；
  • struct 能安全深克隆 ✓：它的字段是语言值（Value）⇒ 递归同一套克隆规则即可 ✓， 接收侧按类型名重建实例（struct 定义的快照机制早已落地 ✓）✓；
  • cstruct 不能 ✗：它是裸 C 内存（Ptr / ffi 句柄 / SDL 纹理 / socket fd / 文件句柄 ✗） ⇒ 拷出来的是假句柄 ✗（比当场报错难查一百倍 ✓）；
  • ⚠ 环形引用：a.next = a 这种自引用 struct 会一直递归 ⇒ 克隆上限 64 层， 超限明确报错（「嵌套层数超过 64」✓）而不是挂死 ✓（用例见 assert\test_channel_struct.leno 的 ⑤ ✓）。

机制补记（本仓多处注释记过 ✓ / ★ 2026-10-12 更正）：子线程访问的是与主线程同一份模块 globals （ObjModule 由 loaded_modules 进程级缓存共享，不按线程隔离 —— 这是有意的口径 ✓）， 所以"模块级可变 var 跨线程共享、并发写就是数据竞争"是真实风险 ✓。 （旧版这里写的是"子线程不加载别的模块的全局变量" ✗ —— 那是 TH2 修掉的那个 bug 的表现， 见 docs/线程并发能力修复追踪.md 的 TH2 ✓）

③ is not 不存在 ✗ —— 取反写 x not is T（条件里）或 not (x is T)（表达式里）

func f(any x): bool { return x is not string }    // ✗ 任何位置都不合法
if x not is int { ... }                           // ✓ 合法：**否定类型守卫**（if / for 条件位置）
if s.age not is int { ... }                       // ✓ 连字段守卫也支持
func g(any x): bool { return not (x is string) }  // ✓ 合法：**表达式**位置（return / 赋值右侧 / 实参）

⚠ 两种位置各有各的写法（这是本条最容易踩的地方 ✗）：

位置 合法写法 备注（都实测过 ✓）
if / for 条件 x **not is** T ✓ 正式特性 ✓（assert/test_narrow_edge.leno 里"测试 11: 否定类型守卫 (not is)"就是这个 ✓）；字段守卫 s.age not is int ✓
表达式（return / 赋值右侧 / 实参…） not (x is T) ✓ 表达式位置没有 not is ✗（实测 return x not is string 报一堆语法错 ✗）

★ 2026-10-10 修：写 is not 原先报两条错 ✗（类型检查表达式期望类型名… + 噪音 期望表达式 ✗）—— 写的人从里面看不出"原来是 is not 不行" ✗ ⇒ 现在单条说清 + 给出两种正确写法 ✓：

error: [语法错误] 本语言不支持 `is not` —— 取反请写 `x not is 类型`（if / for 条件里 ✓
       如 if a not is string）或 `not (x is 类型)`（表达式里 ✓）

⚠⚠ 另一个更阴的（同类"静默给错值"✗ 实测 2026-10-10）：表达式里写 not x is T ✗

func f(any x): bool { return not x is string }   // ✗ 语法**合法**、但它是 `(not x) is string` ✗
// x = 42 ⇒  not x is string = **false** ✗       而   not (x is string) = **true** ✓   ← 结果相反 ✗

⇒ 编译通过、一声不吭、判断反了 ✗ —— 而且从 Python 过来必踩 ✓（那边 not 比 is 低优先级 ⇒ not x is T 就等于 not (x is T) ✓）。同病：not x in arr ⇒ (not x) in arr ✗。 ⇒ 取反要么写 not is、要么老老实实加括号 ✓（别写裸的 not x is T ✗）。

★ 2026-10-10 起这条会被编译器抓住 ✓（新增 [not的优先级陷阱] 警告 ✓）：

  • 改任何 fopen 之前，先搜同一文件/同一个包有没有现成封装 —— 本项目已有 pack_toml_fopen（package_toml.c）、serialize.c 的跨平台 fopen、main.c / module_loader.c 的 _wfopen 段。有就用，别另写一套
  • 没有现成封装时：

wchar_t* wp = (wchar_t*)malloc(wn * sizeof(wchar_t));
MultiByteToWideChar(CP_UTF8, 0, path, -1, wp, wn);

  • 路径来源不同、编码也可能不同：编辑器/LSP 传的是 UTF-8，argv（ANSI 入口）给的是 系统 ANSI ⇒ 稳妥做法是「先 CP_UTF8，失败再按 GetACP() 重试一次」
  • 排查手法：打开失败处打印 errno + 路径字节的 hex。UTF-8 的“桌”是 E6 A1 8C、 GBK 是 D7 C0，一眼分得出 —— 光看 printf 的显示结果会被骗（GBK 控制台显示 UTF-8 路径恰好也可能正常）✗

㊺ 模块级变量按源码顺序初始化 —— 别互相前向引用（2026-10-23 实测）

var B = A + 1      // ✗ 运行时 A 还是 null
var A = 10         //   报「加法运算: null 不能参与运算」

报错里还会带一行 [操作数a] type=null, value=null —— 看到它就说明是顺序问题， 而不是那个值恰好是 null。

为什么编译不报错：semantic 有"模块变量前向引用预扫描" —— A 在符号表里、类型也已知， 所以类型检查能过。但顶层语句执行时严格按源码顺序，B 初始化那一刻 A 还没赋值。

对比别的语言：C# / Java 靠 definite assignment 在编译期就拦住；JS let 是运行时 TDZ（ReferenceError）；Leno 是运行时拿到 null ⇒ 报的类型错误不指向真因（看着像"这个值是 null"， 实际是"顺序错了"）。

函数不受这个限制（2026-10-23 起 ✓）：函数定义只是注册，编译器会把它们排到顶层执行代码之前， 所以下面完全合法，类型也精确：

var LOG = makeLog()            // ✅ 函数可以在调用之后定义
func makeLog(): Dict { ... }

怎么办：把被依赖的变量声明挪到前面。如果报错里出现 [操作数a] type=null，先怀疑顺序。
